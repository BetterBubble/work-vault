# ADR-0065 — Ассистент проектной сессии: журнал обсуждений как общий контекст трёх поверхностей, кандидаты в решения, единый словарь диспозиций

**Дата:** 2026-08-05

## Контекст

В дизайн-сессии участвуют четыре человека: заказчик, архитектор, аналитик, тимлид. Обсуждение идёт в iva-one (созвон + тред). Результат сессии сегодня не материализуется: FR собирается аналитиком вручную через дни, решения живут в головах, через полгода вопрос «почему так решили и кто принял» не имеет адресата. Транскрибация обсуждений существует в контуре ВКС (MCU), но как контекст агентам недоступна.

Одновременно бо́льшая часть нужного уже построена и находится в проде:

- **Факт-база** — `helm-analyst` (`affected_systems`, `arch_map`/`arch_container`, `arch_drift`, `constraints`, `related_tasks`, `nearest_spec`, `requirement_tests`, `requirement_coverage`) и `iva-read`, приходящие из `tacticum-analysis-core`.
- **Постановка** — скиллы `fr-authoring`, `brd/adr/pin/tests-authoring`, агент `tacticum-workflow`, команды `/start-task` → `/approve-docs`.
- **Запись** — `iva-atlassian-write` под личным Atlassian PAT (ADR-0058), авторство родное.
- **Леджер решений с обоснованием** — контур диспозиций, доступный через architecture BC, но физически хранимый в **arch-mcp** (`record_triage`/`list_triage` — MCP-вызовы через `arch_mcp_adapter.py`; SoR = arch-mcp per ADR-0048): `signal_type` / `signal_key` / `disposition` / `rationale` / `tracker_ref` / `expires_at`, upsert по identity, workspace-scoped fail-closed, побочная запись в Memory ([`watershed.py:142-193`](../../apps/backend/src/backend/architecture/application/watershed.py), [`router.py:1210-1258`](../../apps/backend/src/backend/architecture/interface/api/router.py)). `signal_type` и `disposition` — свободные строки без enum-валидации на API. `semantic_anchor` в `signal_key` уже обобщён до «символ кода **ИЛИ** раздел/пункт документа» (ADR-0064 Р.8б — задел под FR-ревью v2).

Не хватает ровно трёх вещей: **журнала обсуждений** (чат — v1, транскрипт — Фаза T — как читаемый агентами контекст), **типа сигнала для решений встречи** в существующем леджере и **двух новых поверхностей** — session-bot в чатах и агента, отвечающего на комментарии к документу.

Проведено рыночное исследование (2026-08-05; продуктовый слой, референсные архитектуры, ~40 источников). Ключевые данные: рыночная граница «notetaker vs agent» проходит по типизированным объектам, филингу в трекер с апрувом и переносу контекста между встречами; ниша «агент отвечает по корпоративному контексту **во время** дизайн-сессии» на рынке не занята — это и есть дифференциация, обеспеченная `helm-analyst`. Академический слой даёт три ограничения, вошедшие в решения ниже: LLM-фасилитация повышает вовлечённость, но **не улучшает качество итогового решения** (pre-registered RCT, N=1475, 281 группа, arXiv 2508.08242); молчание интеракционно — агент обязан молчать на большинстве ходов (arXiv 2605.05626, arXiv 2501.00383); детекция решений и action items — зрелая область с готовыми методиками разметки (AMI DecisionDetector, AutoMin, ALIGNMEET).

Техническое исследование 2026-08-06 (KB installation `bd71f761` + код `D:\iva\workspace` + код helm из main + пробы прод-API) установило:

- **Боты в чатах платформы — обкатанный паттерн helm**: «Поддержка» и `bot_iva_write` уже живут как webhook-роутеры helm (`/api/bot/<имя>/webhook`, секрет-заголовок `Iva-Bot-Api-Secret-Token`, исходящий канал `send-message` с blocks); платформа штатно шлёт webhook наружу контура на helm.tacticum.ru.
- **Identity-резолв реализован в helm**: webhook несёт `author: {profileId, name, login}`; три пути резолва в личность по убыванию доверия (login→справочник Jira; login-as-email; **по имени через справочник — сегодня единственный рабочий**, платформа `login` не шлёт — боевая гоча в роутере); связка с ключами Tacticum (`tacticum_key.py`) есть.
- **Конвейер транскрибации уже в helm** (`/transcribe`, 2026-07-31): ffmpeg → whisper-чанки → `dialogue` (разметка реплик и говорящих) → `summarize` (Codex-тред); таблицы `meetings`/`media_transcript`/`dialogue`; retention 180 дней; «исходник не хранится».
- **Bot API платформы** (контракт «IVA Chat Bot API» v1.30, реализован и MCU, и Go-backend IVA One): send-message + files + `ReplyKeyboard` (кнопки; нажатие = сообщение **от имени нажавшего**); события боту — только `CHAT_NEW_MESSAGE`/`CHAT_EDIT_MESSAGE`. Боты не приглашаются в звонки (`u.type = UserTypeUser`) и не получают системных сообщений (фильтр `AuthorID != SystemUserID`).
- **Канал транскрибации ВКС**: сценарий «Создать ВКС из чата ONE» ведёт на MCU (`ivcs.hi-tech.org`, API жив); в MCU Clients API v2.30 есть `transcription/start|stop`, live-поток `PhraseEvent{authorProfileId, authorName, text, version}` участникам и хранение транскрипта ресурсом типа `TRANSCRIPT` (`findChatCallDocuments`/`listDocuments` → `download`); конец конференции детектится только поллингом; server-to-server auth — app-JWT (AppID/AppSecret). Неизвестными остались: доступность `documents`/`resources` под app-JWT и формат файла транскрипта. **Решение owner 2026-08-06: доступ к транскрибации — вне scope v1**; проектируется отдельной дизайн-сессией, которую команда проведёт в чате с уже работающим ботом (первый боевой кейс продукта).

## Решения

### 1. Журнал обсуждений — Postgres helm, рядом с транскрайб-конвейером и ботами; связь с леджером по `signal_key`

**Где физически.** Три таблицы — `chat_message`, `decision_candidate`, `transcript_segment` (задел Фазы T) — в **Postgres helm** (alembic helm), рядом с уже существующими `meetings` / `media_transcript` / `dialogue`. Точка чтения для агентов — MCP-tools `discussion_*` как расширение уже работающего `helm-analyst` (`/mcp/analyst`); отдельный MCP-сервер не заводится.

**Почему helm, а не backend каталога** (пересмотр первой редакции этого решения по фактам 2026-08-06): голосовое сырьё обсуждений уже материализуется в helm (`media_transcript`, `dialogue` — реплики со спикерами), боты-писатели журнала живут в helm, identity-резолв авторов — в helm. Переносить журнал в `dev.tacticum.dev` значило бы разрезать один поток данных на два хранилища и таскать каждый webhook через второй сервис. Backend каталога остаётся **фасадом леджера** (REST `/triage`, workspace-резолв fail-closed) — журнал он не хранит.

**Почему не внутрь arch-mcp, где лежит леджер.** arch-mcp — адоптированный движок graph-of-standards (ADR-0048), а не хранилище сырья встреч: несопоставимые объёмы и изменчивость, продуктовая доменная область утекла бы в платформенный компонент. Связь обеспечивается ключом, а не колокацией.

**Чем обеспечивается неразрывность с леджером.** Общим `signal_key = hash(session, semantic_anchor)`, хранимым по обе стороны: в леджере — identity диспозиции, в журнале — ссылка кандидата и цитат. Резолв «решение → цитаты» = `list_triage` (фасад backend → arch-mcp) + выборка журнала по ключу. Обратное направление — «пункт документа → решение» — держится **сохранённым линком, а не повторным вычислением якоря**: в момент фиксации пункта FR ещё не существует, хеши не совпадут; при генерации черновика (`/фр`) журнал сохраняет линк «пункт → signal_key» для каждого пункта из решения, и Живая документация разыменовывает его.

**Граница по зрелости сигнала:** кандидат — в журнале (живёт минуты, массово отбраковывается), зафиксированное решение — в леджере arch-mcp (governance-артефакт, общая очередь разбора). Кандидат при фиксации остаётся в журнале следом с исходными цитатами.

**ИБ:** транскрипты и реплики оседают в Postgres helm; **retention журнала = 180 дней** (решение owner 2026-08-06 — единая политика с `/transcribe`, чей срок утверждён 2026-07-31); леджер решений переживает очистку — цепочка деградирует до `rationale` + `created_by` без цитат.

Обязательные инварианты журнала: неразрешённый автор (`author=unresolved`) может быть процитирован, но **не может быть автором решения**; разрыв входного потока фиксируется `gap`-записью, и производные артефакты (recap, драфт FR) печатают предупреждение; чтение workspace-scoped fail-closed.

### 2. Три поверхности — один контекст; агенты тонкие

Поверхностей три и они не сводятся друг к другу: **IDE/CLI-агент роли** (существует — `iva-role-architect`/`iva-role-analyst`), **бот в треде** (новое), **агент комментариев Confluence** (новое). Разные триггеры (команда / реплика / комментарий), разные жизненные циклы (задача / минуты / недели), один контекст.

Дорогой актив — журнал и леджер, а не агенты (урок Teamwork Graph). Поэтому очерёдность строительства: журнал → бот → агент комментариев, а не «сначала бот, контекст потом». Ни одна поверхность не заводит собственного хранилища.

### 3. Кандидаты в решения вместо команды фиксации

Бот **непрерывно** ведёт список кандидатов (детекция по потоку транскрипта и чата): формулировка, автор реплики, цитаты, статус. Каналов фиксации четыре — карточка в момент детекции, витрина по запросу (`@бот что на столе`), recap, ручной ввод. **Ручной ввод — резервный канал** для пропущенного детектором, не основной: одна слэш-команда как единственный вход отвергнута как неудобная и заведомо неполная.

Метрики детекции и проактивности **асимметричны и не сводятся к одной шкале**: у кандидата дорог пропуск (ложняк снимается одной кнопкой) → `recall ≥ 85 %` при `precision ≥ 50 %`; у проактивной реплики дорог ложняк → `precision ≥ 60 %` при потолке 3 вмешательства за встречу.

### 4. Единый словарь диспозиций; эффект — функция от `(signal_type, disposition)`

Решения встречи пишутся в **тот же леджер с тем же словарём**, что отклонения ревью: `enforce` / `waive` / `amend` / `dismiss` (последний уже присутствует в словаре судеб findings, ADR-0064 Р.6). Отдельный словарь `fixed/rejected/deferred` отвергнут.

| Глагол | Над сигналом ревью | Над кандидатом в решение |
|---|---|---|
| `enforce` | признать, провести последствия (фикс-итерация → re-review) | признать решение, провести последствия (пункт FR → публикация → Jira) |
| `waive` | отступление допустимо, подавлено до `expires_at`, `pending` до approve | отложено: вернуться к вопросу к дате |
| `amend` | правило сформулировано неверно → владельцу слоя | кандидат распознан неверно → владельцу детектора |
| `dismiss` | finding отклонён по существу | предложение отвергнуто по существу |

`signal_type = "design_decision"`, `signal_key = hash(session, semantic_anchor)` — тот же якорь, что для пункта документа (Р.8б ADR-0064 переиспользуется как есть, без изменения формата).

Различение **`amend` ≠ `dismiss` обязательно**: «бот выдумал решение» — `amend` (ошибся детектор), «решение распознано верно, но мы его отвергаем» — `dismiss`. Смешение ломает петлю здоровья: детектор станет калиброваться по отвергнутым по существу предложениям и заглохнет.

Что достаётся без разработки: `expires_at` как «вернуться к вопросу»; `status=pending` + approve вышестоящим как эскалация «заказчик предложил → архитектор подтвердил»; **одна очередь разбора с одним SLA** (ADR-0064: «все отклонения — в одной очереди с одним словарём») — второй словарь означал бы вторую очередь и вторую привычку, которая не приживётся; петля здоровья Р.6 работает без правок (`dismissed-rate > 60 %` читается как «детектор шумит» так же, как «правило шумит»).

**Словарь единый — обработчик последствий per `signal_type`.** Глагол описывает, что постановил человек; что сделает система — функция от пары. Это не компромисс, а правильная развязка.

### 5. Идентичность и права

- **READ:** через техканалы `iva-read` + `helm-analyst` под собственным токеном бота (решение owner 2026-08-06). Эти каналы уже выданы всем разработчикам через `tacticum-analysis-core` — их скоуп и есть граница видимости; расчёт прав по составу комнаты в v1 не делается. Остаточный риск фиксируется явно: заказчик в комнате видит то же, что видит любой разработчик с `iva-read`; если это станет проблемой — разделение тредов по составу, не пер-пользовательские права. (Отвергнутый вариант «по наименее привилегированному участнику» требовал identity-мост и расчёт прав до того, как бот скажет первое слово, — цена несоразмерна v1; основание исходного риска — caller identity confusion, arXiv 2603.07473.)
- **WRITE — три уровня:** (1) **черновик FR** — техучётка бота, скоуп page-authoring строго в drafts-пространстве/метке; рождается в Confluence сразу (стыковка с Живой документацией Волны 2 без миграции драфта); при pending-решениях `/фр` не генерирует молча — предлагает довесить их, и только при явном «генерировать с неполным набором» создаёт черновик с тегом `fr-incomplete-decisions` и ссылками на отсутствующие решения в шапке (тег снимается при обновлении с закрытыми pending); (2) **комментарии** — техучётка Живой документации, только `confluence_add_comment`; (3) **финализация FR и задачи Jira** — только человек его ролью (`iva-atlassian-write`, личный PAT, ADR-0058); бот чужие PAT не хранит и от чужого имени не пишет, кнопочная публикация из чата (PAT-стор) — v1.x. Апрув и есть поставщик идентичности: авторство родное, аудит корректный, разграничение возникает само (заказчик кнопку не видит). Подмена техучёткой при отсутствующем/истёкшем PAT **запрещена** — публикация деградирует явно.
- **Атрибуция:** для `signal_type=design_decision` поле `created_by` обязательно (422 без него). В домене и порту поле есть, но **не пробрасывается через HTTP-контракт** — `RecordTriageRequest` его не содержит ([`router.py:1210-1217`](../../apps/backend/src/backend/architecture/interface/api/router.py)); правка контракта входит в scope Фазы 1. Для сигналов ревью прежнее поведение сохраняется.

### 6. «Живая документация» — имя агента, а не документа

Термин закрепляется за **поведением**, а не за хранением. «Живым» документ делает не способ его версионирования, а агент, который отвечает на вопросы к нему. Отсюда разделение:

- **Артефакт** — страница Confluence. История версий, diff, авторство правок — родные механизмы Confluence. Каждое зафиксированное решение = правка = новая версия. Собственная версионируемая сущность не заводится: попытка изобрести своё версионирование была прямым следствием размытого употребления термина.
- **«Живая документация»** — агент: вопрос к любой части документа → ответ из журнала (что решили, кто, когда, почему, цитата первоисточника) в тред комментария. Подстраница — реестр открытых вопросов.

Агент **не реконструирует** причину из текста документа: если пункт не прослеживается до зафиксированного решения, он отвечает именно это и предлагает завести открытый вопрос. Расхождение текста пункта с формулировкой решения показывается явно, обеими формулировками.

**Живая документация комментирует, но не правит.** Ответ в тред комментария публикуется под учётной записью агента — читатель обязан видеть, что отвечал бот. Правка тела страницы остаётся за человеком и уходит под его именем (ADR-0058). Это разграничение — не осторожность, а условие: автономный ответ допустим там, где он отличим от авторского текста, и недопустим там, где он в нём растворяется.

### 7. Проактивность: молчание по умолчанию

Дефолт — молчать; бот отвечает по прямому обращению. Единственный проактивный сценарий v1 — предупреждение о противоречии действующим `constraints` (ADR/НФТ), с потолком 3 вмешательства за встречу и однократностью по теме. Потолок не обходится: четвёртый конфликт уходит в recap. Отсутствие результата — не повод говорить (пустая выдача прецедентов = молчание).

Продуктовое обещание формулируется как «сокращение пути от разговора до заведённой задачи с прослеживаемостью», **не** «решения становятся лучше»: RCT N=1475 показал прирост вовлечённости без прироста качества решений. Метрики продукта (BRD § 9.5) построены на времени и прослеживаемости, не на «качестве решений».

### 8. Границы v1 и обязательная деградация

Вне scope v1: **доступ к транскрибации ВКС** (Фаза T — решение owner 2026-08-06, факты для проектирования зафиксированы в Контексте и Р.10); голосовое участие бота в реальном времени (turn-taking в звуковом потоке — отдельный класс задач с несопоставимой отдачей); автопубликация без апрува; авто-заведение задач без человека; ретро-обработка архива встреч.

Деградация обязательна и явная: при недоступной факт-базе бот сообщает «отвечать не буду» и помечает `degraded=true`, **никогда не догадывается**; при недоступном леджере фиксация не подтверждается ложно; при `gap` в журнале производные артефакты печатают предупреждение. Каждое фактическое утверждение бота несёт проверяемую ссылку — это условие допуска в комнату, где сидит заказчик, а не фича (по вторичным данным Deloitte, 38 % руководителей сообщали о неверных решениях на основе галлюцинированных выходов ИИ).

### 9. Деплой: оба агента — в helm; ни одного нового рантайма

**session-bot — третий бот helm** по обкатанному паттерну `bot_support` / `bot_iva_write`: webhook-роутер `/api/bot/session/webhook` (секрет-заголовок), application-слой без I/O, общий исходящий канал send-message с blocks/ReplyKeyboard. Платформа уже шлёт webhook наружу контура на helm — прецедентом закрыт вопрос входящего канала. Первая редакция этого решения («новый Go-сервис чартом в iva-one-helm») снята: она защищала локальность webhook, которая оказалась не требованием.

**«Живая документация» — воркер helm** (полоса очереди `bot_task`, как `helm-media-worker`): cron-проход раз в 5 минут, поллинг комментариев Confluence — без webhook и входящих каналов вовсе. Первая редакция («cron на стенде `tacticum-re-deploy`») снята вместе со своим основанием «не подселять LLM-прогоны на прод helm» — helm штатно гоняет Codex-треды и медиа-воркеры; второй рантайм и кросс-хостовый доступ к журналу стали бы чистым усложнением.

Исходящие каналы обоих агентов: журнал — своя БД helm; леджер — REST-фасад `dev.tacticum.dev` (workspace-резолв fail-closed); факт-база — `helm-analyst`/`iva-read` (локально же); запись — `helm-iva-write` (канал уже на helm). Деградации: факт-база недоступна → «отвечать не буду», `degraded=true`; леджер недоступен → фиксация не подтверждается ложно; идемпотентность ответа на комментарий — по identity комментария.

### 10. Механика session-bot: штатный Bot API, identity через резолв helm, транскрибация — Фаза T

Бот-механизм платформы используется целиком, **клиентская разработка iva-one не требуется**:

- **Сущность и жизненный цикл** — `entity.Bot{WebHookUrl, WebHookToken, Enable}`, бот = участник чата (`ChatMemberBot`); admin-CRUD и токены: `CreateBot` / `RegenerateBotToken` / `ValidateBotToken` (`profiles/internal/usecase/bots.go`).
- **События к боту** — push-webhook на New/EditMessage с ретраями и backoff (`chats/internal/usecase/tasks.go:1238`).
- **Бот в чат** — `POST /api/bot/v1/chats/:chatID/send-message`: текст ≤ 4096, blocks, `ReplyOnMessageID` (тред), файлы.
- **Карточки** — `ReplyKeyboard = [[{Label, Message}]]`: нажатие отправляет `Message` **от имени нажавшего** → боту прилетает webhook с автором. Это штатная механика и HITL-апрува, и атрибуции `created_by`.

**Identity IVA ↔ Tacticum** — переиспользуется резолв `bot_iva_write` (`application/bot_iva_write.identity_candidates` + подтверждение справочником Jira; боевая гоча: платформа не шлёт `login`, рабочий путь — по `name`); `author.profileId` из webhook кладётся рядом со связкой. Новый реестр не заводится.

**Привязка чат ↔ фича** (решение owner 2026-08-06): все встречи идут в чатах iva-one; фича привязывается к чату один раз — из заголовка, если распознан, иначе единовременной командой `@бот тема <фича>`; сессии чата наследуют привязку (UC-JRN-03).

**Детектор кандидатов** читает журнал по append-курсору, не сидит в webhook-пути: ошибка детектора не роняет приём, перевыкатывается и A/B-калибруется отдельно (журнал append-only — новый детектор прогоняется по старым данным).

**Транскрибация — Фаза T, вне scope v1** (решение owner 2026-08-06). v1 работает на чат-детекции; факты для будущего проектирования зафиксированы в Контексте (MCU: `PhraseEvent` с авторством, хранение ресурсом `TRANSCRIPT`, app-JWT, конец конференции — поллингом; блокеры: боты не в звонках, системные сообщения ботам не доставляются, конференц-событий в Bot API нет). Дизайн-сессия по Фазе T проводится в чате с работающим ботом — она же его первый боевой кейс и первая запись в журнале о самом себе. Ручной мост до Фазы T существует уже сейчас: запись встречи → конвейер `/transcribe` helm.

## Альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| Свой словарь диспозиций для решений (`fixed`/`rejected`/`deferred`) | вторая очередь разбора и вторая привычка архитектора; дублирование петли здоровья и механики `expires_at`/`pending`, которые уже есть; глаголы 0064 ложатся на решения без натяжки |
| Три отдельных хранилища (транскрипты / чат / решения) | решение без цитаты недоказуемо, ответ на комментарий без цепочки невозможен — разнесение создаёт проблему джойна как обязательную |
| Новый bounded context `discussion/` | журнал связан с леджером общим `signal_key` и обслуживает те же поверхности; отдельный BC добавляет границу там, где нет своего языка и своего владельца |
| Журнал внутри arch-mcp, рядом с леджером | arch-mcp — адоптированный движок graph-of-standards (ADR-0048), а не хранилище сырья встреч: несопоставимые объёмы, продуктовая доменная область утекает в платформенный компонент. Связь обеспечивается ключом, а не колокацией |
| Кандидаты в решения хранить в леджере наравне с решениями | кандидат живёт минуты и массово отбраковывается; засорять governance-леджер черновиками — сломать очередь разбора, ради которой и выбран единый словарь |
| Слэш-команда как единственный канал фиксации | неудобно и заведомо неполно — фиксируется только то, что кто-то вспомнил зафиксировать |
| «Живая документация» как собственная версионируемая сущность | Confluence уже даёт версии, diff и авторство; «живость» — свойство агента, отвечающего на вопросы, а не способа хранения |
| Один агент вместо трёх поверхностей | разные триггеры и жизненные циклы (команда/реплика/комментарий, задача/минуты/недели); объединение даёт худшее из трёх |
| Готовый рыночный notetaker (Rovo Meeting Insights, Tana, mymeet) | ни один не отвечает по корпоративному контексту во время сессии; `helm-analyst` — актив, которого у них нет. Слой «транскрипт → action items» у них зрелый, но это не дифференциация |
| Бот как участник голосового потока в реальном времени | turn-taking в звуке — отдельный класс задач; вся ценность сохраняется в текстовом треде |
| Запись в трекер техучёткой с подписью актора | ADR-0058 уже выбрал личный PAT; апрув как поставщик идентичности решает разграничение бесплатно |
| Единая метрика качества для детекции и проактивности | разнонаправленная цена ошибки: пропуск кандидата дёшев, ложное вмешательство дорого; одна шкала гарантированно испортит одно из двух |
| Журнал в Postgres tacticum-backend (первая редакция Р.1) | разрезал бы один поток данных на два хранилища: голосовое сырьё (`media_transcript`/`dialogue`), боты и identity-резолв уже в helm; каждый webhook таскался бы через второй сервис |
| Деплой агентов на стенде `tacticum-re-deploy` (первая редакция Р.9) | основание «не подселять LLM-прогоны на прод helm» опровергнуто фактами: helm штатно хостит двух ботов, Codex-треды и медиа-воркеры; re-стенд дал бы второй рантайм, кросс-хостовый доступ к журналу и публичный ingress для webhook |
| Webhook от Confluence вместо поллинга | требует публичного эндпоинта, ingress и роутинга traefik; НФТ `p50 ≤ 10 мин` закрывается cron'ом раз в 5 минут — входящий канал не окупается |
| Ответы под личным `phk_*` человека через действующий `iva-write` | инвариант канала — «агент пишет только по прямому указанию человека, на каждую запись отдельно»; автономный агент его не выполняет. Узкий скоуп на техучётке честнее, чем ослабление инварианта человеческого канала |
| Живой документации разрешено править тело страницы | автономный ответ допустим, пока он отличим от авторского текста; правка растворяет его в документе. Скоуп физически ограничен `confluence_add_comment` |
| Свой рендер карточек в клиенте iva-one | `ReplyKeyboard` уже рендерится клиентом и атрибутирует нажатие автору — вся клиентская разработка Фазы 1 снимается |
| session-bot как отдельный Go-сервис (чарт в `iva-one-helm`) | защищал локальность webhook, которая оказалась не требованием — платформа уже шлёт webhook на helm наружу контура; отдельный сервис дублировал бы identity-резолв, исходящий канал и очередь, готовые в helm |
| Live-подключение бота к ВКС участником в v1 (вариант «а») | три подтверждённых блокера (боты не в звонках `pg_chat.go:1307`, системные сообщения ботам не доставляются `tasks.go:660`, конференц-событий в Bot API нет) + нерешённый auth; отложено в Фазу T решением owner 2026-08-06 |
| Кнопочная публикация FR из чата в v1 (PAT-стор) | бот не должен хранить чужие PAT; финализация ролью человека уже работает (`iva-atlassian-write`) — ноль новых секретохранилищ; PAT-стор — v1.x отдельным решением |
| Отдельный реестр identity-моста IVA ↔ Tacticum | helm уже хранит связки tacticum ↔ контур ИВА (OAuth-согласия iva-write); добавить ось iva_one_user_id дешевле и не плодит второй источник истины по личностям |

## Последствия

✅ Три поверхности получают один контекст: то, что решено на встрече, доступно IDE-агенту роли и «Живой документации» без пересказа человеком.
✅ Деплой не требует ни одного нового рантайма: session-bot — третий бот helm по обкатанному паттерну, «Живая документация» — воркер полосы `bot_task`; identity-резолв, исходящий канал и очередь переиспользуются.
✅ Вопрос «почему так решили и кто принял» получает машинный ответ с цитатой первоисточника — сквозная цепочка «задача → пункт FR → решение → реплика → участник».
✅ Единый словарь даёт одну очередь разбора: архитектор видит отклонения ревью и предложенные решения встреч в одном месте под одним SLA; петля здоровья ADR-0064 распространяется на детектор кандидатов без доработки.
✅ Схемная цена реиспользования леджера близка к нулю: `signal_type`/`disposition` — свободные строки, `semantic_anchor` уже обобщён под пункт документа (задел Р.8б окупается раньше, чем FR-ревью v2).
✅ Дифференциация опирается на существующий актив (`helm-analyst`), а не на новый — рыночный слой «транскрипт → задачи» не воспроизводится.
⚠️ Качество детекции кандидатов — главный риск принятия: при низком recall продукт вырождается в ручную фиксацию, при низкой precision — в шум. Пороги (recall ≥ 85 %, precision ≥ 50 %) проверяются размеченной выборкой 20 встреч **до** тиража.
✅ Фаза 1 не требует клиентской разработки iva-one: карточки, кнопки, треды и атрибуция нажатий — штатный Bot API (Решение 10).
⚠️ READ через техканалы уравнивает видимость: заказчик в комнате видит то же, что разработчик с `iva-read`. Принято owner как допустимое для v1; при проблеме — разделение тредов по составу, не пер-пользовательские права.
✅ Транскрибация вынесена в Фазу T без потери целостности: v1 полноценен на чат-детекции, ручной мост (запись → `/transcribe` helm) уже работает, факты для проектирования Фазы T зафиксированы в Контексте; сама дизайн-сессия Фазы T — первый боевой кейс бота.
✅ Срок хранения журнала закрыт решением owner 2026-08-06: 180 дней, единая политика с `/transcribe`; цепочка трассировки деградирует до уровня решения после очистки.
⚠️ Зависимости реализации: правка HTTP-контракта `RecordTriageRequest` (`created_by`) в backend каталога, alembic-миграции helm (три таблицы журнала), MCP-tools `discussion_*` в `/mcp/analyst`, заведение бота админом платформы (`CreateBot` + webhook-секрет).
✅ Policy кнопки фиксации утверждена owner 2026-08-06: архитектор/аналитик/тимлид — `enforce` сразу, заказчик — `pending` с approve любым из трёх; классификация решений по типам в v1 не делается (машинно неотличимо «архитектурное» от «продуктового»).
✅ Baseline замерен (2026-08-06, Jira IVAONE, Analytics Task; BRD § 9.0): работа аналитика ~7 дн, согласование — медиана 14 дн с хвостами 99–226 дн, активный цикл постановки — медиана 75 дн; у разобранного кейса 4 из 7 порождённых задач Rejected. Продукт бьёт в подтверждённое данными узкое место — согласование, а не написание FR.
