# Как тестировать профиль ПОСЛЕ деплоя (из живого каталога)

Продолжение `profile-testing-guide.md`. Тот был про уровни 0–2 (статика + e2e ДО мержа).
Здесь — **ручная проверка после сида на прод-каталоге**. Это то,
что e2e не покрывает: e2e гоняет тот же сидер, но против локальной БД; здесь мы проверяем,
что **реальный засиженный каталог отдаёт роль корректно** и агент с ней работает на живой репе.

Так я проверял kmp/web/analyst/java после деплоя #119.

---

## 0. Когда это делать

Профиль уже смёржен в main и **засижен** на прод-каталоге (`dev.tacticum.dev`), деплой прошёл
по runbook'у (`.serena/memories/deployment*.md`): rebuild если менялся `src/`, seed, verify
`/readyz=200` + `POST /mcp=401`. Теперь проверяем, что засиженная роль реально работает.

## 1. Где запускать — тест-стенд, не локально

Нужен стенд, где есть: **codex CLI + node + serena-LSP + VPN до контура ИВА + клоны IVA-репов**.
У команды это RE/KB-тест-стенд (доступ/IP — у Глеба/в инфре). Локально не выйдет: без VPN
Maven/gradle не дотянутся до артифактори, и IVA-репов нет.

> ⚠️ VPN на стенде иногда слетает (конфиг вычищается). Проверка: `sudo swanctl --list-sas | grep ESTABLISHED`.
> Если пусто — берётся рабочий `ipsec.conf`+секреты с прод-RE-стенда (там VPN живой). У меня так и было.

## 2. Токены — САМОЕ важное, тут я потерял время

Два типа, делают РАЗНОЕ:

| Токен | Что | Что открывает |
|---|---|---|
| **`tac_`** (installation-scoped) | пришпилен к ОДНОЙ установке | `tacticum_init` / `tacticum_init_manifest` (рендер профиля из каталога), `pull` конкретной установки, `kb_*` |
| **`phk_`** (личный, org-membership) | твоя личность в каталоге | `provision_installation` (создать установку) |

**Грабли:** `provision_installation` требует `phk_` с org-membership каталога. Даже с личным `phk_`
можно получить **`membership_required`**, если workspace/подписка не настроены. У меня так и вышло.

**Обход, который всё равно всё проверяет:** если provision не проходит — используй
**`tacticum_init(profile_id, target_cli)`**. Он рендерит роль **из живого каталога БЕЗ создания
установки**. Токена `tac_` для него достаточно (лежит на стенде в `kbconsole.env` как
`TACTICUM_MCP_TOKEN`). Именно так я и ставил роль в клон.

## 3. Codex headless — две грабли, без которых MCP не работает

```bash
# 1) папку прогона надо ЗАТРАСТИТЬ (иначе codex не грузит project-config):
#    в ~/.codex/config.toml добавить:
#    [projects."/home/tacticum/<pilot-dir>"]
#    trust_level = "trusted"

# 2) MCP-вызовы в headless режутся аппрувом → нужен bypass-флаг:
codex exec --dangerously-bypass-approvals-and-sandbox -C /path/to/pilot "<промпт>" </dev/null

# для длинных прогонов (>5 мин) — nohup + poll, т.к. у SSH-команды лимит ~5 мин:
nohup bash -c 'timeout 500 codex exec ... > run.log 2>&1; echo done > run.done' &
for i in $(seq 1 40); do [ -f run.done ] && break; sleep 15; done; tail -30 run.log
```

## 4. Три уровня проверки (от дешёвого к золотому)

### A. Serves-check — каталог отдаёт роль корректно (быстро, репа не нужна)

Через `tacticum_init_manifest(profile_id, target_cli="codex")` из живого каталога проверь:
- **version** и **число actions** (совпадают с ожидаемым составом роли);
- **action для AGENTS.md**: `merge_strategy = append_section` + `marker_id = tacticum:<role>`.

Последнее — ключевое: подтверждает, что рендерер **дописывает** пак роли по маркеру, а НЕ
затирает файл. Если тут `write_file` без merge_strategy — рендерер-баг, роль сломает
пользовательский AGENTS.md на codex.

Пример (то, что я гонял для web+analyst):
> READ-ONLY. Через tacticum-mcp: для iva-role-web и iva-role-analyst вызови
> `tacticum_init_manifest(profile_id, target_cli="codex")`, покажи version, число actions,
> и для action AGENTS.md — merge_strategy и marker_id.

Результат был: web 0.1.0 / 33 actions / append_section + tacticum:iva-role-web ✓.

### B. Полный install в реальную репу — «золотой стандарт»

1. **Свежий клон** целевой репы (для стека роли): KMP → su.ivcs.messenger, Java → diskstorage,
   web → Angular-репа. Именно свежий — чтобы у него был **свой оригинальный AGENTS.md**
   (проверим, что пак его не затрёт).
2. В клоне создай `.codex/config.toml` с tacticum-mcp (шаг 0 квикстарта):
   ```toml
   [mcp_servers.tacticum-mcp]
   url = "https://mcp.tacticum.dev/mcp"
   bearer_token_env_var = "TACTICUM_TOKEN"
   ```
3. `export TACTICUM_TOKEN=<tac_ или phk_>`, затрастить папку (см. §3), запустить codex:
   > Установи iva-role-<X> из живого каталога. 1) provision_installation (если
   > membership_required — обойди через tacticum_init). 2) pull/init actions. 3) УСТАНОВИ:
   > write_file пиши; для AGENTS.md — в репе УЖЕ есть свой, ДОПИШИ секцию МЕЖДУ маркерами
   > tacticum:iva-role-<X>, НЕ затирай. Исходный код НЕ трогай, не коммить, не пуш.
   > 4) ПРОВЕРЬ: оригинал AGENTS.md на месте + секция роли ровно одна; какие скиллы/агенты встали.
4. **Проверки после:**
   - `grep -c "tacticum:iva-role-<X>" AGENTS.md` → **2** (begin+end, одна секция);
   - число строк AGENTS.md выросло (оригинал + секция), первые строки = репозиторные;
   - `git status --porcelain | grep -v '^??'` → только `M AGENTS.md`, исходники не тронуты;
   - в `.agents/skills/` и `.codex/agents/` лежат ингредиенты роли.

Для kmp у меня было: AGENTS.md 120→191 строк, 2 маркера, 25 скиллов + 3 агента, исходники чистые.

### C. Реальная задача скиллами роли — ЛОВИТ КОНТЕНТ-БАГИ

Установил → дай агенту **реальную задачу** скиллами роли. Именно тут находятся баги.
- read-only диагностика: «по скиллу kmp-architecture-guards опиши модульную структуру» /
  «найди один подозрительный дефект, укажи файл:строку, план репро+фикса — БЕЗ правок»;
- полный цикл (если репа сборочная и есть VPN): `/fix-bug` — repro-тест → фикс → прогон.

Так на **java/diskstorage** агент нашёл **реальный баг** (ICAP DLP delay-правило по имени файла
регистрировалось как текстовое, `EnvironmentLuncher:202`), написал red-тест, починил,
`mvn test` passed. На **kmp** — кандидат-баг в генерации инициалов (двойной пробел).

## 5. Read-only дисциплина — не сломать чужие репы

- Клоны — **свежие и одноразовые**, не рабочие копии пайплайна/коллег.
- В промпте явно: **не менять исходный код, не коммитить, не пушить, не запускать сборку/тесты**
  (если только это не сам тест).
- После прогона всегда сверяй `git status` — изменений исходников быть не должно.

## 6. Что какой уровень доказывает

| Уровень | Доказывает |
|---|---|
| A serves-check | каталог засижен верно + рендерер работает (глобально для всех ролей) |
| B install | рендерер-фикс на реальной репе (не затирает AGENTS.md), правильная раскладка |
| C задача | **скиллы роли реально работают на живом коде** — ловит контент-баги стека |

Рендерер-фикс глобальный (одна функция на все роли) — доказал на одной роли (kmp), остальные
serves-check-ом достаточно. А вот уровень C стоит гонять на КАЖДОМ стеке отдельно — там
находятся стеко-специфичные баги (как ICAP в java).

## 7. Уборка

Пилотные клоны на стенде: `rm -rf /home/tacticum/<pilot-dir>`. Токены в env прогона, никуда
не сохранять. Записи установок (если provision прошёл) идемпотентны — можно оставить.
