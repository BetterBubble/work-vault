# ТЗ: доработка iva-fr-analyst — новая структура FR и проектирование контрактов

**Дата:** 2026-07-24. **База:** профиль `iva-fr-analyst` 0.1.10 (github/main). **Статус:** утверждено owner'ом, не реализовано.
**Основания:** wiki-страница [«Пример описания контрактов»](https://wiki.iva.ru/pages/viewpage.action?pageId=211847207) (space IM, v3 — предложение аналитиков, база шаблона) · рисерч индустриальных практик (ADDR-процесс, Zalando/Azure/Google API guidelines, EARS, Pact CDC, RFC 8594/9745, Anthropic skill-authoring).

## 1. Мотивация (кратко)

Профиль сегодня останавливается на capability-уровне: правило честности §2 запрещает аналитику фиксировать wire-имена (пути, параметры, enum'ы), которых нет в источниках. Команда мессенджера ожидает от постановки готовый черновик контракта wire-уровня (образец — страница 211847207). Без доработки постановки выглядят недоделанными, а wire-дизайн делается разработчиками без ревью либо дописывается аналитиками мимо анти-галлюцинационной дисциплины. Решение — разделение фаз as-is/to-be по частям документа (индустриальный паттерн: capability-требования и wire-дизайн — разные фазы с ревью до реализации).

## 2. Целевая структура FR

### 2.1 Роли частей

- **Часть 1 «Требуемые изменения» (to-be)** — полная спецификация изменений, включая формальные требования и проектные разделы. Формируется отдельными навыками (по разделу на навык), открывается оглавлением (Confluence-макрос `<ac:structured-macro ac:name="toc"/>` — переживает markdown-конвертацию). Человекочитаемая выжимка — вводные разделы 1.1–1.3 прозой.
- **Часть 2 «Фактура» (as-is + процесс)** — строго проверенные факты: пробы, код-verify, negative evidence, источники, реестры вопросов/решений.

### 2.2 Инварианты честности

1. **Часть 2 — только то, что ЕСТЬ.** Ни одного изобретённого имени; каждая строка с источником. Правило §2 действует без ослаблений.
2. **Часть 1 — то, что ДОЛЖНО СТАТЬ.** Проектные wire-имена, модели и потоки разрешены; каждый элемент обязан иметь основание в Части 2: конвенция ближайшего реестра, аналог, либо negative evidence («операции нет → проектируем»).
3. **Проектные разделы** (контракты, модель данных, события; UI при необходимости) несут плашку «предложение, требует утверждения: разработчик + CTO» и открытый Q-n, пока утверждение не зафиксировано как D-n. Утверждение происходит после публикации — фиксируется через `/update-feature` (комментарий на странице → D-n).
4. **Валидатор границы** — механическая проверка перед публикацией: в Части 2 нет проектных имён; каждое wire-имя Части 1 трассируется к основанию (П.F/П.E) либо находится в проектном разделе. Нарушение = дефект документа, публикация останавливается.

### 2.3 Скелет документа

**Часть 1** (формируется навыками, TOC в начале):

| Раздел | Серия ID | Кто формирует | Статус навыка |
|---|---|---|---|
| 1.1 Суть (проза для заказчика: проблема, кому, что появится) | — | fr-authoring (вводная) | есть |
| 1.2 Как это будет работать (проза + диаграммы взаимодействий) | — | fr-authoring (шаг 7б) | есть |
| 1.3 Скоуп / вне скоупа | — | fr-authoring | есть |
| 1.4 Функциональные требования («Система должна…») | FT-n | fr-authoring | есть (переезд из П.A) |
| 1.5 Пользовательские сценарии GIVEN/WHEN/THEN | UC-n | fr-authoring | есть (переезд из П.B) |
| 1.6 Контракты: реестр изменений + по-операционные секции (REST и JUMP) | CT-n | `api-contracts-discovery` | доработка |
| 1.7 Модель данных и состояния | DM-n | новый навык | новый |
| 1.8 События и консистентность | EV-n | новый навык (серия из жанра ТЗ) | новый |
| 1.9 UI-требования и мокапы (токены DS) | — | `mockup-authoring` + `design-system-discovery` | есть |
| 1.10 Нефункциональные требования | — | fr-authoring (из фактуры П.G) | есть |
| 1.11 Ключевые решения и открытые вопросы (выжимки из реестров) | → D-n/Q-n | fr-authoring | есть |

**Часть 2:** П.C Q-реестр · П.D D-реестр · П.E код-verify · П.F пробы контрактов и negative evidence · П.G собранные факты по НФТ · П.I метаданные · П.J источники. Разделы П.A/П.B/П.H упраздняются — содержимое переезжает в Часть 1.

Правила стабильности идентификаторов (номер выдан один раз, не переиспользуется) распространяются на новые серии CT-n/DM-n/EV-n.

### 2.4 Флоу сборки

1. **Сбор фактуры** (текущие шаги 1–6: analyst-MCP, код-verify, пробы контрактов) → Часть 2. Гейт вопросов — до анализа, как сейчас.
2. **Фаза анализа** — каждый навык читает Часть 2 и формирует свой раздел Части 1. Единый контракт навыка-анализатора: вход — фактура Части 2; выход — раздел Части 1 со своей серией ID; деградации явные («раздел не применим» / «фактуры недостаточно → Q-n»).
3. **Интеграция** — сборка разделов в фиксированном порядке, кросс-ссылки на П.x (существующая anchor-механика), TOC, прогон валидатора границы (§2.2 п.4).
4. **Ревью аналитика и публикация** — как сейчас (шаги 8–9).
5. `/update-feature` перегенерирует только затронутые разделы (решение изменило контракт → перезапуск только контрактного навыка); фиксирует утверждения проектных разделов как D-n.

### 2.5 Жанр ТЗ

Та же модель; отличие от FR — только объём документа и объём доработки. Серии и правила — общие.

## 3. Контрактный раздел (1.6)

### 3.1 Формат

База — образец 211847207: **реестр изменений** (Контур | Контракт | Изменение | Назначение | Совместимость) + **по-операционная секция** (описание; таблица параметров запроса — название/где/тип/обязательность/описание; пример запроса JSON; таблица параметров ответа; коды ответа с семантикой; пример ответа).

Дополнения к образцу:

1. **Права доступа** — строка «кто может вызывать» (роль/scope) у каждой операции + `403` в кодах ответа.
2. **Лимиты** — `429` и ограничение частоты, где применимо.
3. **Асинхронность** — операция потенциально дольше ~1 с → описать механизм отслеживания статуса (`202` + статус-ресурс/событие).
4. **Потребители** — строка «потребители контракта» в реестре изменений (иначе колонка «Совместимость» не проверяема).
5. **JUMP-контур** — те же таблицы: вместо метода+пути — имя команды, вместо body — payload; колонка «Контур» = JUMP; конвенции — из канона distrohost (+changelog-секция дока), цитата по правилам api-contracts-discovery.
6. **Трассировка** — каждая операция ссылается на порождающее требование (CT-n/FT-n) и пробу-основание в П.F.

### 3.2 Чеклист полноты контрактных требований

Общий для FR и ТЗ; пункт неприменим → явно «не применимо», молчание запрещено:

операции от потребностей потребителя · различимые классы ошибок и реакция на них · идемпотентность повторов · пагинация растущих коллекций (добавить потом = breaking change) · версионирование + политика совместимости + deprecation · авторизация per-operation · асинхронные операции и уведомление о завершении · конкурентность · таймауты · лимиты/429 · секреты в логах.

### 3.3 Порядок и основания проектирования

- Проект контракта строится **только после** зафиксированных capability-требований (CT-n) и проб П.F (в т.ч. negative evidence).
- Конвенции наследуются из ближайшего реестра (auth-схема, стиль путей/команд, формат ошибок) с цитатой реестр+версия — проект не выдумывается с нуля.
- При вердикте «проектировать» П.F фиксирует **рассмотренные альтернативы**: существующие аналоги + причина отклонения каждого.

## 4. Доработки dev-конвейера

Потребители FR: dev-профили (`iva-kmp-brownfield`, `iva-web-brownfield`, `iva-brownfield-mail`, role-профили) — скилы `brd-authoring`, `pin-authoring`, `tests-authoring`, команда `/start-task`.

- **К-1. Чтение новой структуры.** BRD-скил берёт FT-n/UC-n из Части 1 (сейчас — из П.A/П.B). Переходный период: распознавать обе структуры по маркеру версии скелета (К-5).
- **К-2. Наследование новых серий.** CT-n/DM-n/EV-n наследуются как FT/UC: BRD ссылается; PIN реализует контракт/модель или фиксирует расхождение; TESTS порождает контрактные тесты с `Covers: CT-n`; report — статус каждого CT/DM/EV (реализован / расхождение / blocked).
- **К-3. Гейт утверждения.** Проектный раздел без D-n утверждения (разработчик + CTO) конвейер НЕ реализует: честный BLOCKED с вопросом, не имитация.
- **К-4. Таблица расхождений FR↔KB** расширяется на проектные разделы: контракт-проект/модель данных сверяются с кодом (`kb_verify_api_exists`); конфликт проекта с реальностью — критичное расхождение в выводе.
- **К-5. Версия скелета FR** — маркер в шапке страницы (`fr_skeleton: 2`); отсутствие маркера = текущий формат v1.

Реализация — парная US на dev-профили (аналог US #719 «приём серий ТЗ конвейером»), синхронно с релизом новой структуры: FR нового формата без обновлённого конвейера теряет трассировку.

## 5. Предлагаемая разбивка на US

1. **Структура FR v2 + оркестрация** — fr-authoring: две части в новых ролях, флоу сборки, TOC, валидатор границы, переезд FT/UC/UI-разделов, `fr_skeleton: 2`.
2. **Контрактный раздел** — доработка api-contracts-discovery: формат 3.1 (REST + JUMP), чеклист 3.2, серия CT-n, альтернативы в П.F.
3. **Новые навыки-анализаторы** — модель данных/состояний (DM-n), события/консистентность (EV-n).
4. **Конвейер** — К-1…К-5 на dev-профилях (парная US).
5. **/update-feature** — пер-раздельная перегенерация + фиксация утверждений проектных разделов (разработчик + CTO) как D-n.
