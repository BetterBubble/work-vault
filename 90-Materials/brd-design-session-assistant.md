## 1. Контекст и границы

### 1.1 Бизнес-ситуация

В проектной дизайн-сессии участвуют четыре человека: **заказчик**, **архитектор**, **аналитик**, **тимлид разработки**. Обсуждение идёт в iva-one (созвон + чат треда). Сегодня результат сессии существует только в головах участников и в транскрипте: FR собирается аналитиком вручную через несколько дней, решения теряются, через полгода никто не может ответить «почему так решили и кто это принял».

### 1.2 Что уже есть (переиспользуется, не строится)

| Актив | Что даёт | Где |
|---|---|---|
| Bot API платформы (контракт «IVA Chat Bot API» v1.30) | бот = участник чата; webhook-push New/EditMessage с ретраями; `send-message` + blocks + `ReplyKeyboard` (кнопки, нажатие = сообщение от имени нажавшего); files | Go-backend IVA One (`chats`, `api-gateway`, `profiles`) и MCU |
| Паттерн «бот helm» ×2 («Поддержка», `bot_iva_write`) | webhook-роутер + application-слой без I/O + исходящий канал с blocks; платформа уже шлёт webhook на helm | helm `src/helm/interface/api/routers/bot_*` |
| Identity-резолв IVA ↔ Tacticum | `author.profileId/name/login` → личность (справочник Jira; рабочий путь — по `name`); связка с ключами Tacticum | helm `application/bot_iva_write.py`, `tacticum_key.py` |
| Конвейер `/transcribe` | ffmpeg → whisper → `dialogue` (реплики+говорящие) → `summarize` (Codex-тред); retention 180 дней | helm (`domain/transcribe.py`, воркер `bot_task`) — ручной мост до Фазы T |
| Транскрибация ВКС на MCU | `transcription/start|stop`, live `PhraseEvent` с авторством, хранение ресурсом `TRANSCRIPT` | MCU `ivcs.hi-tech.org` — **Фаза T** (ADR-0065 Р.10) |

| `iva-read` (MCP) | чтение Jira/Confluence ИВА | там же |
| `iva-atlassian-write` (MCP, личный Atlassian PAT) | `confluence_create_page`/`update_page`, полный Jira issue-ops | `templates/iva-architect-mcp/` |
| Скиллы постановки | `fr-authoring`, `brd/adr/pin/tests-authoring`, `multi-container-pin-authoring` | `tacticum-analysis-core` |
| Леджер диспозиций architecture BC | `signal_type`/`signal_key`/`disposition`/`rationale`/`tracker_ref`/`expires_at`, upsert по identity, workspace-scoped fail-closed, запись в Memory | `apps/backend/src/backend/architecture/` |
| `signal_key` с обобщённым `semantic_anchor` («символ кода ИЛИ раздел/пункт документа») | устойчивый якорь для решения и для пункта документа | ADR-0064 Р.8б |

### 1.3 Чего не хватает (предмет этого BRD)

1. **Журнал обсуждений** — сообщения чата (v1) и транскрипт встреч (Фаза T) как читаемый агентами контекст.
2. **История фиксирования решений** — тип сигнала `design_decision` в существующем леджере + атрибуция + очередь.
3. **Поверхность обсуждения** — session-bot (третий бот helm) в чатах iva-one.
4. **Поверхность возврата** — «Живая документация»: воркер helm, отвечающий на комментарии к документу в Confluence.

### 1.4 Границы v1

**В scope:** текстовое присутствие бота в чате/треде; детекция кандидатов по чату; фиксация решений; драфт FR; финализация в Confluence/Jira человеком его ролью; ответы на комментарии в Confluence.

**Вне scope v1 (осознанно):** **доступ к транскрибации ВКС — Фаза T** (решение owner 2026-08-06: проектируется отдельной дизайн-сессией, проводимой в чате с уже работающим ботом; собранные факты — ADR-0065, Контекст и Р.10; ручной мост уже работает: запись встречи → конвейер `/transcribe` helm); голосовое участие бота в реальном времени; автопубликация без апрува; автоматическое заведение задач без человека; мультиязычность помимо ru/en; ретро-обработка архива встреч до запуска.

## 4. Модуль JRN — журнал обсуждений

Три таблицы в **Postgres helm** (alembic helm) — рядом с уже существующими `meetings`/`media_transcript`/`dialogue` конвейера `/transcribe` и ботами платформы; одна точка чтения — MCP-tools `discussion_*` как расширение `/mcp/analyst`. Чат, кандидаты и (с Фазы T) транскрипт имеют общую форму `(session_id, ts, author, kind, text, refs)` и джойнятся в одной БД.

**Леджер решений при этом лежит не здесь**, а в arch-mcp (SoR per ADR-0048; `record_triage`/`list_triage` — MCP-вызовы). Связь журнала с леджером — по общему `signal_key`, а не по таблице: резолв «решение → его цитаты» = один вызов леджера + одна выборка из журнала по тому же ключу. Граница по зрелости сигнала: **кандидат — в журнале** (живёт минуты, массово отбраковывается), **зафиксированное решение — в леджере** (governance-артефакт, живёт годами, попадает в общую очередь разбора). Подробности и отклонённые варианты — ADR-0065 Решение 1.

### UC-JRN-01 — Приём событий обсуждения

Журнал принимает сообщения чата (webhook бота, v1) и сегменты транскрипта (Фаза T), привязывая их к `session_id`.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** в чате с ботом-участником отправлено сообщение **WHEN** платформа доставляет webhook боту **THEN** сообщение сохраняется в `chat_message` с `session_id` чата, автор резолвится в личность существующим резолвом (`author.profileId`/`name` + справочник); событие доступно для чтения не позднее 5 с. *(Фаза T: тот же контракт для `transcript_segment` — спикер, timestamp, текст.)* |
| 2 | negative | **GIVEN** автор события не сопоставим ни с одной личностью (внешний гость, резолв не подтвердился) **WHEN** журнал сохраняет событие **THEN** оно сохраняется с `author=unresolved` и исходным лейблом; участвует в цитировании, но **не может** быть автором решения |
| 3 | error | **GIVEN** входной поток оборвался (webhook-и не доставлялись, бот был выключен) **WHEN** приём возобновляется **THEN** журнал фиксирует разрыв как `gap`-запись с интервалом; все производные артефакты сессии (recap, FR) обязаны показывать предупреждение «в журнале есть пробел ЧЧ:ММ–ЧЧ:ММ» |

### UC-JRN-02 — Чтение журнала агентом

Единая точка чтения для трёх поверхностей: выборка по `session_id`, по `signal_key` решения, по временному окну, по участнику.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** агент запрашивает контекст по `signal_key` зафиксированного решения **WHEN** вызывается `discussion_get_evidence(signal_key)` **THEN** возвращаются реплики-первоисточники с автором, временем и ссылкой на позицию в транскрипте |
| 2 | negative | **GIVEN** агент запрашивает журнал сессии из чужого workspace **WHEN** проверяются права **THEN** ответ fail-closed 404, факт запроса логируется; ответ не содержит признаков существования сессии |
| 3 | error | **GIVEN** объём журнала сессии превышает контекстное окно агента **WHEN** запрашивается полный контекст **THEN** возвращается усечённая выборка с явным флагом `truncated=true` и указанием критерия отбора; агент обязан отразить неполноту в ответе пользователю |

### UC-JRN-03 — Привязка чата к фиче

Все встречи идут в чатах iva-one; фича привязывается к **чату** один раз (не к каждой встрече): из заголовка чата, если распознан, иначе — единовременной командой. Все сессии чата наследуют привязку; `session_id` остаётся per-встреча.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** создан чат «Дизайн: экспорт отчётов» **WHEN** бот добавлен участником **THEN** привязка распознаётся из заголовка, бот подтверждает одним сообщением «тема: экспорт отчётов»; иначе участник задаёт её командой `@бот тема <фича>` один раз |
| 2 | negative | **GIVEN** привязки нет и заголовок не распознан **WHEN** участник фиксирует первое решение **THEN** бот перед фиксацией просит задать тему; фиксация не теряется — выполняется сразу после ответа |
| 3 | error | **GIVEN** участник меняет тему командой при существующей привязке **WHEN** в чате уже есть зафиксированные решения **THEN** бот предупреждает «в чате N решений по теме X» и просит подтверждение; прежние решения остаются привязанными к X |

## 5. Модуль BOT — бот проектной сессии в iva-one

### UC-BOT-01 — Ответ на вопрос по архитектуре

Участник спрашивает `@бот`, бот отвечает фактами из `helm-analyst` с обязательными ссылками.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** архитектор пишет в тред `@бот как устроен модуль X` **WHEN** бот вызывает `arch_map`/`arch_container` **THEN** в тред публикуется ответ с ≥1 проверяемой ссылкой на источник (C4-узел, ADR, задача), p50 ≤ 15 с |
| 2 | negative | **GIVEN** запрошенный модуль отсутствует в C4-топологии **WHEN** `arch_map` возвращает пусто **THEN** бот отвечает «в топологии не найдено», предлагает ближайшие узлы и **не** достраивает ответ из общих знаний модели |
| 3 | error | **GIVEN** `helm-analyst` недоступен (таймаут, 5xx) **WHEN** бот обрабатывает вопрос **THEN** бот явно сообщает «фактовая база недоступна, отвечать не буду», не деградирует в догадку; инцидент попадает в телеметрию как `degraded=true` |

### UC-BOT-02 — Оценка охвата требования

Формулировка заказчика заземляется в `affected_systems` + `constraints`.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** заказчик описал желаемую фичу **WHEN** бот вызывает `affected_systems(requirement)` и `constraints(requirement)` **THEN** в тред публикуется список затронутых систем/контейнеров и перечень ограничивающих ADR/НФТ со ссылками |
| 2 | negative | **GIVEN** формулировка слишком общая («сделать удобнее») **WHEN** `affected_systems` возвращает > 10 систем или пусто **THEN** бот не публикует список, а задаёт один уточняющий вопрос по наиболее неоднозначному термину |
| 3 | error | **GIVEN** `constraints` вернул ограничение с истёкшим `expires_at` **WHEN** бот формирует ответ **THEN** ограничение показывается с пометкой «срок истёк, требует подтверждения владельца» и не трактуется как блокирующее |

### UC-BOT-03 — Поиск прецедентов и дублей

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** обсуждается тема, по которой есть история **WHEN** бот вызывает `related_tasks` / `nearest_spec` **THEN** публикуется до 5 наиболее близких задач/постановок со статусами и ссылками |
| 2 | negative | **GIVEN** прецедентов не найдено **WHEN** обе выборки пусты **THEN** бот молчит (не публикует «ничего не найдено») — отсутствие прецедента не является информацией, ради которой стоит прерывать обсуждение |
| 3 | error | **GIVEN** найденная задача недоступна текущему составу треда по правам **WHEN** бот формирует список **THEN** задача исключается из выдачи целиком (не показывается «нет доступа») — состав треда включает заказчика |

### UC-BOT-04 — Выявление кандидатов в решения

Непрерывная детекция по потоку журнала (v1 — сообщения чата; с Фазы T — и транскрипт). Кандидат = формулировка + автор реплики + цитаты + статус `candidate`.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** в обсуждении прозвучало «значит делаем через очередь, не синхронно» с последующим согласием **WHEN** детектор классифицирует фрагмент **THEN** создаётся `decision_candidate` с нормализованной формулировкой, автором, цитатами; в тред публикуется карточка «похоже на решение… ✅ зафиксировать / ❌ нет» |
| 2 | negative | **GIVEN** тот же смысл повторно проговорён через 10 минут другими словами **WHEN** детектор создаёт кандидата **THEN** он схлопывается с существующим по семантической близости, а не дублируется; в карточке отражается «упоминалось дважды» |
| 3 | error | **GIVEN** детектор выдал кандидата из гипотетической реплики («а если бы мы делали через очередь…») **WHEN** участник жмёт ❌ **THEN** кандидат уходит в `amend` (ошибка детектора) — **не** в `dismiss`; событие попадает в петлю здоровья для калибровки порога |

### UC-BOT-05 — Витрина кандидатов и pending-решений

Витрина — единственная поверхность разбора pending в Фазе 1 (очередь архитектора UC-LDG-02 приходит только в Фазе 2): без секции «ждут подтверждения» предложение заказчика повисает навсегда. Вторая линия защиты — `/фр` при наличии pending останавливается и предлагает довесить их до генерации (UC-BOT-07 №2).

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** идёт или завершилась сессия **WHEN** участник пишет `@бот что на столе` **THEN** публикуется нумерованный список тремя секциями: кандидаты (`candidate`), **«ждут подтверждения» (`pending` — с кнопками approve/reject, действительными для роли-адресата по policy)**, зафиксированные; каждый пункт снабжён кнопкой действия |
| 2 | negative | **GIVEN** кандидатов ноль (обсуждение ещё не дошло до решений) **WHEN** запрошена витрина **THEN** бот отвечает «пока кандидатов нет» и показывает pending и открытые вопросы сессии, если они есть |
| 3 | error | **GIVEN** список кандидатов превышает 25 позиций **WHEN** запрошена витрина **THEN** pending-секция показывается всегда целиком; кандидаты — 10 свежих с указанием общего числа; порог детектора помечается как требующий калибровки |

### UC-BOT-06 — Фиксация решения (четыре канала)

Каналы: карточка в момент детекции; витрина; recap; ручной ввод для пропущенного. Ручной ввод — резервный, не основной.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** тимлид нажимает «зафиксировать» на кандидате **WHEN** бот записывает решение **THEN** в леджер уходит диспозиция `signal_type=design_decision`, `disposition=enforce`, `rationale`, `created_by` = нажавший, `signal_key` = хеш `(session, semantic_anchor)`; кандидат переходит в статус `fixed`; в тред публикуется подтверждение со ссылкой |
| 2 | negative | **GIVEN** решение фиксирует участник, чья роль не имеет права `enforce` для данного типа решения (например заказчик — по архитектурному) **WHEN** нажата кнопка **THEN** диспозиция записывается со `status=pending`; в треде видно «предложено, ждёт подтверждения»; запись появляется в секции «ждут подтверждения» витрины (UC-BOT-05), approve доступен архитектору/аналитику/тимлиду (policy owner 2026-08-06) — иначе pending повисает до Фазы 2 |
| 3 | error | **GIVEN** леджер недоступен в момент нажатия **WHEN** запись не проходит **THEN** кандидат остаётся в статусе `candidate`, участник получает явную ошибку «не зафиксировано, повторите»; ложное подтверждение не публикуется никогда |

### UC-BOT-07 — Драфт FR из зафиксированных решений

Вход — **только** зафиксированные решения с цитатами, не сырой транскрипт. Драфт рождается **сразу страницей-черновиком в Confluence** (техучётка бота, пространство/метка `draft`), не текстом в треде: правка идёт родным редактором Confluence, и с Фазы 2 «Живая документация» отвечает на комментарии к этому же черновику — стыковка волн без миграции драфта.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** в сессии ≥ 1 зафиксированного решения **WHEN** аналитик вызывает `/фр` **THEN** бот создаёт (или обновляет существующий для этой фичи) черновик страницы по скиллу `fr-authoring`, каждый пункт несёт ссылку на решение и его цитаты, и для каждого пункта журнал сохраняет линк «пункт → signal_key» (по нему Живая документация резолвит комментарии, не вычисляя якорь заново); в тред уходит ссылка на черновик + резюме |
| 2 | negative | **GIVEN** есть pending-решения на момент вызова `/фр` **WHEN** бот обрабатывает команду **THEN** черновик **не генерируется сразу**: бот показывает pending-список с кнопками довесить (approve/reject — механика витрины UC-BOT-05) и предлагает сначала закрыть их; генерация выполняется только при явном подтверждении «генерировать с неполным набором» — тогда на страницу ставится тег `fr-incomplete-decisions`, а в шапке — явные ссылки на каждое отсутствующее решение на момент создания; при последующем обновлении черновика с закрытыми pending тег снимается и шапка обновляется. При нуле зафиксированных бот отказывается и показывает витрину |
| 3 | error | **GIVEN** в журнале сессии есть `gap` (UC-JRN-01 №3) **WHEN** формируется драфт **THEN** в шапке черновика печатается предупреждение о пробеле с интервалом; вердикт полноты не выносится |

### UC-BOT-08 — Финализация под личностью утвердившего

Черновик FR уже в Confluence (UC-BOT-07, техучётка, метка `draft`). Финализация — перевод в постановочное пространство и заведение задач Jira — выполняется **человеком его ролью** (`iva-atlassian-write` уже стоит у аналитика/архитектора): бот не хранит чужие PAT и не публикует под чужим именем. Кнопочная публикация из чата (PAT-стор) — осознанно v1.x.

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** архитектор решил финализировать FR **WHEN** он публикует/переносит страницу и заводит задачи своей ролью и кидает ссылку в тред **THEN** бот распознаёт ссылку, пишет `tracker_ref` в диспозиции решений и помечает черновик финализированным; если на черновике в этот момент висит тег `fr-incomplete-decisions` — бот предупреждает в треде «FR финализирован с незакрытыми решениями: …» со ссылками |
| 2 | negative | **GIVEN** участник просит бота «опубликуй в Jira» **WHEN** бот обрабатывает запрос **THEN** бот отказывается («финализация — вашей ролью, вот готовый текст и инструкция») и никогда не пишет в Jira/постановочное пространство техучёткой |
| 3 | error | **GIVEN** черновик изменён в Confluence параллельно с новой фиксацией решений **WHEN** бот обновляет черновик (`update_page`) **THEN** при конфликте версий бот не перезаписывает правки человека, а публикует diff в тред и просит решения |

### UC-BOT-09 — Recap встречи *(Фаза 2)*

## 6. Модуль LDG — леджер решений

Расширение существующего контура диспозиций architecture BC. Словарь **единый** с контуром ревью ADR-0064: `enforce` / `waive` / `amend` / `dismiss`. Эффект — функция от `(signal_type, disposition)`.

| Глагол | Над сигналом ревью (ADR-0064) | Над кандидатом в решение |
|---|---|---|
| `enforce` | признать, провести последствия (фикс-итерация → re-review) | признать решение, провести последствия (пункт FR → публикация → Jira) |
| `waive` | отступление допустимо, подавлено до `expires_at`, `pending` до approve | отложено: вернуться к вопросу к дате |
| `amend` | правило сформулировано неверно → владельцу слоя | кандидат распознан неверно → владельцу детектора |
| `dismiss` | finding отклонён по существу | предложение отвергнуто по существу («так делать не будем») |

### UC-LDG-01 — Запись диспозиции над решением

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** участник провёл кандидата **WHEN** вызывается запись диспозиции **THEN** создаётся запись с `signal_type=design_decision`, `signal_key=hash(session, semantic_anchor)`, `disposition`, `rationale`, `created_by`, upsert по identity; факт дублируется в Memory (ADR-0006) |
| 2 | negative | **GIVEN** по тому же `signal_key` уже есть диспозиция **WHEN** записывается новая **THEN** выполняется upsert, прежняя сохраняется в истории; в треде показывается «решение пересмотрено: было X, стало Y, изменил Z» |
| 3 | error | **GIVEN** запрос пришёл без `created_by` **WHEN** валидируется контракт **THEN** запись отклоняется 422: для `signal_type=design_decision` атрибуция обязательна (для сигналов ревью — сохраняется прежнее поведение) |

### UC-LDG-02 — Разбор pending-очереди *(Фаза 2)*

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** есть диспозиции со `status=pending` **WHEN** архитектор открывает очередь в своём агент-окружении **THEN** видит единый список: и отклонения ревью, и предложенные решения встреч, с одним словарём и одним SLA (≥ раз в 7 дней) |
| 2 | negative | **GIVEN** pending-запись старше SLA **WHEN** выполняется еженедельный проход **THEN** запись эскалируется владельцу слоя, в треде исходной сессии публикуется напоминание |
| 3 | error | **GIVEN** архитектор, разбирающий очередь, не имеет прав на workspace сессии **WHEN** запрашивается запись **THEN** fail-closed 404 |

## 7. Модуль DOC — «Живая документация» *(Фаза 2)*

Отдельная от бота поверхность: другой триггер (комментарий, не реплика), другой жизненный цикл (недели, не минуты), тот же контекст. Имя закреплено за **агентом**, а не за документом: версионирование даёт сам Confluence, «живым» документ делает агент, отвечающий на вопросы к нему.

**Живая документация комментирует, но не правит.** Ответ публикуется под учётной записью агента — читатель должен видеть, что отвечал бот. Правка тела страницы остаётся за человеком под его именем; скоуп доступа агента физически ограничен `confluence_add_comment`.

**Носитель** — воркер helm (полоса очереди `bot_task`, как `helm-media-worker`): проход раз в 5 минут, поллинг комментариев Confluence — без webhook и входящих каналов. Журнал — своя БД helm; леджер — REST-фасад `dev.tacticum.dev`; публикация ответа — `helm-iva-write` под техучёткой агента. Подробности — ADR-0065 Решение 9.

### UC-DOC-01 — Ответ на комментарий из журнала

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** пользователь оставил комментарий «почему выбрали такой подход?» к пункту FR **WHEN** агент резолвит `semantic_anchor` пункта → `signal_key` → диспозицию → цитаты журнала **THEN** в тред комментария публикуется ответ: что решили, кто (`created_by`), когда, почему (`rationale`), плюс цитата первоисточника; p50 ≤ 10 мин |
| 2 | negative | **GIVEN** пункт документа не связан ни с одним зафиксированным решением **WHEN** агент ищет цепочку **THEN** отвечает «этот пункт не прослеживается до зафиксированного решения» и предлагает завести открытый вопрос — **не** реконструирует причину из текста документа |
| 3 | error | **GIVEN** пункт был изменён после фиксации решения (текст разошёлся с решением) **WHEN** агент строит ответ **THEN** публикуется ответ с явным предупреждением о расхождении и обеими формулировками |

### UC-DOC-02 — Реестр открытых вопросов

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** в сессии зафиксирован вопрос без ответа **WHEN** формируется recap **THEN** вопрос попадает в подстраницу-реестр с адресатом, статусом и сроком; за сутки до следующей встречи бот напоминает адресату в треде |
| 2 | negative | **GIVEN** вопрос не имеет очевидного адресата **WHEN** он заводится **THEN** адресатом назначается аналитик сессии по умолчанию, запись помечается «адресат назначен автоматически» |
| 3 | error | **GIVEN** адресат покинул проект (учётка отключена) **WHEN** срабатывает напоминание **THEN** вопрос эскалируется владельцу документа, реестр помечает запись «адресат недоступен» |

### UC-DOC-03 — Сквозная трассировка

| # | Тип | Сценарий |
|---|---|---|
| 1 | positive | **GIVEN** нужно понять происхождение задачи в Jira **WHEN** запрашивается цепочка по `tracker_ref` **THEN** возвращается «задача → пункт FR → решение → цитаты в транскрипте → участники», p50 ≤ 30 с |

## 9. Нефункциональные требования

Целевые значения — **гипотезы пилота**, сравниваются с ретроспективным baseline ниже.

### 9.0 Baseline (замер выполнен 2026-08-06)

Источник: Jira IVAONE, тип **Analytics Task** (постановка аналитика; всего закрытых — 302), выборка 5 задач разных периодов с полной историей статусов (`IVAONE-7738`, `6870`, `6862`, `6968`, `7789`) + разбор порождённых задач у `7738`.

| Метрика | Значения по выборке | Медиана |
|---|---|---|
| Чистая работа аналитика над постановкой (In Progress) | 2.9 / 3.9 / 6.9 / 9.9 / 66.7* дн | **≈ 7 дн** |
| Согласование (In Review + Approvement) | 0 / 0 / 14 / 99 / 226 дн | **14 дн** (худшие — 99 и 226) |
| Активный цикл постановки (старт работы → закрытие) | 7 / 18 / 75 / 102 / 242 дн | **75 дн** |
| Переделки (кейс `7738`) | 4 из 7 порождённых задач — Rejected: заведены до утверждения постановки, отклонены после | — |

\* 66.7 дн — кейс с Reopened.

**Главный вывод:** время съедает не написание FR (~7 дн), а **согласование** — круги In Review/Approvement (медиана 14 дн, хвосты 99–226 дн) и задачи, заведённые до утверждения и потом отклонённые. Это ровно та точка, куда бьёт продукт: решения, зафиксированные с цитатами на самой встрече, сокращают круги ревью и убирают преждевременные задачи. Целевые значения пилота пересчитаны от baseline: активный цикл постановки ≤ 37 дн (−50 %), согласование ≤ 7 дн.

Ограничения замера: один проект (IVAONE), 5 задач, семантика статусов принята по workflow IVAONE; доля повисших вопросов количественно не измерена (оценивается вручную на пилоте). Расширение выборки — обычным JQL-запросом по остальным 297 закрытым Analytics Task.

### 9.1 Качество (главный риск принятия)

| Категория | Требование | Измеримый критерий | Способ измерения |
|---|---|---|---|
| Обоснованность | Каждое фактическое утверждение бота несёт проверяемую ссылку | **100 %** ответов с ≥1 ссылкой | автопроверка лога бота |
| Обоснованность | Каждое зафиксированное решение имеет цитату-первоисточник и `created_by` | **100 %** | автопроверка целостности ссылок |
| Детекция кандидатов | Пропуск дороже ложняка | **recall ≥ 85 %** при **precision ≥ 50 %** | ручная разметка 20 встреч (методика ALIGNMEET) |
| Проактивные реплики | Ложняк дороже пропуска — **обратная шкала** | **precision ≥ 60 %**, ≤ 3 вмешательства за встречу | ручная разметка первых 50 вмешательств |
| Безопасность решений | Нет решений, принятых по неподтверждённому утверждению бота | **0 инцидентов** | реестр инцидентов |

### 9.4 Деградация

| Условие | Поведение |
|---|---|
