# ADP — три доработки по ТЗ Солонко: реализовано и выкачено в прод

**Дата:** 2026-07-25. Все три ТЗ реализованы, проверены и **задеплоены в прод** (каталог профилей `tacticum-dev`), прод-verify зелёный. Ниже — что сделано по каждому, как проверено, что вынесено другим командам.

---

## ТЗ#1 — Дизайн-процесс Figma↔код
**Суть:** конвейер «дизайн → код» для роли «Разработчик + ИИ-агент» (навыки/правила процесса).
**Сделано и в проде:**
- **Сц.4** — перенос форм из iva-one (Angular) в su.ivcs.messenger (KMP/Compose): навык `web-to-kmp-screen-port` + source-reference (мульти-репо: источник read-only, цель write).
- **Сц.1** — наполнение библиотеки компонентов: навык `angular-ds-component-authoring` (анатомия web-компонента, токены-only, полнота вариантов, folder-anatomy + Storybook/Jest).
- **Сц.2** — новый экран по макету: навык `angular-ds-component-usage` (7 шагов: pre-flight → метаданные → резолв через Code Connect/словарь → сборка по selector → приёмка) + числовое сравнение витрина↔Figma (ΔE≤2, ±2px по токенам).
- **Ось-1** (несколько ДС) — `design-system-discovery` читает framework_hint/surface + навык `iva-core-design-system` + web figma-quickstart.
- **Сц.3** — правило миграции (батчи, не смешивать ДС) в authoring-навыке.

## ТЗ#2 — Режимы работы разработчика (лёгкие флоу + гейты)
**Суть:** классификация задачи на входе + лёгкие режимы вместо тяжёлого конвейера, с гейтами качества.
**Сделано и в проде:**
- **Режимы-лейны:** lite (refactoring-S/feature-S) + research (без кода: отчёт + черновик ADR) + bugfix.
- **1-й гейт классификации** на входе `/start-task`: bugfix → fix-bug, refactoring-S/feature-S → lite, research → start-research (с подтверждением).
- **2-й слой пересмотра режима** в фазе постановки (полный → lite / research / split) и на фазах реализации (тупик = смена режима, не капитуляция).
- **lite → research** мини-эскалация при неподтверждённом корне + ADR-first вход как параметр `/start-task` (контракт research→build).
- **Инфраструктура = свойство задачи** (предупреждение о радиусе поражения + toolchain-ошибка не блокирует), не отдельный режим.

## ТЗ#3 — Аналитик проектирует новые требования
**Суть:** аналитик не только описывает as-is, но проектирует to-be (контракты API, модель данных, события) с механизмами честности.
**Сделано и в проде:**
- **FR v2** — двухзонная структура (Часть 1 to-be / Часть 2 as-is-фактура) + механический валидатор границы + три предохранителя честности (основание в фактуре + плашка «требует утверждения dev+CTO» + валидатор).
- **Контрактный формат** (реестр изменений + по-операционные секции: права/лимиты/async/потребители/трассировка) + серия CT-n.
- **Анализаторы:** модель данных (DM-n) и события (EV-n).
- **`/update-feature`** — пер-раздельная перегенерация + фиксация утверждений (D-n).
- **Dev-интеграция конвейера (US#4):** BRD/PIN/TESTS/start-task читают требования из Части 1 по маркеру версии, наследуют серии, гейт утверждения проектных разделов (D-n) — во всех стеках (web/kmp/mail/rn + композиты ios/firebird).
