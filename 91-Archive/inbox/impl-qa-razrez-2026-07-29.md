## Порядок `depends_on` — обоснование

```yaml
depends_on:
  - tacticum-core-base                          # 1
  - tacticum-autotest-core                      # 2
  - iva-pytest-playwright-canvas-autotest-base  # 3
  - iva-qa-tms-base                             # 4
  - iva-qa-delivery-base                        # 5
  - iva-qa-mcp                                  # 6
```

1. **core первым** — слабейший, его перекрывает кто угодно; конвенция всех ролей.
2. **процесс перед стеком** — если стеку когда-нибудь понадобится перекрыть процессный
   справочник, прецедент `tacticum-ui-base` → `iva-kmp-development-base` даёт такую
   возможность. Сегодня не нужно; переставлять потом дороже, чем поставить правильно сразу.
3. **стек после процесса. Порядок стеков между собой не значим и не должен стать значимым** —
   это инвариант, а не случайность: если он начнёт что-то решать, один стек молча затрёт
   другой. Держится правилом именования (префикс слага в id + `stacks/<стек>/` в пути).
4. **TMS перед delivery** — `jira-issue-autotest` (delivery) резолвит ланч Allure через
   клиент TMS. Порядок отражает направление зависимости, хотя пересечений нет.
5. **MCP последним** — внешние каналы поверх готовой субстанции.

Перекрытий в композиции **нет по построению**; `KNOWN_OVERRIDES` для роли остаётся пустым,
и это проверяет существующий `test_golden_parity_union_equals_sum_of_lanes`.

## Доделано по второму заходу лида

### A. `test_lane_target_files_are_pairwise_disjoint`

Лежит в `apps/backend/tests/catalog/test_iva_role_presets.py`, сразу за
`test_known_overrides_are_real_overlaps` — рядом с зеркалом по `ingredient_id`.
Параметризован дважды: по ролям (`ROLE_LANES`) и по CLI (`claude-code`, `codex`) — 28 кейсов.

Как устроен:

1. **Свёртка по `ingredient_id` идёт первой.** Один и тот же ингредиент, объявленный в двух
   лейнах (`KNOWN_OVERRIDES`), — штатная коллизия «позже выигрывает», её проверяет соседний
   тест. Эта проверка ищет РАЗНЫЕ ингредиенты в одном пути.
2. **Путь считается по контракту авторинга**, тем же порядком, что у рендера и у
   `check_install_links.py`: per-CLI passthrough (литеральный, без `.format` — так его
   отдаёт `renderer._cli_body_passthrough`) → `target_path_template` →
   `metadata.target_file` → дефолт по kind. Ингредиенты без файла-приёмника
   (`mcp_server_spec`) и не поддерживающие CLI отбрасываются.
3. **Штатное сожительство исключено по `merge_strategy`, а не по пути.** `append_section`,
   `append_lines`, `deep_merge`, `create_if_missing`, `merge_json` склеивают приёмник —
   `CLAUDE.md` и `AGENTS.md` собираются из паков по маркерам, `.gitignore` дописывается
   строками, `settings.json` сливается. Владение файлом целиком объявляет `replace` плюс
   kind'ы, у которых путь выводится из id (`skill_spec`, `agent_spec`, `command_spec`,
   `rule_set`).
4. **Сообщение называет виновных** в форме `лейн:ingredient_id` и напоминает правило:
   юниты стек-лейна лежат в `stacks/<стек>/` и носят префикс `<стек>-`.

Проверен на живой коллизии, а не только на зелёном прогоне: подмена `target_file` одного
стекового юнита на путь процессного файла роняет тест на обоих CLI и печатает обоих
владельцев. После проверки манифест восстановлен.

Модульный docstring дополнен строкой про новый инвариант.

### B. Раздел для инженера в `.agent-kit/README.md`

Новый раздел **«⚠️ Обновляетесь с прежней версии? Девять файлов переехали — старые нужно
удалить руками»**, второй сверху — до объяснений про нейтральность каталога, чтобы человек
наткнулся на него раньше, чем на теорию. Что в нём:

- **почему переехали** — у каждого стека теперь свой каталог, чтобы два стека в одном
  репозитории не сталкивались;
- **в чём проблема** — «установщик умеет только класть файлы, удалять он не умеет»: после
  обновления на диске будет две копии канона, одинаковые на вид, обе находятся поиском,
  одна больше не обновляется и постепенно разойдётся с живой;
- **полный список девяти путей** отдельным блоком;
- **куда они переехали** — `craft/stacks/<стек>/…` с примером для canvas;
- **готовая команда `rm`** из корня репозитория;
- **явное «не трогайте `rules/invariants.md`»** — он стек-нейтральный и никуда не переезжал;
- **строка для тех, кто ставит впервые:** ничего из перечисленного нет — делать ничего не
  нужно.

CHANGELOG в тексте не упоминается: раздел рассчитан на человека, который его не читал.

Одна техническая деталь: пути в списке даны **от `.agent-kit/`** (`craft/recon.md`, а не
`.agent-kit/craft/recon.md`). Полная форма попадает под регулярку `check_install_links.py`,
и перечень удаляемых файлов превратился бы в 18 «битых ссылок» — проверено, так и вышло с
первого раза. Смысл для читателя не теряется: над блоком стоит «пути ниже отсчитываются от
`.agent-kit/`», а команда `rm` даёт полные пути (её фигурные скобки регулярка не разбирает).

Надгробий (девять `repo_config` со старыми путями и телом «файл переехал») не заводил —
по решению лида: раздел дешевле и не оставляет девять лишних юнитов в манифесте навсегда.

### C. Перепроверка обоих кусков и правка комментария

**Список девяти путей в README получен командой, а не по памяти** — диф путей установки
между `origin/main` и веткой:

```bash
cd apps/backend && uv run --extra dev python - <<'PY'
import subprocess, re
old = subprocess.run(["git","show","origin/main:templates/iva-qa-autotest-base/manifest.yaml"],
                     capture_output=True, text=True, check=True).stdout
rx = re.compile(r'target_file:\s*"?(\.agent-kit/craft/[^"\s]+)"?')
old_paths = set(rx.findall(old))
new_paths = set()
for lane in ["tacticum-autotest-core","iva-pytest-playwright-canvas-autotest-base",
             "iva-qa-tms-base","iva-qa-delivery-base"]:
    new_paths |= set(rx.findall(open(f"templates/{lane}/manifest.yaml", encoding="utf-8").read()))
print(sorted(old_paths - new_paths))
PY
```

45 старых путей `.agent-kit/craft/*` против 46 новых; **не пишутся больше ровно девять** —
`recon`, `pytest-runner`, `allure-raw-parser`, `failure-taxonomy`, `fix-playbooks`,
`batch-conventions`, `test-templates`, `rules/tests`, `rules/page-objects`. Список в README
совпадает с этой девяткой посимвольно. `rules/invariants.md` присутствует в ОБОИХ
множествах — оговорка «не трогайте» в README верна.

**Мутационная проверка теста повторена.** `target_file` ингредиента `tms-scripts-testops-cli`
подменён на путь стекового `recon.md` → тест падает на обоих CLI и печатает обоих владельцев
(`iva-pytest-playwright-canvas-autotest-base:pytest-playwright-canvas-recon` +
`iva-qa-tms-base:tms-scripts-testops-cli`). Манифест восстановлен обратной подстановкой,
дерево чистое.

**Правка комментария (коммит `979e4bb`).** Докстринг `_install_path` обещал «порядок тот же,
что у рендера» — для codex это неправда: без per-CLI тела канонический `renderers/codex.py`

команды туда же с суффиксом `-cmd`, `rule_set` → фрагмент в `AGENTS.md`). Воспроизводить это
в тесте НЕ нужно, и теперь комментарий говорит почему: первые два ключуются по
`ingredient_id` (коллизия пути = коллизия id, её ловит соседний тест), а `AGENTS.md` —
общий склеиваемый приёмник, подстановка реального пути завалила бы тест на штатном
поведении. Сейчас расхождение латентное: ни одна роль не композит больше одного `rule_set`
(всего их 8 на 55 профилей) — но норма обязана называть свой настоящий механизм.

## Решения, принятые самостоятельно

- **`iva-qa-autotest-base` — deprecated, но версия НЕ поднята и каталог не удалён.** 0.5.1
  уже засижен, версии иммутабельны (ADR-0009), и тела должны остаться на диске, чтобы
  засиженная версия была воспроизводима. `deprecated` / `superseded_by` — lifecycle-ключи,
  исключённые из `payload_hash` (policy A, US #369), поэтому бампа не требуют; это
  подтверждает `check_profile_version_discipline --diff-against origin/main`. Цена —
  дублирование тел между замороженным монолитом и новыми лейнами; иначе заморозка не
  заморозка.
- **`superseded_by` — скаляр, преемников четыре.** Назван процессный как основной,
  остальные три перечислены комментарием рядом.
- **Пути стека литеральные, не плейсхолдер `stacks/{stack}/`.** Пока стек один, литерал
  проверяется `check_install_links.py`; плейсхолдер для этой проверки невидим (`{` не
  входит в класс символов пути), то есть даёт ноль верификации. Второй стек → перевод
  процессных тел на плейсхолдер одним проходом, `{stack}` резолвит агент (механизм kit,
  изменений модели не требует). Записано в CHANGELOG и в тело `craft-stack`.
- **`ingredient_id` навыков и субагентов сохранены.** Переименование сломало бы
  пользовательские имена навыков и потребовало бы миграции когорты.

## Что НЕ сделано и почему

- **`craft-stack` → `craft-home` не переименован — решение лида, отложено.** Проект (§1.1)
  это предлагает, но переименование даёт вторую разницу в дереве
  (`.claude/skills/craft-stack/` → `craft-home/`) и осиротевший каталог у тех, кто уже
  установил профиль. Вернёмся к нему, когда пути будут двигаться и так.
- **Учётки и REST-примеры референс-стенда в теле `playwright-cli` не вырезаны** — это тоже
  поверхность, но лид назвал только карту приложения. Отмечено долгом в CHANGELOG стека.
- **`rebuild-autocore` не удалён** (решение Президента) — лежит в процессе, `tier: full`,
  помечен кандидатом на удаление в CHANGELOG и README процесс-лейна.
- **Надгробий (проект §7.2 вариант «а») нет — решение лида.** Вместо девяти `repo_config`
  со старыми путями и телом «файл переехал» — раздел в `.agent-kit/README.md` (см. §B выше).
  Дешевле и не оставляет девять лишних юнитов в манифесте навсегда.
- **Второго стека нет** — блокирующий вход проекта (§8.1, карта поверхностей) не приходил.
  Каркас под него готов: слой `stacks/<стек>/`, правило именования, пустой
  `KNOWN_OVERRIDES`.
