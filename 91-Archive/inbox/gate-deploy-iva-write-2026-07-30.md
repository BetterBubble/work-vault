# Гейт деплоя iva-write на прод helm

Ветка `feat/iva-write-keystore`, worktree `/Users/bubblemac/tacticum-worktrees/helm-iva-write-keystore`.
Вопрос Президента дословно: «проверь что все ок и мы нашим деплоем не поламаем сервер и не снесем ничего».

**Вердикт: GO с двумя обязательными оговорками.** Сам код ветки ничего не сносит и
сервер не роняет. Снести данные может ШТАТНЫЙ скрипт деплоя, если запустить его так,
как написано в README, — это не дефект ветки, но вопрос был задан именно про снос.

## 1. Миграции против боевой базы — чисто

Пять ревизий: `key300 → oa310 → bot330 → idn340 → mrg350`, прочитаны целиком.

**Операций, трогающих существующие данные, нет ни одной.** Только `create_table`,
`add_column`, `create_index`. Ни `drop_table`, ни `drop_column`, ни `alter_column`,
ни `DELETE`/`UPDATE` в `upgrade`.

Создаются новые таблицы: `external_credential`, `credential_use_log`, `oauth_state`,
`bot_dialog_pending`. `add_column` применяются **только к таблицам, которые эта же
ветка и создала** (`external_credential`, `oauth_state`) — ни одна существующая
прод-таблица не затрагивается вовсе.

Накат на непустой таблице упасть не может: все добавляемые колонки либо `nullable=True`
(`refresh_ciphertext`, `refresh_nonce`), либо с `server_default` (`chat_room_id` → `''`,
`external_login` → `''`, `subject_source` → `'declared'`).

`downgrade` рабочий у каждой (drop в обратном FK-порядке). `mrg350` — пустая
merge-ревизия, сводит линию iva-write и линию PM-бота обратно в одну голову.

Проверено самим alembic: `alembic heads` → **ровно одна голова** `mrg350_iva_write_pmb`.
Значит `alembic upgrade head` на множественных головах не упадёт.

## 2. docker-compose.prod.yml — что меняется на живом сервере

- **Добавляется один новый сервис** `mcp-atlassian` (`ghcr.io/sooperset/mcp-atlassian:0.23.0`).
- **К сервису `helm` добавляются три переменные** окружения: `HELM_IVA_WRITE_MCP_URL`,
  `HELM_IVA_WRITE_JIRA_URL`, `HELM_IVA_WRITE_CONFLUENCE_URL` — внутренние адреса, не секреты.
- **`traefik` и `postgres` не тронуты ни одной строкой.** Их конфигурация не изменилась,
  значит `up -d` их не пересоздаёт. Пересоздаётся только `helm` (поменялось окружение) —
  ожидаемый короткий рестарт, он произошёл бы при любом деплое кода.

Конфликт по портам исключён: у нового контейнера `expose: 9000` **без** публикации на хост.
Наружу он не выходит и через traefik: в traefik стоит
`--providers.docker.exposedbydefault=false`, а traefik-лейблов у нового сервиса нет.
`env_file` с `.env` helm ему не монтируется — окружение по учётным данным пустое намеренно
(это условие безопасности: с заполненным пакет молча пишет служебной учёткой).

Конфликт по имени контейнера теоретически возможен, если на сервере уже висит
`<project>-mcp-atlassian-1`. **Сверял только по конфигу: SSH-доступа к 159.194.233.33 из
моего контекста нет** (в `~/.ssh/config` только `zu_demo`; прямой `root@159.194.233.33` —
`Permission denied (publickey)`). Реальный список контейнеров на сервере не проверен.

## 3. Не ломается ли то, что уже работает — не ломается

Проверено не чтением, а запуском.

**Дифф почти чисто аддитивный: 9806 добавленных строк против 4 удалённых.** Все четыре
удалённые — переписанные тут же версии: строка импорта в `main.py`, две строки докстрингов
и кортеж `_PREFIXES`. Ни одна существующая функция, ручка или ветка логики не удалена и не
изменена по поведению.

**Импорт приложения при ПОЛНОСТЬЮ пустом окружении** (`env -i`, ни одной `HELM_*`):
`from helm.main import app` — **OK**, исключений нет. Крипто-слой ленивый: `KeystoreCrypto`
создаётся на запросе, а не на импорте, поэтому отсутствие `HELM_KEYSTORE_MASTER_KEY`
процесс не роняет.

**Смоук по ручкам на пустом окружении** (ASGI, без lifespan):

| запрос | ответ |
|---|---|
| `POST /mcp/iva-write` | `503 not_configured` («нет адреса контейнера») |
| `POST /mcp/iva-write/` | `503 not_configured` |
| `POST /api/internal/iva/credentials` | `404` (флаг `iva_write_internal_enabled` off) |
| `POST /api/bot/iva-write/webhook` | `404` (флаг `iva_bot_iva_write_enabled` off) |
| `GET /api/auth/config` (существующая) | `200` |
| `POST /mcp/hrd` (существующая) | `403`, как и раньше |

Монтирование: два новых роутера **за флагами** (`iva_internal`, `bot_iva_write`, дефолт
`False` у обоих). Безусловны два: роутер согласия `/api/iva/oauth/*` и ASGI-поверхность
`/mcp/iva-write` — намеренно, чтобы «не настроено» (503) отличалось от «не задеплоено» (404).
Оба при отсутствии переменных отвечают 503, а не падают. Префиксных коллизий с
существующими роутерами нет (`/api/bot/support` ≠ `/api/bot/iva-write` и т. д.).

**Полный прогон тестов на смерженной ветке: `2421 passed, 32 skipped`, падений 0** (77 с).
Это регрессия по всему сервису, не только по новому коду.

Новых зависимостей нет: `cryptography` уже была в `uv.lock` на `main` как транзитивная,
ветка лишь подняла её в прямые. В `uv.lock` изменились 2 строки, новых пакетов ноль —
сборка образа ничего нового из сети не тянет.

## 6. Обратимость — есть, и она дешёвая

**Рекомендуемый откат (БД не трогаем):**

1. `git checkout <sha_прежнего_main>` в `/opt/helm`
2. `docker compose -f docker-compose.prod.yml up -d --build helm`
3. `docker compose -f docker-compose.prod.yml rm -sf mcp-atlassian`

Всё. Прежнее поведение возвращается полностью: старый код о новых таблицах не знает и
в них не ходит, поэтому оставленные таблицы безвредны.

**Миграции откатывать не нужно и не стоит.** `downgrade` есть у каждой, но откат через
merge-point (`mrg350`) на разветвлённой истории требует ручного выбора ревизии — в
аварийной ситуации это лишний риск ради нулевой выгоды. Плюс `downgrade` первых двух
ревизий дропает `external_credential`, то есть стирает уже выданные людьми согласия.

## 7. Что деплой требует, чего может не быть

Набор `HELM_KEYSTORE_MASTER_KEY` + 10 × `HELM_IVA_OAUTH_*` (jira/confluence ×
base_url / connect_url / client_id / client_secret, плюс `PUBLIC_BASE_URL` и
`PKCE_ENABLED`) **по коду достаточен** — он ровно совпадает с блоком в `.env.example`.
Три `HELM_IVA_WRITE_*` приходят из compose. `HELM_RESOLVE_URL` /
`HELM_RESOLVE_SERVICE_KEY` на проде уже есть (без них ручки согласия дают 503).

Чего сверх этого требует деплой:

- **Доступ сервера к `ghcr.io`** для `docker pull ghcr.io/sooperset/mcp-atlassian:0.23.0`.
  Если egress закрыт, `up -d` на этом сервисе упадёт. Проверяется одной командой ДО деплоя.
- **`172.18.0.1` должен быть шлюзом той же compose-сети**, куда попадёт новый контейнер.
  Косвенно подтверждается тем, что `helm` уже ходит на `172.18.0.1:8081` за контрактами и
  оба сервиса живут в дефолтной сети проекта. На сервере не сверено (нет доступа).
- **`redirect_uri` `https://helm.tacticum.ru/api/iva/oauth/callback` — побуквенно
  зарегистрирован** у администратора Atlassian, а `client_id`/`client_secret` — настоящие.
  Если это ещё плейсхолдеры, канал отдаёт 503 / «нет личного доступа»: сервису не вредит,
  но фича не работает.
- **Флаги `HELM_IVA_BOT_IVA_WRITE_ENABLED` и `HELM_IVA_WRITE_INTERNAL_ENABLED` остаются
  `false`** — тогда бот и внутренняя ручка выдачи расшифрованного секрета не поднимаются вовсе.

## Оговорки к GO (обе обязательные)

**О-1 (критичная, ровно про «не снести»). Не запускать `bash scripts/deploy.sh` без
`SEED=0`.** Скрипт по умолчанию (`SEED=1`) после миграций выполняет
`seed_db.py --source synthetic`, а тот вызывает `clear_graph(tenant)` — тенант-скопнутый
`DELETE` по `Person`, `PersonEmail`, `Signal`, `Initiative`, `Block`, `Goal`,
`SalesInitiative`, `SalesLink`, `Assignment`, `Dependency`, `BlockTeam` — и заливает на их
место синтетику. На боевой базе это и есть «снесли всё». К этой ветке дефект отношения не
имеет (он на `main` давно), но это единственное место, где снос физически возможен.

Безопасная последовательность:

```
docker pull ghcr.io/sooperset/mcp-atlassian:0.23.0        # проверить egress ДО деплоя
docker compose -f docker-compose.prod.yml exec -T helm uv run --no-sync alembic current
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec -T helm uv run --no-sync alembic upgrade head
# сид НЕ запускать ни в каком виде
```

**О-2. Снять `alembic current` ДО наката и сверить, что применится.** Если прод отстал от
`main`, `upgrade head` протянет ещё и линию PM-бота (`pmb208…pmb216`). Они сами по себе с
`main` и, вероятно, уже применены, — но узнать это надо до, а не в процессе.

## Что этим гейтом НЕ закрыто

- **Состояние живого сервера не сверялось** — SSH-доступа из моего контекста нет. Имена
  контейнеров, реальный шлюз сети, наличие переменных в `/opt/helm/.env`, текущая ревизия
  alembic проверены только по конфигу и коду.
- **Работает ли канал по существу** — это живая проверка, а не дифф. Тесты зелёные, но
  настоящего OAuth-обмена с Jira/Confluence DC заказчика в них нет по определению.
- **Скоуп против замысла плана** механически не проверен: файл скоупа гейту не передавался.
