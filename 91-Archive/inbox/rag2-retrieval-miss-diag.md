# RAG#2 retrieval-miss — диагностика по каналам

Verifier, read-only (sidecar из образа `helm-helm` + прямые Meili/Qdrant read-запросы; helm-helm-1 не нагружался сверх мелких probe; env-file без вывода секретов, удалён). База main b5d1739, те же 9 размеченных golden (8/9 промахов baseline).

## TL;DR — два независимых корня
1. **Exact-key кейсы (7/8 «ключ в запросе»):** ни dense, ни Meili не поднимают названную задачу, т.к. **оба канала жуют полный NL-запрос**, а не распознанный ключ. Meili по голому «IVAONE-7752» даёт **#1**, по полному запросу — **не в top-60**. → фикс: **key-routed дотяжка** (impl-p2a).
2. **Семантический корень (шире key):** dense находит релевантное лишь в **2/9**; **Meili-канал на NL-запросах мёртв (ft MISS во всех 9)**; **hybrid RRF равным весом ХУЖЕ dense-only** (мёртвый ft топит хорошие dense-хиты). → фикс: ре-баланс/гейтинг hybrid + усиление dense/entity-поиска.

## 1. Точный key — Meili/Qdrant прямо
Кейс a-status-01, индекс `iva_jira` (Meili :7700):
| запрос | rank IVAONE-7752 |
|---|---|
| «IVAONE-7752» (голый) | **#1** (весь top — его чанки) |
| полный NL-запрос | **None** (top = IVAONE-6733/1700/4193) |
| полный + matchingStrategy=all | estTotal=**0** |
| key-фильтр `key="IVAONE-7752"` | 6 чанков — **док в Meili есть** |

Qdrant `iva_jira__bge_m3_1024`: все 8 ожидаемых ключей присутствуют (5/5/4/5/2/4/3/5 чанков, key-формат совпадает, tenant=iva) — **корпус полный, это НЕ пробел данных**.

**Механизм:** дискриминирующий токен ключа тонет среди generic-слов запроса («статус», «спринт», «fixVersion», «блокеры», «история статусов» — есть в тысячах задач). Meili ранжирует по числу совпавших слов/близости → выигрывают задачи, матчащие больше слов, а не единственный ключ. Dense эмбеддит весь запрос семантически generic → тоже не поднимает конкретную задачу.

## 2. Per-corpus candidate limit — НЕ бутылочное горло
`search.py`: `CANDIDATE_K=60`, `want=max(limit,60)` → каждый корпус тянет **60 dense + 60 ft**, RRF (`RRF_K=60`), затем per-corpus rerank, cap, top-`limit`. Оркестратор зовёт корпус с `limit=pool=max(k,30)`. Пул широкий; ключ отсутствует уже в 60-кандидатном пуле обоих каналов → лимит ни при чём. Проблема — **качество ранжирования**, не отсечение.

## 3. Баланс dense↔lexical — hybrid активно ВРЕДИТ
- **ft (Meili) на NL-запросах бесполезен**: MISS во всех 9 (возвращает 60 нерелевантных, не целевой ключ).
- **dense находит лишь 2/9** (a-status-04@7, a-graph-04@5) — запрос-эмбеддинг слишком общий для точечного поиска задачи.
- **hybrid RRF равным весом ухудшает dense**: dense@7 → hybrid@**13**; dense@5 → hybrid@**8**. Мёртвый ft-канал вносит 60 нерелевантных id с равным RRF-весом → разбавляет и опускает хорошие dense-хиты. `_hybrid` сливает `[dense_ids, ft_ids]` с одинаковым `RRF_K=60` без взвешивания источника.
- per-corpus rerank — монетка: a-status-04 hybrid@13→full@**2** (спас), a-graph-04 hybrid@8→full@**13** (утопил).
- **a-cross-02** (ключа в запросе нет, чистая семантика «критический путь к релизу One 2.0») — MISS во всех каналах → **dense-семантика реально слаба**, отдельно от key-проблемы.

## Корневой механизм (итог)
Цепочка отказа: (1) Meili-канал на длинном NL-запросе не выделяет дискриминирующий токен → ft MISS; (2) dense-эмбеддинг всего предложения слишком generic → релевантное в top-60 лишь изредка; (3) hybrid RRF равным весом дополнительно топит редкие хорошие dense-хиты мёртвым ft; (4) per-corpus rerank нестабилен; (5) федерация round-robin срезает вклад jira. Ключ/семантика не доходят до пула ещё на шаге (1)-(2).

## Рекомендованные фиксы (с оценкой)
1. **Key-routed дотяжка (закрывает 7/8 key-кейсов; дёшево, высокая отдача).** Роутер уже извлекает `decision.keys`. При распознанном ключе — прямой `key=`-fetch (Meili key-фильтр / Qdrant payload-filter отдают чанки мгновенно) и **пин этих доков в пул до реранка/федерации**. Это impl-p2a. Не трогает NL-ретрив. Риск низкий.
2. **Гейтинг/ре-баланс hybrid (корень семантики).** Варианты по возрастанию сложности:
   - (быстро) для длинных NL-запросов **понижать вес ft** в RRF или гейтить Meili (при мёртвом лексическом сигнале hybrid хуже dense-only — данные это показали); либо взвешенный RRF `w_dense > w_ft`.
   - (средне) **exact-token boost**: если в запросе есть токен, точно матчащийся в key/title — поднимать такой ft-хит (Meili по голому ключу даёт #1 — сигнал есть, его надо не терять).
   - (глубже) **entity-aware query construction**: искать по выделенной сущности/ключу, а не по всему предложению; или query-expansion для dense.
   Оценка: (быстро) правит вред hybrid и вернёт dense-случаи (a-status-04/graph-04 стабильнее); полноценный recall для чисто-семантических (a-cross-02) требует (глубже).
3. **Не полагаться на cross-rerank/floor для recall** — подтверждено прошлым A/B: reranker переупорядочивает пул, а корень — что релевантное **в пул не попадает**. cross-rerank/floor остаются для helm-fix и Р-2a-порога, но recall решается на retrieval-шаге.

## Проверить следующим (impl-заход)
- Прогнать key-routed дотяжку на 9 → ожидаемо recall@k резко вверх на 7/8 key-кейсов.
- A/B hybrid с пониженным весом ft (или dense-only для длинных запросов) → проверить, что dense-случаи не топятся и семантика (a-cross-02) хоть частично поднимается.
- Расширить golden (сейчас 9, из них 1 чисто-семантический) — для честной оценки семантического фикса нужно больше not-key кейсов.
