# Critic US#1 — §2 (зонная релаксация) против ТЗ Солонко §2.2

ИСТОЧНИК ИСТИНЫ: `90-Materials/fr-analyst-contracts-skill-review.md` §2.2 инв.1–4, §2.3.
РЕВИЗУЕМОЕ: `templates/iva-fr-analyst/ingredients/skills/fr-authoring/SKILL.md` (коммит edc5cc2).

## Вердикт: (б) нужны правки — одна дыра СЛАБЕЕ ТЗ + один пропуск ТЗ + мелочи

§2 в главном верна ТЗ §2.2 инв.1–2: различие «выдумка (везде запрещена)» vs
«проектное предложение с основанием» построено корректно, три предохранителя
= инв.2+инв.3+инв.4, замок «нет предохранителя → выдумка → запрещено» держит.
Часть 2 строгая. НО валидатор границы сформулирован СЛАБЕЕ самого §2 (пропускает
имя по Q-n без основания) — это дыра относительно инв.2. Плюс §2 молча уронил
клаузу инв.3 «UI при необходимости». До апрува чинить два пункта (A, C).

---

## A. КРИТИЧНО — валидатор (ii) слабее §2 и слабее ТЗ инв.2 (дыра)

§2 предохранитель (а) делает **основание** обязательным ВСЕГДА:
> «(а) у имени есть **основание в Части 2** … со ссылкой → П.F/П.E» (все три одновременно).

Но валидатор границы, Шаг 7, пункт (ii):
> «Имя либо трассируется к основанию … **либо помечено как проектное
> предложение с открытым `Q-n`**. → *fail*, если имя без основания **И** без `Q-n`.»

Fail-условие «без основания И без Q-n» означает: имя **с Q-n, но без основания —
проходит валидатор**. Это противоречит §2 (а) и ТЗ §2.2 инв.2:
> ТЗ инв.2: «каждый элемент **обязан иметь основание** в Части 2: конвенция
> ближайшего реестра, аналог, либо negative evidence».

Т.к. по ТЗ инв.4 валидатор — ЕДИНСТВЕННЫЙ механический стоп-гейт перед публикацией,
слабый валидатор = реальная дыра: спроектированное wire-имя без основания
(даже negative evidence не проверено) уедет в публикацию под прикрытием Q-n.
Легитимного кейса «нет основания вообще, но есть Q-n» не существует — negative
evidence («операции нет → проектируем») сам есть основание.

**Правка (точно):** в (ii) сделать основание безусловным —
«*fail*, если имя без основания» (точка). Проверку плашки/`Q-n` оставить в (iii)
(она там уже есть). Тогда валидатор = §2 (а)+(б), Q-n перестаёт подменять основание.

## C. ЗАМЕЧАНИЕ — §2 уронил клаузу ТЗ инв.3 «UI при необходимости» (строже/пропуск)

ТЗ §2.2 инв.3 дословно:
> «Проектные разделы (контракты, модель данных, события; **UI при необходимости**)
> несут плашку … и открытый Q-n».

§2 в SKILL определяет проектные разделы как ТОЛЬКО §1.6/§1.7/§1.8, а §1.9 UI
относит к НЕпроектным (в перечне «1.1–1.5, 1.9–1.11 wire-имена не вводятся»).
§1.9 сформулирован как «интеграции/поля/состояния UI **из фактов Приложения**» —
т.е. проектирование UI (to-be) не допускается вовсе. Это СТРОЖЕ ТЗ: ТЗ разрешает
проектный UI «при необходимости» под плашкой; SKILL его запрещает/не покрывает.
Смягчение: §1.9 по ТЗ §2.3 — зона навыков `mockup-authoring`/`design-system-discovery`
(отдельные US), fr-authoring вправе отложить. Но НОРМА §2 не должна молча ронять
клаузу инв.3.
**Правка:** в §2 добавить одну фразу — проектный UI (при необходимости, инв.3)
подчиняется той же зонной дисциплине и делается навыками UI (US-…), а §1.9 в
fr-authoring держит только as-is факты. Согласовать со скоупом с лидом.

## Мелочи (внутренняя согласованность, не отклонение от ТЗ)

- **B.** §2 (Часть 1): «в НЕпроектных разделах … wire-имена **не вводятся**»
  (абсолютно), но валидатор (iv) допускает подтверждённые код-verify/каноном
  имена («те — факт»). Согласовать: в §2 писать «**проектные** wire-имена не
  вводятся». Не отклонение от ТЗ, чистка формулировки.
- **D.** Предохранитель (в) «проходит механический валидатор» — валидатор сам
  проверяет (а) и (б), поэтому (в) слегка циркулярен. Безвредно; можно оставить
  как отсылку на инв.4-гейт.
- **E.** Валидатор назван «детерминированный/механический» (инв.4), но детекция
  «что есть wire-имя» опирается на распознавание агентом (не regex). По природе
  задачи приемлемо; формулировку «детерминированный» держать как «чек-лист
  pass/fail», не обещать regex-механику.

## Сверка остальных пунктов ассайнмента

**§12 (Часть 1 to-be / Приложение as-is) — ОК.** Строки 721–730 точно ложатся на
ТЗ инв.2: непроектные утверждения → факт (→ П.x), проектные имена → ОСНОВАНИЕ
(реестр/аналог/negative evidence → П.F/П.E), «это НЕ дефект». Конфликта с §1–§11
нет; §11 корректно держит неутверждённые (открытый Q-n) проектные имена вне
диаграмм до D-n. Согласовано.

**Валидатор vs инв.4 — ОК по структуре, дыра в (ii).** (i) «Часть 2 чиста» =
инв.4 «в Части 2 нет проектных имён» ✓. Гейт Шага 9 п.1 ссылается на Шаг 7,
определён один раз ✓. Разбиение инв.4 на (ii) проектные / (iv) непроектные —
даже полнее ТЗ. Единственный дефект — Q-n-байпас в (ii) (см. A).

**5 развилок реализатора:**
1. «Что уже есть» свёрнуто в §1.2 (нет 12-го слота) — **ТЗ-обоснована.** ТЗ §2.3
   даёт ровно 11 слотов; не выдумывать слот и не терять контент — верный выбор.
2. §1.11 «решения И вопросы» — **ТЗ-обоснована.** ТЗ §2.3 дословно «Ключевые
   решения и открытые вопросы». Выбор ТЗ над формулировкой ассайнмента — верно.
3. TOC-макрос — **по ТЗ, не сверх.** ТЗ §2.1 «открывается оглавлением
   (макрос toc)», §2.3 «TOC в начале». В ассайнменте не был, но в источнике истины
   есть → правомерно.
4. Плейсхолдеры §1.7/§1.8 — **ОК.** ТЗ §2.3 помечает 1.7/1.8 как новые навыки
   (US#3). Правило прописано, содержимое DM-n/EV-n не выдумано — верное скоупирование.
5. Переходная совместимость по `fr_skeleton: 2` — **по ТЗ.** ТЗ §4 К-5 (маркер,
   отсутствие=v1) + К-1 (распознавать обе структуры). Окно с US#4 на ГД — корректно.

**Скелет 1.1–1.11 vs ТЗ §2.3 — ОК, полное соответствие.** Все 11 слотов на месте
в тех же ролях; переезд FT-n (П.A→§1.4), UC-n (П.B→§1.5), UI (П.H→§1.9); П.A/П.B/П.H
упразднены, П.C…П.J сохранены (буквы не переприсвоены — ссылки стабильны). Серии
CT-n/DM-n/EV-n объявлены с правилами стабильности (ТЗ §2.3 послед. абзац) ✓.
Расхождений с ТЗ нет.
