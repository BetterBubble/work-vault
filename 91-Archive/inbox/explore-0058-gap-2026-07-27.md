## A. Gateway `mcp-runtime` — маршруты и middleware

Файл: `platform/services/runtime/mcp_runtime/deploy/traefik-mcp-gateway.example.yml` (последний коммит по файлу — `5403ab0 feat: add dev catalog resolver for iva-read (US #95)`).

- Маршрута `/iva-write` **нет**. Есть четыре: `mcp-memory` (:24), `mcp-knowledge` (:30), `mcp-arch` (:36), `mcp-iva-read` (:45).
- Цепочка единственного «write-подобного» (на самом деле read) маршрута к mcp-atlassian, :49: `["mcp-forward-auth", "mcp-iva-read-ratelimit", "mcp-drop-auth", "mcp-strip-iva-read"]` — то есть forward-auth → ratelimit (10/burst 30, :21) → снятие `Authorization` (:19, backend ходит по СЕРВИСНОМУ PAT из env) → strip-prefix. Порядок «forward-auth первым, strip-prefix последним» задокументирован в шапке :4-5.
- Инжект identity в upstream: `authResponseHeaders: ["X-Auth-User-Id","X-Tenant-Id","X-Project-Id","X-Scopes"]` (:13).
- Важно для §5 ADR: **шаблон `mcp-drop-auth` + сервисный PAT в env backend уже существует** — архитектурный кирпич для техучётки готов, но применён к read-инстансу.
- Логирования тул-вызовов на gateway нет — см. строку 5 таблицы.
- Записи `iva-read` в версионируемом `registry.json` нет (там memory/knowledge/arch) — реальный реестр монтируется с хоста (`docker-compose.yml:12-13` `./registry.json:/app/registry.json:ro`). Форма ожидаемой записи видна в тесте: `tests/test_dev_catalog.py:18-22` (`name="iva-read"`, endpoint `http://172.20.0.1:19010/mcp`, tenant-scoped). **Содержимое прод-реестра на хосте я не проверял** (на серверы не ходил).

## B. Forward-auth и scope-гейт

- Гейт: `application/forward_auth.py:23-50` — 404 неизвестный сервер → 401 невалидный токен → 403 не виден тенанту → 403 не хватает scope → 200 + заголовки. Fail-closed.
- Инварианты: `domain/scope.py:12-16` `missing_scopes` (scope `*` = platform_admin покрывает всё), `:19-22` `visible_to` (global ∪ свой тенант). Поле `RegistryEntry.required_scopes` — `domain/models.py:37`, читается из JSON в `infrastructure/registry_store.py:28`.
- Реестр: `registry.json` в репо (3 записи, все `required_scopes: []`), путь настраивается `MCP_RUNTIME_REGISTRY_PATH` (`infrastructure/config.py:19`), стор — `ConfigRegistryStore.from_json_file` (`registry_store.py:39-42`), `put` — только in-memory (`:50-51`), персистентность отложена в Phase 2.
- Источники identity: `ProjectHubResolver` (`infrastructure/resolver.py:15-35`) — scopes = `resolved.capabilities` из project-hub `/resolve`; `DevCatalogResolver` (`infrastructure/dev_catalog.py:73-112`) — scopes жёстко `("iva-read",)` (:32, :109), tenant = org-slug. Цепочка `FallbackResolver` (`resolver.py:38-54`): сначала hub, потом каталог.
- Транспорт для ролевых scope на стороне hub существует: `infrastructure/project_hub.py:29,39,50,60` — ответ `/api/internal/resolve` несёт `capabilities`, которые становятся `Identity.scopes`. То есть scope `iva-req-write` теоретически выдаётся hub-ключом; ключами Dev-каталога — нет (см. ниже). Сам репозиторий project-hub в рабочих директориях сессии отсутствует, его сторону не проверял.
- **Строки `iva-req-write` в коде обоих репозиториев нет** (греп по `platform` — 0; по `tacticum-dev` — только 3 документа, перечислены выше).
- Инжектируемые identity-заголовки, точно (`application/forward_auth.py:45-50`): `X-Auth-User-Id` = user_id (для ключей каталога это **email**, `dev_catalog.py:106`), `X-Tenant-Id`, `X-Project-Id` (всегда `""` для MCP — `resolver.py:33`), `X-Scopes` (CSV).

## E. Схема каталога и рендереры

Схема `templates/_schema/ingredient.v1.schema.json:89-107`: для `kind: mcp_server_spec` обязателен только `transport` (`stdio|http|sse`); опциональны `command`, `url`, `args[]`, `env_required[]`, `auth_type` (`none|bearer|basic|oauth`), `allowed_tools[]`, `required_scopes[]`. Модель — `apps/backend/src/backend/catalog/domain/ingredients/mcp_server_spec.py:14-32` (валидатор `:26-32`: stdio требует command, http/sse требует url).

**Как потребляется `env_required` (проверено сегодня, факт 21.07 подтверждается):**

| Транспорт | claude-code | codex | сколько ключей доезжает |
|---|---|---|---|
| `stdio` | `renderers/claude_code.py:121-122` → `config["env"] = {k: "${env:k}" for k in env_required}` | `renderers/codex.py:152-155` → `entry["env"] = {...}` | **ВСЕ** объявленные |
| `http`/`sse` + `auth_type: bearer` | `renderers/claude_code.py:119-120` → `headers.Authorization = "Bearer ${env_required[0]}"` | `renderers/codex.py:159-160` → `bearer_token_env_var = env_required[0]` | **только `env_required[0]`**, остальные молча теряются |

То же дублируется в живом MCP-пути: `domain/renderer.py:86-92` (`_mcp_server_value`, зеркало claude-code рендерера — комментарий :64-66). Прочие рендереры (`copilot.py:147-148`, `opencode.py:83-84`, `gemini.py:90-91`) кладут env только в stdio-ветке.

**Следствие для iva-write:** http+bearer-канал по построению несёт РОВНО ОДИН клиентский ключ — это ровно та архитектура, которую предполагает ADR-0058 (клиент несёт hub-ключ, а PAT живёт серверно). Многоключевой http-канал сегодня отрендерить нельзя.

**`required_scopes` рендерером НЕ потребляется вообще** — единственные вхождения в бэкенде: схема (`:103`) и pydantic-поле (`mcp_server_spec.py:24`). Ни один из шести рендереров его не читает. **`allowed_tools` — так же: нигде не рендерится** (греп по `apps/` вне `templates/` даёт только модель, схему, доки и подсказку в admin_web `apps/admin_web/src/components/profile-editor/editors.tsx:843`). То есть заявленный в ADR-0060 «скоуп по ролям через `allowed_tools`» на уровне доставки конфига сегодня декларативен: в `.mcp.json` / `config.toml` ограничение тулов не уезжает.
