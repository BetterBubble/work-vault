## 1. `docs/iva-analyst-mcp-design.md` — авторский замысел MCP-сервера

Статус файла: **дизайн-документ, не реализация** (untracked, ревизия 2026-07-14). Расписан детально, до контрактов вход/выход.

### 1.1. Тулы (MCP-инструменты)

| Тул | Корпус | Обёртка над | Вход | Выход (ключевые поля) | Генерация LLM? |
|---|---|---|---|---|---|
| **`analyst_search`** | RAG#2 (Jira/Confluence) | `Rag2Orchestrator.answer` → `Rag2SearchOut` | `query` (str, обяз.), `k` (int, default 5), `filters` (dict project/epic/component/status/type, опц.) | `query, mode(index\|live\|hybrid), structural(bool), as_of, results[]{key,title,status,assignee,epic,component,type,url,freshness,as_of,score}, disclaimer, no_answer` | Нет — broad-recall список задач, без прозы |
| **`analyst_context`** | RAG#2 (Jira/Confluence) | `Rag2Orchestrator.answer` → `Rag2ContextOut` | тот же (`query`, `k`, `filters`) | `query, mode, context (текст с [n]-цитатами), citations[]{n,key,title,url,status,as_of,freshness}, structural{intent,key,result}, as_of, degraded, needs_confluence_body, disclaimer, answerable` | Нет (генерит клиент-агент по контексту) |
| **`docs_ask`** | RAG#1 (публичная дока) | `DocsAssistant.ask` → `DocsAskOut` | `question` (str, обяз.) | `text, not_found, reason, citations[]{n,title,slug,url,heading_path,product}` | **Да** (внутренний triva) |
| **`docs_search`** *(опционально, не в MVP)* | RAG#1 | `DocsAssistant.search` (порт ретрива) | — | сырые хиты без генерации | Нет |

- `search` vs `context` (RAG#2) — ровно контракт текущей морды `/api/rag2/*`: `search` = навигация/фильтрация, `context` = готовый цитируемый блок для промпта агента. Оба под капотом зовут один `orchestrator.answer(query, k, filters)`.
- Дефолт дизайна — **экспонировать оба корпуса** (RAG#2 + RAG#1), `docs_*` под флагом `analyst_mcp_expose_docs=false`, если решат «только RAG#2» (см. §1.4 открытые вопросы).
- Ошибки → JSON-RPC `isError`: не сконфигурировано → «корпус не сконфигурирован» (аналог 503); сбой ретрива/генерации → «временно недоступен» (аналог 502); пустой запрос → «пустой запрос» (аналог 422).

### 1.2. Транспорт и размещение

- **Транспорт:** streamable-http, JSON-RPC 2.0 — тот же паттерн, что helm уже потребляет как клиент у платформенных `mcp.tacticum.ru/{memory,knowledge}/mcp`. Цикл: `initialize` (→ `Mcp-Session-Id`) → `notifications/initialized` → `tools/call`. Ответ — одиночный JSON либо SSE (FastMCP умеет оба; наши тулы отвечают целиком, без стриминга — triva не отдаёт SSE).
- **Эндпоинт:** `POST /mcp/analyst` — в том же helm-приложении (FastAPI), рядом с `/api/rag2/*` и `/api/docs/*`. Монтируется как ASGI sub-app (FastMCP) в тот же процесс.
- **Почему не отдельный сервис:** тулы — тонкая обёртка над `Rag2Orchestrator`/`DocsAssistant`, которые уже живут в helm со своим кэшем на `app.state`. Отдельный процесс = либо дублировать сборку контекста (Qdrant/Meili/Gateway/live-MCP клиенты), либо лишний HTTP-хоп в helm.
- Новый код — **только** `interface/mcp/` (тонкий адаптер) + поля конфига + монтирование в `main.py`. Application/domain/infrastructure RAG#1/RAG#2 не трогаются.

### 1.3. Аутентификация

- **Bearer-токен в конфиге MCP-клиента** (машинный клиент, нет браузера для OIDC) → helm валидирует **тем же путём, что HTTP-морда**: `require_user`-эквивалент → project-hub `/resolve` (service-key, приватно) → `principal_for_tenant(email, memberships, expected_tenant="iva")` → `None` → 403 (**fail-closed**, нет членства в тенанте `iva`).
- Токен авторитетен — tenant/user берутся из резолва токена, не из заголовков клиента (нельзя подделать тенант).
- Секрет резолвера (`HELM_RESOLVE_URL` + `HELM_RESOLVE_SERVICE_KEY`) — только в `.env` сервера, не в git. У клиента — только личный Bearer.
- `auth_required=false` (dev) → открытый dev-принципал, как у морды.
- **«phk / tacticum-deploy»** (метка из концепта) — рабочая интерпретация, **к подтверждению**:
  - **phk** = *project-hub key* — персональный токен аналитика из project-hub (тот же idP, что OIDC веб-морды).
  - **tacticum-deploy** = деплой-идентичность/сервисный ключ — общий сервисный аккаунт (fallback для headless/CI).
  - Рекомендация автора: персональный project-hub токен как основной путь (аудит по пользователю), `tacticum-deploy` — fallback.
- Все тулы работают в scope одного тенанта (`iva`); тест изоляции ADR-0003 должен покрывать MCP-вход так же, как REST.

### 1.4. §7.1 «К подтверждению на встрече» (дословно списком)

1. **Scope тулов:** экспонируем оба корпуса (RAG#2 + RAG#1) или только RAG#2? Дефолт дизайна — оба, RAG#1 под флагом. Влияет на набор тулов и объём тестирования.
2. **Формат auth «phk / tacticum-deploy»:** персональный project-hub токен (аудит по пользователю) или общий сервисный `tacticum-deploy`-ключ (проще раздать, теряем пер-юзер аудит)? Кто и как выдаёт/ротирует?
3. **Rate-limit / квоты:** нужен ли лимит на клиента/токен? MCP-агент может звать тулы в цикле — риск нагрузить Gateway (`embed`), triva-туннель и live `iva-mcp`. Предложение автора: пер-принципал лимит на `docs_ask` (самый дорогой путь — генерация triva) и на live-fetch RAG#2.
4. **Изоляция тенанта:** подтвердить, что тенант-гейт `iva` из `require_user` достаточен, и тест изоляции (ADR-0003) покрывает MCP-вход так же, как REST.

**Риски/зависимости (§7.2, кратко):** зависимость от live-MCP туннеля `iva-mcp` (деградация → откат на индекс + дисклеймер); неполнота тел Confluence IVAPROJECT (уже флагуется `needs_confluence_body`); triva без SSE/таймауты; реранкер заблокирован (403, общий блокер платформы); абьюз машинного клиента (митигируется rate-limit); дрейф REST vs MCP сериализации (митигируется общим хелпером маппинга, §5.3 дизайн-дока).

## 2. Концепты v2/v3/vision — куски про «MCP для аналитиков» / «интерфейс 2» и артефакты аналитика

### 2.1. v2 (`iva-knowledge-rag-concept-v2.md`) — «MCP для аналитиков» как частный интерфейс

- **Три интерфейса** (сквозная рамка v2, §1): (1) чат-бот helm, (2) **MCP-тул для аналитиков** (auth `phk/tacticum-deploy`, отдаёт RAG#2 wiki/jira + опц. RAG#1), (3) встроенный бот Evo/IVA One. Статус интерфейса 2 на момент v2: «⚙️ в коде (морда `/api/rag2/*`), MCP-обёртка проектируется».
- **§3.2, дословно про морду:** «**MCP-сервер для аналитиков** (интерфейс 2, auth phk/tacticum-deploy) — экспонирует `rag2_search` / `rag2_context` как MCP-тулы; текущая реализация — HTTP-морда `/api/rag2/{search,context}`». (Заметка: имена тулов здесь `rag2_search`/`rag2_context` — в финальном design-доке §1 они переименованы в `analyst_search`/`analyst_context`.)
- **§8, открытый вопрос 1 (дословно):** «Приоритет интерфейса 2 (MCP аналитикам): делаем MCP-обёртку сразу в Фазе 1 или сначала добираем корпус Confluence? Auth-контур phk/tacticum-deploy — подтвердить.»
- **§9, целевой путь (важно для архитектуры):** платформенный модуль `knowledge` (`platform/services/data/knowledge_rag/`) — «архитектурно правильный дом» на будущее: контракт `knowledge.{search,ingest,list_collections}` как MCP-тулы, scope-изоляция fail-closed. Дисциплина уже сейчас: писать морды **за портом `search(query, scope) → hits`**, чтобы позже под капотом заменить форк-codex на платформенный `knowledge.search` без переписывания морд.

### 2.2. v3 (`iva-knowledge-rag-concept-v3.md`) — сдвиг к «единый MCP-гейт», не «MCP только для аналитиков»

- **Ключевой сдвиг v2→v3** (по решению встречи руководителей): не «MCP для аналитиков» как частность, а **единый MCP-гейт с RBAC-профилями для всех ролей** (клиенты/поддержка/аналитики/тестировщики/разработчики/продавцы) над общим пулом RAG-корпусов.
- **§2, роль «Аналитики» (таблица):** срез знаний — **«Спеки + код + карта раскладки функционала по сервисам/командам; „что уже есть, где гэпы“»**, глубина — «Глубокий», интерфейс — **`/analyst` + MCP**.
- **§5, разделение RAG vs MCP (дословно, ключевое определение):**
  > «**RAG** = оффлайн-индекс поверх мастер-данных (чтение, broad-recall). **Единый MCP** = (1) профили доступа ролей к корпусам (RBAC), (2) живая подтяжка свежего (задача создана 5 минут назад — через контракт REST Jira/Confluence), (3) запись — заведение задач/страниц/требований в Jira/Wiki/Helm. Проектируем относительно контракта (REST источника), MCP — прослойка актуальности/доступа, не фундамент.»
- **§8, план B (единый MCP-гейт):** «Один MCP над корпусами; профиль роли → доступный срез; RBAC в бэкенде; **обобщить текущую морду `/api/rag2/*`** под этот гейт» — т.е. design-документ analyst-mcp — это шаг именно к этому плану B, но названный частным случаем «для аналитиков».
- **Приложение «что изменилось v2→v3»** явно фиксирует: «„MCP для аналитиков“ (частный)» → «Единый MCP-гейт с RBAC-профилями всех ролей».

### 2.3. vision (`iva-knowledge-vision.md`) — источник видения руководителей (созвон), артефакты аналитика

- **§1.1, роль «Аналитики / сопроводы» (дословно из таблицы):** срез — **«Спецификации + код + карта раскладки функционала по сервисам/командам»**, глубина «Глубокий», комментарий с созвона: *«Получают хотелку клиента → понять, что уже есть по проекту и что доработать; подсвечивать гэпы.»*
- **§1.3 «Конвейер аналитика» — самое близкое к «5 документам» из всего найденного.** Дословный 7-шаговый пайплайн от хотелки клиента до кода (помечен руководителями как «будущее, наступит быстро»):
  1. Аналитик через RAG понимает, **что уже есть** по хотелке и где гэпы.
  2. Аналитик **в диалоге с агентом проектирует UX** нового функционала — опора на **RAG принципов проектирования UX** (небольшой корпус общих принципов/дизайна пользовательских путей).
  3. UX **раскладывается по сервисам** — нужен **архитектурный RAG**: какие сервисы какие функции реализуют (= раскладка функционала по сервисам/командам, ровно то, что просит §3 discovery-заметки про C4).
  4. Задача **детализируется под каждый сервис**; формируются **контракты** сервисов друг к другу.
  5. **Реестр API/контрактов** синхронизирует клиентов и серверов (автоматически находит/подтягивает контракты).
  6. Разработка получает контракты + требования к своему сервису + **архитектурный RAG репозитория**.
  7. Тестирование получает **configuration management** (стенды/версии/фичи/релизы).
  - Это **этапы конвейера, не «5 документов»-артефактов** — ни один из трёх файлов не перечисляет «5 документов» как список deliverable'ов аналитика. Ближайшая по духу вещь — «карта раскладки функционала по сервисам/командам» (шаг 3, = архитектурный RAG / C4) и «контракты сервисов» (шаг 4-5).
- **§1.4, сейлы (не аналитики, но смежный gap-анализ сценарий, дословно):** *«мне что-то спросили, а я хочу… текст напечатать / документ скинуть и получить, что есть, что нет»* — ввод текста/документа клиента → ответ what's-there/what's-missing. Термины «use case»/«установка разработчику»/«пользовательский сценарий» как явный список — **не встречены**.
- **§4, «что скорректировать» пункт 6:** новые корпуса под этот конвейер — код/репозиторий-RAG, config-management, реестр API/контрактов, RAG принципов UX/архитектуры — ни один из них пока не построен (статус 🆕 во всех трёх файлах).

## Итог по «5 документам»

**Явного списка «5 документов аналитика» не найдено ни в одном из четырёх разобранных файлов** (design-документ MCP, v2, v3, vision). Термины «use case», «установка разработчику», «пользовательский сценарий» как поименованный набор артефактов тоже не встречены дословно — есть только:
- «Конвейер аналитика» (vision §1.3) — 7 **шагов процесса** (гэп-анализ → UX-дизайн → раскладка по сервисам → детализация под сервис → контракты API → архитектурный RAG репозитория → config-mgmt тестирования), не список документов;
- «Карта раскладки функционала по сервисам/командам» = архитектурный RAG = наш C4 (`ArchNode`/`ArchEdge`, см. discovery-заметку §3) — это то самое «за что отвечает контейнер», уже есть как данные;
- «Реестр API/контрактов» — упомянут во всех трёх концептах как **новый, ещё не построенный** корпус (🆕), нужен для шага 4-5 конвейера.

Если «5 документов» — термин с другого источника (созвон/презентация, не транскрибированный в эти файлы) — нужна прямая цитата/ссылка от лида, поиском по этим четырём файлам и по Taiga не находится.
