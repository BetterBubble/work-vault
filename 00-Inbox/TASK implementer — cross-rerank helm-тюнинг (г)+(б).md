## ЗАДАЧА
Устранить регресс cross-rerank на helm-корпусе, реализовав **(г) обогащение helm-текста перед реранком + (б) rank-floor** как страховку. Подтверждённый диагноз: helm-требование матчит запрос по обогащённому embed-тексту (title+desc + управленческая **сводка покрытия**), а кросс-энкодер судит его по обеднённому `payload["text"]` (title+desc БЕЗ сводки) → системно недооценивает → роняет (4/16 запросов: Q2/Q6/Q7/Q8).

### (г) Source-aware обогащение helm-текста ⭐ основное
- Точка: `src/helm/infrastructure/rag2/reranker.py` (~строка 31, `JiraReranker.rerank`, где `texts = [jira_rerank_text(d) for d in docs]`). Для `source=helm` строй текст реранка = title+desc **+ управленческая сводка** из полей, уже присутствующих в `JiraDoc` (`entity_type/verdict/track/component/status`; при недоборе — домапь `generation/client/verdicts` из payload в `src/helm/infrastructure/rag2/search.py:_doc_from_payload`, ~стр.73).
- Для jira/confluence поведение НЕ меняй (у них `payload["text"]` = полное тело). НЕ трогай domain-RRF (`domain/rag2.py federate`). Реингест НЕ нужен (поля уже в Qdrant).
- Цель: кросс-энкодер видит тот же сигнал, что дал helm высокий RRF-ранг → перестаёт недооценивать.

### (б) Rank-floor (страховка, ортогонально)
- Точка: `src/helm/application/rag2.py:~182-186` — ЗАХВАТИ исходный RRF-порядок/score ДО вызова `cross_reranker.rerank(...)`, после реранка НЕ давай документу упасть ниже его исходного RRF-ранга (clamp/стабильная пересортировка). Защита от «провала лучшего ответа из топ-10».
- Application-слой, без domain. Подбери разумный порог, чтобы не убить законные перестановки реранка.
