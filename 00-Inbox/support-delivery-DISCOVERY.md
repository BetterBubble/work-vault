# Разведка: доставка + контур + переиспользование аналитик-MCP для support-MCP

**Автор:** explorer (READ-ONLY). **Дата:** 2026-07-16. Источники: basic-memory (tacticum), код `~/tacticum/helm` (ветки `feat/analyst-mcp-server` — текущая, 8 тулов; `main` — полные 14 тулов).

## 1. ДОСТАВКА (последняя миля для оператора в Naumen)

### Что известно про Naumen (факты)
- **Naumen = система ServiceDesk ИВА.** SD-данные лежат в **live-БД PostgreSQL `10.22.2.48` (`d10task_sd`)**, доступ **через `adp_emb`** (транзит контура ИВА). Владелец данных в реестре — **«ServiceDesk-админ / поддержка»** (Control Tower v0.3, реестр данных по сущностям).
- Наш текущий доступ к SD — **READ-only, выгрузкой**: `data/real/service/sd_tasks.csv` (~42k, `servicedesk.py:100` тема→`title`), плюс прямой REST/БД-дамп в паттерне `extract_*` на adp_emb. **Записи (write-back) в Naumen в памяти/коде НЕТ.**
- **S3 ServiceDesk-коннектор (Naumen)** — задача **SD-RCA #60**, статус **не поднят** (в Taiga «прямого источника чатов/почт RAG#3 нет, ближайшее — SD-RCA #60»). Т.е. живой коннектор к Naumen — на бумаге, не в проде.
- **API Naumen / способ, как оператор с ним работает** — **в памяти НЕ задокументировано**. Знаем только про чтение БД `d10task_sd`. Двусторонней интеграции (создать/обновить тикет через API) не нашёл.

### Реалистичные поверхности доставки (от меньшего трения к большему)
1. **Предзапол­ненный черновик ответа** (оператор копирует) — не требует интеграции в Naumen, только наш UI/бот сбоку. Наименьшее трение.
2. **Панель рядом с тикетом** (read-only виджет: ответ по докам + похожие закрытые тикеты + кого эскалировать). Требует места в UI Naumen или внешнюю панель по id тикета.
3. **Бот** (оператор шлёт номер/текст тикета → пакет). Автономно от Naumen.
4. **Write-back в Naumen** (наш ответ/резолюция пишется в тикет) — **highest friction**: нужен API Naumen на запись + владелец, которого в памяти нет.

### Owner-блокер (аналог «владельца бота Медведева»)
- **Явного владельца интеграции в Naumen в памяти НЕТ.** Кандидаты-гейткиперы: владелец SD-данных = **«ServiceDesk-админ / поддержка»**; сетевой доступ = **adp_emb** (транзит контура); тенант-гейт = **project-hub `iva`** / MCP Gateway `/iva-read` (пускает только tenant=iva, tacticum→403).
- **К руководителю:** кто «пустит» интеграцию в Naumen (владелец Naumen/SD-админ), есть ли у Naumen API на запись, и какая поверхность санкционирована. Это блокер уровня «владелец бота».

## 2. КОНТУР / БЕЗОПАСНОСТЬ

### ВАЖНО: в проекте ДВА разных «контура» — не путать
1. **Контур трёх RAG (по источнику данных)** — «Концепт: три RAG для ИВА на общем движке»:
   - RAG#1 — **публичная** дока `iva.ru/docs` (можно у нас).
   - RAG#2 — **внутренний on-prem** (wiki/jira/EVA для аналитиков, MCP-морда).
   - RAG#3 — **внутренний on-prem, пресейл**: ассистент требований + **чаты/почты** (одна морда). ⚠️ В каноне RAG#3 ≠ «support» — это пресейл. SD/Naumen формально ближе к RAG#3-подобному строго-on-prem контуру, но отдельной сущностью не заведён.
   - Водораздел — **по контуру данных, не по аудитории**. Строго on-prem — только чаты/почты (RAG#3). RAG#1/#2 могут жить на нашем CPU-VPS.
2. **ACL-модель Control Tower (`src/helm/domain/access.py`)** — гейт управленческих данных по **КЛАССАМ данных**, не по трём RAG:
   - Классы: 🟢 `green` (операционка) · 🟠 `amber` (commercial/roadmap) · 🔴 `red_identity` (по-фамильно) · 🔴 `red_money` (деньги по-фамильно).
   - Роль (project-hub, тенант iva) → набор классов. Дефолт члена тенанта — только `green`. **fail-closed**.
   - Гейт аналитик-MCP (`analyst_server.py::_require_principal`): Bearer → project-hub `/resolve` → **тенант-гейт `iva`**, нет членства → отказ (403). Роли из БД `user_role` (live). Копия auth из REST-морды.

### Как SD/support ложится на контур
- SD-тикеты + **crm несут Клиент/Контракт/Тариф/Комментарий** — **чувствительно**. По классам Control Tower это тянет на 🟠amber/🔴red (клиент/контракт/деньги), не на дефолтный green.
- Значит support-MCP — **внутренний on-prem контур** (как RAG#3) **И** должен наследовать **классовый ACL** (не отдавать Клиент/Контракт/Тариф оператору без нужного класса). Механизм готов: `data_classes` + `principal_for_tenant` + fail-closed.
- **tenant-изоляция аналитик-MCP:** жёсткая, `iva`, fail-closed (`_require_principal`). «Спейсы IS/~ исключены» — **в коде текущей ветки не нашёл** (нет space-exclude в `ingest/rag2*`); вероятно решается на этапе дампа/ингеста (скрипты `extract_confluence_*`) — **подтвердить у лида**, где именно режется.

### Что согласовать с безопасностью ДО раздачи
- Класс данных SD/crm (Клиент/Контракт/Тариф/Комментарий) и кто из ролей их видит → маппинг в `access.py` (сейчас там нет SD-класса).
- On-prem размещение support-корпуса (закрытые тикеты) — строго в контуре, как RAG#3.
- Владелец Naumen + сетевой путь adp_emb для support.
- Логи/наблюдаемость запросов оператора по чувствительным полям.

## 3. ПЕРЕИСПОЛЬЗОВАНИЕ аналитик-MCP для SUPPORT (вход = ТИКЕТ, не требование)

**Факт по коду:** текущая ветка `feat/analyst-mcp-server` = **8 тулов**; полные **14 на `main`** (+`feat/mcp-constraints`). Все 14 — **тонкие обёртки** над существующими REST-роутерами (rag2/docs/cio/intake/assistant) с общим fail-closed auth. Это и есть переиспользуемый субстрат.

| # | Тул (сигнатура) | Что делает | Применимость к support-входу (ТИКЕТ) |
|---|---|---|---|
| 1 | `analyst_search(query,k,filters)` | поиск задач/req в Jira/Confluence | 🟡 адаптировать — движок ок, но нужен **SD-корпус**, не Jira |
| 2 | `analyst_context(query,k)` | контекст-блок с цитатами [n] | 🟡 паттерн центральный (ответ с источниками), **репойнт на SD/docs-корпус** |
| 3 | `related_tasks(query,k)` | похожие задачи Jira (broad-recall, source=jira) | 🟡 **это «прецедент»** — но source надо сменить на SD (похожие **закрытые тикеты**) |
| 4 | `docs_ask(query)` | ответ по публичной доке (RAG#1) с цитатами | ✅ **как есть — центральный** для «как настроить/поддерживает ли фичу» |
| 5 | `arch_map(parent,focus,level)` | C4-топология | ⚪ маргинально (роутинг к владельцу) |
| 6 | `arch_container(id,level)` | контейнер C4 + владелец | 🟡 «чей компонент» → эскалация/роутинг |
| 7 | `affected_systems(req_id/text)` | требование→системы (через Requirement→Component) | 🔴 путь идёт от Requirement; для тикета нужен **новый ticket→component mapper** |
| 8 | `requirement_coverage(query)` | реализовано ли требование | 🔴 N/A (тикет ≠ требование) |
| 9 | `nearest_spec(req_text,k)` | ближайшие готовые FR-постановки | 🔴 N/A (шаблоны постановок нерелевантны тикету) |
| 10 | `who_to_involve(req_text,system_id)` | владельцы систем + кто вёл похожее | ✅ **сильно** — эскалация «кого подключить» (адаптировать: + кто решал похожие тикеты) |
| 11 | `effort_hint(req_text,system_id)` | как обычно ЕДУТ похожие задачи (lead/active time) | 🟡 адаптировать → **время решения похожих тикетов / SLA-хинт** |
| 12 | `gap_questions(req_text)` | чеклист полноты постановки vs скелет FR | 🟡 паттерн ок, сменить скелет: **чего не хватает в тикете, чтобы решить** |
| 13 | `constraints(req_text,k)` | ADR/НФТ «почему нельзя» | ⚪ маргинально (known-issues) |
| 14 | `contradiction_check(req_text,k)` | кандидаты на противоречие ADR | 🔴 N/A для support |

**Итог по тулам:** ✅ как есть ~2–3 (`docs_ask`, `who_to_involve`, отчасти `arch_container`); 🟡 адаптировать (репойнт корпуса/скелета) ~5 (`analyst_search`, `analyst_context`, `related_tasks`, `effort_hint`, `gap_questions`); 🔴 N/A ~4–5 (`requirement_coverage`, `nearest_spec`, `affected_systems`, `contradiction_check`, +маргинальные constraints/arch_map).

### Чего НЕ хватает для поддержки (новое)
- **`sd_search` / `sd_context`** — ретрив по **закрытым тикетам с резолюцией** (ядро support-корпуса). Сейчас такого корпуса/тула нет.
- **`ticket→component` mapper** — вход тикет (не требование), нужен маппер на компонент/продукт для роутинга/эскалации.
- **one-shot роутер «тикет→пакет»** — один вызов: {ответ по докам + похожие решённые тикеты + владелец/эскалация + черновик}.
- **Генератор черновика ответа** для оператора (предзаполненный draft — поверхность доставки #1).
- **Known-issues / дубль-инцидент детектор** («это известный сбой?»).
- **Delivery-адаптер к Naumen** (панель/бот/write-back).

### Оценка доли переиспользования (тезис «≈60%»)
- **Инфра/движок** (fail-closed auth `_require_principal`, тонкая REST-обёртка, RAG-роутер rag2/docs, паттерн «ответ+цитаты», retrieval-стек Qdrant+Meili+rerank, ACL `access.py`) — **~70–80% переиспользуемо** практически без изменений.
- **Семантика тулов под ticket-вход** — **~40–50%** (5–6 из 14 ложатся, часть N/A).
- **Вывод:** тезис «support-MCP ≈ 60% аналитик-MCP» **правдоподобен как средневзвешенное** (высокий reuse инфры + средний reuse поверхности). Дельта = **новые support-тулы** (sd_search, ticket-router, draft, delivery) + **SD-корпус закрытых тикетов** + маппинг класса данных в ACL.

## 5. ДВУХКОНТУРНОСТЬ ВЫХОДА (ключевое под безопасность) — подтверждено на коде

Классификация по тому, куда безопасен ВЫХОД тула. Проверено по полям возврата в `analyst_server.py` (main).

| Тул | Что реально в выходе (поля) | Контур выхода |
|---|---|---|
| `docs_ask` | ответ + `citations`=DocCitationOut (title/**url**/slug) → страницы **публичной** iva.ru/docs (IVA One/MCU/CS) | 🟢 **НАРУЖУ клиенту OK** (единственный) |
| `analyst_search` / `analyst_context` | хиты `.source`(jira/confluence)/`.url`/`.space`/цитаты [n] — **внутренние** Jira/Confluence ИВА | 🔴 только ВНУТРЬ оператору |
| `related_tasks` | Jira-хиты (`source=jira`, ключи IVAONE-/VCSWEB2-…, url) — **внутренние баг-прецеденты** | 🔴 только ВНУТРЬ (номер бага клиенту не слать) |
| `nearest_spec` | страницы Confluence FR (key/url/space) — **внутренние постановки** | 🔴 только ВНУТРЬ |
| `arch_map` / `arch_container` | C4-топология: узлы, **владельцы (owner_name)**, репозитории, риски | 🔴 только ВНУТРЬ |
| `affected_systems` | контейнеры + `fix_versions` + **`clients` (имена заказчиков!)** + open_risks | 🔴🔴 ВНУТРЬ + **экстра-чувствительно** (имена клиентов) |
| `who_to_involve` | `owners`(owner_name) + `recent_contributors`(**assignee — ФИО людей/PII**) | 🔴🔴 ВНУТРЬ + PII, клиенту нельзя |
| `effort_hint` | медианы lead/active time по внутренним EpicTask | 🔴 только ВНУТРЬ |
| `requirement_coverage` | вердикты покрытия реестра требований | 🔴 только ВНУТРЬ |
| `constraints` / `contradiction_check` | ADR/НФТ Confluence (title/space/url/snippet) | 🔴 только ВНУТРЬ |
| `gap_questions` | детерминированный чеклист (без внешних ссылок) | 🟠 внутренний процесс (клиенту не нужен) |

**Вывод (правило контура):** выход, **безопасный НАРУЖУ клиенту = только `docs_ask` (RAG#1, публичная дока)** — источники публичны. **Всё остальное = строго ВНУТРЬ оператору** (внутренние Jira/Confluence-ссылки, C4-владельцы, номера багов). **Две обёртки экстра-опасны:** `affected_systems` (имена заказчиков) и `who_to_involve` (ФИО исполнителей — PII) — при формировании клиентского ответа их поля обязаны быть отрезаны. Технически граница чистая: outward-корпус (RAG#1) физически отделён от внутреннего (rag2/cio). Значит support-MCP может провести ту же линию — но ответственность за «не переслать внутреннее клиенту» сейчас на операторе; в one-shot роутере это надо зашить машинно (см. §6).

## 6. One-shot «тикет→пакет» (роутер вместо оператора) — чего не хватает

Сейчас 14 тулов — атомарные, оркестрирует агент/оператор. Для одного вызова «тикет→готовый пакет» не хватает:
1. **Ticket-intake / нормализатор** — на входе сырой тикет (текст+метаданные), не `query`/`requirement_text`. Нужен классификатор: продукт/компонент/интент/язык. Ни один тул этого не делает.
2. **Оркестратор-роутер** — один вызов, веером: `docs_ask` (ответ клиенту) + `sd_search` (прецедент по закрытым тикетам) + `who_to_involve`/`arch_container` (эскалация/владелец) + композер черновика. Композитного эндпоинта нет (у аналитиков это делает FR-скилл-«водитель», не сам MCP).
3. **🔑 Контур-сплиттер в выходе** — пакет ОБЯЗАН разделять блок «клиенту» (только docs-ответ + публичные цитаты) и блок «оператору» (Jira-прецедент, владельцы, компоненты), с явной маркировкой. Это и есть машинная защита из §5 — иначе оператор перешлёт внутреннее. Сейчас такого нет.
4. **SD-корпус + `sd_search`** — `related_tasks` сейчас `source=jira`, а не закрытые SD-тикеты с резолюцией. Ядро прецедента для support отсутствует.
5. **Генератор клиентского черновика** — grounded строго по `docs_ask` (RAG#1), без утечки внутренних полей; PII/имена-клиентов скрабятся.
6. **Confidence-гейт / handoff** — когда авто-ответ, когда эскалация человеку (fail-closed по умолчанию, как auth).
7. **Delivery-адаптер** — вывод пакета в поверхность (§1): черновик/панель/бот/Naumen.

**Оценка:** движок для роутера есть (тонкие REST-обёртки + fail-closed auth + RAG-стек ~70-80%). Не хватает именно **склейки**: intake-классификатор, оркестратор с контур-сплиттером, sd_search-корпус, клиентский композер. Это ~«водитель» аналога FR-скилла, но с жёстким контур-гейтом на выходе — главный новый безопасный кусок.
