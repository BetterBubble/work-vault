# Helm — стратегия построения: вертикальный срез, не горизонталь; ручной прогон = проект пайплайна

Зафиксировано 2026-07-06. Отвечает на «срез по одному направлению» руководителя. Как строим сервис Helm — принцип, чтобы не сбиться в горизонталь.

## Принцип 1 — вертикальный СРЕЗ, не горизонталь
- [decision] **НЕ** строить горизонтально (все 30 сущностей → все мосты → граф → RAG — ничего не работает, пока не готово всё, и каждую сущность делаешь вручную).
- [decision] **Строить вертикально: срез = одно направление через ВСЕ слои сразу.** Берём одно направление → вычленяем ТОЛЬКО его сущности → связываем ТОЛЬКО их мосты → мини-граф → витрина. Получаем работающий кусок сервиса быстро; следующий срез расширяет тот же граф. Метафора: дом строим по комнате целиком (стены+крыша+свет), а не «все стены, потом вся крыша».
- [decision] Это ровно «срез по одному направлению», которое просил руководитель.

## Принцип 2 — ручной прогон = ПРОЕКТИРОВАНИЕ пайплайна, не конечный продукт
- [decision] Когда вычленяем сущность вручную (напр. прогон кластеризации Потребностей) — мы не «создаём сущность навсегда», а **выясняем КАК её вычленять** (источник, метод, где гейт оператора, какая точность). Прогон = спецификация для кода.
- [reference] Путь каждой сущности: (1) **ручной прогон** → понять метод/точность/гейт [ПРОЕКТ] → (2) **код в сервис** → делает автоматически [КОД] → (3) **оператор** чистит грязь на входе + курирует в гейте [ЭКСПЛУАТАЦИЯ].
- [decision] Целевой сервис (верно увиден оператором): грязные данные чистятся руками на входе (останется — данные всегда грязные), а вычленение → джойны → граф → RAG делает сервис САМ. Ручной прогон — временный, для проектирования; не путать с продуктом.

## Дорожная карта (по срезу)
- [plan] **Фаза 0 — проектируем срез вручную** (понять «как»): для CPO-среза — Потребность (прогон ✓ сделан), Требование (прогон из потребностей+вики), Потребность→деньги (проигранные+открытые сделки). Выход: понятный пайплайн + оценка точности.
- [plan] **Фаза 1 — кодим срез в СЕРВИС:** заявки/сделки → эмбеддинг → кластер → Потребность → гейт оператора → Требование → привязка к деньгам → мини-граф → витрина «бэклог+ценность». Выход: первый работающий автоматический кусок.
- [plan] **Фаза 2 — следующий срез** (напр. Сервис/инциденты): свои сущности → свои связи → расширяют ТОТ ЖЕ граф. RAG включается уже на мини-графе первого среза, не ждёт всех 30 сущностей.

## Текущий выбор
- [decision] **Первый срез — Сервис / инциденты-SLA** (пересмотр 2026-07-06: критерий сменили с «ценность» на «все данные уже в `data/`, ничего внешнего»). Победил, т.к. `sd_tasks` (42 277) самодостаточен — категория/приоритет/срок/**просрочена**/статус в одном файле, высокая достоверность (прямые факты, не инференс), 0 внешних запросов. CPO-срез отпал: Требование упирается в тела Confluence (внешнее). Task Management — данные есть, но задача→эпик 7% (тяжёлый LLM-инференс, точность ниже).
- [reference] Сущности инцидент-среза: Обращение ServiceDesk (основа) · Категория/Подкатегория · SLA-статус (просрочка). Позже (глубина «инцидент→релиз→компонент→команда») — Продукт, Команда, Релиз (Релиз требует fixVersion — внешнее, не в первом срезе).
- [plan] Витрина среза: «Гигиена инцидентов / где горит по SLA» — сколько просрочено, критические, топ проблемных категорий, динамика.
- [outcome] CPO-срез не отменён — вернёмся, когда будут тела вики. Потребность (прогон 31 шт, `data/needs-first-pass.md`) — задел для него.

## Универсальный план фаз среза (0→3)

- [reference] Полный шаблон: `data/slice-build-phases.md`. Каждый срез проходит 4 фазы зрелости; внутри каждой — один цикл: **вычленить → связать → граф → RAG → проверить**, на разном уровне.
- [plan] **Фаза 0 — Ручной прототип:** вручную вычленить сущности среза из грязных данных → связать → мини-граф → RAG → проверить на вопросах роли + оценить точность. Это проектирование пайплайна, не продукт. Выход: спека + точность.
- [plan] **Фаза 1 — Автоматизация:** тот же цикл кодом (эмбеддинги/LLM/джойны автоматически) + гейт оператора; ручная чистка грязи остаётся на входе. Gate: авто-результат = ручному. Выход: работающий автоматический кусок сервиса.
- [plan] **Фаза 2 — Зрелость:** подключить отложенные внешние источники, темпоральность (тренды vs снимок), eval-gate/мониторинг качества, дочистить инференс-связи. Выход: срезу можно верить в проде + видна динамика.
- [plan] **Фаза 3 — Масштаб и петля:** состыковать с соседними срезами в общий граф, outcome-петля (сработала ли витрина), автономные инсайты. Выход: срез — часть единого сервиса.
- [decision] Не обязательно доводить срез до Ф3 перед следующим: довести первый до Ф1 (работает авто), начать второй с Ф0, зрелость подтягивать параллельно. Ф0 всегда первая для нового среза — дёшева, защищает от кодирования не того.
