# Helm — Conformance v2: 3-этапный план

Источник: созвон с руководителем 2026-07-08 (`data/Созвон по текущей задаче.rtf`). Дизайн модели — [[Helm — IVA Control Tower v0.3 (полная спека продукта)]] + ADR-0001 (`docs/adr/0001-conformance-requirement-model.md`).

## Контекст
- [context] Руководитель грузит требования поколений **1.0 + 1.5** в новую **event-sourced** модель (ADR-0001: `Requirement` / `RequirementAssessment` грань requirement×component×track×source×as_of+verdict+comment / `RequirementComponent` M:N / `ComponentPerson`). Мигрирует из старой плоской `ConformanceRow`. Влил на origin/main 2026-07-08 (коммиты `933bcd5 Add conformance domain models`, `6657e2f Add idempotent requirements CSV ingest`).
- [decision] Старый дэш **Conformance 1.5** (только 1.5, компонент×трек, без дат/комментариев) — **архивируем/оставляем про запас**, новый ставим на первое место.

## Важно: трек RN/KMP — ЛИШЬ ОДНА ОСЬ
- [decision] Новый Conformance — **многомерная матрица**, не «только по треку». Оси: **поколение(1.0+1.5) · продукт · компонент · трек(RN/KMP) · клиент · тип требования · статус · комментарий · дата**. Трек — один из разрезов ячейки.
- Тип требования — **одна сущность с флагом-категорией**: продуктовое (функц./нефункц.) vs архитектурное («бизнесу пофиг, как сделано»). Не две сущности.
- Срез — **самая свежая запись** (latest as_of per requirement×product×track×source), без зависимости от времени. Комментарий привязан к **ячейке (трек × требование)**.

## Этап 1 — БАЗА: новый Conformance-дэш (must, целимся к 15:00)
- [phase-1] Новый роутер `/api/conformance/v2` поверх `RequirementAssessment` (latest as_of) + новый экран `ConformanceV2.tsx`: многомерная матрица, фильтры и своды по всем осям, статус-ячейки по трекам, комментарий в ячейке. Старый дэш — в архив-вкладку. Первый прогон — на ревью руководителю («норм/не норм»).

## Этап 2 — КЛИЕНТЫ/ПИЛОТЫ: какие требования каким клиентам нужны (bonus)
- [phase-2] Связать поток требований/сигналов/sales с **клиентом+требованием** (NER-вычленение) + сверка с CRM (есть ли пилоты, по каким требованиям есть привязка). Разрез по 8 целевым пилотам (ЦБ/ТН/Метро/Еврохим/ВЭБ/Фортеинвест/Мосбиржа/МВД, конец июля).
- [blocker] Привязка клиент↔требование — в колонке **Заказчик/Крит.(Пилоты)** страниц 1.5 Confluence; локально только 2 из ~10 (Мосбиржа/ТН/ЦБ). Метро/Еврохим/ВЭБ/Фортеинвест/МВД — нужны остальные страницы `wiki.iva.ru` или CRM-привязка. Ценность: «то, что вручную не могут собрать годами».

## Этап 3 — ЛЮДИ/ФОКУС (только если 1 и 2 успели и хорошо)
- [phase-3] Слой людей: коммитеры→компоненты (`ComponentPerson`, из коммитов) → кто на каком компоненте. Полный статус: трек × требование × кто занят × статус × для каких клиентов → на чём фокус. Сущность коммитеры→компоненты руководитель заложит позже.

## Отложено
- [later] «Сколько денег зависло на требовании» (логика как с инцидентами) — руководитель: «сложно, пока без этого».

## Разбивка на команду (Agent Team)
- [process] Лид (я) + explorer×2 (backend-схема + frontend-каркас, разведка запущена) → implementer в worktree `~/tacticum-worktrees/helm-conformance-v2` ветка `feature/conformance-v2` (TDD, Serena) → verifier на реальных данных. Каноническую память пишет лид.
