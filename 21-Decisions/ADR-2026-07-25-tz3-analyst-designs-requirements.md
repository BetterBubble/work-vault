Ключевые решения ТЗ#3 (аналитик проектирует новые требования — контракты/модель данных/события). Доведён + принят рантаймом на стенде 2026-07-25. Досье: [[tz3-analitik-proektiruet-trebovaniia]] (исходный план — [[План ТЗ-3 Аналитик — генерация требований к контрактам-модели данных — lead-fr]], перенесён в 91-Archive/plans).

## Контекст
Профиль аналитика умел ОПИСЫВАТЬ as-is. ТЗ#3 (апрув Солонко) — научить ПРОЕКТИРОВАТЬ новые требования с wire-детализацией (эндпоинты/поля/события), НЕ ломая честность as-is-разведки.

## Решения
1. **Маркер версии `fr_skeleton: 2`** отличает v2-FR (проектный скелет) от v1. Backward-safe: нет маркера → legacy-поведение (каждый профиль держит свой v1-layout; канон/web = П.A/П.B, kmp = плоский fr.md).
2. **Форк mirror-пары — вариант А (не Б):** правим OWNER `iva-analysis-base`, mirror `iva-fr-analyst` следует байт-идентично → обе роли получают capability. (Сначала пробовали депрекейт mirror — откатили.)
3. **Двухзонная честность (§2):** Часть 2 (as-is) — строгая (никаких невыдуманных wire-имён как факт). Часть 1 (проектные разделы §1.6 контракты / §1.7 DM / §1.8 EV / §1.9 UI) — проектные wire-имена под 3 гардрейлами: (i) основание в Ч.2, (ii) плашка «требует утверждения: разработчик + CTO» + `Q-n`, (iii) boundary-валидатор.
4. **Гейт — plate-based (по плашке, не по номерам секций):** срабатывает по признаку плашки + открытого `Q-n` на ЛЮБОМ проектном разделе → покрывает §1.6-1.9 И версия-независим (срабатывает даже при битом маркере, no fail-open). `D-n` (зафиксированное решение) снимает плашку → proceed.
5. **Серии со стабильными ID:** `FT-n`/`UC-n` (Ч.1), `CT-n` (контракты), `DM-n` (модель данных), `EV-n` (события, унифицировано со скелетом ТЗ).
6. **Конвейер разработки читает v2 (US#4, К-1…К-5):** brd читает FT §1.4/UC §1.5 + ссылается на серии (К-1); pin реализует CT/DM/EV по стабильному ID + статус {реализован/расхождение/blocked} (К-2); start-task гейтит `D-n` честным BLOCKED без имитации (К-3); таблица расхождений FR↔KB по CT+DM через `kb_verify_api_exists` (К-4); детекция маркера (К-5).
7. **Модель раскатки:** канон-owner `tacticum-dev-base` (brd/pin/tests/start-task) + ручной синк в монолиты (mail/rn/kmp/web); композиты (ios/firebird) наследуют канон (ADR-0056 композиция); аналитик-пара — байт-mirror (`_mirrors.yaml` + parity-тест).
8. **Дивергентные профили:** kmp brd нёс axis-2/KMP-специфику (Jira-вход, D-n, серия (BRD), FR↔KB needs-info, grep self-check) — MUST-KEEP, аккуратный merge дельты; web brd был == канон → чистый verbatim-синк.

## Статус
**Принято и реализовано.** Build-complete (все проходы US#1-5 + US#4 конвейер); финальная сверка полноты = ДА; v2-FR пилот на teststand = зелёный (структурный, оговорка: helm-analyst MCP на стенде не подключён → живая оркестрация тулов = интеграция/рантайм у команды). Осталось: прод-сид (gated президент) + прод-verify.
