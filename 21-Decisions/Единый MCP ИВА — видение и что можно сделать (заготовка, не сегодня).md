# Единый MCP ИВА — видение (из созвона) + что можно сделать

Статус: **обсуждение/заготовка. Реализация — позже, не сегодня.** Подтверждено транскриптом созвона.

## Подтверждено созвоном: ОДИН MCP «всё в одном месте», профили ролей
Цитаты (почищенные):
- «Один МСП на доступ к рагам… под профиль прописываем, какие раги доступны, какие нет… удобнее управлять доступом ролей к ракам через один МСП, который все доступы раздаёт — в бэкенде проверяем: есть доступ → назначаем профиль».
- «Как обновлять данные по Jira/Wiki? У нас же есть **MCP от ИВы**… роутер определяет, есть ли запрос к актуальным данным».
- «Проектировать **не относительно MCP, а относительно контракта** (REST Jira/Confluence); MCP — способ получить актуальную информацию».
- «Хочу возможность **в том числе писать в Jira** и Wiki… RAG — база-источник (индекс поверх мастер-данных); MCP — канал + запись».

## Три функции единого MCP
1. **Доступ + RBAC-профили** — один MCP над всеми RAG-корпусами; профиль роли → какие корпуса доступны (read/write); проверка в бэкенде.
2. **Live-свежесть** — роутер «нужны актуальные данные» → подтяжка по контракту REST; MCP = прослойка актуальности. **У нас уже есть** боевой live-MCP транспорт в RAG#2.
3. **Запись** — заводить задачи/страницы/требования в Jira/Wiki/Helm; сервисный `EvoBot`. Частично есть (intake в helm).

## Что можно сделать СЕЙЧАС (не завися от выгрузки/решений)
- MCP-обёртка (чтение) над уже готовым: `/api/docs/ask` (RAG#1) + `/api/rag2/{search,context}` (RAG#2). Логику не пишем — оборачиваем сервисы. Дизайн-основа: `docs/iva-analyst-mcp-design.md` (обобщить с «аналитики» на все роли).
- Каркас профилей (роль → корпуса + read/write), проверка через `require_user` + тенант-гейт (расширить до профиля). Старт с 2 ролей: аналитик, поддержка.
- Проингестить helm-данные (`helm_mgmt_index`) → MCP отвечает по требованиям/SD **до выгрузки Jira/Confluence** — на этом показать «как выглядит».

## Как выглядит (глазами аналитика)
Добавляет один MCP-эндпоинт (URL+токен) в Claude Desktop/Cursor → агент видит тулы по профилю (`kb_search`, `kb_context`, `docs_ask`, read Jira/Confluence, позже `jira_create_task`/`wiki_create_page`) → спрашивает → агент зовёт `kb_context` → MCP роутит по доступным корпусам (RRF, теги источника), при свежести дёргает live → отдаёт контекст+цитаты → ответ на локальной Gemma/клиентском LLM. Запись — от `EvoBot`.

## Развилка размещения
- **(A)** Расширить сам `iva-mcp` (в контуре ИВА) нашими RAG-тулами+записью — буквально «всё в одном месте», но их инфра (нужен доступ/согласование, владелец iva-mcp).
- **(B)** Наш MCP-слой на helm: отдаёт наши RAG-корпуса + проксирует `iva-mcp` за свежестью/записью. Одна точка входа для клиента, но **делаем сами и уже сейчас**.
- **Рекомендация:** начать с **(B)** read-only на helm-данных; (A) — когда будет доступ к iva-mcp.

## Открытые вопросы
1. Где живёт целевой MCP (A vs B), владелец iva-mcp.
2. RBAC: кто выдаёт профиль (project-hub/свой), гранулярность (роль→корпуса+read/write).
3. Запись/`EvoBot`: когда заводим, какие операции, HITL обязателен ли.
4. Приоритет: единый MCP сразу (этап B концепта) или после наполнения RAG#2 (этап A).
