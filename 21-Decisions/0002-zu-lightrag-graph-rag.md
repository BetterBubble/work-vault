# ADR-0002 — LightRAG (graph-RAG) для базы знаний ЗУ: сравнение, графовый бэкенд, условия внедрения

- **Статус:** Proposed (развёртывание для сравнения одобрено руководителем 2026-07-01)
- **Дата:** 2026-07-01
- **Репозиторий:** `rag_eval_service` (= **Tacticum Codex**), развёртывание — стенд `zu_demo`
- **Контекст-арбитр:** [ADR-0001](./0001-zu-demo-rag-architecture.md) (D6 RAG-ретрив, D7 изоляция, D8 эмбеддинги, D12 eval-гейт)
- **Связано:** baseline-замер semantic vs hybrid 2026-06-30 (recall@k=0.967); golden-set ЗУ (35 кейсов, выверен по истине)

## Контекст

Клиент **«Залог Успеха» (ЗУ)** и его тех-лид (Василенко) предложили рассмотреть **LightRAG** — graph-RAG-фреймворк (HKU, EMNLP2025, `lightrag-hku`), который строит **граф связей между сущностями** поверх документов и ищет по графу дополнительно к векторам. Прозвучал тезис: «выбрать один подход, не плодить дублирующие решения».

Сверка с текущим состоянием на момент решения:
- **Текущий RAG (Codex) работает и измерен.** Baseline на выверенном golden-set (35 кейсов, 70 документов): **semantic recall@k=0.967, MRR=0.860, nDCG=0.875**; на реальных вопросах клиента recall=0.94. Semantic превосходит hybrid без реранкера (доказано числом дважды).
- **Вопросы операторов ЗУ — преимущественно фактологические/точечные** (адрес филиала, тариф, документ, процент), не реляционные. Это зона, где чистый вектор уже близок к потолку.
- **Реальный рычаг качества на этих данных — reranker** (заложен портом ADR-0001 D6, не поднят), не граф.
- **Graph-RAG силён на другом** — многодокументные, реляционные вопросы («как связаны A и B»), где ответ размазан по корпусу.
- **Прод у ЗУ — on-prem** (вся инфраструктура разворачивается у клиента, данные никуда не уходят; диктуется в т.ч. требованиями по ПДн).
- Инфра стенда `zu_demo` (159.194.212.2): Qdrant + **Postgres** (уже работает, история чатов) + Meili + Codex + фронт. Замер RAM: used 1.0Gi, **available 2.8Gi**, swap=0.

Цель ADR — зафиксировать решение **развернуть LightRAG для сравнения по данным** (не «на глаз»), выбор **графового бэкенда** и условия, при которых граф-слой уходит в прод. Решение принимается так, чтобы **не создавать дубль** и не трогать работающее демо.

## Решения

### D1 — Внедряем через сравнение по данным, не заменяя текущий RAG
LightRAG поднимаем **для честного сравнения**, а не вместо semantic-поиска. Текущий RAG (0.967) остаётся боевым. Решение о переводе граф-слоя в прод принимается **по результатам замера на golden-set**, а не авансом. Клиент предложил — проверяем гипотезу числом; если граф даёт прирост на вопросах ЗУ — внедряем, если нет — сохраняем систему простой.

### D2 — Не дубль, а графовый слой в существующей инфраструктуре
LightRAG **не заменяет и не дублирует** текущий RAG. Данные (документы ЗУ) — общие; вектор-слой — общий (D4). LightRAG добавляет **новый тип данных — граф сущностей и связей** — поверх той же базы. С выбором PostgreSQL+AGE (D3) **новый сервис на стенд не добавляется вообще**: граф ложится в **уже работающий Postgres**. Это максимально закрывает тезис «не плодить дубли»: не второй движок и не новая БД, а расширение существующего Postgres. Путь «**от простого к сложному**»: базовый semantic отвечает на фактологию (уже 0.967), граф-слой подключается, когда появятся реляционные задачи.

### D3 — Графовый бэкенд: **PostgreSQL + Apache AGE**
Граф LightRAG хранится в **существующем PostgreSQL** через расширение **Apache AGE** (A Graph Extension, openCypher внутри Postgres). LightRAG абстрагирует графовый бэкенд конфигурацией (env-переменные), поэтому выбор БД — настройка, не архитектура.

Почему AGE, а не специализированная графовая БД:
- **Мультитенантность.** Изоляция арендаторов у нас — базовый инвариант (fail-closed `tenant_id`, ADR-0001 D7). PostgreSQL решает мультитенантность штатно (схемы/RLS/`tenant_id`), и граф AGE это наследует. Отдельные графовые БД в бесплатных редакциях либо ограничены одной базой (изоляция «метками» в общей базе — рискованна и против fail-closed), либо выносят мультиарендность в платную лицензию — лишняя зависимость для on-prem-поставки клиенту.
- **Без нового сервиса (не дубль).** Postgres на стенде **уже работает**. AGE — расширение внутри него, а не отдельный движок и не вторая БД. Любая специализированная графовая БД — это дополнительный сервис на сервере (обслуживание, бэкапы, мониторинг), то есть возврат к вопросу дубля, который AGE снимает.
- **On-prem-совместимость.** Прод ЗУ — on-prem (self-hosted Postgres), где AGE ставится и работает (`CREATE EXTENSION age`). Ограничение «managed cloud (AWS RDS/Aurora, GCP CloudSQL) не поддерживает AGE» **к on-prem не применимо**.
- **RAM.** Граф в уже запущенном Postgres — без отдельного сервиса и его памяти (D5).

### D4 — Векторы: переиспользуем существующий Qdrant
Вектор-слой (эмбеддинги чанков) LightRAG направляем в **существующий Qdrant ЗУ**, не поднимая второе векторное хранилище. Граф — в Postgres+AGE. Вся хранилищная инфраструктура остаётся той, что уже развёрнута: Qdrant (векторы) + Postgres (граф + история чатов). Новых хранилищ — ноль.

### D5 — Инфраструктура: тот же сервер, без апгрейда RAM и без нового сервиса
Разворачиваем **на том же стенде `zu_demo`**, рядом с демо (единая инфраструктура).
- Графовый бэкенд — расширение AGE в **уже запущенном Postgres**; отдельный графовый сервис не поднимается → добавочная нагрузка минимальна.
- Замер `free -h`: занято 1.0Gi, **доступно 2.8Gi**. Апгрейд RAM не требуется.
- Пиковая нагрузка — **индексация** (построение графа через LLM). Мониторить `free -h`; при устойчивой нехватке — добавить ~2Gi (не более).
- **swap=0** → при исчерпании RAM сервер уходит в OOM, а не своп. Как страховку на время индексации — добавить **swap-файл** (дёшево, без апгрейда железа).
- Развёртывание изолировано от боевого контейнера: демо не трогаем, поднимаем отдельным процессом LightRAG.

### D6 — Методика сравнения: golden-set по всем 70 документам
Сравнение — **числом, не на глаз**, тем же инструментом, что дал baseline:
- прогон **выверенного golden-set (35 кейсов)** через LightRAG по **всем 70 документам** базы (pdf/xlsx/docx);
- те же метрики — **recall@k / MRR / nDCG**;
- прямое сравнение с текущим **semantic 0.967** (и срезами по difficulty/source).

Примечание: для самого **сравнения** графовый бэкенд нерелевантен — метрики качества графа не зависят от того, где граф физически хранится. Тест допустимо гонять на любом бэкенде; **прод-бэкенд — AGE (D3)**. Результат — таблица «где граф выигрывает, где нет» на реальных вопросах операторов; это основание решения D1.

## Открытые вопросы
- **O1.** Индексация графа идёт через **LLM** (LightRAG извлекает сущности/связи вызовами модели). Нагрузка на Gateway при построении графа по 70 документам — отследить в ходе прогона.
- **O2.** **ПДн для прода.** Построение графа прогоняет содержимое документов через LLM. Прод ЗУ — on-prem, значит локальный LLM для построения графа ложится в ту же on-prem-картину (как и локальный bge-m3, ADR-0001 D8). Отдельным блокером не стоит — часть общего on-prem-развёртывания.
- **O3.** Совместимость LightRAG-эмбеддингов с существующей коллекцией Qdrant `knowledge__bge-m3_1024` (модель/размерность/payload). Проверить при настройке D4; при несовместимости граф-эксперимент использует отдельную коллекцию в том же Qdrant (не дубль инстанса), не задевая боевую.
- **O4.** **Производительность AGE на росте графа.** AGE уступает специализированным графовым движкам на глубоких многохоповых обходах и развивается неспешным комьюнити-темпом. Для 70 документов ЗУ и фактологических запросов — неощутимо. Если граф разрастётся до миллионов узлов с глубокими обходами — перемерить и при необходимости пересмотреть бэкенд.

## Последствия
- **+** Решение о граф-слое принимается **на данных** (golden-set по 70 документам), а не по запросу клиента вслепую.
- **+** **Максимально не дубль:** ни нового движка, ни новой БД — граф в уже работающем Postgres (D2/D3), векторы в существующем Qdrant (D4). Тезис Василенко закрыт полностью.
- **+** **Мультитенантность решена** штатным Postgres, наследуется графом AGE (D3).
- **+** **On-prem-совместимость:** AGE работает в self-hosted Postgres, что совпадает с прод-направлением ЗУ.
- **+** Единая инфраструктура: тот же сервер, тот же Postgres, тот же Qdrant; без апгрейда RAM и без нового сервиса (D5).
- **+** Путь роста «от простого к сложному»: база отвечает на фактологию, граф подключается под реляционные задачи по мере появления.
- **−** AGE уступает в скорости на глубоких обходах и развивается неспешно (O4) — для масштаба ЗУ несущественно, но точка внимания на росте.
- **−** Индексация графа нагружает Gateway (O1); для прода требует локального LLM (O2, укладывается в on-prem).
- **−** На фактологических вопросах ЗУ (где semantic уже 0.967) ожидаемый прирост графа **невелик**; ценность подтверждается только замером (риск «нулевой дельты» — приемлемый, снимается методикой D6).

## Альтернативы (отклонены)
1. **Заменить текущий semantic на LightRAG** — отклонено (D1): semantic 0.967 работает; граф проверяем как дополнение, не замену.
2. **Специализированная графовая БД в бесплатной редакции как бэкенд** — отклонено (D3): мультитенантность либо ограничена одной базой (изоляция метками рискованна, против fail-closed), либо в платной лицензии; плюс отдельный сервис на сервере (дубль) и доп. RAM. AGE даёт мультитенантность Postgres без нового сервиса.
3. **Графовая БД в платной редакции (ради мультитенантности)** — отклонено (D3): лишняя лицензионная зависимость для on-prem-поставки клиенту; Postgres+AGE закрывает ту же потребность без лицензии.
4. **Встроенное файловое хранилище LightRAG (NetworkX/nano)** — отклонено (D3): годится для прототипа, но разработчики отмечают его как dev-only; AGE даёт прод-путь без нового сервиса.
5. **Отдельный VPS/сервер под эксперимент** — отклонено (D5): RAM текущего стенда достаточно; единая инфраструктура предпочтительна.
6. **Кратный апгрейд RAM под граф** — отклонено (D5): замер показал запас; с AGE (без отдельного сервиса) добавочная нагрузка минимальна.
7. **Второе векторное хранилище под LightRAG** — отклонено (D4): переиспользуем существующий Qdrant.
8. **Внедрять граф сразу в прод без сравнения** — отклонено (D1): неизвестная дельта на фактологии; сначала замер (D6), потом прод.
