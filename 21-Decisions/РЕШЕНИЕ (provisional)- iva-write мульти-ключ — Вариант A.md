# Решение: мульти-ключ iva-write = Вариант A (ПРЕДВАРИТЕЛЬНО)

⚠️ **PROVISIONAL** — принято пользователем 2026-07-21, но подлежит согласованию с руководителем (вечер 21.07 / утро 22.07). **Если руководитель скажет иначе — поменять** (кандидат замены — Вариант C).

## Что решили
**Вариант A:** клиент несёт **один** ключ `phk_` (`TACTICUM_TOKEN`); gateway резолвит его в актора (`X-Auth-User-Id` = подпись актора, ADR-0051); write-PAT и Allure — **серверные** (env mcp-atlassian/helm), в манифест не кладутся. Мульти-ключевость обеспечена архитектурой gateway, а не клиентским манифестом.

## Почему (грунт по коду)
- Рендерер при `auth_type: bearer` доставляет клиенту только `env_required[0]` — «4 клиентских ключа на одном сервере» физически не доставляются.
- Премиса хендоффа «4 ключа на адрес» архитектурно не ложится: write-PAT/Allure серверные.
- Вариант A не требует правки схемы/6 рендереров; по ADR-0058.

## Альтернатива на случай пересмотра
**Вариант C:** клиентский мульти-ключ → расширение схемы манифеста + всех 6 рендереров. Дорого, трогает платформу. Взять, если руководитель настоит на 2+ клиентских секретах на одном сервере.

## Влияние при смене A→C
Меняется только конструкция `mcp_server_spec` в дизайн-спеке [[Дизайн-спека iva-write-base (Вариант A) — на апрув]] + добавляется платформенная работа (схема+рендереры). Композиция лейна, allowed_tools, аддитивность — не меняются.
