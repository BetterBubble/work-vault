Решение 2026-07-10. Новая вкладка **«Таск-менеджмент»** (CIO, рядом с «Внедрение ADP») — «статус по инициативам» из созвона (Стрим 3 / Ф4 «идеального таск-менеджера»). Дизайн одобрен пользователем (макет-артефакт — клон «Внедрение ADP»).

## Что за вкладка
Верхний слой «статус по инициативам»: карточки эпиков/направлений, статус = закрытие требований (не усилие), провал = **модальное окно** (задачи Jira · требования · кто ведёт · расхождения Jira↔модель). Общий с CPO/COO. Источник — MCP (Jira) раз в сутки. Место: под CIO, потом можно впечь в «Соответствие требованиям» (руководитель хотел «перед деталью требования»).

## Данные (уже есть)
- Модель готова: `Initiative` (589, эпики/направления, owner/product/requirement) + `Signal` (46k Jira-задач, колонки status/assignee/epic/project — но **старый CSV-дамп, частичный**).
- `feature/task-manager-ideal` (локально, НЕ влита): Ф0 SQL read-path (golden-тест), Ф1 копилот-гейт orphan→инициатива, Ф2 квадранты. Ф3 (тренд orphan) и Ф4 (tracker-diff Jira↔EVA) — осталось.
- Собрано 2026-07-10: `epics.json` (67 эпиков IVAONE), 300 задач салважом; вика-реализация + per-req Jira-статус (закрытие требований) уже в проде.

## КЛЮЧЕВОЕ ограничение: полный per-task через MCP НЕЛЬЗЯ
MCP-данные идут **через контекст модели** → чтобы сохранить, агент **переписывает их текстом** = ~2× токенов + переполнение контекста (лимит ~200k). Факт: **~470k токенов на ~500 задач**, зациклились. Значит:
- **Bulk per-task через MCP — тупик.**
- Через MCP дёшево: **агрегаты (JQL-счётчики, тела не идут в контекст) + drill-on-demand** (задачи одного эпика по клику). Это и есть «MCP как точка правды» для верхнего слоя.

## Полный per-task снапшот — ПОЗЖЕ, отдельным путём
Прямого доступа к `jira.iva.ru` нет ни у ноута (был), ни у helm-сервера (NXDOMAIN), ни у меня. Доступ только у **`mcp.tacticum.ru`** (хостед MCP `https://mcp.tacticum.ru/iva-atlassian/mcp`) и у **`adp_emb`** (там `extract_jira_quality.py` + PAT `/opt/iva-mcp/env`). У меня SSH только к `helm`/`zu_demo`.
- **Скрипт готов:** `scripts/extract_jira_tasks_local.py` (stdlib, POST /rest/api/2/search, только метаданные+summary, без description/comments). Запускать с хоста с доступом к Jira.
- **ВПН пользователя РАБОТАЕТ:** с ноута `jira.iva.ru` резолвится (10.22.0.10), эндпоинт отвечает 401 → достижим. Нужен **Jira PAT** (jira.iva.ru → профиль → Personal Access Tokens; `phk_` НЕ подходит — это Taiga/Wiki). Осталась мелочь по 400 (перешли на POST).
- **Governance:** решили — до полной выгрузки **подтвердить у руководителя** scope (какие проекты, храним ли снапшот). Пока — только MCP-агрегаты (контент не извлекается, риск ≈ 0). Имена/фамилии/assignee — использовать МОЖНО (руководитель: «всё что можно и нужно»). Проекты security/HR/юр — исключать.

## Выгрузка задач через MCP — финальный дизайн (2026-07-10, готово, ждём сброса лимита 2M)
Разведка MCP `jira_search` дала железную спеку («одна попытка»):
- **Пагинация:** `limit` жёстко 50; `start_at` работает на глубине (проверено 8000+) → все ~11.6к достижимы. IVAONE 11 608, IVAONEHALF 450.
- **Экономия:** явный `fields` → пустые поля НЕ приходят. `*all` = ЯД (~8k ток/задача: worklog+comments+devstatus+AD-блобы+~90 пустых кастомполей). Никогда.
- **Эпик** = `customfield_10000.value` (верхнеуровневый `epic_key` в MCP СЛОМАН — отдаёт дату). **Категория статуса** = `status.color` (inprogress/success/default), стабильнее локализованного `status.category`. **Дата закрытия не отдаётся** — берём `updated`+`resolution`.
- **Физика канала:** MCP всегда грузит ответ в контекст модели → неустранимый 1x на приём. «Скрипт пишет на диск мимо модели» возможно ТОЛЬКО прямым REST (VPN+PAT) — пользователь этот путь закрыл, работаем через MCP. С описаниями ~600 ток/задача (приём+запись).

**Финальный набор полей:** `summary,description,status,issuetype,priority,assignee,components,customfield_10000,reporter,resolution,created,updated`.
**Финальный scope-JQL (замер 3151 задача):**
`project in (IVAONE, IVAONEHALF) AND (statusCategory != Done OR updated >= -90d) AND NOT (issuetype != Epic AND "Epic Link" is EMPTY AND updated <= -365d) ORDER BY key ASC`
— открытые + закрытые за 90д + эпики (для резолва названий), без древних сирот. ~1.9M с описаниями = впритык в одно окно 2M.

**Оснастка (ветка `task-mgmt`, коммиты 43195f4/e8a1952, НЕ пушено):**
- `scripts/wf_extract_jira_mcp.js` — Workflow-скрипт: range-sharded агенты (по `start_at`, окно 150=3стр), пишут компактный JSONL-шард ОДИН раз, в ответ только счётчики; бюджет-предохранитель (стоп при остатке <250k → `nextStartAt` для резюма в след. окне). Запуск: Workflow `{scriptPath, args:{total, startFrom}}`.
- `EpicTask` расширен (миграция `c7d8e9f0a1b2`): +issuetype/priority/reporter_name/resolution/description(Text)/created/updated.
- `scripts/ingest_epic_tasks.py --dir data/iva/tasks` — читает шарды, разворачивает короткие ключи (k/st/cat/an/comp/ep/sum/desc…) в длинные для `load_epic_tasks`. Дедуп по key.

**Разбиение работы (как агенты не пересекаются):** стабильный `ORDER BY key ASC` (ключ неизменен → порядок не плывёт) + каждому агенту явное непересекающееся окно `start_at`, координатор режет заранее, дедуп по key на ингесте. (Прошлый провал был из-за `ORDER BY updated DESC` без разбиения — оба агента брали «голову».)

**Тест пройден (2026-07-10):** фоновый агент × 50 задач → шард (42 с описаниями, 27 с эпиками, категории/типы корректны, макс desc 2323 симв) → трансляция → готовые строки; 850 тестов зелёные; шарды в gitignore. ⚠️ Первый ad-hoc general-purpose агент вернул prompt-инъекцию с 0 вызовов — реальный прогон только через Workflow со schema-forced выводом.

**Следующий шаг (на сбросе 2M):** запустить Workflow `wf_extract_jira_mcp.js`, дождаться шардов, `ingest_epic_tasks.py --dir`, задеплоить данные на прод (docker cp + alembic upgrade). Если упрётся в бюджет — резюм по `nextStartAt`.
