## Стрим 1 — Доработка диаграммы «Соответствие требованиям» (гант по вехам) [ПЕРВЫЙ]
Построчные пункты из диалога:
- [ ] **Вернуть количественные метрики** на плитки клиентов (исчезли). % закрытия + «X из Y» (напр. поколение 1.0 / 1.5). Можно мелким шрифтом.
- [ ] На баре — разноцветная полоса + процент; **можно и с %, и без, и «X из 5» — «и то и то»**.
- [ ] **Читаемость «0 из 5»**: сейчас не читается. Сделать визуально понятнее — напр. «70%» и «0 из 5» второй строкой.
- [ ] **Дельта закрытия требований** (ГЛАВНОЕ, чего не хватает): сколько закрыто ВСЕГО + сколько **за неделю** (динамика). Разместить на этой же диаграмме — под ячейкой клиента (Транснефть*) или сбоку.
- [ ] **Метка/алгоритм «данные о требованиях появились не сразу»**: всплеск скорости (напр. ~73k «вичей»/день) — фейк из-за влитой новой репы (раньше репа без инфы о требованиях → потом с инфой). Не учитывать такие периоды в расчёте дельты/прогноза, иначе прогноз слишком оптимистичен (пример: ВЭБ 31.07 / «13.07 всё сделано» — фейк). **Алгоритм придумать самому.**
- [ ] **Звёздочки** = в документах помечен «пилот». По факту всё пилот (разница только раньше/позже + разные требования). Можно убрать звёздочки и считать всё пилотом, НО метку скорости/различия сохранить (легенда).
- [ ] **Гант = статус готовности РАЗРАБОТКИ.** Заложить пост-разработку: ручное + приёмочное тестирование, раскатка/внедрение (~2 недели). Срок ≠ только разработка.
- [ ] **Точные сроки вместо кварталов** («конец/начало квартала» — плохо). Если срок есть — писать его. Дать **интерактивно менять дату вехи** (drag-and-drop ИЛИ клик + поле со смещением — на выбор, можно проще). Пример: Роскосмос даёт ноябрь, стоит сентябрь.
- [ ] **Скорость/burn-down**: показать темп (напр. 7 фичей/день → сколько до N фичей); общие вехи готовности по всему функционалу. Полный burn-down — если не геморрой; иначе упрощённо. Сейчас «не очевидно».
- [ ] **Ссылка на Wiki** у вехи/клиента, если есть (мелочь).

## Стрим 3 — Таск-менеджмент дэш: Jira ИВА → верхнеуровневый статус + сверка [ВТОРОЙ]
- [ ] **Доступ к Jira ИВА через MCP** (руководитель ищет/перевыпустит токен MCP-сервера). Обновление раз в сутки. Зависит от проекта `iva-control-tower` (id 31): MCP-1 (mcp-atlassian Jira/Confluence, Done), MCP-2 (публикация MCP для агентов, Ready-for-test).
- [ ] **Верхнеуровневая вкладка «статус по проекту/инициативам»** (для CEO-встречи / дэшик «сверху»). Большие **эпики = направления работы** (треки: «доработать Арт», «доработать КМП», …). Внутри — конкретные задачи (story/impediment/task) из Jira, кто ведёт/отчитывается.
- [ ] **Визуал как архитектурная вью** (по образцу ADP-вью CIO): компоненты/репы плана; зелёные статусики — **вместо «усилия» показываем закрытие требований** (закрыто / частично / не закрыто). Можно добавить «оцифровано ADP или нет».
- [ ] **Провал в требования**: статус, кто делает/ответственный, сроки; **фильтр по клиенту** (как дорабатывается под клиента).
- [ ] **Сверка Jira ↔ наша модель (трекер)**: он закрыл в Jira / у нас нет — и наоборот. Это = **Ф4 «Jira↔EVA divergence»** из «идеального таск-менеджера» (уже в работе, ветка feature/task-manager-ideal — см. [[Таск-менеджер «идеальный» — прогресс фаз (Ф0–Ф2 сделано, Ф3–Ф4 осталось)]]). Дэш рабочий на ежедневной основе с ребятами.
- [ ] **Куда встроить**: «запечь» в «Соответствие требованиям» ПЕРЕД проваливанием в деталь требования. Согласовать с руководителем: отдельная вкладка vs внутри Соответствия.
- [ ] **Согласовать с ребятами ИВА формат ведения в Jira** (группировка story → tasks, привязка требований) — концепт руководитель сейчас согласует.
