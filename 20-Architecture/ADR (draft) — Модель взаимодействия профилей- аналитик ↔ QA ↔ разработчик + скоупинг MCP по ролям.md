# ADR (draft v2): Модель взаимодействия профилей — аналитик ↔ QA ↔ разработчик + скоупинг MCP по ролям

**Status:** Draft (proposed), ревизия v2 (учтены ревью critic + verify-на-реальных-данных + bizproc). Драйвер — `lead-arch`; владелец видения — ГД; механизм-часть согласует Д.Солонко; финальный гейт — `critic`.

**DECISION (кратко):** `mcp-analyst` (helm-analyst) **НЕ делить** на серверы-под-роль — разграничивать тул-поверхность **`allowed_tools`-пресетами по ролям** (механизм уже смёржен в `origin/main` и работает в проде). Пайплайн аналитик→QA→dev — на общих артефактах с машиночитаемыми статусами (задел под BPMS) + обратные петли + гейт достоверности. Части профилей отделяемы через single-owner лейны; пересечение = композиция, не копия.

**Источник истины (граница фактов):** только **опубликованное в remote**. `origin/main` = смёрженное; `origin/feat/profiles-lanes-roles-architecture` (ADR-0055–0059) = **proposed/in-flight**. QA — легитимная локальная доработка lead-qa (`feat/qa-kit-subagents`). Прочее локальное в модели не фигурирует. *(Все факты ниже верифицированы на реальных данных 23.07 — см. `00-Board/verify-fakty-adr-model-profilei`.)*

## 1. Контекст

**Видение ГД:** правильный/эффективный пайплайн аналитик ↔ тестировщик ↔ разработчик так, чтобы (а) профили/инструменты удобно ложились на реальную работу ВСЕХ ролей; (б) можно осознанно менять процесс ради эффективности (change management); (в) наши профили/инструменты полностью удобно используемы всеми.

**Опора (что смёржено vs предложено):**
- **ADR-0056** (main) — композиция `depends_on`, depth-1, single-owner лейны.
- **Механизм скоупинга** — **смёржен в `origin/main`**: схема `mcp_server_spec` (`templates/_schema/ingredient.v1.schema.json`) поддерживает `allowed_tools` + `required_scopes`, и это **реально работает в проде** (профили `iva-brownfield-mail`/`iva-kmp-brownfield`/`iva-rn-brownfield` сужают `codegraph`, `tacticum-platform-dev` — `arch`-MCP). ⚠️ **Рекомендация §2 стоит именно на этом смёрженном механизме, а не на статусе документа** ADR-0057 (сам 0057/0059 — на proposed-ветке).
- **ADR-0057 / 0059** (proposed-ветка) — capability-layers + role-presets (0057); single-axis лейны, dev implement-only (0059). Полезны как направление, но НЕ смёржены (§8 п.2).
- **Решение 23.07** — TC пишет аналитик (в фичер-реквест ДО разработки), QA дополняет на ревью.

**Гардрейл:** модель должна лечь на **единый механизм сборки профилей** (три→один, сводит Д.Солонко) — «чтобы за нами не доделывали».

## 2. Ключевой вопрос — делить ли `mcp-analyst`? → НЕ делить, скоупить пресетами

### Факты (верифицированы на реальных данных)
- helm-analyst живёт в `iva-analysis-base`; несут его роли с analysis-лейном (в `origin/main` — аналитик и `iva-role-go`, т.к. в main go полного цикла).
- helm-analyst и iva-read объявлены **без `allowed_tools`** (весь сервер потребителю). Механизм сужения при этом смёржен и используется в проде — просто **к analyst-серверу не применён**.
- **helm-analyst = 19 тулов** (сверено `@mcp.tool()` в `analyst_server.py`, все имена реальны, выдумок нет):
  - **универсальный слой (6):** `analyst_search`, `analyst_context`, `docs_ask`, `requirement_coverage`, `who_to_involve`, `my_todo`;
  - **аналитик-кластер (8):** `nearest_spec`, `gap_questions`, `affected_systems`, `related_tasks`, `constraints`, `contradiction_check`, `api_registry_check`, `contract_check`;
  - **арх-тулы (3):** `arch_map`, `arch_container`, `arch_drift`;
  - **прочее (2):** `requirement_tests` (статус покрытия из Allure), `effort_hint` (lead-time, не трудоёмкость).
- kit-референс (ИВА): доступ роли к тулам = **пресет над общей поверхностью**, не отдельный сервер.

### Рекомендация: один сервер + `allowed_tools`-пресеты по ролям
Причины:
1. Универсальный слой (6/19 ≈ ⅓) нужен всем; отдельные серверы-под-роль **дублировали бы** его + аутентификацию (TACTICUM_TOKEN) + индекс знаний.
2. Деление серверов ортогонально проблеме «роль видит лишнее» — её решает `allowed_tools`.
3. Совпадает с уже работающим в проде паттерном скоупинга и с kit-моделью.

**Пресеты (черновик; принцип: read-only тулы даём щедро — цена «не хватило тула» в моменте выше экономии «шума»; §8 п.1):**

**Универсальный слой — базовый для каждой роли-потребителя** (6 тулов выше).

| Роль | `allowed_tools` = универсальный слой + | Примечание |
|---|---|---|
| **аналитик** | весь сервер (полный набор) | легитимно нужно всё |
| **разработчик (go)** | `nearest_spec`, `related_tasks`, `affected_systems`, `constraints`, `api_registry_check`, `contract_check`, `arch_map` | «что реализую» + арх-карта при реализации |
| **QA** | `requirement_tests`, `gap_questions`, `contradiction_check`, `nearest_spec`, `affected_systems`, `constraints`, `related_tasks` — узкий **read-для-ревью** срез (решение B) | ревью полноты TC + статус покрытия; **авторинг TC/владение покрытием остаётся у аналитика** |

- **Арх-тулы** (`arch_container`/`arch_drift`) — отдельный кластер; в свой пресет при появлении опубликованной арх-роли.
- **Эскейп-хатч:** роли легитимно понадобился тул вне пресета → процедура расширения пресета (владелец лейна апрувит правку `allowed_tools`), а не форк сервера. Владелец поддержки пресетов — назначить (§7).

**Реализация:** проставить `allowed_tools: [...]` в `mcp_server_spec`-ингредиенте helm-analyst нужного лейна/роли (как уже сделано у codegraph/arch в проде). Сервер один, форк не нужен.

## 3. Альтернативы (рассмотрены и отклонены)

**Критерий, когда деление сервера ОПРАВДАНО** (timeless-правило): делить MCP-сервер стоит, только если выполняется хотя бы одно —
(a) **раздельный домен аутентификации/секретов** (разные токены/скоупы физически); (b) **независимый жизненный цикл/владение** (разные команды релизят врозь); (c) **иной бэкенд-источник** данных; (d) **изоляция blast-radius** (сбой/уязвимость одного не должен ронять другое).

| Альтернатива | Вердикт | Почему |
|---|---|---|
| Отдельный MCP-сервер под каждую роль | Отклонено | Ни один критерий (a–d) для helm-analyst не выполняется; дублирует универсальный слой + auth + индекс |
| Отдельный QA-MCP | Отклонено (пока) | Потребность QA закрывается узким срезом + Allure/TestOps CLI; сервер дублировал бы поддержку без выигрыша. Вернуться, если появится ярко-QA-специфичная поверхность |
| Статус-кво «весь сервер всем» | Отклонено | Роль видит лишнее; механизм сужения уже есть — грех не применить |

→ Для helm-analyst верен **скоупинг пресетами над одним сервером**.

## 4. Модель профилей: общие / отделяемые части, ownership

**Лейн = единица авторинга (single-owner); роль = единица установки (leaf-пресет, композиция лейнов `depends_on`)** (ADR-0056).

### 4.1. Роли и их части
- **Аналитик** — полная аналитика (`iva-analysis-base`) + расширенные UC + TC; артефакты постановки single-owner. Публикация — `iva-atlassian-write`.
- **QA** — процесс-лейн `qa-autotest` (автоматизация: скиллы + субагенты `codebase-analyst`/`dom-explorer`/`code-writer`, автотесты в one-web) + **ревью-дополнение TC**. Write-канал — прод `iva-atlassian-write` (сужен до `jira_*`). Read-доступ — **узкий read-пресет helm-analyst** для ревью полноты TC/покрытия (решение B, §8 п.3).
- **Разработчик** — реализация по постановке + юнит-покрытие по TC. *(В main — полный цикл; 0059 предлагает implement-only — развилка §8 п.2.)*

### 4.2. Инварианты пересечения/отделяемости
1. **Single-owner на артефакт** — каждый артефакт принадлежит ровно одному лейну; без копий между лейнами.
2. **Переиспользование = композиция**, не копия (общий лейн через `depends_on`).
3. **Приоритет при коллизии — порядок `depends_on`** (лейны спроектированы непересекающимися).
4. **Граница TC (решение 23.07):** один артефакт TC, три роли по своим правам — аналитик `author`, QA `review-augment`, dev `consume`.

### 4.3. Read-валидация чужой части (единое правило — снят разнобой)
Роли нужен **доступ на ЧТЕНИЕ** чужого лейна (провалидировать постановку, свериться со смежным требованием) без владения. **Единый механизм: read-доступ доставляется скоупленным read-MCP** (helm-analyst/iva-read с узким `allowed_tools`). **Запрет касается композиции чужого ПРОЦЕСС-лейна** (чтобы не тащить чужой процесс и не размывать ownership), а не read-доступа. Упаковка по объёму:
- **(а) `allowed_tools` прямо на роли** — для разовой/точечной read-валидации;
- **(б) общий read-only способность-лейн** («дырка») через `depends_on` — когда один и тот же read-доступ нужен МНОГИМ ролям (напр. dev implement-only, §8 п.2). Это лёгкий лейн знаний, не процесс-лейн — потому композиция здесь допустима.

## 5. Пайплайн аналитик → QA → разработчик

Шаг = **владелец · вход · выход · гейт · машиночитаемый статус**. Хендоффы — по общим артефактам (требование/US в Jira, TC в Allure), не «на словах».

### 5.1. Шаги (это DAG, не строгая цепь: шаги 2 и 3 стартуют ПАРАЛЛЕЛЬНО от `analysis:approved`)

| # | Шаг (владелец) | Вход | Выход | Гейт | Статус |
|---|---|---|---|---|---|
| 1 | **Аналитик:** постановка | FR/запрос | BRD/UC + **TC** + контракт → требование (Jira), TC (Allure) | апрув постановки (владелец продукта) | `analysis: draft→approved` |
| 2 | **QA:** ревью TC *(‖ с 3)* | требование+TC (`approved`) | дополненные TC | ревью завершено | `tc: authored→reviewed` |
| 3 | **Dev:** реализация *(‖ с 2)* | постановка (`approved`) | код + юнит-тесты по TC | реализация готова | `dev: todo→in_progress→implemented` |
| 4 | **QA:** автоматизация + регресс | реализация + TC (`reviewed`) + **Impact-зона из PIN** | автотесты нового требования **+ покрытие затронутой legacy-зоны** (one-web) | тесты зелёные **И** данные достоверны | `tests: <cov%> green/red` + `verified: yes/no` → `tc: reviewed→covered` |
| 5 | **Приёмка/закрытие** | всё выше | закрытое требование | **`tc: covered` И `verified: yes`** (иначе `done` невозможен) | `requirement: done` |

### 5.2. Обратные петли (не только forward — снимает «немые» передачи)
Хендоффы двунаправлены. При находке дефекта постановки dev/QA **возвращают требование в `analysis:rework` с причиной** (машиночитаемо), а не «в чат/устно». Петли: `dev→analyst` (неясность/противоречие постановки), `qa→analyst` (дыра в TC/UC), `qa→dev` (дефект реализации). Это соответствует созвону («роль может залезть и провалидировать чужую часть») и инварианту «без немых передач».

### 5.3. Гейт достоверности (шаг 4/5) — «зелёные тесты ≠ верные данные»
Приёмка НЕ по зелёным логам. На шаге 4/5 — **сверка результата с реальным источником/UI** (не только статус Allure); отдельный машиночитаемый статус `verified: yes/no` рядом с `green/red`. Расхождение по фактам/галлюцинация = дефект.

### 5.4. Задел под BPMS
- **Статусы — данные, не проза** (поля Jira/Allure) → BPMN-процесс Солонко читает/двигает их без переделки модели.
- **Явные владельцы шагов** → BPMS знает, кому назначать апрув; **точки `approved`** (шаги 1/5) — под бот-фиксатор (видение Солонко).
- **Снизить ручной труд:** где можно — двигать статусы **скиллами из событий** Jira/Allure, не вручную; на апрув-гейты задать **SLA** (иначе «стоп на апруве» держит поток на одном человеке).

### 5.5. Change-management
Процесс меняем осознанно и **фиксированно** (решением/ADR, не ad-hoc). Внедрять постепенно, с планом снятия сопротивления (§7): изменения роняют мотивацию, если труд становится невидимым.

### 5.6. Словарь статусов (единый)
`analysis: draft→approved→rework` · `tc: authored→reviewed→covered` · `dev: todo→in_progress→implemented` · `tests: green/red (+cov%)` · `verified: yes/no` · `requirement: done`.
(NB: `tc: covered` выставляется на шаге 4 при зелёных автотестах — §5.7.)

### 5.7. Явные гейты СЕЙЧАС (до BPMS) — предложение Д.Солонко 23.07
Не дожидаясь BPMS, ужесточаем два гейта формально:

**(1) Стоп-кран — новый долг не создаём.** `requirement: done` **невозможен без** `tc: covered` **и** `verified: yes`. Механика: шаг 4 при зелёных автотестах (и пройденном гейте достоверности) переводит `tc: reviewed→covered`. Тогда каждое требование, прошедшее конвейер, по построению покрыто — метрика покрытия не деградирует.

**(2) Покрытие следует за изменением (рычаг для legacy).** Существующий функционал в Jira не описан — конвейеру не за что зацепиться напрямую. Дешёвый хук — **dev-задача**: у каждой реализации есть **Impact-зона в PIN** (`pin-authoring` — в проде). Правило: **задел регрессии — часть гейта шага 4** (не опция): QA-автоматизация покрывает не только новое требование, но и затронутую им legacy-зону из PIN Impact. Так покрытие растёт там, где код реально меняется (= где риск), без отдельного бюджета.

⚠️ **Статус хука (сверено на remote):** PIN Impact-зона — **есть в проде** (`pin-authoring`). А сам механизм покрытия по Impact (`/qa-coverage` / «regression from PIN Impact» в iva-qa) в шаблонах **ещё НЕ существует** (0 совпадений на всех ветках) — его надо **построить** и объявить обязательным на шаге 4, а не «включить существующую опцию». Т.е. это гейт + новая работа для lead-qa/dev-шаблонов, не бесплатная декларация.

**Режим соблюдения (решение президента 23.07):** на старте гейты держим **процессно** (ревью / чек-лист), инструментальную проверку (CI/скилл, блокирующий `done` без `covered`+`verified`) пока НЕ строим — вернёмся к автоматизации позже.

## 6. Как ложится на единый механизм сборки

Модель **не вводит новых механизмов** — только существующие лейны/роли + `allowed_tools`-пресеты. Устройство целевого единого механизма (Солонко) у нас не описано → статус укладки — **«требует сверки с Солонко»** (§8 п.4), не «готово».

## 7. Последствия

**Выигрыши**
- Роли видят только нужные тулы без дубля серверов/аутентификации.
- Всё на существующих механизмах → ложится на единый механизм сборки.
- Ownership и пайплайн (со статусами, петлями, гейтом достоверности) явно зафиксированы — снимают трение «кто следующий».
- §5.4 — прямое попадание в BPMN-видение Солонко.

**Издержки / риски (в т.ч. операционные и принятия)**
- **Дрейф пресетов** по мере роста тул-поверхности → нужен **владелец поддержки пресетов** + процедура эскейп-хатча (§2).
- **Скоуп груб** — `allowed_tools` режет по тулу, не по данным/тенанту.
- **Принятие QA** — «автор TC → дополняющий» может читаться как понижение; вклад QA сделать **видимым**, переупаковать как апгрейд (сложные сценарии + автоматизация — более ценный слой), проговорить с командой Брейкина ДО внедрения.
- **Аналитик-bottleneck** — TC = отдельная компетенция и доп. нагрузка; без инструментальной поддержки авторинга TC риск поверхностных TC → QA переписывает (двойная работа). Признать нагрузку в планировании; дать скилл-инструмент (§8 п.5).
- **Ручные статусы без BPMS** — риск рассинхрона; митигируется §5.4 (события/SLA).
- **Финальную укладку на единый механизм сверяет Солонко.**

**Вне скоупа (системный риск, зафиксировать явно):** модель **перекладывает** тест-дизайн, но **не добавляет рук** (покрытие ~0, один тестировщик) — узкое место сдвигается, а не расшивается. Это вопрос capacity, не распределения; решается отдельно.

## 8. Открытые вопросы / развилки (нужен steer ГД / Солонко / lead-qa)

1. **Ширина read-пресетов.** Принцип — давать read-only щедро + эскейп-хатч. Подтвердить границы go/QA (что именно входит).
2. **go: implement-only vs полный цикл + автономность.** В main go — полного цикла (несёт analysis→helm-analyst). 0059 (proposed, не в main) делает implement-only. Созвон: dev может «залезть-провалидировать». Развилка: (a) оставить полный цикл; (b) implement-only + лёгкий read-лейн (§4.3б) для валидации постановки. Обратные петли (§5.2) нужны в любом случае.
3. **QA ↔ helm-analyst — РЕШЕНО (вариант B, ГД 23.07).** QA получает **узкий read-пресет** helm-analyst (`requirement_tests` + `gap_questions`/`contradiction_check` + support `nearest_spec`/`affected_systems`/`constraints`/`related_tasks`) для **ревью полноты TC и статуса покрытия**. Это **read-для-ревью, НЕ передача авторинга**: TC авторит аналитик, владение покрытием — у аналитика (граница §4.2 п.4 сохраняется). Решение **реверсит Track-B-исключение** в живой QA-роли (`feat/qa-kit-subagents` сейчас явно исключает helm-analyst) → **lead-qa проставляет** helm-analyst `mcp_server_spec` с этим `allowed_tools` в QA-роль/лейн (сигнал 23.07). Граница ownership с аналитиком уточняется при реализации.
4. **Единый механизм сборки (Солонко) — ОТКРЫТО.** Правит/делает Солонко; модель совместима, укладку сверяет он.
5. **Инструмент авторинга TC для аналитика** — есть ли скилл/шаблон, снижающий двойную запись Jira↔Allure? (Иначе «бесплатный первый слой» — миф.)
6. **Терминология — зафиксировано:** «механизм сборки профилей» (Солонко) ≠ kit `[capacity].profile` 0/1/2 (ИВА) — держать раздельно.
