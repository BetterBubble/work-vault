# Концепт доработки MCP RAG#2 — по фазам

Мастер-роадмап. Синтез: [[format-postanovki-analitika-iva-fr-feature-request-kanon]] · [[RAG-2 для аналитика — слои данных за пределами топологии + глоссарий (дизайн)]] · [[RAG-2 — внешние корпуса, упущенное внутри, и «действия важнее данных» (стратегия)]] · [[Решения по MCP-каталогу RAG-2 (критика приоритетов)]].

## Сквозные принципы (действуют во всех фазах)
- **Eval-гейт до изменений ретрива:** любое изменение поиска меряем на `rag2_golden` (recall/precision/ndcg/mrr) ДО включения; гейт = precision не просел.
- **Produce делает КЛИЕНТ:** MCP отдаёт контекст/данные, заполнение FR-скелета — Claude Code. В MCP нет тулов генерации.
- **Тулы различаем по ВОПРОСУ, не по источнику.** Цель — 6-8 неперекрывающихся тулов.
- **Инструменты не врут уверенно:** contradiction = «кандидаты», не «чисто»; effort = «как едет», не «оценка работы».
- **Выход выровнен под FR-скелет** (Начальная постановка · БФТ · ФТТ · Нефункц · Интерфейсные · Дизайн).

## Фаза 0 — Eval-гейт и полнота (фундамент)
- **Сделать:** завершить полную выгрузку (jira идёт на raw-фиксе); прогнать **baseline** на `rag2_golden` → зафиксировать эталон метрик.
- **Довыгрузить:** докачать jira до полноты; проверить полноту (источник vs indexed).
- **В helm:** `src/helm/eval/` (rag2_eval, rag2_runner, sweep, metrics, judge) — уже есть; golden `tests/data/rag2_golden.json`, RAG#1 `golden_iva_rag1.json` (1306).
- Выход: без baseline не начинаем п.1+.

## Фаза 1 — Действия на готовых данных (макс ROI)
- **Сделать (новые тулы):**
  - `nearest_spec(requirement_text)` → 1 ближайшая FR-постановка «взять за основу». Данные: confluence FR-корпус (IVCS) — ЕСТЬ.
  - `who_to_involve(system|requirement)` → владелец + assignee похожих задач + автор ключевого changelog. helm: arch owner; jira assignee/changelog — ЕСТЬ.
  - `effort_hint(system|requirement)` → `active_days` + `lead_time_days` (из статус-переходов changelog), подпись «справка, не оценка». Данные: jira changelog — ЕСТЬ (8693 у IVAONE).
- **Улучшить:** выровнять выход под FR-скелет; описания тулов по вопросу.
- **Мерить golden'ом** каждую.

## Фаза 2 — Улучшить текущие тулы (surface того, что в данных)
- **Доработать `affected_systems`✎:** +`fix_versions` (в какой релиз), +`clients` (кого сломаем), +`open_risks`/НФТ на контейнер.
- **Доработать `analyst_context`/`related_tasks`✎:** подмешать `status` + выжимку changelog + **ключевые комментарии** (решения в комментах).
- **Гигиена роутинга:** переписать описания по вопросу; проверить схлопывание `analyst_context`↔`nearest_spec` на routing-eval → при путанице слить.
- **В helm:** `requirement_client`, `arch_risk`, цепочка `requirement→component→repo→arch_node`, `product_component`, owners. Данные: jira `fv` (fixVersion) — ЕСТЬ.

## Фаза 3 — Слой «почему нельзя» (ADR/НФТ/compliance)
- **Довыгрузить:** спейс **IS** (Information Security), **ProductOffice** (Артефактриум/реестры МинЦифры-ФСТЭК); найти и проиндексировать **ADR** (где живут — искать в Confluence). НФТ уже в FR.
- **В helm:** `arch_risk` (open_risks), requirement-матрица.
- **Сделать:**
  - `constraints(system|requirement)` → {НФТ[], arch_risks[], compliance[152/ФСТЭК/КИИ/реестр], adr[]}.
  - `contradiction_check(requirement_text)` → **кандидаты** на конфликт (с ADR/требованиями) + обоснование; НИКОГДА не «чисто». Данные: requirement-матрица helm + ADR-индекс.

## Фаза 4 — Глоссарий (гейтируемый эксперимент)
- **Довыгрузить/собрать:** харвест IVCS-глоссария (page 149651699, ~195) + per-space «Термины» (UWC/PHON/IVAUC/IOA/IM) → структура `термин → {синонимы RU/EN, аббревиатура, продукт, определение}`.
- **Сделать:** `glossary(term)` (что такое X) + **query-expansion** (product-scoped, только редкие/OOV-термины, за флагом).
- **Гейт:** precision на golden не просел, иначе откат. Не «системный фикс на вере».

## Фаза 5 — Упущенные внутренние источники (data-ingest + surface)
- **Довыгрузить в jira-scope:** **IVASUP** (поддержка — сигнал боли), **IVA1C/IVACRM** (интеграции), тест-кейсы (Jira test-issues).
- **Сделать/улучшить:** surface «N обращений по фиче» в context/related; `contracts(system)` → {REST API, события шины, настройки, тест-кейсы} из FR «Функц.дизайн»; `gap_questions(requirement_text)` → сравнение с FR-скелетом → чего не хватает (актор/отказ/нагрузка/миграция).

## Фаза 6 — Внешние публичные корпуса (тот же краулер, позже)
- **RAG#1-first:** краулер iva.ru/docs (частично — `iva_docs` 8272) — пишется один раз, питает оба рага.
- **Довыгрузить снаружи:** протоколы (SIP/H.323/WebRTC/SMTP/IMAP — публичные спеки), вендорская дока интеграций (1С/CRM/LDAP-AD), сырые тексты нормативки (152-ФЗ, приказы ФСТЭК 17/21/31/239, ГОСТ, реестр МинЦифры).
- **Отложить:** конкуренты (шум). **Не дублировать:** тендеры/ТЗ — корпус RAG#3.

# Ревизия 2 — правки после критики (C4 / свежесть / ACL / routing-eval / наблюдаемость)

## Сквозные принципы — ДОПОЛНЕНЫ
- **Свежесть = условие, не фича.** Jira/Confluence меняются ежедневно; через месяц `affected_systems` «уверенно врёт» (худшая ошибка — аналитик поверит). Нужны: инкрементальная синхронизация (updated-since / вебхуки), фильтр «только текущая версия страницы», бейдж `as_of`/`stale` в выдаче. Заводим как ОТДЕЛЬНЫЙ трек (не «потом»).
- **ACL / изоляция.** Перед ингестом ЛЮБОГО спейса проверять права (особ. **IS = Information Security** — почти наверняка закрыт). Решение: зеркалить ACL спейса/страницы в payload + фильтр на запросе, ЛИБО не тащить закрытое. Иначе RAG отдаёт аналитику то, что ему по правам не положено, и заметят не сразу. Первое реальное применение сквозного теста изоляции.
- **Наблюдаемость MCP.** Пер-тул метрики: число вызовов, доля пустых ответов, latency. Без этого через месяц не видно, какие из 8 тулов мёртвые.
- **Produce = клиент** (подтверждение решения — чтобы не спросили на ревью).

## C4 ВОЗВРАЩЁН в каталог (был потерян при ужимании — это не решение, а потеря)
- `arch_map(parent, focus, level=C1|C2|C3)` + `arch_container(id, level)` — прямой lookup топологии: «за что отвечает контейнер Y, с чем связан, границы» — нужен ПОСТОЯННО, БЕЗ требования на входе. Это ДРУГОЙ вопрос, чем `affected_systems` (требование→системы). Добавлен **параметр уровня C4** (C2/C3) — иначе ответ либо слишком крупный, либо тонет в деталях. Оставляем отдельными тулами, НЕ режимом affected_systems.

## Фаза 0 — РАСШИРЕНА (валидируем не только jira)
- Полнота **И свежесть C4/arch-данных из helm** (граф `arch_node/edge/risk`, requirement-матрица) — фундамент под `affected_systems`. Кривой фундамент = «красивая ложь» на всех верхних тулах.
- **Два РАЗНЫХ eval (это разные инструменты):**
  - retrieval-eval (recall/precision/MRR на `rag2_golden`) — ЕСТЬ.
  - **routing-eval** — набор «вопрос → ожидаемый тул», НОВЫЙ, завести в Ф0. Меряет, выбрал ли агент правильный тул (не качество выдачи). Без него решение о слиянии `nearest_spec`↔`analyst_context` — «на глаз»; роутинг при 7-8 пересекающихся тулах — главный риск.

## docs_ask / RAG#1 — нестыковка порядка снята
- RAG#1-корпус (iva.ru/docs) УЖЕ залит (`iva_docs` 8272), `docs_ask` работает с Ф0. Краулер Ф6 = только ВНЕШНЕЕ публичное (протоколы, тексты нормативки), НЕ RAG#1. Инверсии зависимости нет (RAG#1 сделан по общему концепту раньше).

## gap_questions → Фаза 1 (из Ф5)
- FR-канон известен → тул почти бесплатный, экономит круг переписки с пресейлом. Промоушен в действия Ф1 (на готовых данных). Демоция в Ф5 была по инерции.

## Новый трек «Свежесть/синхронизация» (параллельно, после Ф0-1, раньше внешних корпусов)
- updated-since дельта-ингест (harness уже умеет resume/checkpoint → расширить на «изменённые с даты X»); current-version-only для Confluence; `as_of` в выдаче каждого тула.

## Целевой каталог — ОБНОВЛЁН (~9-10, C4 внутри)
1. `docs_ask` — как работает СЕЙЧАС (RAG#1)
2. `analyst_context` — контекст понять требование
3. `related_tasks` — похожие ЗАДАЧИ (+changelog/комменты/поддержка)
4. `nearest_spec` — готовая ПОСТАНОВКА *(routing-eval → возможно слить с #2)*
5. **`arch_map`/`arch_container(level=C1/C2/C3)`** — топология «за что отвечает Y, границы» (без требования)
6. `affected_systems` — требование→системы (+релиз/клиенты/риски)
7. `constraints` — НФТ/риски/compliance/ADR
8. `contradiction_check` — кандидаты (не вердикт)
9. по фазам: `who_to_involve` · `effort_hint` · `glossary` · `gap_questions`(Ф1) · `contracts`
+ у каждого тула — `as_of`/`stale` бейдж и учёт ACL.

# Ревизия 3 — FR-скилл: вторая половина продукта (оркестратор)

**Проблема:** можно построить 10 безупречных тулов и получить НОЛЬ ценности — аналитик сидит перед пустым окном Claude Code и не знает, что спросить. Тулы = движок, **FR-скилл = водитель**. Без него продукта нет. В прошлых ревизиях он не запланирован и не назначен — это дыра, не деталь.

## Что это
Claude Code скилл/команда `/fr <сырое требование>` (или вставка постановки из пресейла). **Детерминированно** оркестрирует тулы под FR-скелет и ведёт аналитика за руку.

## Поток (оркестрация тулов → секции FR)
1. **Понять** → `analyst_context` + `requirement_coverage`(is_new) + `glossary`(термины). «Вот что уже есть; это новое / с доработкой».
2. **Gap-чек (лечит пустое окно)** → `gap_questions` → «не хватает: кто актор / поведение при отказе / нагрузка / нужна ли миграция — уточни у пресейла». Аналитик отвечает или идёт спрашивать. ЭТО и есть ответ на «пустое окно».
3. **Затрагиваемые системы** → `affected_systems` + `arch_container(level)` → системы/владельцы/tech/риски/релиз/клиенты.
4. **Почему нельзя** → `constraints` + `contradiction_check`(кандидаты) → НФТ/compliance + «проверь эти потенциальные пересечения».
5. **Прецеденты/люди/срок** → `nearest_spec`(«берём за основу») + `who_to_involve` + `effort_hint`(справка).
6. **Черновик FR** → заполнить скелет (Начальная постановка · БФТ · ФТТ · Нефункц · Интерфейсные · Дизайн) из собранного, С ЦИТАТАМИ, в формате ИВА; неуверенные секции и открытые вопросы ПОМЕЧЕНЫ.
7. **Ревью/итерации** → аналитик адаптирует, скилл дозапрашивает тулы.

## Почему это меняет три вещи
- **Лечит «пустое окно»:** скилл сам говорит, что спросить/уточнить (шаг 2).
- **Снимает главный routing-риск:** скилл зовёт тулы в ЗАДАННОЙ последовательности, не полагаясь на угадывание агентом. (routing-eval всё равно нужен — для свободных вопросов вне скилла.)
- **Даёт реальный дифавербл** — черновик FR в их формате, а не «сырой контекст».

## Уточнение решения Р6 (produce = клиент)
Клиент = Claude Code + **FR-скилл** (спроектированный артефакт), а НЕ голое окно. Скилл делает ЛЁГКУЮ композицию (заполнение скелета из данных тулов), не тяжёлую генерацию с нуля — консистентно с «нет тяжёлой генерации в MCP».

## Ко-дизайн (принцип)
Скилл и тулы проектируются ВМЕСТЕ: скилл определяет, ЧТО тулы должны вернуть (контракты выхода под секции FR). Нельзя «сначала 10 тулов, потом скилл» — тогда тулы вернут не то.

## Место в роадмапе — НЕ «потом», а вертикальный срез с Ф1
- **Ф1 = тонкий вертикальный срез:** сырое требование → черновик FR на 2-3 тулах (analyst_context + affected_systems + nearest_spec) + gap_questions. Доказать весь цикл end-to-end, потом углублять каждой фазой.
- Против горизонтали («все тулы → потом скилл»): вертикаль даёт работающий продукт раньше и проверяет контракты тулов на реальном выходе.
- **Владелец:** трек лида (дизайн скилла + контракты), реализация — implementer. Назначить явно, не оставлять «ничьим».

## Целевой продукт = 2 половины
`движок` (MCP-тулы, ~9-10, свежесть+ACL+наблюдаемость) **+** `водитель` (FR-скилл, оркестрация + ведение аналитика + черновик FR). Оба меряются: тулы — retrieval/routing-eval; скилл — «дошёл ли аналитик от требования до валидного черновика FR за N шагов».
