# Helm — Карта срезов (1 срез = 1 вью дашборда)

> 7 срезов. По каждому: что показывает · сущности · связи · источники · готовность по слоям вертикали (ingest→domain→application→router→web). Собрано 2026-07-07.

## Легенда готовности
- Слои: ingest · domain · application · interface/router · web.
- Маркеры: ✓ есть/переиспользуем · ⚙ есть, доработать/перецелить · ✗ нет, писать.

### 1. Инциденты / SLA — COO (вью `ServiceDesk`)
**Что показывает:** Поток обращений поддержки в срезе SLA — открытые обращения и просрочка по категории/статусу/приоритету, возраст и backlog (SR/FR), критические кейсы; обращения-сигналы без привязки к инициативе = разрыв «поддержка/работа без цели». Эталон сверки цифр — `data/incident-phase0-baseline.json`.
**Сущности (из 30):** Обращение поддержки/ServiceDesk · Signal · Контракт · Клиент · Продукт (косвенно: Сервис)
**Связи (рёбра):** Контракт `покрывает` Обращение SD `есть` · Клиент `принадлежит` Контракт `есть` · Обращение SD → Продукт (относится к) `есть` · Обращение SD (FR) → Need/Requirement (порождает спрос→бэклог) `неполно` · Signal `агрегируется` Initiative `нет` (обращение как сигнал без инициативы — это и есть разрыв)
**Источники:** `service/sd_tasks.csv` (42 277 обращений SD: категория/подкатегория/статус/приоритет/создана/срок/просрочена/автор) · `service/sd_summary.csv` (свод категория×статус) · `data-room/support/crm_open_requests.csv` (782 открытых SR/FR, возраст, приоритет, контракт, тариф, семейство продукта) · `data-room/support/executive_summary.csv` (13 фактов: доли SR/FR, открытый хвост) · `data-room/support/backlog_snapshot.csv` (backlog по группам статусов) · `data-room/support/critical_cases.csv` (6 критических кейсов IVA MCU) · `data-room/support/fr_backlog.csv` (FR-backlog + Outlook-кейсы)
**Готовность по слоям:** ingest ✓ `service_source.py` (sd_tasks→Signal, категории IVA=поддержка + 1Ф=FR-бэклог, overdue-маркер, `initiative_id=None` фиксирует разрыв) · ⚙ выделенного адаптера под crm_open_requests/critical_cases/backlog_snapshot/fr_backlog нет — добрать SLA-возраст/контракт/тариф из support-выгрузки · domain ✓ `SignalDesk` (`signal_desk.py`: open_by_category / overdue_by_category); ⚙ `IncidentAttribution` (`incident_attribution.py`: by_component/by_release/by_month) переиспользуем для инцидентов, но его источник `jira/incidents/bugs_ivaone.csv` вне профилированного набора (дефекты — cross c CIO) · application ✓ `company_kb.py` (обращения по категориям через SignalDesk + атрибуция инцидентов), композит готов · interface/router ✗ отдельного `servicedesk`/`incidents`-роутера нет — писать (по образцу `cio.py`, отдавать open/overdue by category + SLA + as_of) · web ⚙ слот COO «ServiceDesk/инциденты (cross с CIO)» в `roles.tsx` — Stub/WIP, живого экрана нет; писать по образцу `Repos.tsx`/`Conformance.tsx`

### 2. Бэклог / Потребности — CPO (вью `Backlog/Needs`)
**Что показывает:** Спрос «снизу» — кластеризованные потребности клиентов и требования/фичи, собранные из FR-заявок поддержки, обращений ServiceDesk и проигранных сделок, с привязкой к продукту и целевому поколению; это вход в воронку §5A (Signal→Need→Requirement→Initiative).
**Сущности (из 30):** Потребность (Need), Требование/Фича (Requirement), Обращение поддержки/ServiceDesk (FR-заявки — источник спроса), Сделка (проигранные — сигнал незакрытой потребности), Продукт, Поколение.
**Связи (рёбра):** Обращение SD (FR) → Need/Requirement `неполно` · Signal → Need (кластеризуется) `нет` · Need → Requirement (порождает) `нет` · Requirement → Initiative (порождает) `нет` · Requirement → Generation (target_generation) `неполно` · Сделка → Продукт (относится к) `неполно`
**Источники:** `data-room/support/crm_open_requests.csv` (782 открытых, Тип=FR — 402 кандидата в Need/Requirement) · `data-room/support/fr_backlog.csv` (FR-беклог по статусам/возрасту/топ-клиентам) · `data-room/support/critical_cases.csv` (6 острых кейсов-эскалаций) · `service/sd_tasks.csv` (42277 обращений; категория 1Ф = FR-беклог) · `service/sd_summary.csv` (свод категория×статус) · `crm/crm_deals.csv` (2178 сделок; терминальные/отменённые как спрос) · `manual/reference_products.csv` (канон 5 продуктов) · `manual/reference_generations.csv` (6 поколений — target_generation).
**Готовность по слоям:** ingest ⚙ `service_source.py` уже отдаёт FR-беклог (категории IVA+1Ф → Signal без инициативы = сам разрыв) — переиспользуем; `crm_source.py` читает `crm_deals`, но исключает терминальные стадии → перецелить, чтобы ловить проигранные как сигнал спроса; кластеризатор Signal→Need и ingest тел Requirement (Confluence-body) — ✗ нет, писать (тела вики — внешний вход) · domain ⚙ `conformance.py` несёт сущность Requirement с verdict (met/partial/not_started/no_work) и target_generation, `gap_detector.py` даёт goal_coverage/goals_without_work, `refdata.py` — SEED_GENERATIONS; ORM-таблицы `need`/`requirement` существуют, но пусты; детектор Need (дедуп похожих FR/SD/проигранных в потребность по проблеме, а не по решению) — ✗ нет, писать · application ⚙ `company_kb.py` даёт обращения по категориям и разрывы графа (goal_coverage); отдельного `build_backlog`/`build_needs` (кластеризация спроса → приоритизированный бэклог) — ✗ нет, писать · interface/router ⚙ `gaps.py` (§6.1 разрывы) и conformance-витрины в `cio.py` переиспользуемы; отдельного `/api/needs`/`/api/backlog` — ✗ нет, писать · web ⚙ `Conformance.tsx` — живой экран, подключён и в CPO; целевые дэши CPO (`requirements` US#35, `feature-value` US#55, `roadmap+demand` US#31-34) в `roles.tsx` пока Stub-WIP → сам экран Backlog/Needs ✗ писать.

### 3. Портфель / Монитор ГД — CEO/COO (вью `Portfolio/Monitor`)
**Что показывает:** Дерево Блок → ЕОЛ → Инициативы со статус-светофором (red/amber/green), дедлайном, план-финишем, важностью (срочно×важно) и блокерами; роллап статусов в блоки, недельный diff снимков «что изменилось», топ-блокеры и «решения на CEO». Гантт инициатив по неделям.
**Сущности (из 30):** Initiative, Блок, ЕОЛ (роль-владелец → Person/person_email), Цель (Goal), Директива/Поручение ГД (MeetingDecision), SalesInitiative, Signal, Dependency, Эпик (кандидат генезиса), Встреча + Снимок (Meeting/Snapshot), Status (RAG, вычисляемая).
**Связи (рёбра):** Initiative→Блок (принадлежит) `нет` · Блок→ЕОЛ (Accountable) `есть` · Цель→Initiative (генезис 'а') `нет` · Эпик→Initiative (генезис 'в') `нет` · Signal→Initiative (агрегируется) `нет` · Initiative→Dependency (исходит) `нет` · Задача→Задача (зависит/блокирует) `есть` · SalesInitiative→Initiative (depends/decomposes, sales→delivery) `нет` · Initiative→Клиент (обслуживает) `нет` · Директива→Блок (тема) `неполно` · Директива→Директива (depends_on) `есть` · Встреча→Директива (содержит) `есть` · Встреча→Снимок (фиксирует) `неполно`
**Источники:** `monitor-gd/ceo_directives.csv` (15 поручений ГД D01–D15, owner/due/block/override) · `manual/blocks.csv` (9 блоков, eol_email 9/9) · `manual/goals.csv` (15 целей D01–D15) · `manual/directives_extra.csv` (depends_on/override к директивам) · `jira/jira_epics.csv` + `jira/ivaone/epics_ivaone.csv` (100+67 эпиков — кандидаты Initiative) · `jira/active_blockers.csv` (220 живых блокеров → краснота светофора) · `jira/jira_issue_links.csv` (5512 Blocks → зависимости) · `crm/crm_deals.csv` (2178 сделок — sales-плечо для sales→delivery) · `sensitive/by_person.csv` / `manual/teams.csv` (резолв ЕОЛ→Person). Ядро (Initiative-экземпляры, sales_link) в данных пусто — собирается генезисом оператора.
**Готовность по слоям:** ingest ✓ `real_source`+`loader` (сборка графа Signal→Initiative, genesis из цели/сделки/эпика), `links_source` (блокеры/связи), `crm_source` (sales), `jira_adapter`/RealJiraAdapter (эпики) — ⚙ реальный засев Initiative из эпиков+целей ещё не прогнан на данных, sales→delivery-мост ✗ писать · domain ✓ `initiative`+`genesis` (genesis()), `calc` (traffic_light, importance_full, детекторы разрывов), `status` (compute_status без LLM), `blocker_graph`, `monitor` (diff_snapshots), `snapshot_gate` — ⚙ `calc.sales_blocked`/sales_link-логика есть частично, ребро SalesInitiative→Initiative без экземпляров не строится · application ✓ `build_portfolio` (portfolio.py: светофор+роллап+GapReport+Гантт-строки), `snapshot`+`diff_snapshots`, `monitor_gd`, `brief` (недельный бриф) — переиспользуемы напрямую · interface/router ✓ `portfolio` (`/api/portfolio`,`/api/gantt`, серверные фильтры), `snapshots` (commit/diff), `initiatives` (PATCH override ЕОЛ + Annotation), `brief`, `gaps` — все живые с тестами · web ✓ `Portfolio.tsx` (COO→Монитор ГД, KPI+BlockCard→InitRow), `Gantt.tsx` (drag→ReasonModal→patchInitiative), `Gaps.tsx` — ⚙ `Brief.tsx` готов, но orphan (ни одна роль в `roles.tsx` не ссылается) — подключить к маршруту.

### 4. Дефекты / Соответствие — CIO (вью `Conformance`)
**Что показывает:** Матрица «требование поколения → реализовано в коде»: три среза RN@снапшот · RN@текущий · KMP@текущий с распределением вердиктов (met / partial / not_started / no_work), burn-rate RN и прогноз до 100 %, KPI активности треков 1.5 и таблица требований с обоснованием.
**Сущности (из 30):** Требование/Фича · Поколение (RN/KMP) · Компонент/Топология-блок · Конформанс-строка (ConformanceRow) · Задача (Jira/EVA как Signal) · Коммит/MergeRequest (evidence) · Снимок (Snapshot).
**Связи (рёбра):** Требование →(target_generation) Поколение `неполно` · Задача →(jira-signal) Signal `есть` · Коммит →(Т1) Задача `есть` · MergeRequest → Задача `неполно` · Репозиторий →(декомпозируется) Компонент `есть` · Продукт →(на поколении) Поколение `неполно` · Need → Требование `нет` · Требование → Initiative `нет`.
**Источники:** `jira/ivaone/tasks_open_ivaone.csv` (Feature/требования IVAONE, epic_link 18 %) · `jira/jira_issues.csv` (задачи type=Bug/Feature, статусы) · `manual/reference_generations.csv` (6 канон. поколений, RN/KMP) · `git/repos_manifest.csv` (репо→product→generation) · `git/commits.csv` (jira_keys 51 % — код→требование) · `git/merge_requests_all.csv` (MR как поставка). Профильный источник самой матрицы (`data/arch/…/conformance_matrix_1.5.csv`) в 65 профилях `data/real` ОТСУТСТВУЕТ — ConformanceRow пока без данных.
**Готовность по слоям:** ingest ⚙ `vitrines.py` (ConformanceRow-витрина) есть, но входной CSV матрицы надо добрать (вне профилей); `re_enrich.py` (repo→product/поколение) ✓, `commits.py` (evidence-коммиты/MR) ✓; структурированный ingest Требований из Confluence-QA — ✗ писать · domain ✓ `conformance.py` (ConformanceReport: verdict met/partial/not_started/no_work, coverage, generation_conformance, gaps, conformance_by_priority — структурный прокси G2), `stack.py` adp_coverage переиспользуем · application ⚙ отдельного строителя нет — матрица собирается в роутере напрямую; `meeting_pack.py` ConformanceSummary (1.5 met/partial/absent + прогресс RN) ✓ переиспользуем · interface/router ✓ `cio.py` (conformance-матрица RN vs KMP под `/api/cio/*`, as_of из ingest_run; тесты test_track_activity/test_contributors и др.) · web ✓ `Conformance.tsx` (VerdictBar, burn-rate, TrackKpis, фильтр/поиск; живёт и в CPO, и в CIO; тестов нет).

### 5. Ценность людей — COO/HR (вью `People`)
**Что показывает:** Вклад человека/команды (закрытые Jira/EVA-задачи × тип + commits × критичность репо), приведённый к ценности (× приоритет продукта) и сопоставленный со стоимостью (FTE-прокси) → квадранты star/valuable/overvalued/underloaded, heatmap команда×ценность, scatter и CV-lite fit (over/under-qualified). Каждый скор несёт explain; по-фамильные секции — под 🔴-контуром.
**Сущности (из 30):** Человек · PersonEmail (идентичность) · Команда/Трек · Организация/Юрлицо (Company + CompanyRole) · Коммит · Задача (assignee) · Экономика/ФОТ (стоимость-прокси, product-level). Косвенно: Продукт (приоритет + владелец-ЕОЛ). CV/зарплата по человеку — отсутствуют (gap §7, fit строится на CV-lite).
**Связи (рёбра):** Человек→PersonEmail `есть` · Человек→Команда `есть` · Человек→Коммит (автор) `есть` · Человек→Задача (assignee) `есть` · Человек→Организация (нанят) `есть` · Продукт→ЕОЛ/Владелец (Человек) `есть` · Продукт→Экономика/Портфельное решение `есть` · Человек→Initiative (Assignment) `нет` (нет слоя Initiative — работа выводима только через задачи→эпик, epic_link 7–18%)
**Источники:** `identity/identity_map.csv` (хаб person_email, 955; 21–30% без email) · `identity/identity_gaps.csv` (147 неразрешённых) · `data-room/team/target_team.csv` (117, Gold/Target-отбор) · `data-room/team/track_owners.csv` (5 контуров/владельцы треков) · `manual/teams.csv` (227, роль/трек/продукт) · `sensitive/by_person.csv` 🔴 (292, ставка_fte как прокси стоимости, gold) · `sensitive/fot_by_product.csv` 🔴 (ФОТ по продукту×тип — не по человеку) · `data-room/economics/product_economics_37m.csv` (приоритет продукта) · `git/commits.csv` / `git/all_commits.csv` (авторство вклада; jira_keys: commits.csv 51%, all_commits ~0.5%) · `git/repos_registry.csv` / `git/repo_activity_all.csv` (repo→продукт для атрибуции вклада) · `eva/eva_tasks.csv` / `jira/jira_issues.csv` (assignee, закрытые задачи) · `manual/product_owners_ref.csv` / `data-room/product_mgmt/product_owners.csv` (владелец продукта).
**Готовность по слоям:** ingest ✓ `identity.py`+`git_identity.py` (person_email, дедуп git-email, очередь ревью), `sensitive.py` (load_person_cost из by_person.csv 🔴), `economics.py` (приоритет продукта + load_fot_by_product 🔴), `commits.py`+`git_source.py`+`mr_source.py` (авторство) · domain ✓ `effort.py` (is_bot/is_bulk-фильтры вклада), `repo_registry.py` (top_committers-слияние), `salary_queries.py` (fot_by_selection Target/Gold/Out), `identity_directory.py`, `stack.py`, `access.py` (контуры 🟢/🔴), `adp_impact.py`; ⚙ `sensitive_inputs.py` (StaffRecord/SalaryRecord/**CvRecord** — валидаторы готовы, но CV/оклад-данных нет) · application ✓ `scoring.py` — ядро вью (compute_contributions/build_value_report/build_fit_report: квадранты, heatmap, scatter, CV-lite fit, explain), `governance.py` scrub_sensitive (редакция по-фамильных секций под 🟢-контур, fail-closed) · interface/router ⚙/✗ `cio.py` отдаёт часть среза (effort/BlueOptima-lite, contributors, adp-impact drill-down), но **value_report/fit-квадранты ни одним роутером не экспонированы** — ✗ писать `people`/`value` router поверх scoring.py + scrub_sensitive; `auth.py` уже даёт контур для 🔴-гейта · web ✗ живого экрана «Ценность людей» нет: COO-дэш «resources/мотивация» и HRD-дэши (roster/SoR, gold-отбор, companies, fuzzy git-автор→человек) — Stub-WIP в `roles.tsx`; `Repos.tsx` показывает усилие/вклад разработчиков (живой, но это CIO-ландшафт, не квадранты ценности) — писать People-экран под scoring-API.

**Сущности (из 30):** Сделка / SalesInitiative · Клиент (Client) · Продукт (Product) · ProductEconomics (маржа/выручка) · Организация/Юрлицо (Company) · Контракт (Contract) · Initiative (ребро sales→delivery) · Человек (менеджер/пресейл)
**Связи (рёбра):** Клиент→Сделка `есть` · Сделка→Продукт `неполно` · Клиент→Контракт `есть` · Клиент→Организация/Юрлицо `неполно` · SalesInitiative→Initiative (sales_link, decomposes) `нет` · Initiative→Клиент (обслуживает) `нет` · Продукт→Поколение (gen3) `неполно` · Продукт→ЕОЛ/Владелец `есть`
**Источники:** `crm/crm_deals.csv` (2178 сделок, воронка 12 стадий, `сумма_iva_с_ндс` 100%, `клиент` с ИНН, `продукт` 34.9%, `в_работу_до`→deadline) · `crm/top_projects_pipeline.csv` (65 топ-проектов, плюс-матрица продуктов MCU/ONE/…, бюджет, статус, менеджер) · `crm/top_projects.csv` (40 проектов, вероятность закрытия по пресейлу, этап, ведущий пресейл) · `data-room/economics/product_economics_37m.csv` (маржа/выручка/прибыль по продукту, «пайп продаж») · `data-room/economics/optimistic_scenario.csv` (оптимистичный сценарий выручки)
