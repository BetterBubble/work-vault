# Формат постановки аналитика ИВА — FR (Feature Request)

Проверено на живых постановках через iva-mcp (спейс **IVCS** — основной продуктовый, серия «FR»). Это НЕ «5 отдельных документов», а ОДИН структурированный документ с фиксированным скелетом. Примеры (page_id): 181180104 (пустой шаблон FR 26.0), 181177739 («Поддержка сервиса профилей IVA One», частично заполнен), **150113311 («Транскрибирование в звонках чата», v101 — эталон полного заполнения)**, 165709452 («Запись в звонках чата»), 160715148, 124063388, 124078234, 100974574 — все по нашему кейсу (запись/транскрибация ВКС).

## Скелет FR (канон)

**Шапка (метаданные):**
- Заказчик требования (напр. ПродОфис / IVA-Terra / ИБ,ПСБ)
- Представитель заказчика в IVCS (логин)
- **Задача в Jira** (ссылка, напр. VCSWEBR-511)
- Best practice · IVA MCU Guideline · Серверное описание (ссылки)

**Требования (Requirements)** — каждая секция с чекбоксом «Ревью пройдено»:
1. **Начальная постановка** — краткая цель + подсекция **«Вопросы»** (открытые вопросы с ответами стейкхолдеров: «Сергей: нет / Даниил: да») + тип задачи (Технологическая/Интеграционная).
2. **Бизнес-функциональные требования (БФТ / Business requirements)** — на языке пользователя: «Пользователю необходимо иметь возможность управления (запуск, остановка) стенограммой…».
3. **Функционально-технические требования (ФТТ / Functional requirements)** — нумерованные «Система должна…», глубоко технические: настройки (boolean-флаги), ограничения по типам пользователей/сетей, клиентский/интеграционный REST API, состояния/исключения, события NATS, журнал аудита/SIEM.
4. **Нефункциональные требования** (напр. «Все функции API должны быть задокументированы»).
5. **Интерфейсные требования** (часто «-»).

**Дизайн-спецификация (Design specification)** — тоже с ревью:
1. **Функциональный дизайн (Functional design)** — очень детально: таблицы настроек (Название/Описание/Тип/Дефолт/Группа/доступность), спеки REST API (path/tags/operationId/parameters/responses/security), схемы событий (websocket callback + поля body), системные сообщения (константы CALL_TRANSCRIPTION_START), записи журнала аудита (таблицы ru/en).
2. **Графический дизайн (UI design)** — макеты/скрины (часто «-» или вложения).
3. **Клиентский рабочий процесс (Client workflow)** — в некоторых FR.

Плюс отдельные **поэкранные функц-спеки** («26.х - Окно … (Web)»): заголовок · тексты · действия · контролы · переходы, привязаны к тест-кейсам (VCSWEB2-T970).

## Ключевые инсайты
- FR = near-implementation-ready: аналитик доводит до API-контрактов, событий шины, настроек, аудита. Это не «бизнес-бумага».
- «Вопросы» с ответами — важный артефакт (трекинг уточнений со стейкхолдерами).
- «Затрагиваемые системы / C4» — ОТДЕЛЬНОЙ секции в шаблоне НЕТ (есть только «Серверное описание»). → наш `affected_systems`/`arch_map` это **усиление** (какие системы, владельцы, tech — для координации и заполнения ФТТ/серверного описания).

## Сверка с нашим предположением о «5 документах»
| Предполагали | Реально |
|---|---|
| разбор требования | Начальная постановка + шапка (+Вопросы) |
| функц+нефункц (одно) | **4 секции**: БФТ · ФТТ · Нефункц · Интерфейсные |
| use case/сценарий | часть ФТТ + Client workflow |
| постановка | весь FR = постановка |
| затрагиваемые системы C4 | секции нет — наш value-add |

## Что делать с MCP (рекомендация)
1. Выровнять терминологию/выход MCP под реальные секции FR (Начальная постановка · БФТ · ФТТ · Нефункц · Интерфейсные · Дизайн), а не «5 абстрактных документов».
2. Скилл/промпт для Claude Code «заполни FR-скелет из данных MCP» → аналитик получает черновик постановки В ИХ формате (шапка + секции), а не сырой контекст.
3. `affected_systems`/C4 — killer-фича для «Серверного описания» + координации владельцев.
4. При ретриве прецедентов приоритезировать спейс IVCS (там эталонные FR).
