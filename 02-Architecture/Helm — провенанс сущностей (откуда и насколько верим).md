# Helm — справочник сущностей: из чего собираем картину для ГД

> 2026-07-06 · 30 сущностей · 11 готово / 16 уточнить / 3 переделать

## Как читать этот документ

Это справочник **сущностей** системы Helm — тех объектов, из которых складывается управленческая картина для гендиректора (потребности клиентов, инициативы, продукты, сделки, люди и т.д.). Задача документа — зафиксировать по каждой сущности: **откуда мы её берём, из каких данных, насколько ей можно верить и что осталось доделать**, прежде чем собирать всё это в единый граф.

**Тип сборки** — насколько сложно собрать сущность:
- **Справочник** — берём как есть, ведёт оператор (напр. список продуктов).
- **Прямая выгрузка** — строки источника один-в-один (напр. коммиты, сделки).
- **Дериват по джойну** — связываем существующее по общему ключу (напр. зависимости задач).
- **Вычленяемая** — собираем вычислением: группировка похожего, ИИ, с оценкой достоверности (напр. потребность, инициатива). Самое сложное.

**Статус готовности** (к сборке в граф):
- **✓ Готово** — данные готовы, собираем как описано.
- **⚙ Уточнить** — сущность определена, но перед сборкой нужен один конкретный шаг (нормализация / связка / добор данных).
- **⚠ Переделать** — структуру надо изменить до сборки.

Статусы — про готовность **данных**, а не про полноту описания: сам справочник полный, по каждой сущности всё прописано. Часть шагов закрывается на текущих данных, часть — требует внешних выгрузок (см. раздел «Что добрать»).

## Приоритет — Потребность и Инициатива

### ⭐ Потребность (Need) — ⚙ Уточнить · _Вычленяемая_

- **Откуда:** Из обращений и запросов фич в ServiceDesk, сделок CRM (включая проигранные) и требований в Confluence — объединением похожих проблем.
- **Файлы data:** crm_open_requests.csv, sd_tasks.csv, IVAPROJECT_205489583.md
- **Достоверность:** инференс (метка достоверности + оператор)
- **Почему так:** Достаточно на старте, но взгляд «снизу»: ловим боль из поддержки и продаж. Работает: похожие сигналы кластеризуются в одну потребность, оператор подтверждает; для стратегических потребностей «сверху» нужны тела требований из Confluence.
- **Что делаем:** Сущность ключевая (фокус). Механика: симптомы → кластеризация по проблеме → Need. Источники расширяем: + проигранные сделки (стадия «Отменено» 602) + critical_cases + fr_backlog. Внешне нужны тела вики (видение PO/аналитиков). _↳ Дедуп по проблеме, не по решению — иначе 400 дублей вместо ~40 потребностей._

### ⭐ Инициатива (Initiative) — ✓ Готово · _Вычленяемая_

- **Откуда:** Собирается из эпиков Jira, целей руководителя и клиентских сделок; объединение подтверждает оператор.
- **Файлы data:** jira_epics.csv, epics_ivaone.csv, goals.csv, crm_deals.csv
- **Достоверность:** инференс (оператор в цикле, не автомат)
- **Почему так:** Достаточно: все три источника есть в данных. Работает: инициатива — единая точка сборки, ссылается на источники с пометкой происхождения; когда на неё сходятся и цель, и деньги, и работа — это «золотой эпик».
- **Что делаем:** Единая единица-агрегат управления. Источники (Эпик/Цель/Сделка/Requirement) остаются отдельными сущностями — Initiative ссылается на них genesis-рёбрами с пометкой источника, НЕ поглощает. «Золотой эпик» = сходятся цель+сделка+эпик; «мимо цели» = только эпик. _↳ Жёстко хранить genesis_source на каждом ребре и не смешивать в отображении — иначе потеряем природу источника._

## Все сущности — по сложности сборки


### Справочник (5) — _берём как есть из справочника_

### Продукт — ✓ Готово · _Справочник_

- **Откуда:** Из ручного справочника продуктов, который ведёт оператор.
- **Файлы data:** reference_products.csv, product_owners_ref.csv, product_economics_37m.csv, portfolio_decisions.csv
- **Достоверность:** детерминированная (после нормализации)
- **Почему так:** Достаточно: номенклатура мала и стабильна, справочник — источник истины. Работает: всё остальное (сделки, репозитории, требования) привязывается к продукту по названию.
- **Что делаем:** Держим 5 укрупнённых коммерческих единиц (One/Mail/MCU/CS/Largo) как управленческий срез ГД — осознанное упрощение по канону. Реальный портфель шире (терминалы/SBC/GPT), но для витрины укрупняем. _↳ Под-линейки можно завести атрибутом продукта, не отдельными сущностями — если понадобится детализация выручки._

### Поколение — ✓ Готово · _Справочник_

- **Откуда:** Из ручного справочника поколений (1.0 / 1.5-RN / 1.5-KMP / 2.0 / 3.0).
- **Файлы data:** reference_generations.csv, repos_manifest.csv, blocks.csv, goals.csv
- **Достоверность:** детерминированная
- **Почему так:** Достаточно: это фиксированная технологическая ось из 6 значений. Работает: как метка на репозиториях, требованиях и инициативах — «на каком стеке».
- **Что делаем:** Технологическая ось (1.0/1.5-RN/1.5-KMP/2.0/3.0). Держать ОТДЕЛЬНО от версии продукта — это про стек/долг, не про roadmap-версию.

### Блок — ✓ Готово · _Справочник_

- **Откуда:** Из ручного справочника управленческих блоков (ведёт оператор).
- **Файлы data:** blocks.csv, track_owners.csv, directives_extra.csv
- **Достоверность:** детерминированная
- **Почему так:** Достаточно: блоки задаёт руководство, их немного (9). Работает: инициативы группируются в блок, у блока один ответственный (ЕОЛ).
- **Что делаем:** Управленческая группировка с одним ЕОЛ — валидна. Обязательно сделать связь блок→продукт явной (4 сквозных блока без продукта — ок, это платформа/инфра).

### ЕОЛ — ⚠ Переделать · _Справочник_

- **Откуда:** Из поля-владельца в справочнике блоков (резолвится в человека по почте).
- **Файлы data:** blocks.csv, product_owners_ref.csv, track_owners.csv, ceo_directives.csv
- **Достоверность:** детерминированная
- **Почему так:** Достаточно: у каждого блока заполнен ответственный. Работает: это не отдельная сущность, а роль-владелец блока — связывает блок с конкретным человеком.
- **Что делаем:** НЕ отдельная сущность — сворачиваем в роль-владельца Блока (поле eol_email, резолв в Человека). Отдельный узел избыточен.

### Цель — ⚙ Уточнить · _Справочник_

- **Откуда:** Из целей руководителя (ручной ввод по итогам встреч).
- **Файлы data:** goals.csv, ceo_directives.csv, directives_extra.csv, eva_tasks.csv
- **Достоверность:** детерминированная
- **Почему так:** Пока узко: есть 15 целей от гендиректора, но нет полноценных метрик/OKR. Работает: цель — то, чего надо достичь; порождает инициативы и задаёт важность.
- **Что делаем:** Отделяем от Директивы (две сущности по канону). Цель = что достичь (стратегия/метрика, живёт долго). Нужны настоящие OKR/метрики — сейчас только 15 строк от ГД. _↳ Ребро: Директива уточняет/порождает Цель._

- **Почему так:** Достаточно как факт поручения, но истории мало (одна встреча). Работает: операционное поручение с привязкой к дате; уточняет цели и запускает инициативы.
- **Что делаем:** Операционное поручение встречи (MeetingDecision) — отдельно от Цели. Привязано к дате/встрече. Накопить историю встреч для динамики исполнения.

### Клиент — ⚙ Уточнить · _Прямая выгрузка_

- **Откуда:** Из карточек клиентов в CRM и кодов клиентов в ServiceDesk.
- **Файлы data:** crm_deals.csv, top_projects.csv, crm_open_requests.csv, critical_cases.csv
- **Достоверность:** детерм. + инференс (дедуп имён)
- **Почему так:** Есть по объёму, но не нормализован (ИНН склеен, дубли написаний). Работает: единая карточка клиента через все каналы — связывает его потребность, сделки и обращения с выручкой; требует дедупликации.
- **Что делаем:** Сущность критична, но не нормализована (ИНН склеен, 84 кода vs 87 имён). Нужна единая карточка через каналы (сделки+поддержка+потребности) — иначе не связать потребность клиента с его выручкой.

### Сделка — ⚙ Уточнить · _Прямая выгрузка_

- **Откуда:** Из сделок CRM (воронка продаж).
- **Файлы data:** crm_deals.csv, top_projects_pipeline.csv, top_projects.csv
- **Достоверность:** детерминированная
- **Почему так:** Достаточно по объёму (2178), но продукт указан лишь у трети. Работает: сделка несёт деньги и обещание клиенту; привязывается к продукту и инициативе — без продукта выручку к продукту не свести.
- **Что делаем:** Отдельна от Initiative (Initiative на неё ссылается). Продукт заполнен лишь 34% — блокер привязки выручки к продукту, добить маппинг.

### Контракт — ⚙ Уточнить · _Прямая выгрузка_

- **Откуда:** Из договоров поддержки в выгрузке ServiceDesk.
- **Файлы data:** crm_open_requests.csv, sd_tasks.csv
- **Достоверность:** детерминированная
- **Почему так:** Неполно: видны только контракты поддержки, не лицензионные/продажные. Работает: связывает клиента с обязательствами по SLA; картина по деньгам смещена в саппорт, пока нет продажных договоров.
- **Что делаем:** Сейчас только контракты поддержки (172). Упущены лицензионные/продажные контракты — картина по деньгам смещена в саппорт. Нужен источник продажных договоров.

### Задача — ⚙ Уточнить · _Прямая выгрузка_

- **Откуда:** Из задач Jira и EVA, а также обращений ServiceDesk.
- **Файлы data:** eva_tasks.csv, jira_issues.csv, tasks_open_ivaone.csv, sd_tasks.csv
- **Достоверность:** детерминированная
- **Почему так:** Достаточно по объёму, но теряется иерархия (какая задача под каким эпиком). Работает: задача — единица работы; её ценность видна только в связке с эпиком и инициативой.
- **Что делаем:** Сохранить иерархию epic/parent/story-points (сейчас в ORM плоско как Signal — теряется трассируемость). epic_link дырявый (7-18%) → добить LLM-судьёй.

### Эпик — ⚙ Уточнить · _Прямая выгрузка_

- **Откуда:** Из эпиков Jira (основной трекер и IVAONE).
- **Файлы data:** jira_epics.csv, epics_ivaone.csv, monitor_ivaone_brief.md
- **Достоверность:** детерминированная
- **Почему так:** Достаточно как справочник, но связь задача→эпик заполнена слабо (7-18%). Работает: эпик — кандидат в инициативу; без связи с задачами рвётся трассировка от стратегии к исполнению.
- **Что делаем:** Дедуп Jira (100) + IVAONE (67) в единое пространство. Связь задача→эпик добить (сейчас 7-18%) — иначе рвётся трассировка стратегия→исполнение.

### Человек — ⚙ Уточнить · _Прямая выгрузка_

- **Откуда:** Из карты идентичности, состава команд и штатного справочника.
- **Файлы data:** identity_map.csv, teams.csv, by_person.csv, target_team.csv
- **Достоверность:** детерм. + инференс (21-30% без email)
- **Почему так:** Есть хаб на 955 человек, но у 21-30% нет корпоративной почты. Работает: почта — ключ, которым коммиты, задачи и роли сходятся на одном человеке; при пробелах в почте связи могут двоиться.
- **Что делаем:** Хаб идентичности нужен. Качество: дедуп 2776 git-email, добить 21-30% без email (147 gaps). Резолвить человека к роли (owner/ЕОЛ). _↳ Без надёжного person_email все джойны коммитов/задач текут — это шаг №1 сборки графа._

- **Файлы data:** teams.csv, target_team.csv, track_owners.csv

- **Почему так:** Достаточно (5 треков, 60 подразделений), но принадлежность — сырая строка. Работает: связывает людей с продуктом и блоком; нужна нормализация, чтобы свести производительность.
- **Что делаем:** Нормализовать принадлежность (сейчас сырая строка, не FK). Следить, чтобы Трек и Блок не расходились по смыслу.

### Организация — ⚠ Переделать · _Прямая выгрузка_

- **Откуда:** Из юрлиц-работодателей в штатке и клиент-юрлиц в CRM.
- **Файлы data:** by_person.csv, crm_deals.csv, sd_tasks.csv
- **Достоверность:** детерм. + нормализация
- **Почему так:** Проблема: смешаны внутренние юрлица IVA и внешние клиенты. Работает правильно только после разметки роли (мы / клиент / партнёр) — иначе путается внутренний и рыночный контур.
- **Что делаем:** Разметить CompanyRole (мы/клиент/партнёр) — сейчас склеены внутренние юрлица IVA и клиент-юрлица. Внутренний и рыночный контур нельзя держать одной неразмеченной сущностью.

- **Что делаем:** 233 репо, но связь репо→продукт явна лишь у 8-9 — вклад разработки нельзя атрибутировать продукту. Достроить маппинг (эвристика+curated).

### Запрос на слияние (Merge Request) — ⚙ Уточнить · _Прямая выгрузка_

- **Что делаем:** Нет reviewers/approvals (нужен GitLab PAT), автор=git-логин без маппинга на человека. Для оценки потока поставки этого мало.
