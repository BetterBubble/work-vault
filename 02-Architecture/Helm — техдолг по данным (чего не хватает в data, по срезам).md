# Helm — техдолг по данным (чего не хватает в data, по срезам)

Живой список: что и чего и где не хватает в `data/` для срезов. Дополняется по ходу. Зафиксировано 2026-07-06.

## Инцидент-срез (Сервис/качество)

- [gotcha] **`sd_tasks.csv` (42k) — НЕ источник обращений.** Это журнал-метаданные: «тема» = код заявки (SR.GRN.3.xxx), не текст; приоритет-заглушка «1», просрочка 0% (SLA-полей нет); ~82% строк — 1С-справочники (_Тех_Админ, Юр_Лица_1С). Для инцидент-аналитики бесполезен.
- [reference] **Реальный источник обращений — `crm_open_requests.csv`: 782** (264 SR-обращения + 402 FR-фичи + 6 IS). Есть продукт (MCU 546), статус, группа статуса, возраст, исполнитель, контракт, тариф.
- [gotcha] **Формального SLA нет** — нет времени реакции/решения по договору. Единственный сигнал застревания — **ВОЗРАСТ** (медиана 246 дн, 66% >90 дней).
- [followup] **Нет привязки инцидент → релиз → компонент → команда** (глубокая аналитика, которую хотел руководитель). Есть только продукт. Релиз — нужен fixVersion (внешнее). Команда — возможно через Исполнителя ⋈ teams (проверяется). Компонент — топология по репо, не по обращениям.
- [followup] Данных тонко: 782 обращения (не десятки тысяч). Витрина возможна как «гигиена застрявших обращений», не полноценный SLA-мониторинг.
- [reference] **Обогащение НАШЛОСЬ в том же crm_open_requests** (искали по всем файлам): **Тариф = SLA-уровень** (Премиальный 266 / Расширенный 206 / Стандартный 302) — можно мерить застревание относительно уровня клиента; **Исполнитель** заполнен 86% → связь с командой (13/20 матчатся с `teams` по ФИО); **Контракт** 100% → клиент. То есть срез = обращение × продукт × тариф × команда × возраст — богаче, чем казалось.
- [gotcha] `sd_summary.csv` — агрегат (категория/статус/count), бесполезен. Время реакции/решения SLA нет нигде в data.

## Team-разметка инженеров саппорта (для разреза «По команде» ServiceDesk) — 2026-07-07

- [followup] Разрез **«По команде»** в витрине ServiceDesk (Фаза 1, ветка `feature/servicedesk-phase1`) резолвит исполнителя (crm_open «Исполнитель», ФИО) → команда через `identity_map.csv` (955). Покрытие **18.5%** (145/782), но разрез **схлопывается в ~1 команду** («Отдел клиентского сервиса» 144/145): `identity_map.team_dep` у большинства инженеров саппорта заполнен одинаково либо пуст. **Код готов и корректен — нужна ДАННЫЕ:** гранулярная team-разметка инженеров саппорта (различающие значения team_dep/team_track), чтобы разрез стал полезным. До этого панель остаётся (оператор видит, что данных мало), покрытие вырастет по мере наполнения. Резолвер: `_TEAM_FIELDS=(team_dep→team_track→team_product)` в `ingest/servicedesk.py`.


## Дедуп/чистка канона клиентов (ServiceDesk by_client / clients-money) — 2026-07-07

- [followup] После фаззи-резолва `sd_request.company_id` (782/782, Fix2 CEO-слоя) разрезы «Клиенты» и «Клиенты×деньги» наполнились, НО канон клиентов содержит **мусор/внутренние сущности**: в топе мелькают **«ИВА»** (внутреннее юрлицо IVA, НЕ клиент) и **«Клиент2»** (плейсхолдер). Фаззи-норма дотягивает совпадения агрессивно → возможны и ложные матчи. **Нужно:** разметить CompanyRole (мы/клиент/партнёр — уже в модели, но не заполнено), отфильтровать внутренние юрлица и плейсхолдеры из клиентских разрезов, дедуп написаний. Не срочно — разрез работает, но цифры по клиентам «грязные». Связано с [[Helm — согласованный вердикт по сущностной модели (30 сущностей)]] (Организация → ⚠ Переделать, разметить CompanyRole).
