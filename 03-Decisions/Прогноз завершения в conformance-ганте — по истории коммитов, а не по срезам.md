**Дата:** 2026-07-09. **Статус:** Внедрено в прод (US104, iter-5, `cio.py`). **НЕ валидировано против факта.**

## Контекст
Гант «Соответствие» показывает ETA завершения треков (kmp/one/rn) и прогноз завершения по клиентам. Изначально считалось по **скорости закрытия из ежедневных срезов** (`RequirementAssessment.as_of`).

## Проблема
В проде срезов всего **2 (07-08, 07-09)**, окно 1 день, между ними влита репа → скорость вырождена/фейкова (kmp «авг'26», у `one` уходила в минус → линия пропадала). Одного-двух дней истории для скорости недостаточно.

## Решение (меняет прежний подход)
ETA считаем по **реальной истории коммитов** (232k коммитов, даты 2024→2026): темп = `закрыто требований ÷ период активной разработки реп`. Репы достаём из evidence оценки (`[repo/путь]`, regex `_EV_REPO`), период — `min/max Commit.commit_date` с cutoff `2024-01-01`.
- **Трек-ETA** (`conformance_timeline`): приоритет `eta_source`: коммиты → план (`target_quarter`) → пусто. Прежний скоростной ETA убран; `velocity_per_day` (когорта) оставлен только для краткосрочного текста.
- **Прогноз клиента** (`list_bundles`): по репам ЕГО требований × темп → у каждого свой срок (`forecast_date`/`forecast_per_week`).

## Достоверность (честно — озвучено руководителю)
- ✅ Годится как **«светофор отставания» и ранжирование** (порядок величины, год/полугодие). Кросс-проверка: `one` по коммитам (2027-06) ≈ план Q2'27.
- ❌ НЕ годится как календарь сдачи. Допущения: линейный темп; связка требование→репа приблизительная; `met ÷ период всех коммитов репы` — прокси; общие репы → прогнозы скоррелированы.
- Модель новая, **не сверена с реально завершёнными задачами**.

## Как усиливать (открыто)
Взвесить по `Commit.effort` (не числу); валидировать на 5-10 закрытых; копить ежедневные срезы (краткосрочный кросс-чек); точнее связать через jira-ключи (76k коммитов их имеют).
