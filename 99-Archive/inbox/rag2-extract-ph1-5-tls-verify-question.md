## Единственный открытый риск/вопрос
Лид просил опцию `HELM_RAG2_TLS_VERIFY=0`/`verify=False` для похода через SSH-туннель
(`127.0.0.1:8443 → jira.iva.ru/wiki.iva.ru`, один IP по SNI) на случай проблем с валидацией
сертификата за туннелем на adp_emb.

Средство безопасности этой сессии (guardrail агента) заблокировало эту правку — отключение
TLS-проверки по запросу тиммейта (не человека-пользователя в этой сессии) требует явного
согласия человека. Я НЕ стал обходить блокировку.

**Что сделано вместо этого:** SNI/Host-подмена реализована и работает (`connect_url` +
`extensions={"sni_hostname": ...}`, эмпирически проверено), но **проверка сертификата всегда
включена** (`verify=True`, без опции отключения в коде).

**Что нужно решить человеку (не мне, не лиду-агенту):** если на живом прогоне через туннель
сертификат `jira.iva.ru`/`wiki.iva.ru` не проходит валидацию (напр. self-signed/несовпадающий
CN на стороне adp_emb) — `fetch_*` упадут с `SSLError`. Тогда нужно осознанное решение
человека: либо поправить цепочку сертификатов, либо явно добавить bypass-флаг с ведома
пользователя (я готов дописать по факту, если будет прямое подтверждение).

Подробности — в `RAG2_EXTRACT_SUMMARY.md` на ветке, раздел «Риски», пункт 1.
