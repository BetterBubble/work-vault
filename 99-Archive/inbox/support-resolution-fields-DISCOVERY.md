# Support-MCP — из чего состоит РЕЗОЛЮЦИЯ (выход №2). Разбор 21 реальной crm-заявки

> Прогнаны все **21** crm-заявки с непустым «Решение» (placeholder=False). PII замаскировано: `<клиент>`/`<контракт>`/`<ФИО>`/`<тел>` (серийники и телефоны → `<тел>`). Сырьё в отчёт не копировалось.

## TL;DR
- «Решение» — **не единый жанр**. 21 запись раскладывается на ~8 повторяющихся полей: инструкция-навигация, диагноз/причина, что сделали, целевая версия+ETA, ссылка, статус доработки, роутинг/эскалация, запрос обратной связи.
- **Качество очень неровное:** ~4 записи — содержательные (диагноз+фикс+версия), ~5 — процессные заглушки без решения («Уточнение», «По согласованию с заказчиком», «прошу подтвердить актуальность»). Это важный сигнал: тул выхода №2 должен уметь возвращать и «нужны данные» (needs-info), а не только готовое решение.
- Три выхода концепта прямо видны в данных: **ответ клиенту** (инструкция/консультация), **резолюция в тикет** (диагноз+фикс+версия), **эскалация** (в бэклог / на N линию / к аккаунт-менеджеру).

## 2. Пары вход→выход (обезличено) — как «крик клиента» превращается в резолюцию

**Пример A — how-to / консультация (→ выход №1 «ответ клиенту»)** · SR · IVA MCU
- **Вход (клиент):** при звонке из ТфОП по неответу инициатор слышит «Неправильно набран номер…», не понимаем как исправить.
- **Выход (резолюция):** *инструкция-навигация* → «Администрирование → Аудио/видео IVR → Схемы IVR → IVR сообщения → выбрать → Детально → Заменить». + follow-up «Остались вопросы?»
- Поля: `instruction_steps`, `follow_up`.

**Пример B — баг, фикс в релизе (→ выход №2 «резолюция в тикет»)** · SR · IVA MCU
- **Вход:** периодически пропадает видео VVoIP/H.323-участника в раскладке, помогает переподключение.
- **Выход:** *диагноз+фикс+версия* → «Вышел релиз IVA MCU 25.11, устранено периодическое отсутствие видео от H.323-терминалов, восстановлено стабильное отображение».
- Поля: `diagnosis`, `action_taken`, `fix_version`.

**Пример C — фича-запрос (→ выход №3 «эскалация»)** · FR · IVA MCU
- **Вход:** прошу реализовать централизованный CallBranding (фон/музыка при подключении). Есть тикет №13835.
- **Выход:** *статус доработки + роутинг* → «Добавлено в список пожеланий (сроков нет). Для повышения приоритета — к вашему менеджеру».
- Поля: `resolution_type=limitation/backlog`, `routing` (к аккаунт-менеджеру), `references` (связанный тикет).

**Пример D — инцидент/ремонт, диагноз+действие (→ выход №2)** · SR · IP-телефон IVA
- **Вход:** три IP-телефона (сер. № `<тел>`) не включаются от штатного PoE-БП, просим ремонт.
- **Выход:** *диагноз+действие+итог* по каждому устройству → «КЗ по линии 5В, замена DA4/DA5/DA6/DA9…, работоспособность восстановлена».
- Поля: `diagnosis`, `action_taken`, `outcome` (по единице оборудования).

## Вывод: какие поля должны отдавать тулы под выход №2 (резолюция в тикет)

Минимальный набор полей резолюции, покрывающий наблюдаемую структуру:

1. **`resolution_type`** — enum: `how_to` | `workaround` | `fix_in_version` | `limitation` | `needs_info` | `hardware_repair`. (needs_info обязателен — ~5/21 именно такие.)
2. **`diagnosis`** — причина/трактовка (опц.; есть в 4/21). Для консультаций = объяснение настройки.
3. **`action_taken`** — что сделали (замена/установка/проверка на версии).
4. **`instruction_steps`** — навигация/шаги для клиента (self-service; 4/21). Пересекается с выходом №1 (ответ клиенту).
5. **`fix_version` + `eta`** — целевой релиз и срок (5/21 версия, 3/21 срок). Ключевое поле для баг/фича.
6. **`references`** — ссылки: URL доки/релиз-нотес, связанный тикет/баг-id (в тексте клиенты сами шлют номера тикетов — надо тянуть).
7. **`routing` / `next_line`** — мост к выходу №3 (эскалация): «в бэклог», «к аккаунт-менеджеру», «на III линию» (в crm это ещё и в статусе — `Выполняется III линией`).
8. **`follow_up`** — приглашение/ожидание ОС («Остались вопросы?», «подтвердите актуальность»).

**Замечания для концепта:**
- Выход №1 (ответ клиенту) и №2 (резолюция в тикет) частично делят поля (`instruction_steps`, `diagnosis`) — вероятно один генератор, две проекции (клиентская формулировка vs внутренняя).
- Выход №3 (эскалация) в данных = `routing`+`resolution_type=limitation/backlog` — триггерится типом FR и статусом линии.
- Корпус «эталонных» резолюций для few-shot тонкий: ~10–12 содержательных из 21. Заглушки (#11,#18) в обучение/примеры не брать.
