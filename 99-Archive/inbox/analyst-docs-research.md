# Ресёрч: артефакты аналитика в потоке «требование → задача разработчику»

Контекст: дизайн RAG#2-MCP — помощник системному/бизнес-аналитику, который должен максимально автоматизировать сборку типовых документов на пути от сырого требования до постановки задачи разработчику.

## 1. Стандартный набор артефактов

### RU-практика (waterfall/гибрид, встречается в среднем и крупном энтерпрайзе)
Цепочка документов и их авторство (см. источник 1):

1. **BRD (документ бизнес-требований)** — бизнес-аналитик: цели проекта, бизнес-контекст, границы/scope, стейкхолдеры.
2. **ТЭО (технико-экономическое обоснование)** — бизнес-аналитик: текущая/будущая ситуация, варианты решения, финансы, риски.
3. **ТЗ / спецификация требований** — системный аналитик: цели решения, функциональные требования, модели данных, НФТ, ограничения.
4. **Проект решения (HLD)** — архитектор/системный аналитик: архитектурная категория, элементы системы и их взаимодействие, протоколы, стек, схемы БД.
5. **ПМИ (программа и методика испытаний)** — совместно: цель/объём испытаний, порядок, отчётность.

Отдельно от этой «формальной» цепочки — практика «постановки задачи на реализацию» (источник 4), более гибкий документ для передачи разработчику, обычно 6 разделов (не все обязательны — состав зависит от сложности задачи):
1. Контекст задачи (бизнес-язык, бизнес-процесс, проблемы).
2. Ключевые источники информации (глоссарий, API-спеки, HLD, стандарты).
3. Заинтересованные стороны (роли, кто принимает решения/результат).
4. Критерии приёмки (функциональные требования, use case-сценарии, чек-листы).
5. НФТ и ограничения.
6. Описание решения: use case-сценарии, информационные модели, алгоритмы, макеты, компонентные схемы, интеграции.

### Международная практика (BABOK / waterfall BA artifacts)
Похожая цепочка «работы» → «поставки» (источник 2, 3):
1. **BA Approach Plan** — драйверы, проблема, видение, scope, роли, план вовлечения стейкхолдеров.
2. **Business Requirements Specification** — бизнес-домен-модель, business use cases, activity-диаграммы, бизнес-требования.
3. **Business Case** — обоснование решения (затраты/выгоды/риски) на основе собранных требований.
4. **Functional Specification** — system use cases, user requirements, activity/class-диаграммы, функциональные требования — именно этот документ «мостит» бизнес-потребность к тому, что реализуют разработчики.
5. **Non-Functional Specification** — производительность, безопасность, доступность, интерфейсы, комплаенс.

BABOK разделяет **work products** (черновые артефакты в процессе — заметки, диаграммы, наброски) и **deliverables** (финальные, согласованные со стейкхолдерами документы). User story, use case, acceptance criteria — это техники/артефакты уровня work product, которые могут как войти в SRS, так и существовать самостоятельно (источник 2).

**Use Case Specification** (источник 3) — типовая структура: имя (глагол+объект, «Оформить заказ»), актёры, основной поток событий (шаги), альтернативные потоки, пред-/постусловия, специальные (нефункциональные) требования к сценарию.

**Acceptance Criteria** для user story — почти повсеместно формат Given/When/Then (источник источники по AC, не приводим отдельно — общеизвестная практика Cucumber/BDD).

## 2. Минимальный ценный набор (~5 документов) — что реально закрывает поток

Синтез из обоих источников: полная waterfall-цепочка (5+5 документов) избыточна для большинства задач среднего размера. Ядро, которое покрывает «требование → постановка задачи разработчику», сводится к:

1. **Разбор/анализ требования** (краткий BRD-экстракт: проблема, цель, контекст, границы, стейкхолдеры).
2. **Пользовательский сценарий / use case** (актёры, основной и альтернативные потоки, пред-/постусловия).
3. **Функциональные + нефункциональные требования** (мини-SRS: что должна делать система + ограничения/производительность/безопасность).
4. **Impact-анализ / затрагиваемые системы** (какие контейнеры/компоненты и интеграции задействованы, зона ответственности каждого).
5. **Постановка задачи разработчику** (user story/задача + acceptance criteria + при необходимости sequence/activity-диаграмма и ссылки на API/контракты) — финальный документ, синтезирующий 1–4.

Диаграммы (sequence/activity) и API-контракты в обеих практиках — не отдельный «пятый документ», а вложение/приложение к use case или к постановке задачи.

## 3. Что RAG может генерировать/грунтовать vs что пишет аналитик сам

| Документ | RAG генерит/грунтует | Аналитик сам |
|---|---|---|
| Разбор требования | Черновик из текста требования + похожие прошлые требования из базы знаний (RAG#1) | Уточнение бизнес-цели, приоритетов, финального scope |
| Use case / сценарий | Черновик потоков по шаблону, подстановка актёров из известных ролей системы | Бизнес-логика альтернативных сценариев, edge cases от реального опыта |
| Функц./нефункц. требования | Черновик на основе похожих прошлых ТЗ + список типовых НФТ по типу задачи | Конкретные цифры (SLA, нагрузка), финальная формулировка |
| **Impact-анализ / затрагиваемые системы** | **Полностью грунтуется на C4-топологии в RAG: контексты/контейнеры/компоненты, их зоны ответственности → RAG предлагает список затронутых систем и обоснование** | Проверка/корректировка (аналитик знает нюансы, которых нет в модели) |
| Постановка задачи разработчику | Сборка/синтез из пп. 1–4 + AC-шаблон (Given/When/Then) | Финальная приёмка, специфичные технические детали, договорённости с командой |

Это отвечает на вопрос п.3 задания: наиболее «RAG-дружелюбный» документ — именно impact-анализ, потому что он прямо опирается на архитектурную топологию (C4), которая уже есть/предполагается в RAG-базе знаний. Остальные документы RAG может «подсветить черновиком» (grounding по похожим прошлым документам), но финальное решение — за аналитиком.

## 4. Как C4-модель обычно применяется аналитиком

По официальным материалам c4model.com (источник 5) модель — это 4 иерархических уровня абстракции: **Context** (система в окружении, внешние акторы/системы) → **Container** (развёртываемые единицы: сервисы, БД, фронтенды) → **Component** (логические компоненты внутри контейнера) → **Code** (классы/модули).

Прямого готового рецепта «impact-анализа через C4» в открытых источниках Brown не описывает — это универсальная практика, которую команды строят поверх модели сами. Логика, которая напрашивается и хорошо ложится на RAG:
- **Context-диаграмма** даёт быстрый ответ «какие системы вообще в периметре» — по ней аналитик/RAG может отфильтровать нерелевантные системы.
- **Container-диаграмма** нужна для ответа «что именно затронуто»: у каждого контейнера — заявленная зона ответственности (то, что в C4-нотации описывается как краткое назначение контейнера). Если формулировка требования пересекается по домену/данным/интеграции с зоной ответственности контейнера — он попадает в impact-scope.
- **Component-уровень** нужен реже (для крупных/сложных задач) — детализирует, какая часть контейнера меняется.

Практический вывод для нашего MCP: если в RAG-базе знаний закреплена C4-топология с текстовыми описаниями ответственности каждого контейнера/компонента, то impact-анализ можно строить как retrieval + semantic match требования против этих описаний ответственности — то есть это наиболее автоматизируемая часть постановки задачи.

## 5. Предложение: 5 документов для нашего кейса (RAG#2-MCP)

1. **Разбор требования** — краткая выжимка: бизнес-цель, проблема, контекст, границы, ключевые стейкхолдеры. *(RAG грунтует черновик по тексту требования + похожим прошлым разборам)*
2. **Пользовательский сценарий (use case)** — актёры, основной поток, альтернативные потоки, пред-/постусловия. *(RAG предлагает шаблон-скелет + похожие сценарии; аналитик пишет логику)*
3. **Требования (функц. + нефункц.)** — мини-SRS: что делает система, ограничения/производительность/безопасность. *(RAG грунтует черновик списком типовых требований по классу задачи; аналитик — цифры и финальные формулировки)*
4. **Impact-анализ (затрагиваемые системы)** — список контейнеров/компонентов C4-топологии, попавших в scope, с обоснованием через их зону ответственности. *(RAG генерит почти полностью — прямой retrieval по C4-топологии знаний)*
5. **Постановка задачи разработчику** — user story/задача + acceptance criteria (Given/When/Then) + при необходимости диаграмма/ссылка на API-контракт. *(RAG собирает синтез из пп. 1–4 + AC-шаблон; аналитик — финальная приёмка и технические договорённости с командой)*
