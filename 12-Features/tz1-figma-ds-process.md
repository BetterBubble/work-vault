# ТЗ#1 Дизайн-процесс Figma↔код   ·   🧪 ждёт живой проверки

> **Для руководителя.** Доработка по ТЗ закрыта и выкачена в прод-каталог профилей 25.07: разработчик с ИИ-агентом теперь умеет по макету собирать и применять компоненты дизайн-системы, переносить готовые экраны из веб-клиента в мобильный и числом (а не «на глаз») сверять результат с макетом. Статус не «готово», а «ждёт живой проверки»: на реальном рантайме экран ещё не собирали — это произойдёт при интеграции у команды мобильного клиента. Часть работ по ТЗ сознательно вынесена другим командам — список в [[tz1-figma-ds-handoff-ostatok]].

## Зачем
Дизайн и код расходились: макеты в Figma живут отдельно, компоненты в репозиториях собираются по-разному, перенос экрана между клиентами делался вручную и каждый раз заново. ТЗ просило описать процесс так, чтобы связка «разработчик + ИИ-агент» работала по правилам: брала макет, находила нужный компонент дизайн-системы, собирала экран из готового и проверяла результат по числам, а не на глаз.

## Как работает
Разработчик даёт агенту задачу и ссылку на макет. Агент:
- определяет, с какой дизайн-системой и поверхностью имеет дело (веб-клиент или мобильный, какая ДС);
- при **создании** нового компонента — держит конвенции репозитория (анатомия, только токены, полнота вариантов, история в Storybook);
- при **сборке экрана по макету** — идёт 7 шагами: предпроверка макета → метаданные → сопоставление элемента макета с реальным компонентом (через словарь и связки Code Connect) → сборка → приёмка, причём **непонятный элемент останавливает работу**, а не додумывается;
- при **переносе экрана из веб-клиента в мобильный** — читает исходный репозиторий строго на чтение, переводит по таблице соответствий, проверяет паритет и не выдумывает отсутствующих компонентов;
- при **приёмке** — сравнивает витрину с макетом численно (цвет в пределах ΔE≤2, отступы ±2px по токенам).

## Что конкретно сделано
- **Перенос экрана веб → мобильный (Сц.4).** Было: перенос вручную, каждый раз с нуля. Сделали навык-оркестратор переноса + отдельный навык чтения второго репозитория (источник только на чтение, цель на запись). Теперь агент работает сразу с двумя деревьями кода и не путает, где можно писать.
- **Создание компонентов библиотеки (Сц.1).** Навык авторинга компонента веб-ДС: анатомия папки, только токены вместо хардкода, полнота вариантов, Storybook и тесты. Эффект: новые компоненты выходят однотипными, а не «как получилось».
- **Новый экран по макету (Сц.2).** Навык применения компонентов: 7 шагов от предпроверки макета до приёмки, с обязательным стопом на незамапленном элементе.
- **Числовая приёмка макета.** Было: «похоже» на глаз. Стало: числовое сравнение цвета и отступов витрины с макетом, с допусками.
- **Несколько дизайн-систем (ось-1).** Определение ДС по признакам платформы/поверхности + отдельный навык под вторую ДС (`iva-core`) + быстрый старт для веба. Эффект: агент не тащит компоненты одной ДС в чужой репозиторий.
- **Правило миграции репозитория на новую ДС (Сц.3).** Тонкое правило: батчами, не смешивать две ДС в одном экране, нет аналога — сначала создать компонент, удаление легаси — отдельным шагом.
- **Словарь соответствий компонентов.** 49 компонентов мобильной ДС сопоставлены с веб-компонентами; у 32 есть ключ Figma, у 17 честно null (компоненты из других файлов ДС — матч по имени). Ключи взяли из файла в репозитории, доступ к Figma для этого не понадобился.
- **Конфиг/доставка:** навык доставляется каталогом профилей в **репо-нативный путь** мобильной команды (`AI common/skills/…`) — потребление «как у них принято», версионирование и пиннинг остаются едиными. Прод-сид — 25.07 вместе с остальными ТЗ.

## Что осталось
- **Рантайм-проверка** собранного экрана (компиляция, скриншот-тесты, паритет с макетом) — при интеграции у команды мобильного клиента.
- **Хвосты словаря:** дозаполнить 17 пустых ключей Figma и полные сигнатуры компонентов; промоция словаря в серверные связки.
- **Работы, вынесенные другим командам** (по разделению ролей в самом ТЗ): прогон миграции iva-one, серверная ДС + словарь v2 с автопересборкой, дозаполнение фреймов в Figma. Список: [[tz1-figma-ds-handoff-ostatok]].

## Блокеры
- Живой рантайм упирается в чужой контур (мобильный репозиторий + тулчейн команды) — не наш шаг, ждём интеграции.
- ADR-канон по базовому ui-лейну не оформлен (не блокирует использование).

## Как проверяли (доказательства)
- **Автотесты каталога** на каждом изменении (схемы, покрытие ролей, дисциплина версий, байт-сверка дублей) — зелёные.
- **Независимая сверка полноты по ТЗ** ([[final-fidelity-tz1]]): все 4 сценария + оси покрыты как способность профиля, «сверх ТЗ» не найдено; один найденный дефект (навык применения компонентов утверждал, что числовая приёмка ещё недоступна) исправлен до прода.
- **Сухой пилот на реальном экране** (ContactDetail): нашёл 5 расхождений с веб-версией, по итогам уточнили сам навык (4 правки). Ported-код остался черновиком на scratch — это была валидация, не доставка.
- **Живой рантайм — НЕТ.** Поэтому статус не «готово».
- **Прод:** пакеты активны на целевых версиях, verify зелёный ([[prod-deploy-3tz-done-2026-07-25]]).
