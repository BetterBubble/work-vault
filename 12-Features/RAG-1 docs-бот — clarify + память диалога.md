# RAG#1 docs-бот — уточняющие вопросы + память диалога

**Статус:** готово (2026-07-21). Прод `helm.tacticum.ru`, `main = 9571b1f`. Всё задеплоено, флаги ON, проверено сквозным прогоном через реальную петлю бота И подтверждено пользователем в живом Telegram (2026-07-21).

> **Для руководителя.** Публичный бот по документации в Telegram научился двум вещам, которых людям в чате не хватало: переспрашивать, когда вопрос двусмыслен, и помнить предыдущий вопрос. Раньше на «как добавить участника в идущий звонок» он отвечал про запланированное мероприятие, а на уточнение «у меня iOS» отвечал «не нашёл». Теперь при двусмысленности он задаёт **один** уточняющий вопрос и после ответа сразу отвечает по делу, а follow-up понимает в контексте предыдущего вопроса. Выкачено на прод 21.07 и проверено сквозным прогоном через реальную петлю бота плюс живой перепиской в Telegram: на эталонном наборе из 18 вопросов уточнение срабатывает ровно там, где нужно, и ни разу там, где не нужно; качество ответов на контрольном наборе не просело.

## Зачем
Публичный бот по докам ИВА (Telegram). Три жалобы из живого чата:
1. На двусмысленный «как добавить в идущий ВКС» отвечал про мероприятие — неверно.
2. Не переспрашивал, когда стоило (вываливал ответ по всем продуктам).
3. Не помнил предыдущий вопрос (follow-up «у меня iOS» → «не нашёл»).

## Как работает (итог)
- **Уточняющие вопросы (clarify):** бот сам решает переспросить (маркер `[[CLARIFY]]`), если запрос двусмыслен по сценарию (идущий звонок vs запланированное мероприятие) ИЛИ ответ ветвится на 3+ продукта/платформы без указанного выбора. **Спрашивает один раз, затем отвечает** (кап=1). Флаг `docs_clarify_enabled`.
- **Память диалога:** последние 3 хода на чат хранятся (таблица `docs_conversation_turn`, TTL 30 мин), подмешиваются в промпт, И ретрив follow-up идёт по контекстному запросу (пред. вопрос + текущий). Флаг `docs_conversation_context_enabled`.

## Что конкретно сделано
- Диагностика на реальных данных: retrieval-фикс проблемы 1 — тупик (rewrite/синонимы ухудшали и точность, и базу); лечится переспросом.
- Откалибрована clarify-инструкция v1→v2→**v3.1 (18/18 на живом LLM)**: добавлено правило «3+ продукта → переспроси, а не вываливай всё», починен флагман «идущий ВКС».
- Память диалога: стор + инжект + **контекстный ретрив** (фикс — без него follow-up «у меня iOS» давал «не нашёл»).
- **Кап уточнений 2→1**: «спросить раз, потом ответить» — иначе на «создать мероприятие»→«у меня iOS» бот переспрашивал дважды.

## Как проверяли (реальные данные)
- **Сквозной прогон через реальную петлю бота (`resolve_with_clarify`) на проде:**
  - [x] «создать мероприятие» → «у меня iOS» → бот ОТВЕЧАЕТ (было «не нашёл»/зацикливание).
  - [x] «...в One Web» → «а на iOS?» → отвечает про создание события на iOS (память+контекст-ретрив).
  - [x] «идущий ВКС» → переспрашивает продукт. [D] «очередь вызовов CS» → отвечает.
- clarify v3.1: verify_clarify на живом LLM 18/18 (двусмысл. 8/8, однозначные 10/10, 0 ложных).
- golden-184 judge: correctness 0.768→0.778, faithfulness 0.982→0.984 (регресса нет).

## Что осталось
