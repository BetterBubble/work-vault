# Критик верности: вынос канала записи helm-iva-write в лейн iva-write-base

Ветка `feat/iva-write-base-lane`, дерево `/Users/bubblemac/tacticum-worktrees/iva-write-lane`, база `origin/main` = `d607513`.

Статус: в работе. Ниже дописывается по мере проверки трёх вопросов.

## Вопрос 1 — правка `_dedupe_actions_by_path`

Чем проверял: (а) дифференциальный прогон старой и новой реализации — исчерпывающий перебор всех
последовательностей длиной 2 и 3 над алфавитом из 7 форм действия (два маркера на один путь, пустой
маркер, отсутствующий маркер, `create_if_missing`, второй путь, `merge_json`); (б) рандомизированный
фузз 20 000 композиций (до 9 действий, 4 пути, 5 вариантов маркера, 4 стратегии); (в) сквозной прогон
`render_for_codex` / `render_for_copilot` + `apply_actions` на диск поверх заранее созданного
пользовательского `AGENTS.md`.

### Где новая логика отличается от старой (исчерпывающе)

Ровно один класс расхождений: **один путь получает ≥2 действия с ≥2 различными непустыми
`marker_id`**. Тогда вместо одного склеенного действия возвращается k действий (k = число различных
маркеров), в порядке первого появления маркера. Всё остальное совпадает побитово.

Дифференциальный прогон: расхождений при ОДИНАКОВОМ числе действий — **0** (перебор n=2,3), то есть
содержимое никогда не переезжает из группы в группу, меняется только разбиение. Фузз 20 000:
потерянных фрагментов контента — **0**; случаев, когда новая выдала голый `write_file` туда, где
старая выдавала действие с маркером, — **0**.

Частные случаи, которые НЕ отличаются от старых (проверены прогоном):
- markerless-действие всегда прилипает к первой группе своего пути и никогда не создаёт вторую
  группу, если группа уже есть → безмаркерных групп на путь не больше одной, и она всегда первая;
- первый маркированный «усыновляет» безмаркерную группу → markerless не остаётся голым;
- `marker_id: ""` ведёт себя ровно как отсутствующий (`a.get("marker_id") or None`);
- один и тот же маркер в разных путях не склеивается (группировка сперва по пути);
- `merge_strategy` без маркера — совпадает со старой;
- 500 различных маркеров на один путь → 500 действий, контент цел и в исходном порядке.

### Инвариант #677 — сохранён (прогон, не чтение)

`render_for_codex` и `render_for_copilot` на композиции «markerless `rule_set` первым, затем пак лейна,
затем пак роли», поверх существующего `AGENTS.md` с пользовательским текстом:

- действий в `AGENTS.md` без `marker_id` — нет;
- тело `rule_set` уехало ВНУТРЬ секции лейна: `<!-- tacticum:iva-write-base -->\nRULE-BODY\n\nLANE\n<!-- /… -->`;
- пользовательский текст на диске уцелел, обе секции дописаны.

То же при обратном порядке (markerless последним) — прилипает к первой группе, голого `write_file` нет.

**Пред-существующая дыра, НЕ регресс:** если путь получает ТОЛЬКО markerless-действия (`rule_set` без
единого пака), результат — голый `write_file`, который затирает пользовательский `AGENTS.md`. Прогон
это показывает, но старая реализация вела себя так же — фузз подтверждает, что множество «голых»
путей у новой не выросло ни разу из 20 000.

### Находка 1 — разбиение не смотрит на `merge_strategy` · надо починить

`apps/backend/src/backend/catalog/domain/renderer.py:400-430`

Функция делит по маркеру ЛЮБЫЕ `write_file`, включая те, где два действия на один путь клиентом
не складываются:

- `create_if_missing` — клиент пропускает действие, если файл уже есть
  (`tests/e2e_install/oracles.py:87-89`). Прогон: два пака в `.codex/config.toml` с маркерами
  `tacticum:lane` и `tacticum:role` → на диске остался только `LANE-TOML`, `ROLE-TOML` **потерян
  молча**. Старая реализация отдавала одно действие с `'LANE-TOML\n\nROLE-TOML'`.
- `append_lines` — в клиенте ветки нет вовсе, действие падает в обычную перезапись. Прогон: два
  `repo_config` в `.gitignore` (`a:secrets`, `b:secrets`) → на диске только `B-LINES`, `A-LINES`
  **затёрт**. Старая отдавала `'A\n\nB'`.

Сегодня ни одна композиция сюда не попадает: разобрал все `templates/*/manifest.yaml` вместе с
`depends_on` — путей, куда при НЕ-`append_section` пишут два разных маркера, ноль; единственный путь
с двумя маркерами — `CLAUDE.md`/`AGENTS.md` у `iva-role-analyst`, и там `append_section`. Но
`.codex/config.toml` с `create_if_missing` + `marker_id: tacticum:<role>` несут 25 профилей
(`templates/iva-role-analyst/manifest.yaml:107-116` и аналоги), и первый же лейн, которому понадобится
свой кусок `config.toml`, тихо потеряет содержимое. Это латентно, но цена — молчаливая потеря, а
сторож, который бы её поймал, в этом же PR ослаблен (см. Вопрос 2, находка про `action_identity`).

Лечение по месту: делить только когда `merge_strategy == "append_section"`, иначе склеивать как
раньше — ровно тот контракт, который умеет клиент.

### Находка 2 — ключи групп не сталкиваются с `_unique_sentinel()` · подтверждено

Утверждение автора верно. `_unique_sentinel()` (`renderer.py:434-437`) возвращает
`__sentinel__<uuid4>` — символа `\x00` в нём нет по построению (hex + дефисы). Ключ группы всегда
содержит `\x00`. Множества не пересекаются. Проверил и вырожденный случай: путь, буквально равный
строке-сентинелу, даёт ключ `<sentinel>\x000` и живёт отдельно. Отображение `path → path\x00n`
инъективно (последний `\x00` однозначно отделяет счётчик, а счётчик — только цифры).

### Находка 3 — порядок действий · придирка

`renderer.py:421-424`: группы уходят в вывод в порядке создания, поэтому один путь может встретиться
в списке несколько раз и не подряд (прогон F: `[P/M1, merge_json, P/M2]`). Для `append_section` это
безопасно, downstream индексирует действия по `seq`, а не по пути
(`interface/mcp/tacticum_init_manifest.py:113-127`, `expected_action_count=len(actions)`), так что
учёт не ломается. Отмечаю только как то, на что нельзя опираться в будущих потребителях.

## Вопрос 2 — не ослаблены ли тесты

Все мутации гонял на ИЗОЛИРОВАННОЙ копии каталога
(`scratchpad/cv1/templates`) и через monkeypatch модулей — рабочее дерево не трогал: его в это же
время правит другой агент (см. предупреждение в конце).

### 1. `oracles.py:42-63` — `action_identity` + `marker_id` · **уточнение с одним конкретным ослаблением** · надо починить

Что ловит по-прежнему (прогон, сравнение старого и нового тождества на четырёх входах):

| вход | было | стало |
|---|---|---|
| дубль одной и той же секции (один маркер) | ловит | **ловит** |
| две безмаркерные доставки в один путь | ловит | **ловит** |
| лейн + роль, разные маркеры, `append_section` | ловит (ложно) | пропускает — так и задумано |
| **два `create_if_missing` в один путь, разные маркеры** | ловит | **пропускает** |

Последняя строка — реальная потеря. Прогон `render_for_codex` + `apply_actions`: два пака в
`.codex/config.toml` с разными маркерами → на диске только первый, второй пропущен как
`exists (create_if_missing)`, а `assert_unique_ingredients` при этом печатает OK. То есть дефект из
находки 1 Вопроса 1 остаётся невидимым для единственного оракула, который его видел.

Лечение: держать маркер в тождестве только для `append_section`; для остальных стратегий тождество
по пути, как раньше.

### 2. `test_role_modes_routed.py:134-161` — «пак роли ровно один» · **уточнение** · принято

Мутация (лейну выдан маркер роли, каталог-копия, полный прогон с БД):
`test_declared_modes_are_delivered_and_routed[claude-code-iva-role-analyst]` **падает** с
«в CLAUDE.md пишут несколько источников с ОДИНАКОВЫМ маркером». Сторож работает.

Два предела, которые стоит знать:

- **На codex тот же дефект не ловится** (в мутационном прогоне codex-вариант прошёл). Причина
  структурная: одинаковый маркер новая склейка объединяет в ОДНО действие, тест видит один пак и
  доволен. На диске при этом текст лейна оказывается внутри секции роли — ровно тот дефект, ради
  которого правился рендерер, только теперь с обратной стороны. Дыра узкая (нужно руками выдать
  лейну маркер роли), но заявленная в комментарии симметрия «одинаковый маркер ловится» на codex
  не выполняется.
- **Число писателей больше ничем не ограничено.** Старое `len(packs) == 1` заодно ловило лишний пак,
  приехавший из чужого лейна. Теперь любой второй пак со своим маркером проходит молча; частично
  прикрыто голденами, но голдены есть у 24 профилей из 67 (`tests/e2e_install/golden/`).

Отдельно: в рабочем дереве (ещё не в коммите) добавлен `assert all(markers)` —
`test_role_modes_routed.py:147-153`. Он закрывает дыру «писатель без маркера уедет голым
`write_file` и затрёт секцию роли на claude-code». Придирка к нему: «есть маркер» определяется
регуляркой `tacticum:[\w.-]+` (`:112`), поэтому пак с маркером другого неймспейса (в каталоге такие
есть — `iva-qa-tms-base:secrets`, `iva-qa-autotest-base:secrets`) будет объявлен «БЕЗ маркера».
Сегодня такие маркеры живут только в `.gitignore` и под сторож не попадают, но сообщение будет
врать, когда попадут.

### 3. `test_install_flow.py:1096-1116` — зеркальная половина `_IVA_WRITE_ROLES` · **уточнение, чистое усиление** · принято

Мутации на копии каталога:

сам не проверяет.
