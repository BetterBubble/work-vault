# triva как движок пайплайна генерации документов — проверка живыми вызовами

Разведка 2026-08-06. **Только прямой путь, без шлюза и без фолбэка в Google:**
`http://127.0.0.1:8790/v1` на прод-`helm` (SSH-туннель `helm → adp-jump → 10.0.196.14:9034`),
модель `/models/triva_llm_instruct`. Единственный фолбэк на этом эндпоинте —
`/models/triva_llm_instruct-backup`, то есть та же triva; наружу с него ничего не уходит
(фолбэк `tacticum/triva → tacticum/cheap` живёт в конфиге шлюза, а не здесь).
Read-only: на серверах ничего не менял, файлов не писал, ключи не выписаны.

Движок опознан по ответу: `system_fingerprint: vllm-0.23.0-fe03fd38` — под LiteLLM стоит vLLM 0.23.0.

---

## Главное в трёх строках

**triva умеет ВСЁ, что нужно агентному пайплайну: function calling, зрение с OCR, строгий JSON,
стриминг, реальные 128K контекста. Прошлая заметка `explore-nashi-modeli-2026-08-06` в части
«стриминга нет» — неверна, стриминг есть и работает.**
**Единственное узкое место — prefill на длинном входе: 106K токенов = 33 секунды ожидания.**
Генерация быстрая (58–115 ток/с), короткий запрос отвечает за секунду.

## 1. Function calling — ЕСТЬ, работает полный агентный цикл

Запрос с `tools` + `tool_choice: auto`, инструмент `get_weather(city)`:

```
finish_reason: "tool_calls"
tool_calls: [{"function":{"name":"get_weather","arguments":"{\"city\": \"Paris\"}"},
              "id":"chatcmpl-tool-a7da27748a14b7a4","type":"function"}]
content: null                     usage: prompt 77 / completion 15
```

**Выбор из двух инструментов — правильный.** Дал `get_weather` и `search_document`, спросил
по-русски «найди в реестре документ про требования к электропитанию стойки»:

```
tool_calls: [{"name":"search_document","arguments":"{\"query\": \"требования к электропитанию стойки\"}"}]
```

Взят нужный инструмент, необязательный параметр `limit` не выдуман, запрос переформулирован осмысленно.

**Полный round-trip тоже работает** — это важнее самого факта вызова: агентный цикл требует, чтобы
модель ПОТРЕБИЛА результат инструмента, а не только его позвала.

```
шаг 1 (0.4 c): tool_calls = get_gost_clause({"clause":"2.3","gost":"34.602"})
шаг 2 (0.5 c): скормил роль "tool" с текстом пункта →
   «Согласно ГОСТ 34.602, пункт 2.3 требует следующего: **«Техническое задание оформляют
    на листах формата А4 без рамки, основной надписи и дополнительных граф к ней»**.»
```

Ответ построен на данных инструмента, а не на памяти модели. Цикл замыкается.

## 2. Зрение — ЕСТЬ, включая чтение текста с картинки (OCR)

Сгенерировал PNG прямо на сервере (чистый stdlib, без промежуточных файлов) с надписью `ABC 42`,
432×84, отправил как `image_url` c `data:image/png;base64`:

```
png bytes: 319   time 0.3s   usage: prompt 293 / completion 5
ОТВЕТ: ABC 42
```

Дословно и мгновенно. На однопиксельной картинке (красный 1×1) модель тоже отвечает по существу —
«однотонный розовый (или коралловый) квадрат», `prompt_tokens` вырастает до 278, то есть картинка
реально уходит в модель как ~256 токенов, а не игнорируется.

**Практическая оговорка, на которую напоролся.** PNG, сделанный macOS-утилитой `sips`
(620×150, с ICC-профилем и XMP-чанками), эндпоинт отверг:

```
litellm.BadRequestError: OpenAIException - Failed to load image:
broken data stream when reading image file
```

Тот же путь с чистым PNG отработал сразу. То есть **декодер на стороне модели придирчив к формату,
и пайплайн обязан нормализовать картинки перед отправкой** (перекодировать через Pillow в
простой RGB-PNG/JPEG). Что именно триггерит отказ — ICC-профиль, XMP или что-то ещё — **не проверено**,
разбирать нечем: Pillow нет ни на `helm`, ни на моей машине.

**Не проверено:** OCR кириллицы и мелкого текста реального скриншота — мой генератор PNG умеет
только латиницу и цифры, а реальный скриншот отвалился по причине выше.

## 3. Структурированный вывод — ЕСТЬ, обе формы

`response_format: {"type":"json_object"}`, попросил схему `{"разделы":[{"номер","название"}]}`:

```json
{"разделы":[{"номер":"1","название":"Общие положения"},
            {"номер":"2","название":"Технические требования"},
            {"номер":"3","название":"Порядок испытаний"}]}
```

`response_format: {"type":"json_schema", strict: true, additionalProperties: false}` — тоже принят,
вернул ровно `{"nomer":"4","nazvanie":"Требования к надёжности"}`. Схема соблюдена, лишних полей нет,
преамбулы вокруг JSON нет.

## 4. Скорость — числа

Короткий запрос (вход 140 токенов, выход ~125):

| Режим | TTFT | Полное время | Генерация |
|---|---|---|---|
| non-stream, прогон 1 | — | 1.13 с | 109 ток/с |
| non-stream, прогон 2 | — | 1.14 с | 114 ток/с |
| stream, прогон 1 | **0.08 с** | 1.02 с | 114 ток/с |
| stream, прогон 2 | **0.09 с** | 1.02 с | 116 ток/с |

Длинный вход — **холодный** prefill (замер сделан ДО любого другого обращения к этому тексту,
срезы корпуса непересекающиеся):

| Вход | prompt_tokens | Холодный TTFT | Скорость prefill | Генерация | Повтор того же входа |
|---|---|---|---|---|---|
| 95 тыс. симв. | 25 026 | **3.18 с** | 7 860 вх.ток/с | 83 ток/с | 0.32 с |
| 190 тыс. симв. | 44 266 | **7.52 с** | 5 888 вх.ток/с | 77 ток/с | 0.47 с |
| 390 тыс. симв. | 106 113 | **33.21 с** | 3 195 вх.ток/с | 58 ток/с | 0.72 с |

Три вещи, которые из этой таблицы следуют.

1. **Prefill деградирует нелинейно:** вчетверо больше входа — вдесятеро дольше ожидание.
   На 100K+ пользователь ждёт полминуты до первого символа.
2. **Prefix-кэш есть и он огромной силы** — повтор того же входа даёт 0.3–0.7 с вместо 33 с.
   Для пайплайна это прямая подсказка: держать неизменную часть промпта (образец ГОСТ, инструкция,
   исходный документ) в НАЧАЛЕ и не менять её между запросами — тогда платишь за prefill один раз.
3. **Генерация от длины контекста почти не страдает** — 58 ток/с против 115 на коротком.

Оговорка о методе: первый заход я сделал неверно — считал `prompt_tokens` отдельным вызовом
ПЕРЕД замером, чем прогревал кэш, и получил красивые, но ложные 0.9 с на 125K. Таблица выше — из
перезамера, где отдельный вызов идёт ПОСЛЕ. Числа первого захода отброшены.

## 5. Реальный контекст — 131 072, честные, без молчаливой обрезки

- Реально принял и обработал **125 365** токенов в одном запросе.
- **Needle-тест:** в текст на 98 882 токена вставил в СЕРЕДИНУ метку `кодовое слово — ЯКОРЬ-7413,
  ответственный Кузнецов`. Ответ: `Кодовое слово: ЯКОРЬ-7413, ответственный: Кузнецов.` Середина
  длинного контекста реально читается, а не игнорируется.
- Превышение лимита даёт **честную ошибку 400**, а не тихое обрезание:
  `litellm.ContextWindowExceededError: … maximum context length is 131072 tokens.
  However, you requested 50 output tokens and your prompt contains at least 131023 input tokens`.

Для задачи техписа это значит: ГОСТ-документ целиком + образец + инструкция влезают в один запрос,
и если не влезут — узнаешь ошибкой, а не порчей текста.

## 6. Качество на нашей задаче — годится как черновик под вычитку

Дал разговорный русский текст («мы сделали так, что сервис сам следит за туннелем…») и системный
промпт «технический писатель, ГОСТ 19/34, сухой безличный стиль, нумерация 4.1/4.2, никакого «мы»».
**2.0 с, 235 токенов выхода.** Фактический ответ целиком:

> **4 Требования к надёжности**
>
> 4.1 Система должна обеспечивать непрерывность соединения с целевой моделью посредством
> автоматического контроля состояния туннеля.
>
> 4.2 При обнаружении разрыва соединения система должна выполнять повторную попытку установления
> туннеля. Количество повторных попыток не должно превышать трех. Интервал между попытками
> устанавливается равным 5 с.
>
> 4.3 При невозможности восстановления соединения по истечении трех попыток система должна выполнить
> следующие действия:
> 4.3.1 зафиксировать ошибку соединения в журнале регистрации событий;
> 4.3.2 переключить обработку запросов на резервную модель.
>
> 4.4 Время ожидания ответа от модели должно составлять не более 45 с. При превышении указанного
> времени запрос классифицируется как завершившийся с ошибкой.
>
> 4.5 Журналирование событий должно осуществляться в формате JSON. Запись в журнале должна содержать
> следующие сведения:
> 4.5.1 время выполнения каждого запроса;
> 4.5.2 количество затраченных токенов.

Что сделано правильно: «мы» вычищено полностью, стиль безличный, размерности оформлены по-госту
(`5 с`, `45 с` — с пробелом и без точки), многопунктовые перечисления развёрнуты в подпункты
4.3.1/4.5.1, ни одного оценочного слова, ни одного добавленного факта. Все пять фактов исходника
на месте.
Что придётся править человеку: сплошное «должна» — это стиль ТЗ по 34.602, и для другого вида
документа (например, описания применения по 19.502) редактор его снимет. Заголовок раздела модель
повторила в теле ответа.
Вывод: **как черновик под вычитку — годится**, экономит основную часть работы.

## 7. Стриминг — ЕСТЬ. Прошлая заметка ошибалась

`"stream": true` отдаёт нормальный SSE потоком, `chat.completion.chunk`, по токену в `delta.content`:

```
data: {"object":"chat.completion.chunk","choices":[{"delta":{"role":"assistant","content":""}}]}
data: {"object":"chat.completion.chunk","choices":[{"delta":{"content":"1"}}]}
data: {"object":"chat.completion.chunk","choices":[{"delta":{"content":","}}]}
```

Первый чанк — через 0.08 с. Утверждение «стриминг нет, ответ отдаётся целиком»
(`explore-nashi-modeli-2026-08-06`, §1, со ссылкой на `20-Architecture/Gemini→Gemma (triva)…:22`)
**опровергнуто живым вызовом**. Похоже, это устаревшая запись про прежнюю установку: сейчас под
LiteLLM стоит vLLM 0.23.0. Для UX пайплайна это важно — 33 с prefill можно прикрыть стримингом,
и пользователь увидит текст сразу, как только начнётся генерация.

## ВЕРДИКТ

**triva годится как движок пайплайна генерации документов. Функционально она закрывает все
требования агентного цикла — блокеров нет.**

Умеет: **function calling** с корректным выбором из нескольких инструментов и полным round-trip
(вызов → результат → обоснованный ответ); **зрение с точным OCR** — задача описания скриншотов
интерфейса решается локально, наружу картинки отдавать не нужно; **строгий структурированный
вывод** обеих форм (`json_object` и `json_schema` со `strict`); **стриминг**; **честные 128K
контекста** с рабочей серединой и явной ошибкой при переполнении; **приличный русский ГОСТ-стиль**
черновиком.

Не умеет / где узко:
1. **Prefill на длинном входе — единственное реальное узкое место.** 106K токенов = 33 с до первого
   символа, и деградация нелинейная. Лечится архитектурно: неизменную часть промпта держать в начале
   (prefix-кэш даёт 0.3–0.7 с на повторе) и прикрывать ожидание стримингом. Гонять по 100K на каждый
   чих — упрёшься в минуты.
2. **Придирчивый декодер картинок.** PNG от macOS `sips` отвергнут «broken data stream»; изображения
   надо нормализовать перед отправкой.
3. **Она по-прежнему не наша** — железо ИВА, доступ через туннель, квот и приоритетов не видно.
   Это не про возможности, а про надёжность, и в этой разведке не проверялось.

**Проверено:** 7 пунктов задания, ~25 живых вызовов на прямой путь `127.0.0.1:8790` с прод-`helm`:
`tools` (1 и 2 инструмента, round-trip), `image_url` (1×1 и сгенерированный PNG с текстом),
`json_object` и `json_schema`, `stream`, 8 замеров латентности (короткий ×4, длинный ×3 холодных
+ 3 тёплых), needle-тест на 98 882 токена, проба превышения лимита, ГОСТ-переписывание.

**Данные:** TTFT короткий — **0.08 с**; полное время короткого запроса — **1.0–1.14 с**; генерация —
**115 ток/с** (короткий контекст) … **58 ток/с** (106K контекста); холодный prefill — **3.2 с**
на 25K, **7.5 с** на 44K, **33.2 с** на 106K; prefill-скорость — **7 860 … 3 195** вх.ток/с;
тёплый кэш — **0.32–0.72 с**; максимум принятого входа — **125 365** токенов; жёсткий лимит —
**131 072**; картинка в промпте — **~256** токенов; ГОСТ-раздел на 235 токенов — **2.0 с**;
движок — **vLLM 0.23.0**.

**Подтверждение (команды и вывод):**
```
helm$ curl 127.0.0.1:8790/v1/models                  → 200, /models/triva_llm_instruct (+ -backup)
helm$ POST tools=[get_weather]                       → finish_reason=tool_calls, {"city": "Paris"}
helm$ POST tools=[get_weather, search_document] (ru)  → search_document {"query":"требования к электропитанию стойки"}
helm$ POST role=tool с текстом пункта                → ответ построен на данных инструмента
helm$ POST image_url (PNG 432x84 "ABC 42")           → "ABC 42", 0.3 c, prompt_tokens=293
helm$ POST image_url (PNG от sips 620x150)           → 400 Failed to load image: broken data stream
helm$ POST response_format=json_object               → валидный JSON по заданной схеме
helm$ POST response_format=json_schema strict        → {"nomer":"4","nazvanie":"Требования к надёжности"}
helm$ POST stream=true                               → SSE chat.completion.chunk, первый чанк 0.08 c
helm$ POST 390K симв. (холодный)                     → prompt_tokens=106113, TTFT=33.21 c, всего 34.01 c
helm$ POST тот же вход повторно                      → TTFT=0.72 c (prefix-кэш)
helm$ POST needle в середине 98882 токенов           → "Кодовое слово: ЯКОРЬ-7413, ответственный: Кузнецов."
helm$ POST 600K симв.                                → 400 ContextWindowExceededError, max 131072,
                                                         prompt contains at least 131023 input tokens
```

**НЕ проверено / осталось:**
1. **OCR кириллицы и реального мелкого скриншота интерфейса** — сгенерированный мной PNG содержит
   только латиницу и цифры, а настоящий скриншот отвергнут декодером (§2). Нужен Pillow, чтобы
   перекодировать картинку в приемлемый формат; на `helm` и на моей машине его нет.
2. **Что именно в PNG триггерит «broken data stream»** — ICC-профиль, XMP, разрядность. Разбирать нечем.
3. **Параллельная нагрузка и квоты.** Все замеры — одиночные последовательные запросы на, судя по
   скорости, свободной машине. Сколько даст triva под несколькими одновременными пользователями и
   не подвинет ли ГОСТ-нагрузка ВКС-стенограммы ИВА — не мерил, ограничителя нагрузки не видел.
4. **Стабильность на длинной дистанции** — падений за сессию не было, но сессия короткая; в `helm`
   под падения triva заведён обходной механизм, значит они случаются.
5. **Тюнинг качества под ГОСТ** — один тест на одном абзаце. Полноценная оценка на разных видах
   документов (19.502, 34.602, ПМИ) не делалась.
