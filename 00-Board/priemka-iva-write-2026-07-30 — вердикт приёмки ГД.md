# Приёмка iva-write — ВЕРДИКТ ПО ЦЕЛИ: НЕТ

Приёмка ГД двумя независимыми агентами (норма от 29.07). Ниже — вердикт **агента цели**
(сверка с постановкой). Вердикт агента безопасности прода допишется сюда же.

Проверка велась **по первоисточникам**: сырьё созвона, план, досье, материалы 30.07 и код ветки
`feat/iva-write-keystore` (HEAD `49aeb3d`) — отчёт лида был объектом проверки, а не источником.

## Суть вердикта

**Инженерное ядро сделано как просили, и заявленные свойства подтверждаются кодом.** Но
**интерфейс для человека — бот и инструкция, то есть ровно то, что руководитель назвал выходом
работы, — не работает по описанному им пути.** Дефекты известны внутри команды с 30.07 (их нашла
собственная сверка) и **не вынесены ни в отчёт, ни в текст PR**. Отчёт представляет работу
готовой к мержу и деплою.

## Блокирующее — без этого мержить нельзя

**Б1. Бот выдаёт первой ссылку, которая гарантированно будет отклонена.**
`interface/api/routers/bot_iva_write.py:179` — `sorted(client.configured_systems())` даёт
`["confluence","jira"]`. Через бота `subject_source=SOURCE_DECLARED`; в `_verify_identity`
(`application/iva_write.py:250-268`) Confluence почты не отдаёт никогда, привязки логина ещё нет
→ `identity_unverified`, доступ не сохраняется. Закреплено тестами
`tests/application/test_iva_write_consent.py:414-436` и `:463-497`, порядок — в
`tests/application/test_bot_iva_write.py:81-93`.
Противоречит дословному «бот кидает ссылку… по ней прошёл — можешь пользоваться» и требованию
инструкции «для человека не очень умного, но исполнительного»: такой человек открывает ссылки
сверху вниз. **Собственная сверка предложила чинить это текстом инструкции** («открывайте не по
порядку»), тогда как правка `sorted` → явный порядок `("jira","confluence")` снимает дефект целиком.

**Б2. Бот не умеет отзывать доступ, а инструкция обещает, что умеет.**
`application/bot_iva_write.py:81-86` — два намерения, всё кроме слов-статуса падает в
`INTENT_ACCESS`; слов `revoke`/«отозв» нет ни в одном из трёх файлов бота. Инструкция
([[instrukciya-iva-write-2026-07-29]], строка 183): «напиши боту "отозвать доступ". Доступ
перестанет работать сразу». Фактически бот пришлёт новые ссылки на выдачу. Противоречит критерию
приёмки собственного плана «отзыв гасит доступ».

**Б3. Инструкция не поправлена после того, как дефекты в ней нашли.**
[[sverka-instrukcii-iva-write-2026-07-30]] — 12 расхождений, три блокирующих, написана 30.07 11:36.
Файл инструкции по mtime не менялся с 29.07 16:55. Третий блокирующий: `HELM_RESOLVE_URL` и
`HELM_RESOLVE_SERVICE_KEY` не названы ни разу, без них все ручки отдают 503
(`routers/iva_write.py:97-102`), а диагностика шага 6 уводит не туда.

**Б4. Отчёт и текст PR не содержат ничего из Б1–Б3.** [[report-iva-write]] (mtime 30.07 11:37 —
на минуту позже сверки): «Следующий шаг: PR → мерж → деплой»; в «Что заблокировано» только ключи
ботов и Д1. [[pr-iva-write-2026-07-30]] описывает бота как рабочий, раздел «Чего в этом PR НЕТ»
дефекты бота не упоминает. Противоречит норме собственного плана §5а: «что НЕ доказано — отдельным
списком, честно».

## Обязательное перед докладом руководителю

**О1. Допущение о совпадении логинов проверено на ОДНОЙ технической учётке, а подано как
подтверждённое.** Сверка личности держится на равенстве Jira `name` = Confluence `username`
(`application/iva_write.py:226-233`). [[probe-iva-prava-2026-07-30]] §3 **сам оговаривается**:
«проверено на одной учётке; для полной уверенности нужна вторая, живого человека» — и это
`monakhov-tech`, техническая, не сотрудник. В отчёте это стало «ПОДТВЕРЖДЕНО», в PR — «подтверждена
живой проверкой». Оговорка потеряна в обоих. Проверка второй, живой учётки — один GET в каждую
систему.

**О2. Текст отказа `login_mismatch` обвиняет человека:** «Согласие выдано под другой учётной
записью». Это может быть штатным расхождением директории, а обходного пути нет — в роутере ровно
пять ручек, ручной привязки среди них нет. Поведение fail-closed правильное, формулировка — нет.

**О3. Требование плана §3.3 (ручной путь привязки, когда идентичность не сводится к почте
автоматически) не выполнено и нигде не помечено невыполненным.**

**О4. Автоопределение почты ботом не подтверждено.** Работает только если платформа пришлёт почту
в `login` (`routers/bot_iva_write.py:234-237`), а план v2 §1 сам фиксировал «почты в теле вебхука
нет», платформа за 90 дней ни разу не достучалась. Значит реально сработает ветка «спросить в
чате» = `SOURCE_DECLARED` = сломанная ветка из Б1.

# Вердикт по безопасности прода: НЕТ — не в текущем виде

Второй агент приёмки, независимо. Код к проду годен: новые настройки все fail-closed, миграции
аддитивны, у **всех 14 новых ревизий рабочая `downgrade`** (не `pass`), секретов в git нет,
существующий код тронут на 17 строк. **Проблема не в коде, а в обвязке деплоя.**

## Риск №1 — `deploy.sh` стирает боевой граф. Разобрано по строкам

- `scripts/deploy.sh:23` → `SOURCE="${1:-synthetic}"`
- `scripts/deploy.sh:24` → `SEED="${SEED:-1}"`
- `scripts/deploy.sh:54` → запускает `seed_db.py --source "$SOURCE"`
- `scripts/seed_db.py:150` → `clear_graph(session, tenant)`; `clear = not args.no_clear`, дефолт
  **True**, а `--no-clear` из `deploy.sh` не передаётся никогда
- `infrastructure/db/repository.py:1406-1407` → `DELETE` по списку `_CLEAR_ORDER`
  (`repository.py:1379-1392`), **12 таблиц**: Annotation, Dependency, Assignment, Signal,
  SalesLink, SalesInitiative, BlockTeam, Initiative, Block, Goal, PersonEmail, Person.

DELETE тенант-скопнутый — чужой тенант не заденет, но **внутри тенанта сносит всё
перечисленное**, затем заливает случайную синтетику.

**Защит на этом пути ровно ноль.** Условия по источнику нет — чистит при `synthetic`, `csv` и
`real` одинаково. Нет подтверждения, нет dry-run, нет проверки «это прод», нет проверки «в
таблицах уже есть данные». Единственный способ не выстрелить — знать заранее и передать `SEED=0`.

**Отягчающее:** `README.md:118` подаёт разрушительную форму **первой** в списке команд —
`bash scripts/deploy.sh` с комментарием «собрать образ, поднять стек, миграции, сид синтетикой».
Оператор, идущий по README сверху вниз, сносит прод.

**Дефект лежит на `main`, ветка ни при чём** — подтверждено фактически: `git log --follow` по
`deploy.sh` даёт **один коммит** (`8c6251f`), файл создан с этими дефолтами и с тех пор не
менялся. Под этой миной ходили всё время.

## Риск №2 — восстанавливаться после №1 нечем

`git grep` по `pg_dump|pg_restore|бэкап|backup` в ветке — **ни одного механизма бэкапа БД**.
Упомянутый в отчёте `.env.bak-2026-07-30-preiva` — копия файла окружения, **не базы**.
Если `clear_graph` отработает, восстанавливать не из чего. **Именно поэтому вердикт «нет»:
риск №1 необратим.**

## Откат — по слоям, подтверждённость разная

- **Схема БД — подтверждена кодом.** Все 14 ревизий имеют рабочую `downgrade` с реальными
  `drop_column`/`drop_index`; merge-ревизия схему не трогает. Команда:
  `alembic downgrade hrd224_allure_activity`.
- **Код — откат есть, но дорогой.** `docker-compose.prod.yml:31` → `build: .`: образ собирается
  локально, **без тега и без реестра**, предыдущего образа не существует. Откат = чекаут прежнего
  sha + полная пересборка, то есть минуты простоя, а не переключение тега.
- **Данные — отката нет вообще** (см. риск №2).

## Прочие риски

- **Новый внешний образ** `ghcr.io/sooperset/mcp-atlassian:0.23.0` (`docker-compose.prod.yml:134`,
  файл **в диффе ветки**). `up -d --build` его тянет; при закрытом egress compose прервётся на
  середине. Что egress ограничен — видно из самого репозитория: воркер гоняет трафик через
  локальный xray-прокси, а docker-демон переменные из systemd-юнита не наследует.
- `.env.example` **не обманывает оператора**: проверено, что `KeystoreKeyError` бросается лениво
  (`keystore_crypto.py:134`) и перехвачен в трёх точках входа с отдачей 503
  (`routers/iva_write.py:162`, `routers/iva_internal.py:108`, `mcp/iva_write_surface.py:357`).
  Правка отчёта обоснована.
- **Секреты чисто:** скан добавленных строк по паттернам и по высокой энтропии дал три совпадения,
  все — тестовые фикстуры. Файлов `.env`/`.pem`/`.key` в диффе нет. `cryptography>=43` зафиксирована
  в `uv.lock` — `uv sync --frozen` не сломается.
- **Коллизий маршрутов нет**, новых ошибок линтера ветка не вносит.

## Безопасный порядок деплоя — `deploy.sh` в нём не участвует

1. **Дамп боевой БД** (`pg_dump -Fc`) и проверка, что файл ненулевой — **до всего остального**.
2. Зафиксировать точку отката: `git rev-parse HEAD` и `alembic current` (ожидается
   `hrd224_allure_activity`).
3. `docker pull ghcr.io/sooperset/mcp-atlassian:0.23.0` — убедиться, что образ тянется, **до**
   того как трогать стек.
4. Чекаут merge-коммита → `docker compose -f docker-compose.prod.yml up -d --build`.
5. Миграции руками: `alembic upgrade head` → `mrg350_iva_write_pmb`.
6. **`seed_db.py` не запускать ни с какими флагами.**

**Откат:** `alembic downgrade hrd224_allure_activity` → чекаут прежнего sha → пересборка; данные —
из дампа шага 1.
