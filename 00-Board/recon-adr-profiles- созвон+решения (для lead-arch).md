## 1. Пересечение и отделяемость частей профилей (анализ / QA / разработка)
- **Профили ПЕРЕСЕКАЮТСЯ, но части ОТДЕЛЯЕМЫ** — это прямой материал для ADR-концепта (созвон 23.07).
- Выделяемые переиспользуемые части: **анализ / QA / разработка**.
- Профиль аналитика пишет **всю аналитику**; разработчик может по ней разрабатывать И **сам написать юз-кейс**; при необходимости — **«залезть и провалидировать» чужую часть**.
- Требование: части должны быть **отделимы и переиспользуемы между профилями**.
- Стэк-агностичное НЕ дублировать между лейнами: авторинг тест-кейсов (`tests-authoring`) + покрытие (`requirement_tests`) живут в **analysis**, шарятся всеми QA-ролями (из qa-profile-model).
- **Два слоя QA:** (1) первый слой — тест-дизайн/написание тестов БЕЗ генерации кода (это то, что уже есть у аналитиков) → уходит к аналитику; (2) второй слой — 9 скиллов + 3 субагента → генерация/проверка/автозапуск/валидация автотестов.

## 2. Ownership (кто пишет / ревьюит / валидирует)
- **РЕШЕНО (approved 23.07):** тест-кейсы пишут **аналитики** (расширенные юз-кейсы + тест-кейсы); **QA/тестировщики дополняют на ревью** (неочевидные сценарии). Авторинг с нуля — НЕ у QA.
- Аналитику дать скилл «расширенные юз-кейсы + тест-кейсы» + скилл **ревью фичи-реквеста**. У аналитиков «первый слой почти весь уже есть» → добавить дёшево («первый слой бесплатный»).
- **Профиль QA (`iva-role-qa`)** = исполнение/автоматизация автотестов (9 скиллов + 3 субагента) + **ревью-дополнение** TC (не авторинг). `tests-authoring` живёт у аналитика, шарится.
- Валидация чужой части — механизм **«залезть и провалидировать»** (разработчик валидирует аналитику и наоборот); должен быть заложен в модель.
- Обоснование ownership — **пирамида тестирования**: максимум тестов на юнит-этапе; инфа (сценарии/TC) должна быть в фичер-реквесте ДО разработки, чтобы разработчик покрывал юнит-тестами. TC в конце от QA — поздно.
- Целевое видение (Дима Солонко): аналитики пишут всё, тестировщикам остаётся **реализовать** тест-кейсы.

## 3. Пайплайн аналитик→QA→разработчик (как описан/подразумевается)
Явной пошаговой схемы в заметках нет, но подразумевается:
1. **Аналитик** пишет аналитику + расширенные юз-кейсы + тест-кейсы (тест-дизайн, первый слой) → всё в **фичер-реквест ДО разработки**.
2. **QA/тестировщик** на ревью **дополняет** TC (неочевидные сценарии) + скилл ревью фичи-реквеста; далее — исполнение/автоматизация (9 скиллов + 3 субагента: генерация/проверка/автозапуск/валидация автотестов, сколько прошло).
3. **Разработчик** разрабатывает по аналитике, покрывает **юнит-тестами** (по TC из фичер-реквеста); может сам написать юз-кейс; может «залезть и провалидировать» чужую часть.
- Ключевой инвариант хендоффа: **интеграция с аналитиком без разрыва процесса**.
- Статусы согласования пока — в **Project** (трекер); долгосрочно — минимальная BPMS (см. §6).
- Открытый вопрос: как «спрямить» процесс (аналитик пишет TC) без BPMS — дать широкие возможности всем, приучать к правильному подходу постепенно.

## 4. Единый механизм сборки профилей (три→один)
- Сейчас **ТРИ механизма сборки профилей** → цель **мигрировать в ОДИН**.
- **Глеб** закончил интеграцию основных; надо протестировать + спланировать миграцию.
- **Доделывает Дима Солонко** за Глебом и **Димой Лебедевым** (НЕ Саша).
- **ГАРДРЕЙЛ для нашей работы:** строить QA-профиль (и модель профилей) так, чтобы он **ложился на целевой единый механизм — чтобы за нами не пришлось доделывать**. Посмотреть, как именно Дима Солонко сводит, и **следовать канону**.
- Деталей внутреннего устройства целевого механизма в заметках НЕТ — только факт «три→один» и владелец. (пробел для ADR — нужно изучить у Д.Солонко).
- Смежный технический канон профилей есть в kit: профиль выбирается человеком в анкете `base:install` одним полем `[capacity].profile` (0/1/2), смена = правка поля + карта ролей + перерендер. Неясно, тот ли это «механизм», что сводит Солонко (kit — это upstream QA-скиллов ИВА/Женя, а не обязательно tacticum-механизм сборки ролей). **Не смешивать** без проверки.

## 5. «Дырка» / лёгкая опция под общие/разделяемые части
- Сделать **«дырку» (лёгкую опцию)** под **разделяемые/переиспользуемые части** профилей — точка интеграции QA-профиля с аналитиком **без разрыва процесса**.
- Смысл: общие части (напр. `tests-authoring`, покрытие) не дублировать, а подключать через эту опцию из analysis/шаренного слоя.
- Строить на базе скиллов команды **Брейкина (Никита)** — команда уже привыкла/использует.

## 6. BPMS / фиксация статусов согласования (долгосрочно)
- Пока статус — в **Project**; долгосрочно — **минимальная BPMS для фиксации статуса**.
- Видение Димы Солонко (3 шага, смежное, не наша прямая задача, но контекст для ADR):
  1. Нарисовать **BPMN** процесса разработки (роли/согласования).
  2. Внедрить как **веб-интерфейс** (продукты/ключевые видят по фиче все решения + артефакты, согласовывают).
  3. **a-la Slack**: фича → авто-группа + бот, который **фиксирует статус согласования** («какая гипотеза принята/утверждена», не суммаризация). IVA-чат уже поддерживает агентов.
- Боль-пример: фича Диск — Тарасова возвращается с уже обсуждёнными 9 вопросами; Медведев не понимает статус.
- Для ADR: закладывать **машиночитаемые статусы согласования** частей профиля/артефактов, чтобы легли в будущую BPMS/бота.

## 7. MCP и кто какими тулами пользуется
- Своего **QA-MCP нет**. QA-лейн: `iva-write` (из iva-write-base) + `tacticum-mcp`/`context7` (core). Allure/TestOps — **локально (allurectl/glab/playwright-cli + модуль `tools/testops` в one-web), НЕ MCP**. `mcp_server_spec` для QA не нужен.
- Аналитик (helm-analyst MCP, из системного контекста) — тулы `requirement_tests` (покрытие требования автотестами из Allure TestOps), `nearest_spec`, `gap_questions`, `who_to_involve` и т.п. `requirement_tests` — кандидат в шаренный analysis-слой (сейчас QA его не дают — resheniia Трек B).
- kit (upstream QA-скиллов, ИВА/Женя): кросс-провайдерный маркетплейс плагинов **Claude Code + Codex**. Вызов встречной роли — только через обёртку `invoke_role` (`dispatch:invoke`), руками `claude -p`/`codex exec` не вызывают. `tms:read` — read-only порт Allure TestOps, зовётся всеми. 3 субагента craft (`codebase-analyst` read-only Read/Glob/Grep; `dom-explorer` — единственный с браузером Bash/Read/Write; `code-writer` Read/Edit/Write/Glob/Grep/Bash) — те самые, что разблокируют write/batch/fix.
- Профили ёмкости kit `[capacity].profile`: **0** — Codex-only; **1** — CC только в роли reviewer (кросс-провайдерность незаменима); **2** — CC-полный (fog_writer/scout=claude). Деградация: базовый носитель каждой роли — Codex, при недоступности Claude тихий откат с событием `degraded`.

## Риски / пробелы для ADR
- **Терминологическая коллизия «механизм сборки профилей»:** tacticum-механизм (Солонко, три→один) vs kit `[capacity].profile` (ИВА/Женя). В заметках это РАЗНЫЕ вещи; не отождествлять без проверки у Солонко.
- **Нет деталей целевого единого механизма** — только владелец и гардрейл. Нужна разведка «как Солонко сводит».
- **Пайплайн явно не расписан** — реконструирован из решений; хендоффы/статусы согласования не формализованы (пока Project, потом BPMS).
- kit-репо `git.hi-tech.org/ivaqa` — **доступа нет** (нужен PAT read_repository / деплой-ключ); детали профилей взяты из уже распакованного архива `kit-main` в recon-kit-full.
