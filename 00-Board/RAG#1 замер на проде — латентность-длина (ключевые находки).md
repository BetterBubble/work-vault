# RAG#1 замер на проде helm (2026-07-20, ГД напрямую по SSH)

Замер делал ГД сам через ssh-manager (алиас `helm`, контейнер `helm-helm-1`), т.к. делегированный воркер дважды завис на «ожидании» вместо отдачи чисел. Golden `/app/golden_iva_rag1.json` (1306 кейсов).

## 🔴 Латентность — узкое место = РЕРАНКЕР, не ретрив (разворот плана)
Разбивка по стадиям (пробники в контейнере, warm-переиспользование клиента):
- **EMBED (Gateway bge-m3): ~63мс** · **QDRANT: ~22мс** · **MEILI: ~21мс** → `search.search()` целиком ~**106мс**. Ретрив ТРИВИАЛЕН.
- **RERANK (bge-reranker-v2-m3 через Gateway): ~1200–1560мс** (mean, p90 ~1.4–1.9с). **Это и есть латентность.**
- Полный eval-путь `DocsSearchRetriever.retrieve` (search+rerank, limit=30): **mean 1246мс, p90 1424мс** (чисто).
- ⚠️ `docs_rerank_enabled = **True**` на проде (`.env`) — план ошибочно считал реранк выключенным (дефолт False, но прод его включает).

**Артефакт первого замера:** `docs_eval --limit 50` показал retrieve_latency mean **4550мс / p95 11 281мс** — раздуто в ~3.6×, т.к. прогон шёл ОДНОВРЕМЕННО с осиротевшим `--limit 200` прогоном зависшего воркера (оба долбили Gateway-реранк). Осиротевший прогон убит. Чистое число — ~1.2с/запрос.

### Следствия для плана
- **Ф1b (параллелить Qdrant∥Meili) для скорости ПОЧТИ БЕСПОЛЕЗЕН** — экономит ~20мс из ~1200. Оставить как гигиену или отбросить.
- **Настоящий рычаг латентности — реранкер.** Варианты: реранкать меньше кандидатов (cap входа ~20 вместо CANDIDATE_K=60), более быстрый rerank-тир, условный реранк. Кэш — пользователь запретил.
- **Тензия с Ф2:** confidence-гейт clarify опирается на КАЛИБРОВАННЫЙ скор реранка (rerank ON = откуда берётся confidence). Реранк нельзя просто выключить — он кормит и качество, и clarify-гейт. Снижать стоимость, не убирать.
- Качество ретрива хорошее: **recall@5 0.96, MRR 0.90, ndcg@5 0.91** (не трогать).
- `answer_in_context=0.00` по всем срезам — golden БЕЗ эталонных ответов (judge-качество не считается; известный гэп).
