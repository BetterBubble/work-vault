# Что реально может учётка `monakhov-tech` — проверено живьём 30.07

Только GET, ничего не создавалось и не менялось, POST/PUT/DELETE не отправлялись вообще.
Ход: сервер `helm` → контейнер `helm-helm-1` → SSH-туннель `172.18.0.1:8443`, различение систем
по `Host`/SNI. Jira — Basic `monakhov-tech`, Confluence — Bearer из `HELM_RAG2_CONFLUENCE_TOKEN`.
Значения секретов не выводились.

Прежняя запись «проверял четырежды 29.07, последний раз 18:25» — **переподтверждена сегодня**:
не изменилось ничего, права не выданы.

*(Первая попытка шла воркером и не состоялась: у него в контексте не оказалось MCP-инструментов,
а прямой `ssh` закрыт deny-правилом. Правила не трогали — прогнал тимлид, у которого доступ есть.)*

## Главное в одну строку

**Регистрация OAuth-клиента требует именно System Administrator — это сказал сам сервер
заказчика, дословно, в обеих системах.** В рамках OAuth обхода нет. Зато выяснилось, что путь
вообще без администратора существует и работает (§5).

## 1. Кто мы и что можем — Jira

`GET /rest/api/2/myself` → **200**

| Поле | Значение |
|---|---|
| `name` | `monakhov-tech` |
| `key` | `JIRAUSER32317` |
| `displayName` | `Monakhov-Tech` |
| `emailAddress` | **`monakhov-tech@iva.ru` — непустой** |
| `active` | `true` |

`GET /rest/api/2/mypermissions` → **200**, прав со значением `true` — **54 штуки**.

| Право | Есть |
|---|---|
| `SYSTEM_ADMIN` | **нет** |
| `ADMINISTER` | **нет** |
| `ADMINISTER_PROJECTS` | **нет** |
| `CREATE_ISSUES` / `CREATE_ISSUE` | да |
| `EDIT_ISSUES` / `EDIT_ISSUE` | да |
| `ADD_COMMENTS` / `COMMENT_ISSUE` | да |
| `CREATE_ATTACHMENTS` | да |
| `DELETE_ISSUES` | да |
| `TRANSITION_ISSUES`, `ASSIGN_ISSUES`, `LINK_ISSUES`, `MOVE_ISSUES` | да |

**Вывод:** учётка полноценно пишет в Jira, но админских прав нет ни одного уровня. Наш режим
«только чтение» для неё — договорённость, а не ограничение прав (фиксировалось 28.07,
подтверждено снова).

## 2. Административные эндпоинты — и разница формулировок, которая всё решает

| Запрос | Jira | Confluence | Дословно в ответе |
|---|---|---|---|
| `/rest/oauth2/latest/client` | **403** | **403** | «Client must be authenticated as a **system administrator** to access this resource» |
| `/rest/applinks/1.0/applicationlink` | 401 | 401 | «Ресурс доступен только администратору» / «Only an admin can access this resource» |
| `/rest/applinks/3.0/applinks` | 403 | 403 | «Вам нужно быть **администратор**…» / «You need to be an **administrator**…» |
| `/rest/api/2/application-properties` | 403 | — | «must be authenticated as an **administrator**» |
| `/rest/api/audit` | — | 403 | «must be authenticated as an **administrator**» |
| `/rest/api/2/serverInfo` | 200 | — | — |
| `/rest/api/settings/systemInfo` | — | 404 | пути нет |

**Это и есть ответ на вопрос «точно ли нужен System Administrator».** Сервер сам различает два
уровня и называет их по-разному: `applinks` просит **administrator**, а `oauth2/latest/client` —
**system administrator**. Эндпоинт OAuth-клиента **существует** (иначе был бы 404, а не 403) и
закрыт строго системным администратором.

Отсюда важное следствие: **регистрация клиента доступна по REST, а не только через UI.** Это
меняет цену запроса — при наличии прав человек, кликающий в интерфейсе, не нужен.

## 3. Идентичность между системами — несущее допущение ПОДТВЕРЖДЕНО

Оно нигде не проверялось и держало всю сверку личности для вики.

| Система | Запрос | Логин | Внутренний ключ |
|---|---|---|---|
| Jira | `/rest/api/2/myself` | `name` = **`monakhov-tech`** | `JIRAUSER32317` |
| Confluence | `/rest/api/user/current` | `username` = **`monakhov-tech`** | `ff8081819db3351c019e83e0ea5c0007` |

**Логин совпадает — сверка по нему работает. Внутренние ключи разные и для сверки непригодны.**
Наш код сверяет по логину, то есть идентификатор выбран верный. Проверено на одной учётке; для
полной уверенности нужна вторая, живого человека, но общая база пользователей это подтверждает.

## 4. Почта: в Jira видна, в Confluence НЕТ — и это уточняет схему

| Проверка | Результат |
|---|---|
| Jira `/rest/api/2/myself` → `emailAddress` | **`monakhov-tech@iva.ru`** |
| Jira `/rest/api/2/user?username=…` (чужая почта) | **200, почта видна** |
| Confluence `/rest/api/user/current` → `email` | **`null`** |
| Confluence `?expand=details.personal` | поля нет вообще |
| Confluence `?expand=details.business` | поля нет вообще |
| Confluence `/rest/api/user?username=…` | поля нет вообще |

**Риск «почта скрыта» снят наполовину и уточнён.** Jira почту отдаёт — первый идентификатор
человека мы получим, и бот на этом заработает. Confluence не отдаёт её ни в одном виде, поэтому
привязка для вики обязана идти **по логину**. Ровно так в коде и сделано — но теперь это факт,
а не предположение.

## 5. Путь БЕЗ администратора существует и работает

`GET /rest/pat/latest/tokens` → **200 в обеих системах**, обычным пользователем, без единого
админского права. Jira вернула список собственных токенов учётки:

```
[{"id":16,"name":"tacticum-vps-iva-jira",
  "createdAt":"2026-07-03T09:22:16","lastAccessedAt":"2026-07-29T15:41:01",
  "expiringAt":"2026-10-01T09:22:16"}]
```

`GET /rest/pat/latest/admin/tokens` → **405** (эндпоинт есть, GET не поддерживается).

**Значение:** самовыпуск личного токена сотрудником — не гипотеза, он доступен и по REST, и через
UI, администратор не нужен вообще. Это вариант «А» из реестра, отклонённый в пользу OAuth из-за
одного ручного шага. Он остаётся полностью рабочим запасным путём, если прав не дадут.

⚠️ **Попутная находка, к задаче не относится, но потерять нельзя:** действующий токен
`tacticum-vps-iva-jira`, на котором работает наш ингест, **истекает 2026-10-01**. Через два
месяца он умрёт молча.

## 6. Чего проверить не удалось

- **Есть ли уже зарегистрированные application links / OAuth-клиенты** — списки закрыты теми же
  403/401. Возможно, нужный клиент уже кем-то заведён, но без прав этого не увидеть.
- **Группы учётки в Confluence** — отдельного доступного эндпоинта не нашлось; в Jira ответ
  `myself` вернул пустой список групп, что не то же самое, что «групп нет».
