# Канонический прогон: агент сам ставит и обновляет обе роли

**Что это.** Не суррогат с раскладкой файлов, а настоящий путь пользователя: `whoami` →
`provision_installation` → `pull_installation_content_manifest` → **агент сам применяет действия**,
и отдельно — обновление командой «проверь обновления профиля и обнови». Всё через боевой каталог.

**Вердикт: доставка работает, пожелания Евгения закрыты. Найден один серьёзный дефект платформы —
установка ломает `~/.codex/config.toml` и codex перестаёт запускаться вообще.**

Среда: `teststand`, codex-cli 0.146.0, юзер `tacticum`.

## 🔴 Дефект платформы: установка профиля ломает конфиг Codex

**Воспроизведено живьём.** После первой же установки следующий запуск codex падает:

```
Error loading config.toml:
/home/tacticum/.codex/config.toml:15:18: missing assignment between key-value pairs, expected `=`
env = {"JIRA_URL": "${env:JIRA_URL}", "JIRA_PERSONAL_TOKEN": "${env:JIRA_PERSONAL_TOKEN}"}
```

**Корень найден точно** — `apps/backend/src/backend/catalog/infrastructure/renderers/codex.py:162`:

```python
body_lines.extend(f"{k} = {json.dumps(v)}" for k, v in entry.items())
```

`json.dumps` на словаре даёт `{"KEY": "value"}` — валидный JSON и **невалидный TOML** (inline-таблица
требует `KEY = "value"`). Для строк и списков `json.dumps` случайно совпадает с TOML, для словаря —
нет. Словарь появляется ровно там, где у MCP-сервера есть `env_required` при stdio-запуске.

**Масштаб — 6 профилей**, считано по манифестам: `iva-qa-mcp` (обе наши QA-роли),
`iva-analysis-fr`, `iva-fr-analyst`, `iva-architect-mcp`, `iva-techwriter-mcp`,
`iva-2-client-shell-dev`. **Аналитик — на проде.**

**Тяжесть выше, чем считали.** В памяти это значилось как «пишет невалидный TOML». На деле codex
**не стартует вообще** — ломается не один MCP-сервер, а весь CLI, включая работу, не связанную с
профилем. Пользователь получает нерабочий инструмент сразу после установки.

**Почему Евгений этого не поймал:** quickstart велит настраивать MCP **руками** (Шаг 0) — там
блок написан верным TOML. Дефект срабатывает, когда действие применяет **агент** из манифеста.

**Чинить не нам:** `renderers/codex.py` — платформенный код, действует правило «чужую работу не
чиним, авторство выясняется первым вопросом». Правка тривиальна (для `dict` отдавать TOML
inline-таблицу вместо `json.dumps`), но это их зона. **Отдать платформе с этим отчётом.**

Улика сохранена на стенде: `~/.codex/config.toml.broken-2026-07-30`. Конфиг стенда починен.

## 🟡 Находка: `provision_installation` возвращает ЧУЖУЮ установку

Первый вызов `provision_installation(profile_id="iva-role-qa")` без `workspace_id` вернул
**установку инженера** `b258bb6b` с его пином 0.5.5 — не создал новую.

Это заложенное поведение (`provision_installation.py:71-79`, find-first по org, issue #663): «коллега,
присоединяющийся к командной установке, не должен упираться в `workspace_ambiguous`». Данные при этом
**не портятся** — установка возвращается как есть, label не перезаписывается (проверено).

**Но следствие для инструкции опасное.** Quickstart говорит: «в `whoami` найди строку с
`profile_id = iva-role-qa` — её `id` это твой `<INSTALLATION_ID>`». `whoami` показывает **все 19
установок организации**, а не свои. Значит второй QA-инженер в ИВА, дойдя до этого шага, штатно
сядет на установку первого: его pull будет двигать чужие счётчики, а перепин — чужую версию.
**Для одной роли на команду это норма, для двух инженеров с разными репозиториями — нет.**

Обход для изолированной установки: `workspace_id` явным параметром (использован в этом прогоне).

## ✅ Обновление: ведёт себя ровно как обещано в PR

Прогнано дословной фразой пользователя: «проверь обновления профиля и обнови».

- **0.5.5 → 0.6.1**, 79 действий, **удалений ноль** (агент честно ответил «Удалены файлы: НЕТ»);
- после обновления в дереве **89 файлов против 79 у чистой установки** — **9 осиротевших**,
  недостающих **0**;
- **все 9 совпали с предупреждением в `.agent-kit/README.md` поимённо** — тот самый список
  «Девять файлов переехали — старые нужно удалить руками». Предупреждение не декларация: оно точное.
- десятый лишний файл — `.tacticum/context.yaml` — **не осиротевший, а новый**: его создаёт сам
  процесс обновления (id установки, CLI, workspace).

То есть риск, записанный в PR-1 («файлы, переехавшие в `stacks/`, не удаляются — механики удаления у
потребителя нет»), подтверждён числом и полностью покрыт инструкцией.

## Границы прогона

- **Только codex** — `claude` на стенде не установлен.
- **Реального прогона автотестов нет** — на стенде нет клонов `one-web`/`one-web-kmp`, VPN до ИВА,
  кредов TestOps и Docker. Это по-прежнему только у Евгения.
- **Действие в `~/.codex/config.toml` во втором и третьем прогонах пропускалось намеренно** — после
  того, как дефект был воспроизведён и задокументирован, иначе стенд ложился каждый раз.
- Неинтерактивный `codex exec` **отменяет MCP-вызовы** штатной политикой подтверждений; пришлось
  запускать с `--dangerously-bypass-approvals-and-sandbox`. Живой пользователь в интерактиве просто
  подтверждает вызов — для него это не дефект, но автоматизацию прогонов надо учитывать.
