## Что делает US#2 (почти полностью новое)
Сейчас скилл — АЛГОРИТМ РАЗВЕДКИ (Карта источников стр.19–29, 5 шагов стр.31–99, правила честности 8 п. стр.101–120). Формата документа и серии CT-n НЕТ. US#2 надстраивает поверх разведки формат ПРОЕКТИРОВАНИЯ контракта.

## Правки (по строкам verbatim-заметки)

### 1. Новый раздел «Контрактный раздел FR — формат 3.1» (вставить ПОСЛЕ Алгоритма, после стр.99; до «Правил честности»)
База — образец 211847207 (ТЗ §3.1):
- **Реестр изменений** (таблица): `Контур | Контракт | Изменение | Назначение | Совместимость | Потребители`. Колонка «Потребители» обязательна (иначе «Совместимость» не проверяема, ТЗ §3.1 п.4).
- **По-операционная секция** на каждую операцию:
  - описание;
  - таблица параметров запроса: `название | где (path/query/body/header) | тип | обязательность | описание`;
  - пример запроса (JSON);
  - таблица параметров ответа;
  - коды ответа с семантикой;
  - пример ответа.
- **Дополнения к образцу (ТЗ §3.1):**
  - права доступа — строка «кто может вызывать» (роль/scope) у каждой операции + `403` в кодах;
  - лимиты — `429` + ограничение частоты, где применимо;
  - асинхронность — операция потенциально >~1с → механизм отслеживания статуса (`202` + статус-ресурс/событие);
  - трассировка — каждая операция ссылается на порождающее требование (`CT-n`/`FT-n`) и пробу-основание в П.F.

### 2. Серия CT-n (ТЗ §2.3, §3)
Ввести серию `CT-n` для контрактных требований. Правила стабильности ID (номер выдан один раз, не переиспользуется) — как у FT/UC/DM/EV. Каждая операция формата 3.1 трассируется на CT-n.

### 3. JUMP-контур (ТЗ §3.1 п.5)
Те же таблицы, но: вместо метода+пути — имя команды; вместо body — payload; колонка «Контур» = `JUMP`. Конвенции — из канона distrohost (+ changelog-секция дока), цитата по правилам скилла (Шаг 3, стр.56–68 — probe-first сохраняется). Источник паттернов уже в скилле: Шаг 3 (JUMP-команды) + Шаг 5 (конвенции стиля, стр.88–90).

### 4. Чеклист полноты контрактных требований 3.2 (ТЗ §3.2) — новый подраздел
Общий для FR и ТЗ; пункт неприменим → ЯВНО «не применимо», молчание запрещено:
операции от потребностей потребителя · различимые классы ошибок и реакция · идемпотентность повторов · пагинация растущих коллекций · версионирование + политика совместимости + deprecation · авторизация per-operation · асинхронные операции и уведомление о завершении · конкурентность · таймауты · лимиты/429 · секреты в логах.

### 5. Порядок и основания проектирования (ТЗ §3.3) — встроить в Алгоритм/новый раздел
- Проект контракта строится ТОЛЬКО после зафиксированных capability-требований (CT-n) и проб П.F (вкл. negative evidence).
- Конвенции наследуются из ближайшего реестра (auth-схема, стиль путей/команд, формат ошибок) с ЦИТАТОЙ реестр+версия — не выдумывается с нуля.
- При вердикте «проектировать» — П.F фиксирует **рассмотренные альтернативы**: существующие аналоги + причина отклонения каждого (расширить Шаг 5, стр.79–99).

### 6. Правила честности (стр.101–120) — согласовать с двухзонной моделью US#1
- Рула 1–2 (запрет wire-имён без источника) сейчас безусловны. Под двухзонной моделью: **разведочная фактура и negative evidence (П.F) — строго as-is** (правила без ослаблений); **спроектированный контракт формата 3.1 живёт в §1.6 Части 1 (to-be)** — там проектные wire-имена разрешены под 3 предохранителями (основание в П.F + плашка «требует утверждения dev+CTO»/Q-n + валидатор границы US#1).
- Переформулировать п.1–2 так, чтобы явно: «в П.F — только источниковое; спроектированный контракт — в §1.6 с плашкой и трассировкой к CT-n/основанию». Синхронно с §2 US#1 (не противоречить).

## Куплинг с US#1 (важно)
Формат 3.1 = наполнение раздела **§1.6 «Контракты»** Части 1 (переномерация US#1). US#2 определяет ФОРМАТ; US#1 создаёт МЕСТО (§1.6) + валидатор границы, который проверяет проектные имена контракта. Мержить согласованно (один PR US#1+US#2 или US#1 первым). Правило честности §2 (US#1) и правила честности api-contracts (US#2) — держать непротиворечивыми.

## Приёмка US#2
- Контрактный раздел по формату 3.1 генерится для REST И JUMP (реестр изменений + по-операционные секции + права/лимиты/async).
- Серия CT-n трассируется на FT-n + пробу П.F.
- Чеклист 3.2 отрабатывает, «не применимо» явное.
- Порядок соблюдён: проект только после CT-n + проб; альтернативы фиксируются в П.F при вердикте «проектировать».
- Правила честности непротиворечивы с §2 US#1.
- Существующие тесты скилла/каталога зелёные.
