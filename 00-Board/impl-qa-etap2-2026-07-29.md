## Главное: корневая причина у дефектов 3 и 4 общая

**У `run-tests` и `fix-failed-test` не было секции «Прежде всего»** — той, что есть
у `write-autotest` и `prepare-mr-branch`. То есть на двух скиллах из трёх, что прошёл
инженер, директивы «не спрашивай разрешения между фазами» не существовало физически.
Это не гейт, работающий как задумано, и не особенность CLI — это дыра в теле.

**Вторая дыра — в самой директиве `prepare-mr-branch`:** «останавливайся только на
ожиданиях ответа от `AskUserQuestion`». `AskUserQuestion` там — неограниченная лазейка:
любое «продолжаем?», завёрнутое в тул-вопрос, формально легально. Через неё и проходила
Phase 2.5.

Аналогично с коммитами: инженер сказал «разделять умеет, делать без напоминания — нет».
Причина в теле прямым текстом — `fix-failed-test` **запрещал** коммит («финальный коммит
оставить пользователю»), `write-autotest` говорил «Skill сам не коммитит. Пользователь
просит закоммитить → …». Коммит-точки не было ни у одного скилла.

**Почему Phase 2.5 безопасно снимать:** source неизменна, target живёт только локально,
скилл не пушит, Phase 5 ловит утечку, последний фильтр — человек, который и делает пуш.

### Работает как задумано, но не озвучено

- **`run-tests` → `fix-failed-test`.** Тело говорит «Запускаю», агент «предложил запустить».
  Следствие отсутствия «Прежде всего»; вылечено там же + явной строкой в ветке B.
- **Chromium в песочнице** — **(в)** особенность CLI, в теле не описана вообще. Дефект 5.
- **Finalization печатает push, но не выполняет; MR не открывает.** Прямой инвариант

  снятие означало бы, что поставляемый профиль пушит в репозитории заказчика. Сделан
  минимум — шаг назван ожиданным и финальным. Хотят иначе — отдельное решение.

## Что реализовано

### 1. Post-MR цикл — `prepare-mr-branch` Phase 7

**Отдельный вход по явному сигналу «MR влит»**, а не продолжение Finalization: между
Phase 6 и Phase 7 лежит действие человека (пуш, ревью, мерж) длиной в часы или дни,
и момент мержа агент определить не может. У скилла теперь два входа, разнесённых во
времени, — это описано в «Инварианте».

Шесть шагов в порядке инженера (он же технически обязателен — с удаляемой ветки надо
сойти раньше, чем её удалять; интеграционную обновить раньше, чем вливать):
возврат на агентскую → удаление артефактов подготовки → удаление локальной MR-ветки →
обновление интеграционной до `origin/` → влитие её в агентскую → останов.

**Ничего вслепую:**
- перед удалением ветки — доказательство вливания: `merge-base --is-ancestor`, при
  squash/rebase-мерже (GitLab по умолчанию умеет оба) — `git cherry` по патчам.
  Не подтвердилось ни то, ни другое → STOP, ничего не удаляем;
- удаление только `git branch -d` (строчное) — git сам откажется от невлитой ветки;
  `-D` разрешён лишь после подтверждённого squash и **с озвученной причиной**;
- артефакты сносятся только те каталоги `.tasks/prepare-mr-branch/{ts}/`, чей `state.md`
  называет этот target. `.tasks/work/`, реестры, `tc-review/`, кандидаты в трекер —
  не артефакты подготовки MR, это работа человека и других скиллов;
- remote-ветка не трогается никогда.

**Финал проверяемый** — три печатаемые проверки: `git branch --show-current` = агентская,
`git status --porcelain` пуст, `rev-parse` интеграционной и `origin/` совпадают.

Finalization теперь ставит `awaiting_merge` вместо `completed` — работу закрывает Phase 7.

### 2. Уборка `allure-raw-*` — `run-tests` Phase 3b

Создаёт их сам `run-tests` (Phase 3, копия после каждого прогона), никто не убирал.

**Правило: живут три самые свежие, включая только что созданную.** Три, а не одна:
свежая нужна для разбора текущего падения, предыдущая — для сравнения «было/стало»
после фикса, третья — запас на серию прогонов. Уборка **сразу после создания копии**,
а не перед прогоном: иначе мусор всё равно остаётся «после себя», а инженер видит
именно то, что осталось после.

Гарды: рабочая `./allure-raw` под шаблон не попадает и не удаляется никогда (с ней
работает `fix-failed-test`); только каталоги в корне репо; трекаемые git пропускаются
с явной строкой в выводе.

**Попутно найдена дыра в deny-list.** Копии `allure-raw-*` **уезжали бы в MR**:
`**/allure-raw/**` их не ловит — `allure-raw-smoke` это другой сегмент пути, а не
`allure-raw`. Добавлены `allure-raw-*/**` и `**/allure-raw-*/**`.

### 3. Дисциплина коммита — инвариант 16

Канон — `craft/rules/invariants.md` (tier `trial`, доступен всем скиллам; конвенции
сообщений лежат в `full`-справочнике батча и потому не годились как дом).

Таблица «скилл → коммит-точка», смысл один — **первый момент, когда результат проверен**:

| Скилл | Точка |
|---|---|
| `write-autotest` | тест написан и прошёл зелёным → шаг 9 |
| `fix-failed-test` | корзина `fixed` после Phase 7 → Phase 8 |
| `batch-autotest` | по завершении каждого TC (шаг 10, уже был) |

Правило «проектное и агентское двумя раздельными коммитами, всегда, без просьбы»
+ границы: коммитим только проверенное, `git add` явными путями (не `-A`), пуш и MR
не часть коммит-точки, вложенный запуск не коммитит — коммитит внешний оркестратор.

### 4. Chromium в песочнице — `run-tests`

Описан как **ожидаемый шаг**: сигнатуры отказа (`Failed to move to new namespace`,
`no usable sandbox`, …), одна просьба разрешить запуск вне песочницы, запрет подбирать
обходы (`--no-sandbox`, root, подмена headless на headed), признак отличия от настоящего
падения — все тесты валятся на старте одинаково, `fix-failed-test` не вызывается.

## Кусок 1 — fallback Phase 7.0 не собирал половину входа

Гейт прав: первый реальный вход инженера («у меня уже есть влитый MR, собранный прежней
версией») уходил в fallback, а fallback спрашивал `source` и `target` — два поля из
четырёх. Прошёл цикл по шагам и выписал, что каждый требует:

| Шаг | Требует |
|---|---|
| 7.1 проверка 1 (`merge-base --is-ancestor`) | `target`, `integration_branch` |
| 7.1 проверка 2 (`git cherry`) | `target`, `integration_branch`, **`base_commit`** |
| 7.2 шаг 1 (`checkout`) | `source` |
| 7.2 шаг 2 (удаление артефактов) | `target` (матч по `state.md`) |
| 7.2 шаг 3 (`branch -d`) | `target` |
| 7.2 шаг 4 (обновить интеграционную) | **`integration_branch`**, `source` |
| 7.2 шаг 5 (`merge`) | **`integration_branch`**, `source` |
| 7.2 шаг 6 (три проверки) | `source`, `integration_branch` |
| 7.3 закрытие | папка сессии (может не существовать) |

То есть застревание было бы на **третьем** шаге из шести — ровно как описал гейт.

**Как собирается теперь.** Таблица «поле → кому нужно → откуда», порядок поиска
«`state.md` → вывести из git → спросить». Новых сущностей не заводил:

- `integration_branch` — **выводится**: `git symbolic-ref --short refs/remotes/origin/HEAD`,
  та же механика, что в Phase 0 шаг 2; не разрешилось — `main`. Вопрос остаётся ровно для
  одного случая — проект ведёт несколько линий (`main`/`rc`), там дефолтная ветка на вопрос
  «в какую линию поехал MR» не отвечает;
- `base_commit` — **выводится**: `git merge-base {target} origin/{integration_branch}`.
  Это корректно именно там, где он нужен: вторая проверка 7.1 работает только когда target
  НЕ предок интеграционной (squash/rebase-мерж), и merge-base тогда даёт точку ветвления,
  от которой target собирали;
- `source` — **выводится** из текущей ветки, если она не `{target}` и не
  `{integration_branch}`; иначе вопрос;
- `target` — **вопрос**. Единственное поле, которое действительно знает только человек:
  какой именно MR влит, из git не следует;
- `target_head_after` — только из `state.md`, и его отсутствие теперь явно объявлено
  не-блокером: сверку пропускаем, доказательство мержа даёт 7.1.

Плюс шаг «напечатать собранное одной строкой до первого действия» — с указанием, откуда
каждое поле взято. Дальше идут `branch -d` и merge, там ошибка во входе уже дорогая.

**Порядок в 7.0 переставлен:** `git fetch origin --prune` поднят выше сбора полей — иначе
`origin/HEAD` и `merge-base` читались бы по протухшим ссылкам.

## Статус `completed` — обработан как нормальный вход

Разведён по наличию `merged_at`, и это разделение работает потому, что `merged_at` пишет
только Phase 7.3:

- `completed` **без** `merged_at` — сессия прежней версии скилла, закрывавшейся на
  Finalization, когда Phase 7 не было. **Нормальный вход**: данные годные, цикл по ним
  просто не проходили. Берём поля, недостающие доводим по таблице, говорим одной строкой,
  что это сессия от прежней версии;
- `completed` **с** `merged_at` — цикл по этому MR уже пройден: назвать дату, спросить,
  ничего не удалять до ответа;
- `aborted`/`interrupted` — это вход в Resume, а не в Phase 7: сказать и остановиться;
- папки нет — все поля по таблице, цикл не блокируется.

## Две дыры того же сценария, найденные по дороге

Обе — про первый живой вход, обе закрыты в тех же строках; расширения объёма не считаю,
но называю явно.
