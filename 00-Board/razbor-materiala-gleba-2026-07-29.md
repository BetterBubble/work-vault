# Материал Глеба: как тестировать профиль ПОСЛЕ деплоя

Источник: `90-Materials/post-deploy-profile-testing.md`, прислал Глеб. Это продолжение
`profile-testing-guide.md` (уровни 0–2, статика и e2e **до** мержа); здесь — **ручная проверка
после сида на прод-каталоге**, то есть ровно то, чего у нас не было.

**Вывод: помогает сильно и по четырём разным вопросам, которые у нас висели.**

## 1. Даёт способ проверить каталог БЕЗ установки — то, чего нам не хватало весь день

`tacticum_init_manifest(profile_id, target_cli="codex")` рендерит роль **из живого каталога, не
создавая установку**. Проверяются: **версия**, **число actions** и — ключевое — для действия с
`AGENTS.md`: `merge_strategy = append_section` и `marker_id = tacticum:<role>`.

**Чем это закрывает наши дыры:**
- **Наш дефект доставки на Codex** (четыре навыка склеивались в один файл по литеральному пути) —
  этот же serves-check ловит его сразу: число actions не сойдётся с составом роли.
- Вопрос «**поставилось ли под Codex живьём**», висевший с 27.07 и закрывавшийся только через
  человека, теперь проверяется нами.
- Отдельная ценность: если у действия с `AGENTS.md` стоит `write_file` без `merge_strategy` — это
  рендерер-баг, и роль **затрёт пользовательский `AGENTS.md`**. Такой проверки у нас не было
  вообще.

## 2. Разводит два типа токенов — и объясняет ошибку, которую мы видели в логах

| Токен | Что это | Что открывает |
|---|---|---|
| **`tac_`** | пришпилен к ОДНОЙ установке | `tacticum_init` / `tacticum_init_manifest`, `pull` этой установки, `kb_*` |
| **`phk_`** | личный, org-membership | `provision_installation` (создать установку) |

**`provision_installation` требует `phk_` с org-membership каталога**, и даже с личным `phk_`
можно получить **`membership_required`**, если workspace или подписка не настроены.

**Это прямо наши два висящих факта:**
- `lead-qa` видел в логах прода `AuthError`: `installation_id_required — Membership keys cover
  multiple installations`;
- п.11 очереди аналитика: «тип ключа ломает код-verify, membership-ключ требует явный
  `installation_id`, нужен single-installation `phk`» — висит с 21.07.

**Обход, который даёт материал:** если `provision` не проходит — использовать `tacticum_init`,
которому достаточно `tac_`. То есть **проверять можно уже сейчас, не дожидаясь решения по ключам.**

## 3. Две грабли Codex headless, без которых MCP просто не работает

1. **Папку прогона надо затрастить** — в `~/.codex/config.toml` секция
   `[projects."<путь>"] trust_level = "trusted"`, иначе codex не грузит project-config.
2. **В headless MCP-вызовы режутся аппрувом** — нужен
   `codex exec --dangerously-bypass-approvals-and-sandbox`.
3. Плюс: у SSH-команды лимит ~5 минут, длинные прогоны — через `nohup` + опрос файла-флага.

**Это стоит проверить как гипотезу по нашим «не поставилось под Codex»:** возможно, часть жалоб —
не наши дефекты, а незатрастенная папка.

## 4. У команды ЕСТЬ стенд с VPN — а мы считали, что окружения нет

Нужен стенд с **codex CLI + node + serena-LSP + VPN до контура ИВА + клоны IVA-репозиториев**. У
команды это **RE/KB-тест-стенд, доступ и IP — у Глеба или в инфраструктуре**.

**Это меняет наш вывод «доказать не можем».** `lead-qa` честно писал, что прогон у инженера — не
наше доказательство, потому что нет ни `kmp-stage`, ни VPN, ни секретов TestOps. Оказывается,
стенд существует, и вопрос упирается в доступ, а не в его отсутствие.

⚠️ Оговорка из материала: **VPN на стенде иногда слетает** (конфиг вычищается), проверка —
`sudo swanctl --list-sas | grep ESTABLISHED`; лечится переносом рабочего `ipsec.conf` с
прод-RE-стенда.

## 5. Три уровня проверки — готовая лестница приёмки

| Уровень | Что доказывает | Цена |
|---|---|---|
| **A. Serves-check** | каталог засижен верно + рендерер работает (глобально для всех ролей) | дёшево, репозиторий не нужен |
| **B. Install в реальный клон** | рендерер не затирает `AGENTS.md`, раскладка верна | средне, нужен свежий клон |
| **C. Реальная задача скиллами роли** | **скиллы реально работают на живом коде** — ловит контент-баги | дорого, нужен стенд |

**Экономия, которую он сам называет:** рендерер-фикс глобальный (одна функция на все роли) —
достаточно доказать на одной роли, остальные закрываются serves-check'ом. А вот **уровень C надо
гонять на каждом стеке отдельно** — там находятся стеко-специфичные баги.

**Уровень C уже окупился у него:** на `java/diskstorage` агент нашёл реальный баг (ICAP DLP,
delay-правило по имени файла регистрировалось как текстовое, `EnvironmentLuncher:202`), написал
red-тест, починил, `mvn test` прошёл. На KMP — кандидат-баг в генерации инициалов.

## 6. Проверки уровня B — готовый чек-лист, которого у нас не было

- `grep -c "tacticum:iva-role-<X>" AGENTS.md` → **ровно 2** (begin+end, одна секция);
- число строк `AGENTS.md` выросло, первые строки остались репозиторными;
- `git status --porcelain | grep -v '^??'` → только `M AGENTS.md`, исходники не тронуты;
- в `.agents/skills/` и `.codex/agents/` лежат ингредиенты роли.

Эталон из материала (KMP): `AGENTS.md` 120 → 191 строк, 2 маркера, 25 скиллов + 3 агента,
исходники чистые.

## 7. Дисциплина read-only — совпадает с нашей

Клоны свежие и одноразовые, не рабочие копии коллег; в промпте явный запрет менять код, коммитить,
пушить; после прогона обязательная сверка `git status`. Уборка — `rm -rf` пилотного клона, токены
только в env прогона.

## Что предлагаю сделать (решает Президент)

1. **Взять уровень A в нашу приёмку прямо сейчас** — он дешёвый, не требует стенда и ловит ровно

   даёт уровень C.
3. **Проверить гипотезу про `trust_level`** на жалобах «не ставится под Codex» — возможно, часть
   из них не наши дефекты.

   проверяет ссылки и пути по дереву установки, его — что каталог отдаёт и что установка легла
   поверх чужого репозитория не разрушительно. Пересечения нет, дополняют друг друга.
