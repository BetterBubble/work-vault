# Находки для Diaret — профиль аналитика (после валидации 1-в-1)

Профиль прогнан целиком (FR→BRD→ADR→PIN→TC) на реальном требовании, достоверность сверена независимо. **Вердикт: работает, готов аналитикам.** Ниже — что улучшить (не блокеры).

1. **Recall discovery неполный (устойчиво).** Grounding точный, галлюцинаций нет, но профиль иногда НЕ находит релевантное: пропустил DESIGN-страницу `131670871` (дизайн-секция FR), ранее — семейство API `/resources/*` (счёл «проектировать с нуля», хотя есть база). → расширить охват `api-contracts-discovery` + дизайн-поиск (шире запросы/пороги).

2. **SD (sequence diagram) отсутствует.** Аналитики на созвоне прямо просят. Профиль его не делает. → добавить навык SD.

3. **CJM не делает** — совпадает с «убрать из скоупа аналитика». ✅ действий не нужно.

4. **KB покрывает только клиентские репо** (ios/web/rn/kmp/mail/firebird). Бэкендов `disk`/`servercore` в KB НЕТ → бэкенд-контракты (в т.ч. API-описание, которое ключевое для разрабов) код-verify'ом не проверить, только реестрами (`api_registry_check`/`contract_check`). Плюс: аналитику нужен **single-installation phk под целевой клиентский репо** — иначе `kb_*` требует явный `installation_id` (membership-key ломает авто-скоуп). → проверить с Монаховым тип раздаваемых ключей; рассмотреть индексацию бэкенд-репо в KB.

5. **2 подозреваемых бага НЕ воспроизвелись** в боевых прогонах: `gap_questions`/`who_to_involve` (param `query` vs `requirement_text`) отработали; `fr-authoring` publish — до записи не дошли (тест no-write). Приоритет понижен, но при желании — перепроверить публикацию отдельно.
