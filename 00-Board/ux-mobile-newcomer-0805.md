# Путь новичка: QA-инженер ИВА ставит `iva-role-qa-mobile`

Критерий один: где человек остановится и спросит «а как?», «а где?», «а что это значит?».
Фактическая верность не проверялась — только удобство. Ветка `feat/qa-mobile-kit-adoption`,
воркитри `/Users/bubblemac/tacticum-worktrees/qa-integrate`. Находок 20.

## Шаг 1 — читает инструкцию

### 1. БЛОКЕР. Первая же таблица описывает репозитории, которых у него нет

Строки 11-14: `one-mobile-ios` (`su.ivcs.ucim`) и `one-mobile-android` (`su.ivcs.kmp`).
Вся остальная поставка знает ОДИН репозиторий `ivaqa/mobile` и ОДНО приложение `su.ivcs.aura`:

## Шаг 2 — установка

### 5. БЛОКЕР. Про то, что установка перезапишет его файлы, не сказано нигде, где он это прочтёт вовремя

Предупреждение существует в двух местах, и оба недостижимы до момента, когда оно нужно:

- `manifest.yaml` §`post_install_notes`:151-212 — в репозиторий не устанавливается, и сказано это
  там же (строка 153); человек манифест не видит вообще;
- `CLAUDE.md.fragment`:26-78 — приезжает ВМЕСТЕ с перезаписью, то есть читается после неё.

В quickstart слов «перезапис», «бэкап», «git status», «git diff» нет ни одного (проверено grep по
обоим QA-quickstart). А цена измерена в самом манифесте (182-183): в `ivaqa/mobile` совпадает
**15 файлов, 3236 строк**, из них 1095 — их собственный `dom-explorer`, который богаче нашего.
Человек нажмёт и потеряет.

**Предложение:** шесть строк в quickstart ПЕРЕД блоком «Установка»: у вас уже есть свой кит →
чистый `git status` → ветка-бэкап → установка → `git diff` глазами до коммита → свой
`dom-explorer` вернуть `git checkout`.

### 6. БЛОКЕР. Единственный сниппет установки ставит раскладку Codex

Строка 129: `pull_installation_content_manifest(installation_id="<ID>", target_cli="codex", update=false)`
— без развилки по CLI. Скопировавший это в Claude Code получит навыки в `.agents/skills/` и
субагентов в `.codex/agents/*.toml`, которых Claude Code не читает: «поставилось, и ничего не
работает». При этом `manifest.yaml`:135-136 объявляет `claude-code: full`, `codex: best-effort`, а
причина best-effort (нет PostToolUse-хуков → `rebuild-autocore` звать руками, манифест 122-133) в
документе человека не названа вовсе — хотя у web-роли под тот же случай есть отдельный раздел
(`iva-role-qa-web-profile-quickstart.md`:60-80).

**Предложение:** две строки сниппета (`claude-code` и `codex`) и одна строка про ручной
`rebuild-autocore` на Codex.

### 7. «Проверка боем» врёт в числе навыков и в раскладке

Строка 141: `ls .agents/skills/  # 14 навыков (на Claude Code — .claude/skills/)`.
По golden-дереву установки (`apps/backend/tests/e2e_install/golden/iva-role-qa-mobile/claude-code.json`)
навыков **18**, и лежат они в репо-скоупе `.claude/skills/`. Человек считает 18, читает 14 →
«поставилось лишнее» или «поставилось не то». Проверка написана Codex-раскладкой вперёд при
`claude-code: full`.

**Предложение:** `ls .claude/skills/ | wc -l   # 18`, вторая строка — для Codex.

### 8. Установка делегирована документу про другую роль, и там четыре ловушки

Строка 123: «Порядок и команды — те же, что в quickstart первой роли… Отличается только
`profile_id`». В `iva-role-qa-profile-quickstart.md` он прочитает:

- ожидаемый состав со скиллом `playwright-cli` (B.2, 259-263) — в мобильной роли его нет и быть
  не может (`recon.md`:13);
- проверку `python -m tools.testops --help   # окружение one-web` (B.3, 283) — упадёт, и его же
  роль объявляет этот модуль ненужным (`manifest.yaml`:244-246);
- навыки в `~/.claude/skills/` (user-scope, 259-263) против фактического репо-скоупа;
- `grep -c "tacticum:iva-role-qa" CLAUDE.md` (281) — маркер другой роли; пройдёт по подстроке и
  даст ложную уверенность.

**Предложение:** не отправлять человека целиком. Оставить в мобильном quickstart свои 8-10 строк
(MCP → `whoami` → `pull` → перезапуск), а в соседний документ ссылаться только за «Три
ключа-секрета».

### 9. В «Что понадобится» нет двух вещей, без которых не заработает ничего

§109-119 не называет:

- **сборку приложения** (`one.apk` / `iosApp.app` / `Ucim.ipa`). В git её нет (`.gitignore` держит
  `*.apk`/`*.app` — `runner.md`:242-252), после клона её нет, кладёт человек руками, и место
  зависит от `--device-host`. Без неё падают и прогон, и разведка, до контакта с Appium
  (`AUT_BUILD_MISSING`);
- **доступ к Allure TestOps** (`TESTOPS_ENDPOINT` / `TESTOPS_TOKEN` / `TESTOPS_PROJECT_ID`) — хотя
  публикация в TestOps стоит в первой строке документа (3-5), а вход «URL тест-кейса» —
  самый естественный первый запрос.

Плюс мелочь того же шага: ссылка на чат поддержки в мобильном документе — просто текст без URL
(113), в web-документе URL есть (52).

**Предложение:** две строки в таблицу («Сборка приложения — кто собирает и куда класть»,
«Токен Allure TestOps — apitoken, не пароль») и вернуть ссылку на чат.

## Шаг 3 — первая задача

### 10. БЛОКЕР. «Как начать?» уводит в чужой продукт

В поставке едет навык `getting-started`
(golden: `repo/.claude/skills/getting-started/SKILL.md`), чей description триггерится на
«как начать», «что делать», «help», «onboarding» — ровно на первую фразу новичка. Тело
(`templates/tacticum-core-base/ingredients/skills/getting-started/SKILL.md`) написано
по-английски и про другой продукт: `@tacticum-workflow`, `/start-task`, «5-Phase Workflow:
Design → Review → Code → Test → Report», BRD / MOCKUPS / ADR / PIN, агенты
`coder` / `tester` / `test-runner` (107-115), которых в QA-роли нет.

Человек спрашивает «с чего начать» и получает инструкцию утверждать макеты.

**Предложение** (правка лейна core, но бьёт по этой роли): не возить `getting-started` в QA-роли
либо заменить тело на QA-версию. Минимум — строка-роутер в `CLAUDE.md.fragment` §«Выбор процесса»:
вопрос «с чего начать» разбирается этим разделом, а не навыком `getting-started`.

### 11. Команда прогона в документе человека не запускается

§«Команда одного теста», строки 70-74:
`<раннер-проекта> -k <test_name> --env … --device-os … --device-host … --device-name … --tb=native --showlocals`.

Канон (`runner.md`:45-50 и 373-378) требует в рабочей форме ещё три вещи:
`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`, `-p allure_pytest.plugin` (без них на Python 3.13 — `Empty
suite` и трейс из `trio`, то есть похоже на «ничего не отобралось», а не на «команда собрана
неверно») и маркер платформы `-m <android|ios>` (`CLAUDE.md.fragment`:178-182 — «маркер
обязателен»). Плюс `<раннер-проекта>` — плейсхолдер, которого канон не знает: там их два и путать
их прямо запрещено (`runner.md`:11-37, `<python-проекта>` против `<pytest-проекта>`).

Человек скопирует, получит пустой прогон и пойдёт искать несуществующий дефект.

**Предложение:** заменить блок точной строкой из `runner.md` плюс одна поясняющая строка
«`<pytest-проекта>` = `./.venv/bin/python -m pytest`».

### 12. Четыре значения, которых у него нет, и негде их записать

Правило «спрашивают, а не подставляют» (`CLAUDE.md.fragment`:150-152, `run-tests/SKILL.md`:182-198)
означает: на «прогони смоук» агент задаёт четыре вопроса — `--env`, `--device-os`,
`--device-host`, `--device-name`. Человек не знает ни одного. Документ говорит «стенд называет
человек или соглашение проекта» (52), но не говорит, где это соглашение смотреть, — при том что
канон знает и договорный стенд `at-develop3` (`runner.md`:126-133), и команды получения остальных
трёх (`adb devices`, `xcrun simctl list devices booted`, `runner.md`:317-329).

Закрепить значение один раз можно только `default_env` в `[craft]` `.kit/answers.toml`
(`craft-answers.example.toml`:17-18) — о нём в документе человека ни слова; координат устройства
там нет вовсе, то есть их агент будет спрашивать каждую сессию.

**Предложение:** блок «Ваши четыре значения» с командами получения и строкой «назовите их агенту
один раз в начале сессии; постоянный стенд закрепляется `default_env` в `.kit/answers.toml`».

### 13. Самый вероятный первый вход — URL тест-кейса — упирается в третий секрет

`write-autotest/SKILL.md` шаг 1 (93-97) принимает URL TC; клиент падает честно и с инструкцией
(`iva-qa-tms-base/ingredients/tms/scripts/testops/client.py`:62-64), но человек в этот момент
впервые узнаёт, что секрета три. Закрывается пунктом 9.

## Шаг 4 — первое падение

### 14. Вставил трейс — агент переустановит приложение на устройстве, прежде чем прочитать трейс

`fix-failed-test/SKILL.md` идёт Phase 1 «Reproduce on target» (189-196) до классификации в
Phase 4, а канон стека говорит обратное: слой 0 (`ENV_CONFIG`, `AUT_BUILD_MISSING`,
`IMPORT_OR_REGISTRY`, `API_CONTRACT_CHANGED`) определяется **по трейсу, без устройства**, и это
дешевле всего (`failure-taxonomy.md`:108-119, `fix-playbooks.md`:12-24). У новичка первое падение
почти наверняка из слоя 0-1, а цена репро здесь не «минута прогона»: каждый прогон сносит
приложение и его данные с устройства (`runner.md`:224-240).

**Предложение:** в Phase 0 — шаг «прочитать трейс, сверить со слоем 0 таксономии стека; совпало →
диагноз и стоп без репро».

### 15. `fix-failed-test` знает про `--env`, но не знает про три опции устройства

Phase 0 3a (139-143): «Определить `env` (один на батч): параметр `default_env` секции `[craft]`» —
и всё. Что делать, если `.kit/answers.toml` нет (обычный случай), не сказано; про device-опции в
скилле нет ни строки, хотя без них не соберутся ни Phase 1, ни Phase 5. В `run-tests` тот же
вопрос разобран разделом (182-198).

**Предложение:** одна строка в 3a — «плюс все опции, помеченные в `runner.md` как „дефолта нет",
по лестнице `run-tests` §Прочие обязательные опции».

### 16. Отчёт даёт класс и «что произошло», но не даёт первого действия для не-кодовых классов

Шаблон `fix-failed-test/references/batch-report.md` (53-87) рассчитан на починку кодом. Для
`AUT_BUILD_MISSING` / `DEVICE_UNAVAILABLE` / `ENV_CONFIG` человеку нужна одна строка «сделай вот
это» (`appium -p 15555`; «положи `one.apk` в рабочий каталог»), а такие исходы уедут в
«Deferred / escalation с обоснованием».

**Предложение:** строка в Summary «🔧 Предусловия окружения: N — что сделать человеку», с точной
командой.

> Не находка, чтобы лид не тратил время: терминологией классов его не завалит. Имена согласованы
> с таксономией его же команды (`failure-taxonomy.md`:32-38), дискриминаторы однозначны («кадр
> `webdriver.Remote` в трейсе есть/нет»), плейбуки читаются как процедура.

## Пять правок, которые дадут больше всего

1. **Переписать шапку quickstart под один репозиторий `ivaqa/mobile` и одно приложение
   `su.ivcs.aura`** (п. 1). Пока она врёт, остальные 170 строк не читаются.
2. **Перенести в quickstart, перед «Установкой», шесть строк про перезапись чужого кита и
   бэкап** (п. 5). Единственная необратимая потеря на всём пути — и предупреждение о ней сейчас
   лежит в двух местах, куда он не заглянет вовремя.
3. **Свой блок установки: `target_cli` под оба CLI + верные проверки (18 навыков,
   `.claude/skills/`), без отсылки в документ соседней роли** (п. 6, 7, 8).
4. **«Ваши четыре значения + сборка» с командами получения и рабочей строкой прогона из
   `runner.md`** (п. 9, 11, 12). Это то, обо что он споткнётся при первом же «прогони смоук».
5. **Перевернуть точку входа: маршруты и «незыблемое» наверх, пост-установочный разбор вниз**
   (п. 18) + убрать `getting-started` из QA-роли (п. 10).

## Сколько минут до первого успешного действия

Считаю первым успехом зелёный одиночный прогон или снятое дерево элементов.

**Сейчас: 1.5-3 часа при удачном стечении, и это без учёта главного риска.** Чтение quickstart
6-8 минут; несовпадение имени репозитория — либо 15 минут догадок, либо стоп до ответа в чате
(реалистично следующий рабочий день). Установка через второй документ 20-30 минут, плюс 10 минут
сомнений на расхождении проверок (14 против 18, `~/.claude/skills` против `.claude/skills`,
падающий `python -m tools.testops`). Первый прогон: `--env` он не знает и идёт спрашивать;
координаты устройства добывает сам; сборки нет — про неё в его документе не написано, и он
узнаёт о ней из падения (+20-40 минут). Если скопирует команду из документа — ещё круг на
`Empty suite` из-за отсутствующих `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` / `-p allure_pytest.plugin`.

**После пяти правок: 30-45 минут.** 15 на установку с верными проверками, 15-20 на добывание
сборки и координат устройства по готовым командам, остальное — прогон. Главное изменение не в
минутах: все стопы становятся видны ДО нажатия, а не после, и ни один из них не выглядит
поломкой поставки.
