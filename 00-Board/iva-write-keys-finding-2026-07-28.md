# Ключи iva-write: главный факт и что из него следует

Только изучение и проверка фактами. Ничего не правил, код не трогал, в Jira/Confluence не ходил.
Источники — официальная документация Atlassian и документация пакета `mcp-atlassian`; версии систем
заказчика взяты из нашего репозитория.

Контекст задания — [[call-2026-07-28 — дом дизайн-системы, схема ключей iva-write, статус профилей у команд]]
(созвон 10:30). Картина «как есть» — [[iva-write-picture-2026-07-27]].

---

## 1. Главный факт: выпустить PAT за другого человека нельзя

Задание сформулировано как «мы знаем человека → сами генерим его PAT, сами храним». **Через
механизм Personal Access Token это невозможно в принципе.**

Дословно из документации Atlassian:
- «**You can only create PATs for your own use**» — страница Personal Access Token для Jira DC
  (developer.atlassian.com/server/jira/platform/personal-access-token/);
- «**Please note that you cannot create PATs on behalf of someone else**» — там же, в разделе про
  REST API;
- «All users are allowed to create their own PATs, which will **match their current permission
  level**» — Using Personal Access Tokens (confluence.atlassian.com/enterprise).

Что может администратор: **видеть список всех токенов на инстансе и отзывать их** — поштучно или
массово. **Создавать токены за других — не может.** Эндпоинт `POST /rest/pat/latest/tokens`
выпускает токен исключительно тому, кто аутентифицирован в этом запросе.

### Почему это важнее, чем прозвучало на созвоне

Руководитель назвал риск так: «технической учётке, скорее всего, не хватит прав; я могу расширить
её из-под своей личной админской» (говорил **Иван Монахов**, не руководитель). **Расширение прав здесь не поможет** — это не вопрос прав, а
ограничение самого продукта. Даже полный системный администратор Jira не может выпустить PAT за
другого пользователя. Значит путь «дайте техучётке побольше прав, и мы будем штамповать ключи»
закрыт, и проверять тут нечего.

## 2. Но цель достижима — и ровно в той формулировке, которую он произнёс

Цель руководителя: человек пишет **под своей учётной записью, в своей зоне видимости**, и при этом
**не занимается настройками сам**. Это достигается — но не через PAT, а через **OAuth 2.0**.

Обе системы заказчика это умеют. Версии наши же: **Jira 10.3 и Confluence 9.2**
(`templates/iva-fr-analyst/manifest.yaml:163`), и у обеих есть OAuth 2.0 provider API — документация
Atlassian существует ровно для этих версий (`adminjiraserver103`, `conf92`).

**Как это работает:**
1. Администратор **один раз** регистрирует наше приложение — «incoming link» в Application Links.
   Получаем Client ID и Client secret. Дальше администратор не нужен.
2. Человек **один раз** нажимает «разрешить» на экране согласия в браузере
   (`/rest/oauth2/latest/authorize`).
3. Мы программно получаем access token и **refresh token** (`/rest/oauth2/latest/token`), кладём в
   хранилище по e-mail и дальше **обновляем сами** — человек больше ничего не делает никогда.
4. Все действия идут от имени этого человека. Права — его собственные: «actual permissions will
   always be **capped at what this user can do**» (документация Confluence DC по scope'ам incoming
   links). То есть «своя зона видимости» получается сама собой, ограничивать вручную не нужно.

Scope'ы задаются при регистрации: `READ`, `WRITE`, `ADMIN`, `SYSTEM_ADMIN`. Нам нужен `WRITE`
(«Create, update, and delete projects and issues»), он включает `READ`.

**Наш пакет это поддерживает.** В документации `mcp-atlassian` (sooperset), раздел
`docs/compatibility.mdx`: для Server/DC перечислены API Token, Personal Access Token, **OAuth 2.0
(Application Links)** и BYOT. В коде (`src/mcp_atlassian/jira/config.py`) OAuth для Server/DC
присутствует явно — есть даже правило приоритета: «Server/DC: PAT takes priority over OAuth».

## 3. Три реальных пути — что каждый требует

| | **А. Управляемый самовыпуск** | **Б. OAuth 2.0** | **В. Общая техучётка** |
|---|---|---|---|
| Кто выпускает | человек сам, один раз | человек одним нажатием, дальше система | администратор один раз |
| От чьего имени запись | человека | человека | робота, автор — строкой в тексте |
| Права | все права человека | все права человека, `capped` автоматически | нарезаются узко |
| Нужен админ Jira | **нет** | **да, один раз** (регистрация приложения) | да, постоянно |
| Что делает человек потом | ничего | ничего | ничего |
| Ручной шаг остаётся | **да, один** (создать и вставить токен) | нет | нет |
| Срок жизни / ротация | токен истекает → человек делает заново | refresh token, обновляем сами | одна централизованная ротация |
| Готовность пакета | работает сегодня | заявлена, **у нас не проверялась** | работает (как read-канал) |
| Соответствие заданию | частично: «геморрой» снимается почти весь | **полностью** | отвергнуто руководителем 28.07 |

**Про вариант А.** Он ближе к нынешнему состоянию, чем кажется, и его не стоит списывать: боль,
которую назвал руководитель, — не столько «создать токен», сколько «много настроек» — переменные
окружения на каждой машине, отдельно под каждую систему, по инструкции из quickstart на шесть
экранов. Если мы храним токен у себя и подставляем сами, эта боль уходит целиком, а остаётся один
разовый шаг «создай токен и вставь сюда». Это можно сделать **без единого внешнего участника** и
проверить на живых людях за день.

**Про вариант Б.** Это то, что заказано, буквально: «мы сами генерим и храним, человек не
занимается настройками». Требует одного разговора с администратором Jira — и это тот же разговор,
который в любом случае предстоит.

## 4. Что это меняет в постановке

1. **Термин «подключи» из задания не соответствует ничему в Atlassian.** Ни PAT, ни OAuth не имеют
   понятия «подключ» — токен либо принадлежит человеку целиком, либо это отдельный токен
   приложения. Стоит переформулировать в «персональные ключи доступа, выпускаемые централизованно».
2. **Проверять права техучётки не нужно** — вопрос снят фактом из §1. Вместо этого администратору
   нужно задать другой вопрос: разрешено ли регистрировать incoming application link.
3. **Хранилище в helm остаётся нужным при любом из трёх путей** — меняется только то, что в нём
   лежит: PAT (А), пара access+refresh (Б) или ничего персонального (В). Схему хранения стоит
   делать так, чтобы она пережила выбор: запись «человек (e-mail) × система × тип credential ×
   значение × срок».
4. **Хранение чужих секретов — новая ответственность.** Сегодня helm хранит только свои сервисные
   токены в env. Появляется хранилище учётных данных живых людей: нужно шифрование на покое,
   разграничение доступа и понятная процедура отзыва. Это отдельный разговор, а не деталь.

## 5. Что спросить и у кого

| Вопрос | К кому | Зачем |
|---|---|---|
| Разрешено ли зарегистрировать incoming application link (OAuth) в `jira.iva.ru` и `wiki.iva.ru` | **Администратор Atlassian** через руководителя | Единственный внешний блокер варианта Б |
| Приемлемо ли, что один ручной шаг остаётся (вариант А) | Руководитель | Если да — можно стартовать сегодня, без внешних зависимостей |
| Согласны ли люди, что мы храним их ключи доступа | Руководитель / команда | Это учётные данные живых людей, не сервисные |
| Политика срока жизни и отзыва | Руководитель | Нужна до того, как хранилище появится |

Развилки, по указанию руководителя, **адресовать в общий чат**, не лично Солонко.

## 6. Что не проверял

- Включён ли OAuth 2.0 provider и Application Links на инстансах заказчика — нужен доступ/админ.
- Работоспособность OAuth-режима `mcp-atlassian` против Server/DC на нашем контуре — заявлена в
  документации пакета, живьём не запускал.
- Allure — по заданию идёт следом за Atlassian, отдельная схема токенов (см. §4 картины «как есть»).
- Точные версии Jira/Confluence на проде — взяты из комментария в нашем манифесте, на серверах не
  сверял.
