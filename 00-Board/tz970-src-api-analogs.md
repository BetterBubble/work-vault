## 1. Что есть в API ИВА вокруг записей и ресурсов

  создание/загрузка/скачивание файла.

### 1.3 Единственное, что похоже на владение — внутренний примитив diskstorage, и это не то

В репозитории `modules/diskstorage` (KB run `e4c5a6a8-…`) подтверждены:

- `FileOwningController.ownFile(@SpanAttribute(LOGICAL_FILE_ID) @FileId UUID logicalFileId, ServiceFileMetadata metadata): Uni<OwnInfo>`
  — `server/src/main/java/ru/iva/diskstorage/controller/FileOwningController.java`
- `FileCopyController.copyFile(UUID logicalFileId, ServiceFileMetadata metadata): Uni<UUID>`
  — `.../controller/FileCopyController.java`
- `FileJoinController.joinFiles(...)`, `FileReplicateController`, `FileDeleteController.deleteFile(UUID)`,
  `FileDownloadController.resolveUploadedFile(UUID)`, `FilesSearchController`
- аспект логического файла: `createLogicalFileAspect(LogicalFile logicalFile, @Nullable OwnInfo ownInfo)`
  и метод **`fileOwnerService(): Uni<@Nullable String>`**

**Ключевая деталь: владелец здесь — это сервис (строка `fileOwnerService`), а не пользовательский
профиль.** `ownFile` принимает `ServiceFileMetadata`, а не идентификатор пользователя. Это
инфраструктурный примитив «за файлом закреплён сервис-владелец», а не смена владельца записи между
людьми. Путать нельзя.

Источники: `kb_kb_get_code_context_15.txt`, `_20`, `_21`, `_22`, `kb_kb_get_block_compact_14.txt`.

### 2.2 Правила, которые задал аналог

1. **Вводится отдельная роль «Владелец».** Если владелец одновременно администратор — в списке
   участников он отображается как «Владелец» (роль владельца перекрывает отображение админа).
2. **Владелец может передать права другому участнику чата/канала** — то есть получатель обязан
   быть уже участником, передача «наружу» не предусмотрена.
3. **Владельцем может быть ровно один участник** — единственность владения зашита в постановку.
4. **Точка входа в UI:** список участников чата → контекстное меню участника → сменить владельца.

### 2.3 DoD аналога (дословно по смыслу)

- при успешной смене владельца **обновляются статусы у пользователей** (Админ / Владелец /
  обычный участник) — то есть пересчитывается вся ролевая раскладка списка, а не одна строка;
- при успехе — **тост об успешной смене владельца**;
- при ошибке — **тост с ошибкой**.

### 2.4 Что осталось незакрытым в самом аналоге (раздел Notes карточки)

Это ровно те вопросы, которые встанут и для записи:

- «Какой тост при ошибке смены владельца? Нужна ли кнопка повтора? Какой текст?»
- «Будут ли приходить события при смене владельца? Какие?»

**Ответов в дампе нет.** То есть контракт realtime-событий для передачи владения не был
зафиксирован даже в реализованном аналоге.

### 2.6 Что переносится на записи, а что нет

Переносится: единственность владельца · получатель из числа «своих» · вход через контекстное меню
в списке · тост успех/ошибка · пересчёт ролевой раскладки после успеха · связка
[аналитика → backend → клиенты + отдельный дизайн на платформу] · backend-first как порядок.

**Не переносится и придётся проектировать заново** (в чате этого нет вообще): квота и её перенос ·
физическое хранилище файла · аудит/SIEM · атомарность и идемпотентность операции над файлом ·
судьба доступа прежнего владельца к файлу (в чате он остаётся участником и доступ сохраняет —
для записи это отдельное решение) · состояния записи, при которых передача запрещена.

  — в перечне ИБ-требований к аудиту прямо назван пункт **«Передача прав владения файлом другому
  пользователю»**. То есть требование логировать передачу владения уже сформулировано заказчиком.
- `[ТЗ] Обмен файлами и изображениями в чате ВКС — IVAONEHALF-898`,
  `wiki.iva.ru/spaces/IM/pages/215286808` — соседняя постановка того же контура (см. раздел 6).

Остальное в выдаче — обзорные реестры требований (`208700396`, `205489325`, `205489583`) и явно
помеченная неактуальной сводная таблица (`211845443`).

### 3.2 Реальные ограничения — из IVCS-вики (сильнее, чем выдача тула)

**Квоты — `wiki.iva.ru/pages/viewpage.action?pageId=153363340` «Ограничение дискового пространства»:**

- при создании пользовательских файлов проверяется доступное пространство **будущего владельца**
  с учётом индивидуального лимита (`limitOwnerId`) и группового (`limitGroupId`);
- индивидуальное доступное = «Индивидуальный лимит пользователя» − «Пользовательские файлы» пользователя;
  групповое = «Групповой лимит» − «Пользовательские файлы» группы;
- **владелец файлов определяется объектом, в котором файл лежит:** личное пространство → сам
  пользователь; чат → тот, кто загрузил; **мероприятие → создатель мероприятия**;
- запуск записи/стенограммы разрешён, только если доступное индивидуальное И групповое > 0.

Это ключевое ограничение для ТЗ: владелец записи сегодня **вычисляется** как создатель мероприятия,
а не хранится как отдельное изменяемое поле. Отсюда же берётся, что передача обязана трогать
квотный учёт двух пользователей и двух групп.

**Аудит — `pageId=165709273` «Фиксация событий управления записями мероприятий в логе аудита»**
(заказчик требования — ГПБ, задача `VCSWEBR-560`, версия страницы 33, ревью пройдено):

- факты скачивания и просмотра записи любым пользователем или участником фиксируются в логе аудита;
- отдельно учтён случай доступа **не из мероприятия**, а из личного кабинета
  («Настройки → Управление диском») — он тоже логируется;
- в полях **субъект и IP субъекта** обязательно фиксируются данные того, кто выполнил действие;
- логируется и попытка, и её результат (успешно / запрещено / заблокировано).

**Работа с файлом записи — `pageId=149652575` «Запись мероприятия (работа с файлом)»** (версия 18):
страница есть, но в дампе от неё остались только заголовки диаграмм «как есть» / «как будет» —
содержательного текста нет.
