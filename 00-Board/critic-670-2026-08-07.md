# #670 — разбор ветки `fix/670-merge-strategy-actions-meta`

Ревизор, 2026-08-07. Дерево `/Users/bubblemac/tacticum-worktrees/bl-670`, голова `84b110b5`.
Работал только чтением и прогонами тестов. Ничего не правил, не коммитил, на сервер не ходил.

**ВЕРДИКТ: прошло, с двумя долгами.** Доставку не блокирует ничего. Два утверждения авторов
опровергнуты замером, ещё одно уточнено.

## 0. Цель сдвинулась: `origin/main` ушёл вперёд на 4 коммита

Оба отчёта считали базой `origin/main` = `757c5dc2`. Сегодня `origin/main` = `0176410b`
(смержен PR #267, канал записи для qa-desktop/qa-mobile/techwriter). Наивный
`git diff origin/main` в дереве `bl-670` показывает **22 файла**, включая `templates/**` и голдены —
это обратный дифф четырёх новых коммитов main, а не скоуп ветки.

Истинный скоуп по merge-base — **4 файла, +186/−10**, ровно как заявлено:

```
git merge-base origin/main HEAD → 757c5dc2
git diff --stat 757c5dc2..HEAD  → 4 files changed, 186 insertions(+), 10 deletions(-)
```

Пересечения файлов ветки с новыми коммитами main нет (`comm -12` пусто),
`git merge-tree --write-tree origin/main HEAD` → RC=0. **Мерж чистый, конфликтов не будет.**

Значение для лида: числа контролёра сняты на `757c5dc2` и остаются верными, но **любой, кто повторит
проверку скоупа командой из отчёта, увидит 22 файла и решит, что `templates/` тронуты.** В отчёт
контролёра стоит вписать базу хешем, а не именем ветки.

## 1. Направление «белый список — фильтр веса или защита?» — опровергнуть не удалось, вывод автора верен

Пытался доказать обратное тремя путями, все три подтвердили автора, причём **сильнее, чем его
собственное обоснование** (он читал сообщение коммита; ниже — структурные факты).

**а) Контроль доступа стоит выше и не на уровне ключей.** В `tacticum_init_manifest.py:98-105`
приватность решается один раз на профиле — `caller_membership_org_id()` +
`can_caller_read_profile(profile, caller_org_id)` (Issue #289). Дальше рендер идёт без единой
проверки. Белый список применяется **после** гейта доступа и поэтому не может быть его частью.

**б) `path` отдаётся безусловно.** В проекции безусловны `action_id`, `action`, `path`, `size_bytes`.
Если бы кортеж скрывал чувствительное, раскладка файлов пользователя утекала бы мимо него уже сегодня.

**в) `notes` уже в списке и весит ~200 символов** (`_MANUAL_APPLY_NOTES`, renderer.py:44-48) — то есть
и «только лёгкое» список соблюдает нестрого. Это перечисление ключей планирования, не граница.

**г) Происхождение.** `9fdd1465` (Diaret, 2026-05-23) — сообщение: *«manifest tools return small
actions_meta … while keeping each MCP response small and reliable»*. Мотив назван весом.

**Значение `merge_strategy` не может нести приватного:** это `Literal` из 5 значений
(`instruction_pack.py:11`, `repo_config.py:15`), максимум 17 символов.

**Итог: правка ничего не открывает наружу.** Это единственное направление, где ответ «всё хорошо»
и он подтверждён, а не принят на веру.

## 2. Вес ответа — ОПРОВЕРГНУТО. Порог из собственного докстринга превышен вдвое, и правка добавляет ещё 1.9 КБ

Автор аргументировал вес **на одно значение** («17 символов»), контролёр повторил тот же замер.
**Никто не мерил вес ОТВЕТА**, а именно он и есть предмет issue #347.

Перемерил сквозным прогоном настоящего рендерера по всем 64 профилям × 3 target_cli, **с композицией
`depends_on` и `with_builtins`** — ровно тем конвейером, который зовёт сам тул
(`tacticum_init_manifest.py:132-133`). `action_id` брал реальной длины (68 символов, проверено
`make_action_id`).

| | было | стало |
|---|---|---|
| самый тяжёлый `actions_meta` (`iva-role-qa`, codex) | **19 382 Б** | **21 306 Б** |
| манифестов тяжелее 10 КБ (из 192 замеров) | **16** | **16** |
| максимальный прирост на один манифест | — | **+1 924 Б (+9.9 %)** |
| суммарно по 192 замерам | 327 508 Б | 340 185 Б (+3.9 %) |

Топ-5 после правки: `iva-role-qa`/codex 21.3 КБ · `iva-role-qa-web`/codex 19.7 КБ ·
`iva-role-qa-desktop`/codex 18.9 КБ · `iva-role-qa-mobile`/codex 18.9 КБ ·
`iva-role-qa`/claude-code 18.1 КБ.

Три следствия:

1. **Докстринг, который эта ветка переписала, утверждает ложь.**
   `tacticum_init_manifest.py:7-8` — *«each MCP response is small (<10KB) so it can never exceed any
   tool-result cap»*. Уже на `origin/main` шестнадцать манифестов вдвое больше заявленного. Автор
   тронул именно эти строки и оставил утверждение нетронутым.
2. **Встроенный скилл называет ещё меньшую цифру.** `tacticum_context_skill.md:143` —
   *«Fetch the manifest (small response, ~5KB)»*. Реальность 10–21 КБ, вчетверо.
   Там же строка ~229: *«Manifest carries only `(action_id, path, size_bytes)` — no bodies»* —
   неверно и до правки (`compat`/`notes`/`json_pointer`/`marker_id` ездили), после — тем более.
3. **Механизма, охраняющего порог, нет вовсе.** Ни одного теста на размер ответа манифеста:
   `grep -rn "10240\|<10\|len(json.dumps" tests/ src/…/interface/mcp/` даёт только сам докстринг.
   Классический «норма без механизма»: единственная защита #347 — фраза в комментарии.

**Это не блокер:** правка не переводит ни один манифест через порог — он уже перейдён шестнадцатью,
и ветка лишь расширяет перелёт с ×1.89 до ×2.08 на худшем случае. Но обоснование «вес не проблема»
было получено измерением не той величины, и в отчёт оно попало как факт.

## 3. Слоистость — нарушения НЕТ, и новый импорт единственно правильный из имеющихся

ADR-0012 §«Cross-context dependencies», строка 88: *«Запрещено: cross-context import из `domain/`
напрямую. Cross-context взаимодействие — через **interface adapters** / domain events»*.
Направление `Workspace → Catalog` разрешено там же явно.

Что реально импортирует `pull_installation_content_manifest.py`:

| строка | импорт | по ADR-0012 |
|---|---|---|
| 17 | `catalog.application.composition` | вне запрета |
| 18 | `catalog.domain.builtins` | **против §88** |
| 19 | `catalog.domain.renderer` | **против §88** |
| 24-27 | `catalog.interface.mcp.…` (`MANIFEST_META_KEYS`, `_action_size`, `make_action_id`) | **разрешённая форма** |

Обратных импортов нет: `grep -rn "from backend.workspace" src/backend/catalog/` пусто, цикла не будет.

**Прецедент автор занизил и назвал неудачно.** Из того же модуля уже импортировался не только
`_action_size`, но и `make_action_id`. При этом `_action_size` — приватное имя под
`# noqa: PLC2701`, то есть плохой прецедент; `MANIFEST_META_KEYS` — публичная константа, и новый
импорт **чище существующего**. Настоящие нарушения ADR-0012 лежат двумя строками выше, старше ветки
и ею не тронуты.

Мелочь: `MANIFEST_META_KEYS` не добавлен в `__all__` модуля (там только три имени, `_action_size`
тоже отсутствует). На работу не влияет, но публичная константа, которую импортирует другой контекст,
в `__all__` просится.

## 4. Инвариант `content`/`value` — держит. Но три ключа из пяти не покрыты ничем

**Обойти нельзя, проверено:** `MANIFEST_META_KEYS` — кортеж, `ws.MANIFEST_META_KEYS.append("content")`
даёт `AttributeError: 'tuple' object has no attribute 'append'`. Мутация на импортирующей стороне
невозможна.

**Оговорка о единственности копии.** Workspace связывает имя при импорте
(`from … import MANIFEST_META_KEYS`), поэтому переприсваивание в catalog-модуле её НЕ достигает —
проверено:

```
catalog:   ('compat',)
workspace: ('compat','notes','json_pointer','marker_id','merge_strategy')  ← не изменился
```

Для статики это неважно (правка исходника меняет обе), но «копия одна» верно про файл, не про рантайм.

**Главное — мутационный прогон константы.** Выбрасывал по одному ключу и гонял
`pytest tests/catalog tests/workspace`:

| выброшен ключ | RC | упало |
|---|---|---|
| ничего (базис) | 0 | 0 |
| `json_pointer` | **0** | **0** |
| `compat` | **0** | **0** |
| `notes` | **0** | **0** |
| `marker_id` | 1 | 2 |
| `merge_strategy` | 1 | 2 |

**Три ключа из пяти можно молча удалить — весь набор тестов останется зелёным.** Причём `compat` —
не косметика: именно он несёт `"manual"` для `.claude/settings.json`, по которому клиент понимает,
что писать файл нельзя (renderer.py:36-56, ветка `compat == "manual"` в скилле). Потеря `compat`
заставит агента писать файл, который Claude Code блокирует классификатором.

До ветки цена такой ошибки была одна копия из двух; после — обе сразу, потому что константа общая.
Радиус поражения одной правки вырос, покрытие осталось на 2/5. Ловится тестом на 5 строк:
`assert set(MANIFEST_META_KEYS) == {"compat","notes","json_pointer","marker_id","merge_strategy"}`.

Отдельно: имя теста `test_manifest_never_leaks_action_bodies` шире содержимого — он проверяет
отсутствие двух строковых имён в кортеже, а не то, что тело не утекло и не то, что ответ лёгкий.
Настоящий инвариант #347 — размер — не проверяет никто (см. §2).

## 5. Потребитель — ОПРОВЕРГНУТО как «дефект у клиента». Правка полезна, но сегодня инертна

Отчёт реализатора: *«клиент, планирующий установку по манифесту, ни для одного из 25 профилей не
видел, что `.codex/config.toml` трогать нельзя»*. Проверил единственного поставляемого клиента —
встроенный скилл `catalog/domain/builtins/tacticum_context_skill.md`.

Он **не планирует по манифесту**. Цикл (строки 176-186) качает тело КАЖДОГО action и только потом
ветвится:

```
for entry in manifest["actions_meta"]:
    full = call("tacticum_fetch_action", action_id=entry["action_id"])
    strategy = full.get("merge_strategy")          # ← из ответа fetch, не из entry
    elif strategy == "create_if_missing" and exists(full["path"]): skip(...)
```

`merge_strategy` в путь fetch рендерер кладёт уже на `origin/main` (renderer.py:220-232, комментарий
`Issue #670` — это более ранняя часть той же задачи). **Значит полевой сценарий 15.07 закрыт до этой
ветки**, а ветка добавляет данные, которых поставляемый клиент пока не читает.

Ценность реальная, но отложенная: манифест впервые становится самодостаточным для планирования, и
именно это открывает оптимизацию «не качать 27 тел ради `create_if_missing`». Реализатор честно
вынес её в долг п.2 (49 голденов). Но приёмочная формулировка «цена дефекта: 0 из 260 доезжало,
среди них файл из полевого инцидента» читается как «правка чинит живой ущерб пользователю» — она
чинит будущий, а не текущий.

**В комментарий при закрытии #670 это стоит внести дословно**, иначе задача закрывается с
преувеличенным эффектом.

## 6. Фикстура workspace-теста невозможна в каталоге — тест меряет не то, что обещает докстринг

`test_pull_manifest_carries_merge_strategy` строит ингредиент
`kind="repo_config"` + `merge_strategy="create_if_missing"` на `.codex/config.toml`.
Такой комбинации **не существует и не может существовать**:

```
RepoConfigMergeStrategy = Literal["replace","deep_merge","append_lines"]     repo_config.py:15
MergeStrategy           = Literal[…, "create_if_missing"]                    instruction_pack.py:11
```

Прогон через доменную схему:

```
ОТКЛОНЁН kind=repo_config      merge_strategy=create_if_missing  → repo_config.metadata.merge_strategy
OK       kind=instruction_pack merge_strategy=create_if_missing
```

Ирония: **правило написано в комментарии соседнего теста той же ветки** —
`test_tacticum_init_manifest.py`, комментарий *«create_if_missing is an instruction_pack strategy —
RepoConfigMetadata deliberately forbids it … all 27 create_if_missing declarations in templates/ sit
on instruction_pack»*. Catalog-тест правило соблюдает, workspace-тест — нарушает. Перемерил каталог:
все 27 `create_if_missing` действительно на `instruction_pack` (25 → `.codex/config.toml`,
2 → `secrets.yaml.example`), комментарий верен.

Тест зелёный только потому, что `pull_installation_content_manifest` без `target_cli` идёт в
`render_for_claude_code`, который читает сырой словарь метаданных без валидации. Для codex та же
фикстура падает:

```
claude-code: [{'action':'write_file','path':'.codex/config.toml','merge_strategy':'create_if_missing'}]
codex:       ИСКЛЮЧЕНИЕ ValidationError repo_config.metadata.merge_strategy
```

Механику проекции тест проверяет корректно. Но его докстринг обещает воспроизведение полевого
сценария («overwrites a user-owned `.codex/config.toml`»), а воспроизводит состояние, которого в
каталоге быть не может. Лечится сменой одного слова: `kind="repo_config"` → `kind="instruction_pack"`.

## 7. Хвост 2 — опровергнуть не удалось, закрывать целиком правильно

Проверил фактом, включая то, что контролёр не проверял, — **было ли требование аудита верно в момент
написания**. Восстановил срез `cd0ddfc7^`:

| | до `cd0ddfc7` | сегодня |
|---|---|---|
| codex `config.toml.template` всего | 25 | 25 |
| с **активной** `[mcp_servers.*]` | **24** | **0** |
| `iva-fr-analyst` активных | **0** | 0 |

То есть аудит 05.08 10:33 был фактически прав, коммит `cd0ddfc7` (05.08 23:20:57, Gleb Feliust)
обогнал его тем же вечером. Хронология контролёра подтверждается, вывод реализатора тоже: сегодня
все 25 единообразны, критерий «как у остальных 24» выполнен без работы. **Закрывать целиком верно.**

Уточнение к формулировке реализатора: в `iva-fr-analyst` секции были **закомментированы**, а не
активны, — `cd0ddfc7` удалил у него комментарии, у остальных 24 живые секции. Требование аудита
буквально означало бы не «вернуть как было», а «сделать активным то, чего у профиля не было никогда».

**Осиротевшая строка серьёзнее, чем «косметика».**
`templates/iva-fr-analyst/ingredients/repo-configs/codex/config.toml.template:10` —
`# личными Atlassian PAT из env, см. quickstart):` — обрывок с непарной скобкой, потерявший начало
(`cd0ddfc7` вырезал две строки выше). Это **тело ингредиента `codex-config-toml`**, который ставится
пользователю в `.codex/config.toml` с `create_if_missing`. То есть оборванное полупредложение
попадает в файл клиента, а не остаётся внутри репозитория. Решение лида «не трогаем» из-за бампа
версии и голденов принимаю, но в долге это стоит записать как «видно пользователю», а не «мусор».
