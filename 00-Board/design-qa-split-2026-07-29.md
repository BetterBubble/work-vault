# Разделение QA-профиля на процесс и стеки — проект

Проект разреза `iva-qa-autotest-base` (0.5.0, 72 ингредиента) на процесс-лейн + стек-лейны так,
чтобы поверхности и стеки не конфликтовали, а роль собиралась из кирпичей. Только чтение и
проектирование; кода не тронуто.

## Рамка: это не новая архитектура, а применение уже принятой

ADR-0059 Решение 1 задаёт таксономию дословно: **`Роль = core + процесс-лейны + стек-лейн(ы) +
способность-лейны`**. Все роли по ней уже собраны — кроме QA. `iva-role-qa` = `core` +
`iva-qa-autotest-base` (монолит: процесс + стек + TMS-порт + гейты в одном) + `iva-qa-mcp`.
То есть решать нужно не «как разделить», а «почему QA единственный не разделён» — ответ
исторический: содержимое взято из `kit`, а раскладка — из `aqa-agent-toolkit`, где стек был один.

**Их слой стеков уже описан контрактом**, мы его уплостили. `kit/craft/`:

```
craft/
  agents/{code-writer,codebase-analyst,dom-explorer}.md   ← процесс
  rules/invariants.md                                     ← процесс (стек-нейтральный якорь)
  shared/{ledger-and-deviations,jira-candidates,coverage-ledger.template}.md ← процесс
  skills/{write,fix,batch,issue,update}/SKILL.md + references/  ← процесс
  stacks/README.md                                        ← контракт: 9 обязательных файлов
  stacks/pytest-playwright-canvas/{9 файлов + rules/}      ← стек
  stacks/pytest-selenium/{9 + 2 опциональных + rules/}     ← стек
```

У нас `stacks/<stack>/` уплощён в `.agent-kit/craft/`. **Разрез = восстановление этого слоя**,
а не изобретение своего. Ссылки в их телах имеют вид `$CRAFT/stacks/{stack}/pytest-runner.md` —
`{stack}` резолвится агентом в момент чтения из `[craft].stack` файла `.kit/answers.toml`.
Это ровно тот механизм, который нам нужен, и он **не требует подстановки в модели**.

## 1. Разрез нынешнего лейна: файл → лейн

Предлагаются **четыре контент-лейна** (плюс существующий `iva-qa-mcp`):

| Лейн | Тип по ADR-0059 | Кому | Юнитов |
|---|---|---|---|
| `tacticum-autotest-core` | процесс | QA **и** разработчикам | 37 |
| `iva-<slug>-autotest-base` | стек (по одному на стек) | QA и разработчикам | 17 |
| `iva-qa-tms-base` | процесс (порт TMS) | только QA | 15 |

### 1.3 `iva-qa-tms-base` — порт TMS (15)

Порт Allure TestOps ортогонален стеку: TestOps — не тест-стек, а трекер прогонов. Один и тот же
порт обслуживает и canvas, и selenium, и squish.

`tms-read` (скилл) · `tms-scripts-testops-cli` + `tms-testops-{init,main,client,testcase,launch,params}` (7 файлов клиента) ·
`tms-read-{aql-notes,launch-json,tc-plain}` (3 справочника) · `secrets-example` · `gitignore-secrets` ·
`craft-write-autotest-testops-api` (вход «TC из TestOps») · `craft-fix-failed-test-launch-input` (вход «ланч»).

Два последних сейчас лежат среди справочников навыков `write-autotest`/`fix-failed-test`. Они
описывают **вход из TMS** и без клиента мертвы — переезжают сюда. Это единственная межлейновая
зависимость в схеме (§5).

### 1.4 `iva-qa-delivery-base` — гейт и покрытие (4)

`jira-issue-autotest` (скилл: Jira → автотесты → ланч) · `craft-shared-pipeline-gate`
(`.agent-kit/craft/shared/pipeline-gate.md`) · `craft-shared-coverage-ledger-template` ·
**новый** `craft-shared-coverage-ledger-convention`.

Последний — результат **расщепления файла**. `shared/ledger-and-deviations.md` сейчас несёт две
разные вещи: (а) инвариант «финальный исход ⇔ строка метрик в `.tasks/metrics.jsonl`» +
связывание отступлений — это дисциплина закрытия работы, нужна всем; (б) конвенция
coverage-ledger — это метрика покрытия, собственность QA. Их надо разнести, иначе разработчик
получит либо гейт покрытия, который ему не принадлежит, либо не получит дисциплины закрытия.

### 1.5 Спорные случаи — по каждому вердикт с основанием

| Юнит | Вердикт | Основание |
|---|---|---|
| **`run-tests`** | **процесс** | Тело — оркестрация цикла «чистка `allure-raw` → прогон → архив копии → развилка в `fix-failed-test`». Она одинакова на любом раннере. **Но** в теле сидит стековый абзац: «стек знает один браузер: headless chromium», `--headed`, `pytest.ini --strict-markers`. Он переезжает в `stacks/<slug>/pytest-runner.md`; в скилле остаётся ссылка. Без этой правки лейн «процессный» только по имени |
| **`playwright-cli`** | **стек** | Это драйвер разведки. Контракт kit кладёт модель поверхности и инструмент разведки в `stacks/<stack>/recon.md`; у selenium-стека драйвер другой. Ставить его в процесс — значит навязать Playwright squish-стеку. **Оговорка:** в теле сидит третья сущность — «IVA ONE WEB, карта приложения». Это не процесс и не стек, а **поверхность**. Её место — файл проекта `.tasks/aut-research/AUT_OVERVIEW.md` (скилл сам называет его опциональным); из тела вырезать |
| **`fix-failed-test`** | **процесс** | Восемь фаз разбора — механика, общая для стеков. Всё стековое уже вынесено: таксономия, плейбуки, парсер raw, команды раннера — отдельные файлы. Скилл на них ссылается |
| **`batch-autotest`** | **процесс** | Матрица верификации живёт в `batch-conventions.md` (стек), сам батч — процесс |
| **`prepare-mr-branch`** | **процесс** | Git-дисциплина, стек-нейтральна. Отдельно: у него **известный дефект** — `exclusion-patterns.md` не содержит `.agent-kit/**`, `.agents/**`, `.codex/**`, `AGENTS.md`; после разреза агентных файлов станет больше, утечка вырастет (зафиксировано в `qa-pipeline-fit-2026-07-29`) |
| **`retro`** | **процесс, но не автотестовый** | Гигиена агентной инфры (размеры CLAUDE.md, память, беклог) — к автотестам отношения не имеет. Кладу в core, чтобы не плодить лейн, но **помечаю кандидатом на переезд** в гигиенический лейн (`tacticum-lite-base` рядом) |
| **`rebuild-autocore`** | **ни то ни другое — рекомендую выкинуть** | Это инфраструктура проекта (вендоренная зависимость), не процесс и не стек. Тело само пишет: «в референсе `one-web-kmp` скилл не работает — там `autocore` приходит с внутреннего PyPI». Единственный известный репозиторий, где он мёртв. Если оставлять — только в core, `tier: full`, с явным гейтом по параметру `vendored_dep` |
| **`craft-shared-jira-candidates`** | **процесс** | Заведение дефекта в Jira — QA-собственность, но *черновик кандидата в файле* нужен и разработчику, нашедшему продуктовый баг. Собственность проходит по write-каналу (`iva-qa-mcp`), а не по формату файла. Оставляю всем |
| **`craft-shared-pipeline-gate`** | **только QA** | Формальный гейт шага 4 конвейера ADR-0060. Шаг принадлежит QA |
| **`craft-rules-invariants`** | **процесс** | Сам файл объявляет себя «стек-нейтральным каноном»: правила, выжившие в обеих референс-реализациях |
| **`agents/*` (3 субагента)** | **процесс** | ADR-0059 Решение 3 держит тексты агентов стековыми **для разработки**; здесь иначе — тела уже параметризованы, ссылаются на файлы стека, а не воспроизводят их. Ставить три копии агентов на стек — это ровно тот дубль, от которого уходим |

## 2. Именование: как гарантировать, что два стека не столкнутся

### 2.1 Что реально проверяется, а что нет

Проверено по коду:

- `compose()` (`apps/backend/src/backend/catalog/domain/composition.py:41`) сливает **только по
  `ingredient_id`**. Коллизия легальна, позже объявленный выигрывает.
- Предупреждение в логе сида — тоже **только по `ingredient_id`**
  (`seed_profile.py:313–334`, `seed_base_ingredient_collision`).
- Тест `test_single_owner_lanes_are_pairwise_disjoint`
  (`apps/backend/tests/catalog/test_iva_role_presets.py:248`) — **только по `ingredient_id`**.
- **`target_file` не проверяет ничто.** Ни схема, ни сид, ни тесты.

Отсюда главный вывод: **уникальности `ingredient_id` недостаточно.** Два лейна с разными id и
одинаковым `target_file` оба доедут до рендера, оба дадут `write_file` в один путь, и победит тот,
чей `action` выполнится позже, — молча, без предупреждения. Для `skill_spec`/`agent_spec` путь
выводится из id (`.claude/skills/{ingredient_id}/SKILL.md`), поэтому там уникальность id
достаточна; для `repo_config` — нет, а у нас 57 из 72 юнитов именно `repo_config`.

### 2.2 Правило именования (два условия, оба обязательны)

> **Всякий юнит стек-лейна: `ingredient_id` начинается со `<slug>-`, а `target_file` —
> с `.agent-kit/craft/stacks/<slug>/`. `<slug>` равен имени каталога стека буква-в-букву.**

Правило механическое: столкновение видно глазом, не выводится рассуждением.

Примеры двух стеков рядом:

| Стек | ingredient_id | target_file |
|---|---|---|
| canvas | `pytest-playwright-canvas-pytest-runner` | `.agent-kit/craft/stacks/pytest-playwright-canvas/pytest-runner.md` |
| selenium | `pytest-selenium-pytest-runner` | `.agent-kit/craft/stacks/pytest-selenium/pytest-runner.md` |
| canvas | `pytest-playwright-canvas-rules-tests` | `.../stacks/pytest-playwright-canvas/rules/tests.md` |
| selenium | `pytest-selenium-rules-tests` | `.../stacks/pytest-selenium/rules/tests.md` |
| selenium (опц.) | `pytest-selenium-cross-browser-verification` | `.../stacks/pytest-selenium/cross-browser-verification.md` |

**Исключение — скиллы-драйверы разведки.** `playwright-cli` не начинается со слага, и переименовывать
его в `pytest-playwright-canvas-cli` не надо: это пользовательское имя навыка. Драйверы уникальны
естественно (`playwright-cli`, `squish-cli`, `selenium-cli`) — но уникальность держится не правилом,
а именем инструмента. Закрывается тем же тестом попарной непересекаемости, который уже есть.

### 2.3 Что доделать в проверках

Одна новая проверка обязательна:

```
test_lane_target_files_are_pairwise_disjoint(role_id, lanes)
```

— зеркало существующего `test_single_owner_lanes_are_pairwise_disjoint`, но по
`metadata.target_file` (для `repo_config`/`instruction_pack`) и по развёрнутому
`target_path_template` (для остальных). Без неё правило §2.2 — соглашение, а не гарантия, и
первое же нарушение пройдёт молча.

Отдельно стоит завести предупреждение в сиде по `target_file` — по образцу существующего
`seed_base_ingredient_collision`. Это не блокер разреза, но дыра общая, не только QA-шная.

## 3. Состав ролей

### 3.1 Роль на поверхность, не роль на компанию

`depends_on` объявляется в манифесте и **замораживается на сиде**
(`seed_profile.py:238` — `depends_on_immutable`). Значит набор стеков — свойство **роли**, а не
установки. Из этого следует прямо: **роль заводится на поверхность**, и одна роль `iva-role-qa`
на все репозитории невозможна, если стеки различаются.

| Роль | `depends_on` |
|---|---|
| `iva-role-qa-kmp` | `tacticum-core-base`, `tacticum-autotest-core`, `iva-pytest-playwright-canvas-autotest-base`, `iva-qa-tms-base`, `iva-qa-delivery-base`, `iva-qa-mcp` |
| `iva-role-qa-web` | то же, но стек `iva-pytest-selenium-autotest-base` |
| **`iva-role-qa-oneweb`** (два стека) | `tacticum-core-base`, `tacticum-autotest-core`, **`iva-pytest-selenium-autotest-base`**, **`iva-pytest-playwright-canvas-autotest-base`**, `iva-qa-tms-base`, `iva-qa-delivery-base`, `iva-qa-mcp` |
| `iva-role-kmp` (разработчик) | нынешние 7 лейнов **+ `tacticum-autotest-core` + `iva-pytest-playwright-canvas-autotest-base`** |

Альтернатива — одна жирная `iva-role-qa`, композящая **все** стек-лейны, и селектор решает, чем
работать. Цена: канон всех стеков на диске у каждого инженера, включая ненужные; ровно тот
конфликт поверхностей, который просили убрать. **Не рекомендую.**

Цена рекомендации — рост числа ролей (одна на поверхность). Но роли тонкие (4 пак-ингредиента),
и это уже принятая модель: `iva-role-go` / `-kmp` / `-web` / `-ios` / `-mail` живут ровно так.

### 3.2 Что видит агент при двух стеках

```
.agent-kit/
├── README.md
├── craft/
│   ├── craft-answers.example.toml
│   ├── rules/invariants.md              ← стек-нейтральный якорь
│   ├── shared/{ledger-and-deviations,jira-candidates}.md
│   ├── shared/{pipeline-gate,coverage-ledger.template,coverage-ledger-convention}.md  ← только QA
│   ├── skills/<навык>/references/…      ← процессные справочники, один комплект
│   └── stacks/
│       ├── pytest-selenium/{9 + 2 опц. + rules/}          ← ЛЕГАСИ
│       └── pytest-playwright-canvas/{9 + rules/}          ← НОВЫЙ
└── tms/…                                 ← только QA

.claude/skills/  write-autotest · batch-autotest · fix-failed-test · run-tests ·
                 prepare-mr-branch · retro · craft-home · tms-read · jira-issue-autotest ·
                 playwright-cli ·  selenium-cli        ← по одному драйверу на стек
.claude/agents/  codebase-analyst · dom-explorer · code-writer
```

Один комплект процессных навыков, два комплекта стекового канона, два драйвера. Ни один путь не
пересекается — это и есть ответ на «чтобы не конфликтовали».

## 4. Выбор стека, когда их два

### 4.1 Честная констатация

Механизма параметров в модели нет: тела доставляются дословно (`renderer.py:212` —
`content: body`, без подстановки; `.format()` применяется только к `target_path_template` и только
по `{ingredient_id}`). Значит выбор стека **не может** решаться на сборке. Он решается либо на
установке (одна роль = один стек — но нам нужны два), либо **на чтении, агентом**.

`kit` решает ровно так: пути в телах — `$CRAFT/stacks/{stack}/pytest-runner.md`, `{stack}`
резолвится агентом из `[craft].stack` в `.kit/answers.toml`. Текст доставляется дословно —
плейсхолдер живёт в тексте, а не в модели. **Механизм нам подходит без изменений в модели.**

### 4.2 Предложение

**Где хранится выбор — в репозитории, не в профиле.** Соответствие «эти каталоги — легаси, те —
новый код» меняется по мере переезда кода и не должно требовать релиза профиля.

Носитель — `.tacticum/autotest.toml`, рядом с `.tacticum/context.yaml` (репо-владение, поставка
его не трогает):

```toml
[autotest]
default_stack = "pytest-playwright-canvas"

[[autotest.map]]
paths = ["tests/legacy/**", "pages/legacy/**"]
stack = "pytest-selenium"

[[autotest.map]]
paths = ["tests/kmp/**", "pages/kmp/**"]
stack = "pytest-playwright-canvas"
```

**Почему не `.kit/answers.toml`:** `[craft].stack` там — скаляр, один стек. Расширять чужой
контракт под нашу нужду нельзя, а вести карту в двух местах — гарантированный дрейф. Если проект
ведёт базу kit, `.kit/answers.toml` остаётся источником прочих параметров (`default_env`,
`product_clone`, `vendored_dep`), а стек берётся из нашего файла. Это надо явно написать в
`craft-home`, иначе разъедутся.

**Порядок резолва — фаза 0 всякого стеко-трогающего навыка:**

1. пользователь назвал стек явно («почини легаси-тест») → берём его;
2. у работы есть конкретный файл/каталог → первое совпадение в `[[autotest.map]]`;
3. под `.agent-kit/craft/stacks/` ровно один каталог → берём его, вопроса не задаём;
4. иначе — **`AskUserQuestion`, и не угадывать.**

Пункт 3 важен отдельно: в одностековом репозитории (большинство) резолв обязан быть немым, иначе
разрез сделает хуже, чем было.

### 4.3 Оценка честно — чего это решение не даёт

- **Ничто не заставляет агента выполнить фазу 0.** Это инструкция в теле навыка, а не проверка.
  Пропустит — прочитает канон не того стека и напишет тест по чужим шаблонам. Ошибка будет тихой:
  файлы существуют, ссылки не битые, просто не те.
- **Карта в репозитории может отстать** от реального переезда кода — тогда resolve отдаёт
  уверенно неверный ответ, что хуже вопроса.
- **Смешанная работа** (один тест трогает и легаси-страницу, и новую) правилом не покрывается
  вообще — попадает в пункт 4 (вопрос человеку), и это правильно, но это не автоматизация.

**Что стоит добавить, чтобы это не было только текстом** (рекомендую, ~60 строк):
резолвер-скрипт `.agent-kit/craft/resolve-stack.py` в процессном лейне. Навык вызывает его вместо
рассуждения, получает имя стека либо код «неоднозначно», и цитирует выдачу в отчёте. Детерминизм
вместо дисциплины; проверяемо в отчёте; ставится тем же `repo_config`, никаких изменений модели.
Без него схема рабочая, но держится на том, что агент прочитал инструкцию.

## 5. Переиспользование разработчиками

### 5.1 Что подключать

`iva-role-kmp` += `tacticum-autotest-core` + `iva-pytest-playwright-canvas-autotest-base`.
Больше ничего. Разработчик получает: написание автотеста по сценарию, пакетную автоматизацию,
прогон, разбор падений, чистую MR-ветку, трёх субагентов и канон стека.

### 5.2 Что НЕ должно уехать разработчику — и где это отрезано

| Что | Лейн, который не даём | Почему |
|---|---|---|
| заведение дефектов в Jira | `iva-qa-mcp` | write-канал идёт под **личным Atlassian PAT** и сужен до Jira-дефектов/статусов. Разработчик, заводящий дефекты в потоке QA от своего имени, ломает процесс, а не помогает |
| публикация прогонов (ланчи TestOps) | `iva-qa-tms-base` | клиент TestOps + `jira-issue-autotest`. Локальный прогон разработчика — не ланч. Секреты TestOps (`secrets.yaml`) тоже здесь |
| чтение покрытия | `iva-qa-mcp` (`helm-analyst.requirement_tests`) + `iva-qa-delivery-base` | покрытие — метрика QA; гейт шага 4 конвейера ADR-0060 — шаг QA |
| coverage-ledger | `iva-qa-delivery-base` | реестр покрытия ведёт владелец покрытия |

Отрез проходит **по границе лейнов**, а не по тексту навыков — это его главное свойство: ничего не
нужно «выключать», разработчику просто не ставится лейн.

### 5.3 Что придётся доделать — единственная межлейновая зависимость

`write-autotest` принимает вход «URL Allure TestOps», `fix-failed-test` — вход «ланч». Оба
справочника (`testops-api.md`, `launch-input.md`) уезжают в `iva-qa-tms-base`. У разработчика их
не будет → **битая ссылка** в теле процессного навыка.

Правится текстом, но правится обязательно: в обоих навыках вход из TMS помечается условным —
«источник доступен, если установлен лейн `iva-qa-tms-base`; не установлен → скажи об этом и работай
от CSV/текста». Это единственное место в схеме, где лейн ссылается на содержимое другого лейна;
всё остальное самодостаточно.

### 5.4 Пересечения, которые надо развести в паке роли

Коллизий `ingredient_id` нет (проверено: id стек-лейна автотестов и id `iva-kmp-development-base`
не пересекаются). Но есть **смысловые** наложения, которые модель не поймает:

- **четыре агента, пишущие код**: `coder` + `tester` + `test-runner` (dev-core/kmp) и `code-writer`
  (автотест). Роль обязана в своём `CLAUDE.md`-фрагменте сказать, кто когда;
- **два драйвера браузера**: `playwright` (MCP-сервер из `tacticum-ui-base`, есть у web/kmp-ролей) и
  `playwright-cli` (скилл-драйвер стек-лейна). Разные вещи, но агент выберет любой;
- **два тест-навыка**: `kmp-ui-testing` (dev) и `run-tests` (автотест). Первый про юнит/UI-тесты
  модуля, второй про e2e-автотесты. Разграничить в паке роли.

### 5.5 Вопрос, который решает не разработка

Должна ли QA-автоматизация быть у разработчиков — **это решение заказчика, не наше**. Схема
позволяет и то и другое одним словом в `depends_on`. Но от ответа зависит **имя**
`tacticum-autotest-core`: если лейн только для QA, честнее `iva-qa-autotest-core`, и его non-goals
пишутся иначе. Переименование лейна после сида — не бесплатно. **Спросить до реализации.**

## 6. Порядок лейнов

### 6.1 Где порядок значим

Порядок = приоритет при коллизии `ingredient_id`, позже объявленный выигрывает
(`composition.py`, ADR-0056 Addendum 3). На `tacticum-ui-base` обжигались именно так: он стоит
**перед** `iva-kmp-development-base` сознательно, чтобы Compose-версии четырёх ДС-навыков перекрыли
веб-версии (`KNOWN_OVERRIDES` в `test_iva_role_presets.py:236`).

**В предлагаемой схеме перекрытий нет по построению** — правило §2.2 разводит и id, и пути.
Это осознанный выбор: перекрытие между двумя стеками одной роли было бы катастрофой (легаси-канон
молча съел бы новый), поэтому его надо сделать невозможным, а не управляемым.

Отсюда: `KNOWN_OVERRIDES` для QA-ролей должен остаться **пустым**, и это утверждение проверяется
существующим `test_golden_parity_union_equals_sum_of_lanes`.

### 6.2 Предписанный порядок

```yaml
depends_on:
  - tacticum-core-base                              # 1. общий минимум
  - tacticum-autotest-core                          # 2. процесс автотестов
  - iva-pytest-selenium-autotest-base               # 3. стек A (легаси)
  - iva-pytest-playwright-canvas-autotest-base      # 4. стек B (новый)
  - iva-qa-tms-base                                 # 5. порт TMS
  - iva-qa-delivery-base                            # 6. гейт и покрытие
  - iva-qa-mcp                                      # 7. MCP-каналы
```

Обоснование позиций:

- **core первым** — слабейший, его перекрывает кто угодно (общая конвенция всех ролей);
- **процесс перед стеками** — если когда-нибудь стеку понадобится перекрыть процессный справочник,
  прецедент `ui-base` → `kmp` даёт ему такую возможность. Сегодня не нужно, завтра дешевле;
- **порядок стеков между собой не значим и не должен стать значимым.** Это инвариант, а не
  случайность: если он нарушится, один стек начнёт затирать другой. Проверяется тестом §2.3;
- **QA-лейны последними** — они добавляют, а не спорят; позиция выбрана для детерминизма.

### 6.3 Настоящая ловушка порядка — не там, где смотрят

Коллизия `ingredient_id` хотя бы **логируется** на сиде. Коллизия `target_file` — **нет**:
оба юнита доезжают до рендера, оба дают `write_file`, побеждает тот, чей action выполнится позже
(лейны конкатенируются в порядке объявления — `load_composed_ingredients`), и об этом не узнает
никто. Это тот же ожог, что на `ui-base`, только без предупреждения. Отсюда обязательность §2.3.

## 7. Стоимость и риски перехода

### 7.1 Объём

| Работа | Объём |
|---|---|
| манифесты | 1 переписать (`iva-qa-autotest-base` → депрекация), 4 новых лейна, 1–3 роли. ~1400 строк YAML (нынешний манифест — 910 строк на 72 юнита, ≈12,6 строки/юнит) |
| тела: переписать пути стековых файлов на `stacks/<slug>/` + фаза 0 резолва | **~32 файла** (посчитано грепом: 6 тел агентов, 8 тел навыков ×2 провайдера, ~14 справочников, 4 стековых файла с перекрёстными ссылками) |
| расщепление `ledger-and-deviations.md` | 1 файл → 2 |
| вырезать стековый абзац из `run-tests`, карту AUT из `playwright-cli` | 2 файла |
| тесты | `ROLE_LANES` (+3 роли), `_mirrors.yaml`, **новый** `test_lane_target_files_are_pairwise_disjoint` |
| второй стек (selenium/squish) | 9 файлов канона **с нуля** — их у нас нет (§8) |

**Вес — крупная.** Далеко за 10 файлов и 150 строк; план обязателен, два критика с оппонированием.

### 7.2 Что ломается у уже установленного инженера

**Повторный pull обязателен** — автообновления нет.

**Главный риск: осиротевшие файлы.** Проверено по коду: словарь действий рендера —
только `write_file` и `merge_json` (`renderer.py`), **действия удаления не существует**. Значит
после переезда девяти стековых файлов из `.agent-kit/craft/*.md` в
`.agent-kit/craft/stacks/<slug>/*.md` старые копии **остаются на диске** — рядом с новыми. На диске
окажутся два канона, оба читаемые грепом, и агент не отличит живой от мёртвого. Это ровно тот
дрейф, от которого предостерегает сам `.agent-kit/README.md` («канон обязан оставаться одинаковым
у всех»). То же — с переименованием `craft-stack` → `craft-home`: осиротеет
`.claude/skills/craft-stack/`.

Три варианта, цена каждого:

| Вариант | Что делает | Цена |
|---|---|---|
| **(а) надгробия** *(рекомендую)* | 9 юнитов `repo_config` со старыми `target_file` и телом «файл переехал в `stacks/<slug>/…`, не читать» | 9 лишних юнитов в манифесте навсегда (или до вычистки когорты); зато работает в нынешней модели, без изменений кода |
| (б) `delete_file` в рендере | правильное долгосрочное решение | изменение модели доставки — своя ADR, свой риск; **вне объёма разреза QA** |
| (в) «снеси `.agent-kit/` руками перед pull» | строчка в релиз-ноте | опирается на то, что инженер прочитает и сделает; при живой когорте — не опора |

Рекомендую (а) для девяти переехавших + (в) в релиз-ноте как страховку; (б) завести отдельной
задачей — дыра общая, не QA-шная.

### 7.3 Версии

- `tacticum-autotest-core` — **1.0.0**. Не 0.6.0: пути канона несовместимы с 0.5.0, мажор это и
  означает.
- Стек-лейны, `iva-qa-tms-base`, `iva-qa-delivery-base` — 0.1.0 (новые).
- `iva-qa-autotest-base` — **`deprecated: true`, заморожен на 0.5.0**.
- **Зеркала (`_mirrors.yaml`) здесь не применимы**, и это надо сказать прямо. Правило зеркал
  (ADR-0059 Решение 7) требует **байт-в-байт** одинаковых тел у владельца и зеркала; у нас тела
  меняются (пути). Это осознанное расхождение, а не зеркало: переключаем роль на новые лейны одним
  PR, старый лейн замораживаем. Пары в `_mirrors.yaml` не заводить.
- `iva-role-qa` — если роли переименовываются в `iva-role-qa-<поверхность>`, старая роль
  депрекируется, а установленным придётся ставить новую. **Альтернатива:** оставить `iva-role-qa`
  как имя для kmp-поверхности (у неё живая когорта) и завести новые имена только для новых
  поверхностей. Рекомендую альтернативу — миграция когорты дороже красоты имён.

## 8. Чего не хватает для реализации

Данные, без которых проект не превращается в работу. Ничего из этого не додумываю.

1. **Карта поверхностей.** Для каждого репозитория: имя репо, поверхность, стек(и), сосуществуют ли
   два стека, и если да — **какие каталоги какому принадлежат**. Без этого нельзя ни посчитать
   число стек-лейнов, ни заполнить `[[autotest.map]]`, ни решить, сколько ролей заводить.
   *Это блокирующий пункт: всё остальное — оформление.*

2. **Стек-профили `squish` и мобильных — девять обязательных файлов контракта**, заполненных:
   команды раннера и его артефакты · формат сырых результатов · таксономия падений и их улики ·
   плейбуки правок · инструмент и модель разведки поверхности · каркасы теста/page-модуля ·
   конвенции батча и матрица верификации · дисциплина тест-функций · модель page-слоя и стратегии
   адресации. Сейчас у нас есть **один** заполненный стек (`pytest-playwright-canvas`) и один
   чужой референс (`pytest-selenium` в kit, среды Angular-эры — под их репозиторий, не под наш).
   Написать их по аналогии нельзя: `recon.md` и `rules/page-objects.md` — это знание о живом
   приложении, не о фреймворке.

3. **Выгрузки репозиториев** (или read-доступ) минимум по одному legacy/selenium-репо и одному
   squish-репо. Нужны, чтобы писать канон с натуры. Без них стек-лейны будут пустыми оболочками
   с правильными именами файлов.

4. **Владелец на стек.** Стек-лейны будут авторить инженеры поверхности, не мы; в манифесте есть
   `maintainer`, и его надо кем-то заполнить. Нужен ответ, кто это по каждому стеку.

5. **Решение: получают ли разработчики автотест-лейны** (§5.5). От него зависит имя процессного
   лейна и его non-goals; переименование после сида — не бесплатно.

6. **Ведут ли целевые репозитории базу kit** (`.kit/answers.toml`). От этого зависит, живёт ли
   селектор стека рядом с их параметрами или отдельным файлом `.tacticum/autotest.toml`, и не
   разъедутся ли два источника.
