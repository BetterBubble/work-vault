## Вопрос 1. Механизм продления есть; ФОНОВОГО запуска нет, ленивый — есть

Механизмов продления **два, и их нельзя смешивать**.

**А. Фоновое продление пачкой — код есть, вызывающего в проде нет.**

| что | где |
|---|---|
| `refresh_due(...)` — обходит доступы в горизонте, продлевает | `helm/src/helm/application/iva_write.py:531-562` |
| выборка кандидатов | `helm/src/helm/infrastructure/db/credential_repo.py:288` (`list_due_for_refresh`) |
| настройка горизонта, 3600 с | `helm/src/helm/config.py:630` (`iva_oauth_refresh_horizon_seconds`) |

Call-sites `refresh_due` — **ровно один вне тестов**:
`helm/src/helm/interface/api/routers/iva_write.py:661`, внутри ручки
`POST /api/iva/oauth/refresh` (роутер объявлен на `:648-669`, префикс — `:75`).
Тесты: `tests/application/test_iva_write_consent.py:837` и `:855`. Больше ничего.

Кто дёргает саму ручку — **никто**:

- планировщика в коде нет: `APScheduler` / `celery` / `AsyncIOScheduler` / `crontab`
  не встречаются ни в `src`, ни в `pyproject.toml`, **ни в одной из ~60 веток** репо
  (проверял `git grep` по всем `refname`);
- в `lifespan` приложения фоновых задач нет — там только engine и три MCP
  session-manager'а: `helm/src/helm/main.py:78-98`;
- в `docker-compose.prod.yml` нет сервиса, cron'а или `command`, который бы звал
  `/api/iva/oauth/refresh` (искал `refresh` — совпадения только в комментариях про
  витрины, строки `:102` и `:105`);
- systemd-юниты репозитория к продлению не относятся: `ops/bot-worker/helm-bot-worker.service`
  (воркер очереди `bot_task`, `ExecStart=scripts/bot_worker.py`, слова `refresh` в нём
  нет), `ops/media-worker/`, а `scripts/systemd/iva-rag-refresh.service.d/*` +
  `scripts/helm_daily_refresh.sh` — это refresh **витрин RAG/HRD**, к OAuth-токенам
  отношения не имеет;
- в `scripts/bot_worker.py` и `src/helm/application/bot_worker.py` слова `refresh` нет.

**Код сам это признаёт тремя местами прямым текстом:**
- `src/helm/application/self_service.py:150` — «Отдельного планировщика в helm нет»;
- `src/helm/application/iva_write.py:543` — «Вызывается планировщиком либо ручкой —
  своего таймера модуль не заводит»;
- `tests/application/test_bot_iva_write.py:742` — «фонового продления в деплое нет».

→ **Запись памяти направления «таймер продления НЕ запускается ничем» — подтверждается
по коду.** Функция и HTTP-ручка существуют, планировщика/крона/таймера, который бы их
звал, нет ни в приложении, ни в деплой-конфигах репозитория.

**Б. Ленивое продление при обращении — существует и вызывается.**

`refresh_credential(...)` — `src/helm/application/iva_write.py:458-528`.
Прод-call-sites два:
- `src/helm/application/iva_write.py:552` (внутри `refresh_due`, см. выше — мёртвая ветка);
- **`src/helm/application/iva_write.py:698`** — внутри `issue_credentials`: если
  `reason_for_denial(row) == "expired"`, доступ продлевается **на месте**, и уже

`issue_credentials` зовут из живых путей:
- `src/helm/interface/mcp/iva_write_surface.py:277` — каждый запрос к `/mcp/iva-write`

Тест ленивого продления: `tests/application/test_iva_write_linked_identity.py:183`

## Вопрос 2. Тексты «статуса»: ветка «истёк» есть, «всё работает» условно

Генерация — `helm/src/helm/application/bot_iva_write.py`, функция
`status_text(email, items)` — **`:650-712`**. Формат даты `_WHEN_FORMAT = "%d.%m.%Y %H:%M UTC"`
— `:190`.

Три запрошенные фразы:

| фраза | файл:строка |
|---|---|
| `", дальше продлится сам"` | `bot_iva_write.py:686` (ветка `item.live and item.renewable`) |
| `", действует до {…}"` | `bot_iva_write.py:690` |
| `"Сейчас всё подключённое работает — делать ничего не нужно."` | `bot_iva_write.py:709` |

Полный набор веток `status_text` (`:674-711`), состояний **четыре**:

- `live` + срок + `renewable` → «подключено, действует до …, дальше продлится сам» (`:685-691`);
- `live` + срок + не `renewable` → «…, дальше нужно будет согласие заново» (`:688`);
- `live` без срока → «подключено (без срока)» (`:678`);
- нет записи / `reason == "missing"` → «не подключено» (`:693`);
- `reason == "revoked"` → «доступ отозван, нужно согласие заново» (`:695`);
- **`reason == "expired"` + `renewable`** → «срок доступа вышел, но он продлится сам при
  первом обращении — согласие заново давать не нужно» (`:696-700`);
- **`reason == "expired"` + не `renewable`** → «срок истёк, нужно согласие заново» (`:702`).

**Что бот говорит на ПРОТУХШИЙ доступ.** Ветка «истёк» есть, и она разводит два случая
по наличию живого refresh-токена. Итоговая строка выбирается на `:705`:

```python
if all(item.live or (item.reason == "expired" and item.renewable) for item in items):
    lines.append("Сейчас всё подключённое работает — делать ничего не нужно.")
else:
    lines.append("Чтобы подключить или продлить — напишите «дай доступ».")
```

То есть **«всё работает — делать ничего не нужно» приезжает и на протухший доступ**, если
у него живой refresh (`renewable=True`). Это сделано намеренно (докстринг `:653-658`), и
опирается ровно на ленивый refresh из вопроса 1. На протухший доступ БЕЗ живого refresh
бот говорит «срок истёк, нужно согласие заново» + «напишите „дай доступ"» — правду.

**Тесты на ветку «истёк» есть, но только на уровне чистого текста:**
- `tests/application/test_bot_iva_write.py:386` — `revoked` против `expired`;
- `tests/application/test_bot_iva_write.py:737` — `expired`+`renewable` не зовёт за согласием;
- `tests/application/test_bot_iva_write.py:882` — приглашение «дай доступ» только там, где есть что делать;
- снимок текстов `tests/data/bot_texts_snapshot.txt:64-71` — секции «статус · истёк,
  продлится сам» и «статус · истёк насовсем».

**Сквозного теста (HTTP-вебхук бота + настоящая строка в БД с прошедшим `expires_at`) на
ветку «истёк» НЕТ.** Единственный интеграционный тест статуса —
`tests/interface/test_bot_iva_write.py:587` (`test_status_command`) — проверяет только
«не подключено» и «подключено». В `tests/interface/*.py` нет ни одного места, где
`expires_at` кладётся в прошлое для проверки бота (проверял grep по `expires_at` во всём
каталоге; прошлые даты есть только в `test_consent_before_key.py:262,290` — это про ключ,
не про статус).

**Мелочь по формату даты:** `bot_iva_write.py:690` печатает `item.expires_at.strftime(...)`
без явного `.astimezone(UTC)`, суффикс «UTC» в формате зашит константой (`:190`). Колонка
`timestamptz` (`models.py:3384`), asyncpg отдаёт tz-aware UTC — так что сегодня подпись
верна, но она держится на драйвере, а не на коде.

## Вопрос 3. «Статус» живость доступа НЕ проверяет — читает только свою БД

Сборка данных для `status_text` — `helm/src/helm/interface/api/routers/bot_iva_write.py:298-337`
(`_status_reply`). Внешних вызовов там нет ни одного: только

- `iva_write.person_subjects` (`:317`) — БД;
- `iva_write.credential_of_person` (`:320-322`) — БД;
- `creds.reason_for_denial(row, now=now)` (`:323`) — **чистая функция над полями строки**:
  `credential_repo.py:187-199`, смотрит `row is None` / `row.revoked_at` / `row.expires_at <= now`;
- `creds.can_renew(row, now=now)` (`:334`) — тоже чистая: `credential_repo.py:202-221`,
  смотрит наличие `refresh_ciphertext`/`refresh_nonce` и `refresh_expires_at > now`.

Запрос `whoami`/`myself` к Jira/Confluence в коде есть, но **только на колбэке согласия**:
`src/helm/application/iva_write.py:377` (`client.whoami` внутри `complete_consent`),
эндпоинты — `src/helm/infrastructure/iva_oauth/client.py:54-55`
(`jira: /rest/api/2/myself`, `confluence: /rest/api/user/current`). В пути «статуса» этот
вызов не встречается.

→ **Факт: «статус» отвечает по полям строки в таблице `external_credential`, живость
токена в Jira/Confluence он не проверяет.** Если токен погашен на стороне заказчика
(человек отозвал его в своём профиле, админ погасил сессию), запись у нас остаётся живой,
и бот скажет «подключено, всё работает». Такое расхождение кодом не ловится нигде —
`revoke` в `routers/iva_write.py:619-645` гасит только НАШУ копию, и это в докстринге
названо прямо (`:625-628`).

## Вопрос 4. Доступы Confluence/Jira и инструмент `iva_write_connect` — РАЗНЫЕ вещи

Инструмент определён в **helm**, а не в контейнере Atlassian:

- имя: `helm/src/helm/interface/mcp/iva_write_tools.py:27` (`CONNECT = "iva_write_connect"`,
  префикс `:25`); объявление для `tools/list` — `CONNECT_SPEC`, `:52-67`; список — `:104`,
  `listing()` — `:107-109`;
- обработчик: `helm/src/helm/interface/mcp/iva_write_surface.py:450-523` (`_tool_connect`);
- поверхность: `iva_write_surface.py:936` (`surface`), `MOUNT_PATH = "/mcp/iva-write"` (`:78`),
  монтируется в `src/helm/main.py:233`.

**Инструмент виден НЕЗАВИСИМО от наличия доступов Confluence/Jira — это в коде явно:**

- `iva_write_surface.py:1030-1036`: при `tools/list` **без единого доступа** helm отдаёт
  свои инструменты сам, не спрашивая контейнер;
- `iva_write_surface.py:1013-1028`: `initialize`/`notifications/*`/`ping` без доступов helm
  тоже отвечает сам (`_handshake_reply`, `:841-885`) — чтобы клиент поднял сессию и дошёл
  до `tools/list`;
- порядок перехвата описан в комментарии `:991-995`: наши инструменты обрабатываются **до**
  проверки доступов.

**От чего видимость инструмента ЗАВИСИТ (всё это к согласию Confluence/Jira отношения не имеет):**

1. **MCP-сервер должен быть подключён у человека в клиенте.** Не подключён — helm вообще
   не получает запроса, и никакого `iva_write_connect` в списке нет.
2. **Bearer-токен должен резолвиться:** `require_write_identity` —
   `src/helm/interface/api/routers/iva_write.py:92-…`, зовётся из
   `iva_write_surface.py:957`. Нет заголовка `Authorization: Bearer` → **401** (`:112-118`),
   не признан ни project-hub `/resolve`, ни dev-MCP `phk_*` → отказ (`:122-137`).
   401 приходит на ЛЮБОЙ запрос, включая `initialize` (`iva_write_surface.py:956-966`) —
   для клиента это «сервер не подключился», список инструментов не появится вовсе.
3. **`HELM_IVA_WRITE_MCP_URL` должен быть задан**, иначе поверхность отвечает 503 на всё
   (`iva_write_surface.py:947-954`; в проде задан — `docker-compose.prod.yml:81`).
4. Отдельный путь: при живых доступах список берётся у контейнера и наши инструменты
   **дописываются** в его ответ — `_proxy_tools_list` (`:730-780`) → `_with_our_tools`
   (`:783-832`). Если ответ контейнера не распарсился, тело возвращается нетронутым
   (`:786-787`, `:831-832`) — то есть **есть путь, где доступы живы, а `iva_write_connect`
   из списка пропал**.

→ **Факт: это две разные вещи.** Доступы Confluence/Jira живут в таблице
`external_credential` и проверяются на выдаче токена; `iva_write_connect` — инструмент
helm'овской MCP-поверхности, и его наличие у человека определяется тем, подключён ли
MCP-сервер `iva-write` в его клиенте и проходит ли его ключ через `require_write_identity`.
Ситуация «доступы живы, а инструмента нет» кодом полностью допускается — минимум по трём
причинам выше (сервер не добавлен, ключ не резолвится → 401, ответ контейнера не распознан).

## Пункт 3 (следы Острякова) — не снял; и ДО сервера видно, что часть следов не существует

Не снял. Но два ограничения источников видны по конфигу и коду, и их стоит знать заранее,
иначе поход на сервер даст ложный вывод:

1. **У traefik НЕ включён access-лог.** В `docker-compose.prod.yml:11-31` среди флагов
   `command:` нет ни `--accesslog`, ни `--accesslog.filepath`. Значит источник
   «прокси видел запрос на `/mcp/iva-write` со статусом 401» **отсутствует физически** —
   искать надо в логе uvicorn контейнера `helm-helm-1`.
2. **401 нельзя привязать к человеку по логу приложения.** Отказ поднимается в
   `require_write_identity` (`routers/iva_write.py:113-118` — нет заголовка;
   `:135-142` — токен не признан ни project-hub `/resolve`, ни dev-MCP). **Ни в одной из
   этих веток нет вызова логгера**, и взяться идентификатору неоткуда: 401 означает ровно
   то, что личность не установлена. В access-логе uvicorn останется метод, путь, статус и
   IP — почты там не будет никогда.

   → Развилка лида «401 от него против отсутствия запросов» по логам **не разрешается
   напрямую**. Различить можно только косвенно: по IP и времени, либо по тому, что при
   УСПЕШНОМ резолве след остаётся в таблице `credential_use_log` (`subject` = почта).
   Отсутствие строк в `credential_use_log` по `d.ostryakov@iva.ru` + отсутствие 401 в
   access-логе = сервер у него не подключён; 401 без строк в журнале = блок есть, ключ не
   резолвится. Это лучшее, что даёт имеющаяся телеметрия.

## Пункт 4 (живо ли ленивое продление) — не снял; где смотреть, установил по коду

Не снял. Но искать надо не в логах, а в БД, и запрос точный:

`refresh_credential` при успехе пишет строку в журнал — `iva_write.py:519-527`:

пусто» ≠ «не продлевалось»; отвечает только SQL.
