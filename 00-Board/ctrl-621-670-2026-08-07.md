### Разбор №1: риск обратного хода на noop — риска нет, проверено поведением

Вопрос лида: если секцию из CHANGELOG удалили, а в базе она есть — не обнулит ли молча.

**Не обнулит.** Защита стоит в двух местах, и обе я проверил не чтением, а прогоном:

1. Парсер физически не может вернуть пустую строку — `return section or None` (`seed_community.py`). Нет файла, нет секции, пустая секция → `None` + предупреждение в stderr с именем профиля.
2. Ветка noop пишет только при `payload.changelog is not None and existing.changelog != payload.changelog` (`seed_profile.py:258`).

Поведенческое подтверждение — тест `test_reseed_without_changelog_does_not_wipe_existing` **на живом Postgres 16** (`conftest.py` поднимает контейнер `postgres:16-alpine`, alembic прогоняется — это не sqlite и не фикстура): сеет непустой changelog, затем пересевает с `changelog=None`, ассертит, что старое значение на месте. Зелёный.

Запись действительно доезжает до базы: `session.commit()` в `seed_community.py:268` вызывается безусловно, после `seed_profile`, независимо от статуса — то есть «грязный» ORM-объект на noop сохраняется.

**Два следствия, которые стоит знать Президенту (не провал гейта, а названная цена):**
- **Храповик в одну сторону.** Сид теперь не может очистить changelog никогда. Удалили release notes из файла — в базе останется прежний текст навсегда. Исправить можно только заменой на другой непустой текст. Для release notes цена приемлемая, но это осознанный выбор, а не свойство.
- **Мутация на noop не оставляет следа в `seeded_by`.** `seeded_by=actor` проставляется только в ветке создания (`seed_profile.py:368`); на noop колонка не меняется. След есть только в структурном логе — `seed_changelog_updated_on_noop` с `profile`/`version`/`was_empty`. Для CI-сидера достаточно, но «кто переписал changelog» из строки таблицы не восстановить.

Отдельно отмечу: запись на noop слегка трётся о дисциплину неизменяемости версии (ADR-0009 / ADR-0056). Считаю её законной — `changelog` намеренно не входит в `payload_hash`, и код стоит рядом с lifecycle-полями Profile, которые эта же ветка уже мутирует на noop со ссылкой на US #369 policy A. Прецедент в файле есть, новый не заводится.

## Заявление 1: «обнуления нет» — ПОДТВЕРЖДЕНО, с названной границей

Проверял не чтением условия, а полным конвейером: реальный каталог профиля на диске (`manifest.yaml` + `CHANGELOG.md`) → `_build_payload` → `seed_profile` → мутация файла → пересев → `SELECT` из колонки.

| # | Что сделал | Статус пересева | Значение в базе |
|---|---|---|---|
| A | **удалил секцию** `## [0.1.0]` из файла | `noop` | **прежний текст, 60 симв.** |
| B | **удалил `CHANGELOG.md` целиком** | `noop` | **прежний текст, 60 симв.** |
| C | пустая секция / нет файла на первом севе | `created` | `'## [0.1.0]'` / `None` |

Пустая строка в колонку не доходит — подтверждаю: `return section or None` плюс `or` в `_build_payload`. Состояния ровно два: `NULL` или непустой текст.

**Граница, которой заявление не покрывает: защищено УДАЛЕНИЕ, не защищено ОПУСТОШЕНИЕ.** Отдельный прогон (`[H]`):

```
после сева в базе:      '## [0.1.0] — 2026-08-05\n\n### Added\n\n- Настоящие release notes…'  (89 симв.)
секцию выпотрошили, оставив ОДИН заголовок
payload после этого:    '## [0.1.0] — 2026-08-05'   (не None → защита не срабатывает)
статус:                 noop
в базе стало:           '## [0.1.0] — 2026-08-05'   (23 симв.)
ИТОГ: release notes ПОТЕРЯНЫ
```

Заголовок остаётся, значит `payload.changelog is not None`, значит запись проходит и затирает настоящие release notes огрызком. Предупреждение в stderr при этом **не печатается** — оно висит только на ветке `section is None`. Формально это частный случай заявления 2 («правка перезаписывает, это намеренно»), и противоречия между заявлениями нет. Но охранник ловит **исчезновение**, а не **деградацию**, и в таком виде это стоит знать: достаточно кому-то вычистить содержимое секции, не тронув заголовок и не бампнув версию.

Вердикта не меняет: сценарий требует ручной порчи файла, данные не теряются необратимо (следующий корректный сид восстановит), а поведение согласовано с объявленным замыслом.

## Заявление 2: граница неизменяемости — ПОДТВЕРЖДЕНО, обхода хеша нет

Это был единственный пункт, способный дать отрицательный вердикт. **Не дал.**

```
[E] хеш при трёх РАЗНЫХ changelog (полный / отредактированный / файла нет) одинаков:
    cd967519b2723be6…   → changelog действительно ВНЕ payload_hash

[F] подменил ТЕЛО ИНГРЕДИЕНТА (настоящий контент) + заодно changelog, версию не бампал:
    seed_rejected_immutable
    статус   = rejected
    reason   = version_already_exists_with_different_content
    changelog в базе НЕ тронут — запись не прошла мимо отказа
```

Ветка `noop` физически недостижима при расхождении контента: она стоит **под** `if existing.payload_hash == payload_hash`, а отказ по контенту — в `else` того же сравнения. Записать что-либо в обход отказа этим путём нельзя. Мутируется ровно одна колонка `changelog`, ничего больше.

**Асимметрия, которую стоит зафиксировать (`[G]`).** `changelog`, объявленный **ключом в манифесте** (тот самый «явный override»), входит в `payload.manifest`, а `manifest` целиком идёт в хеш — в `_profile_meta_keys` исключены только `deprecated`/`visibility`/`owner_org`/`superseded_by`. Проверено поведением: два манифеста, отличающиеся только значением `changelog`, дают **разные хеши**, и пересев получает `rejected / version_already_exists_with_different_content`.

То есть один и тот же по смыслу правкой результат зависит от того, откуда взято значение: **правка `CHANGELOG.md` опубликованной версии проходит молча (noop + перезапись), правка `changelog:` в манифесте той же версии — отвергается.** Ни одного манифеста с этим ключом в каталоге нет (`^changelog:` — 0 из 64), так что сегодня это мёртвая ветка. Но если ключ когда-нибудь применят, поведение будет неочевидным. Дефектом ветки не считаю — это свойство `canonical_payload_hash`, существовавшее до неё.

## Заявление 3: заголовок остаётся в значении — ПОДТВЕРЖДЕНО

- **Консьюмер своей шапки не добавляет.** `check_updates.py:99` — `"changelog": latest.changelog if latest else None`, дословный проброс. Это **единственный агентский канал**: в `catalog/domain/builtins/` слово `changelog` не встречается вовсе, то есть builtin install-скилл поле не показывает и не оборачивает.
- **Ни один профиль каталога не добавляет второй заголовок.** Прогнал парсер по всем 64 профилям и посчитал строки `## ` **внутри** каждого значения: у **всех 64 — ровно одна**. Распределение: `{1: 64}`, профилей с другим числом — нет.
- **Ветка `admin_web` не трогает** — 0 файлов (`git diff --name-only origin/main...HEAD`, полный список: `seed_community.py`, `seed_profile.py`, `test_seed_changelog_section.py`).
- Косметику в админке посмотрел, находкой не считаю, как и договаривались: `versions/[ver]/page.tsx:213-225` рисует статичную подпись `Changelog` (класс `eyebrow`), а под ней `{v.changelog}` в `<div style={{whiteSpace:"pre-wrap"}}>`. Markdown не рендерится, поэтому админ видит символы `## [0.4.3] — 2026-08-05` буквально, и версия дублирует ту, что уже стоит в шапке страницы версии. Долг зафиксирован верно.
