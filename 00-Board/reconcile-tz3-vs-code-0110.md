# Реконсиляция ТЗ#3 ↔ код 0.1.10 — что уже есть, что реально новое

Основано на: ТЗ Солонко (`90-Materials/fr-analyst-contracts-skill-review.md`) + baseline-разведка ([[explore-fr-analyst-baseline]]). Read-only, кода не трогал. Цель — точный дельта-скоуп, не зависящий от mirror-развилки.

## TL;DR
Из 5 US плана **US#1 и US#3 сильно сужаются** (каркас уже есть), **US#2 и US#4 — почти полностью новые**, **US#5 — частично**. Ядро реально новой работы компактно: **(1) релаксация wire-имён в Части 1 под 3 предохранителями, (2) механический валидатор границы, (3) формат контрактов 3.1 + серия CT-n, (4) навыки DM/EV с единой нумерацией, (5) пер-раздельный /update-feature с D-n.** «Деление на две части», «двухчастная структура», разделы «Доменные модели/События» — **уже реализованы**, их не создаём, а достраиваем/переосмысляем.

## Дельта по US

### US#1 — Структура FR v2 + оркестрация
**УЖЕ ЕСТЬ (0.1.5):** двухчастная структура внедрена — Часть 1 «Постановка» (§1.1–1.7) + Часть 2 «Приложение» (П.A…П.J), anchor-макросы, оркестрация 9 шагов, стабильные ID (FT-n/UC-n/Q-n/D-n).
**НО семантика частей — ДРУГАЯ, чем в ТЗ.** Сейчас: Часть 1 = человекочитаемые *выводы* прозой, Часть 2 = *факты* (в т.ч. ФТТ П.A и UC П.B живут в Приложении). ТЗ хочет: Часть 1 = *полная to-be спецификация* (формальные FT-n/UC-n **переезжают наверх** как разделы 1.4/1.5 + проектные разделы 1.6–1.8), Часть 2 = только as-is фактура.
**РЕАЛЬНО НОВОЕ:**
- ⭐ **Релаксация §2** — сейчас правило честности §2 запрещает wire-имена ВЕЗДЕ без исключений; ТЗ вводит зону Части 1, где проектные wire-имена РАЗРЕШЕНЫ под 3 предохранителями (основание в Ч.2 + плашка «требует утверждения dev+CTO»/Q-n + валидатор). Это ядро.
- ⭐ **Механический валидатор границы** — не существует. Проверка: в Ч.2 нет проектных имён; каждое wire-имя Ч.1 трассируется к основанию; нарушение = дефект, публикация стоп.
- **Переезд FT-n/UC-n** из П.A/П.B (Приложение) в Часть 1 как формальные to-be разделы.
- **`fr_skeleton: 2`** маркер версии скелета — не существует (поля/версионирования скелета нет вообще).
- **TOC-макрос** Confluence в начале Части 1.
**Сужение:** «создать две части» вычёркиваем — есть. Остаётся переархитектура семантики + 4 новых механизма выше.

### US#2 — Контрактный раздел (api-contracts-discovery)
**УЖЕ ЕСТЬ:** скилл существует (121 стр.), оба контура REST+JUMP, конвенции distrohost цитируются, probe-first, таблица negative evidence. Но это **алгоритм разведки** (5 шагов «как искать»), НЕ формат-спека документа.
**РЕАЛЬНО НОВОЕ (почти всё US):** формат «3.1» отсутствует; серия **CT-n** отсутствует (grep пусто). Новое: реестр изменений (Контур|Контракт|Изменение|Назначение|Совместимость+Потребители) + по-операционные секции (таблицы параметров запроса/ответа, примеры JSON, коды с семантикой) + права доступа/403 + лимиты/429 + асинхронность/202 + трассировка на CT-n/FT-n + чеклист полноты 3.2 + рассмотренные альтернативы в П.F. **US#2 ≈ полностью новая надстройка** над существующим алгоритмом разведки.

### US#3 — Навыки модели данных (DM-n) и событий (EV-n)
**УЖЕ ЕСТЬ (частично, только в жанре ТЗ):** внутри `fr-authoring` ТЗ-скелет уже содержит раздел 7 «Доменные модели» (ролевая матрица, «предлагаемая, требует Q-n»), раздел 8 «Состояния», раздел 9 «События и консистентность» с серией **EV-nn**. В жанре FR (двухчастном) отдельных DM/EV разделов НЕТ.
**РЕАЛЬНО НОВОЕ:** выделить DM/EV в отдельные навыки-анализаторы + внести в жанр FR. ⚠️ **Риск дублирования:** новая серия EV-n vs уже существующая EV-nn в ТЗ-скелете. Требует консолидации нумерации (см. вопрос 3).
**Сужение:** концепты DM/EV не проектируем с нуля — есть образец в ТЗ-скелете; работа = вынести в навыки + унифицировать серию + добавить в FR.

### US#4 — Конвейер (dev-профили, парная US)
**УЖЕ ЕСТЬ:** ничего под ТЗ#3 (это чтение НОВОЙ структуры потребителями). Аналог — US #719 «приём серий ТЗ конвейером».
**РЕАЛЬНО НОВОЕ (полностью):** К-1 чтение структуры v2 по маркеру fr_skeleton; К-2 наследование CT/DM/EV (BRD ссылается, PIN реализует, TESTS «Covers: CT-n»); К-3 гейт D-n (BLOCKED без утверждения); К-4 таблица расхождений FR↔KB на проектные разделы; К-5 версия скелета.
⚠️ **Вне моего прямого edit-скоупа:** правит dev-профили (`iva-web-brownfield` — **точка пересечения с lead-ds**, `iva-kmp-brownfield`, `iva-brownfield-mail`). Эти профили — тоже зеркала (iva-web-brownfield зеркалит iva-web-development-base). Координация через ГД обязательна. Пока — только карта, не трогаю.

### US#5 — /update-feature (пер-раздельная перегенерация + D-n)
**УЖЕ ЕСТЬ:** команда `update-feature` подключена (command_spec). Точный текущий объём команды разведкой не детализирован (нужен доп. проб при планировании).
**РЕАЛЬНО НОВОЕ:** перегенерация ТОЛЬКО затронутого раздела (решение изменило контракт → перезапуск только контрактного навыка) + фиксация утверждений проектных разделов (dev+CTO) как D-n. Частично новое — надстройка над существующей командой.

## Ответы на 5 открытых вопросов (предложения лида)

**1. Mirror-конфликт (критично).** Согласен с рекомендацией ГД — **вариант б (депрекировать mirror-пару)** предпочтителен: правки ТЗ#3 лягут ТОЛЬКО в `iva-fr-analyst`, заморож. база Diaret нетронута. НО следствие: `fr-authoring`/`api-contracts-discovery`/… **разойдутся** между `iva-analysis-base` (обучение аналитиков as-is честности — старый инвариант §2) и `iva-fr-analyst` (design-capable эволюция — релаксация §2). Это **осознанное расхождение аудиторий**, а не баг → предлагаю при депрекации зафиксировать причину в `_mirrors.yaml`/мини-ADR, чтобы будущий maintainer не «починил» дрейф обратно. Решение — президент (граница заморозки Diaret).

**2. Формат «3.1» / серия «CT-n».** В коде их НЕТ. US#2 вводит их **с нуля** (план опирался на образец wiki 211847207, не на текущий скилл). Подтверждаю: это новая надстройка, не доработка существующего формата.

**3. Граница DM/EV vs существующие разделы ТЗ.** Предлагаю **консолидацию, не дублирование:** новые навыки DM/EV становятся ЕДИНЫМ источником нумерации для ОБОИХ жанров (FR и ТЗ). Разделы 7/9 ТЗ-скелета рефакторятся так, чтобы их порождали новые навыки; серия одна (EV-n = EV-nn, унифицировать формат ID). Так избегаем параллельных EV-n/EV-nn.

**4. Двухчастная структура «уже сделана».** Да — 0.1.5. US#1 это **НЕ «создать части»**, а **переархитектурировать семантику**: Часть 1 → полная to-be спека с релаксацией §2 под предохранителями; FT/UC переезжают наверх; +валидатор +fr_skeleton:2 +TOC. Дельта US#1 существенно уже, чем читается из плана.

**5. Куда DM/EV в жанре FR.** Добавить как новые разделы Части 1 FR-скелета (§1.7 Модель данных, §1.8 События — по ТЗ §2.3), порождаемые новыми навыками (вопрос 3). В жанре ТЗ у них уже есть дом (разделы 7/9) — рефакторить на те же навыки.

## Предлагаемый уточнённый скоуп (для апрува ГД)
- **US#1** ← сузить: переархитектура семантики частей + релаксация §2 + валидатор границы + fr_skeleton:2 + TOC + переезд FT/UC. (Не «создание частей».)
- **US#2** ← оставить: формат 3.1 + CT-n + чеклист 3.2 — почти полностью новое.
- **US#3** ← сузить: вынос DM/EV в навыки + консолидация серии с ТЗ-скелетом + внесение в FR.
- **US#4** ← оставить, но **вынести в отдельную парную US с координацией через ГД** (пересечение lead-ds по iva-web-brownfield; профили-зеркала).
