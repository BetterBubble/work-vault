# Что стоит закрыть приёмку #750 честно

Приёмка из постановки: «убрать поле из схемы и запретить его валидацией — тогда авторы профилей
не смогут на него положиться». Оценка цены запрета по трём точкам, **без реализации**.

Мерил в отдельном worktree `acc-750` на `origin/main` 78a7031a (снят после замеров); `bl-750` и
`bl-816` не трогал. В проде только `SELECT`.

**Короткий ответ.** Точка 1 дёшева, безопасна и **достаточна**: авторы профилей ходят только через
манифест и PR — это подтверждено журналом прода, а не рассуждением. Точка 2 дёшева при одном
условии. Точка 3 технически безопасна, но для приёмки бесполезна. И по дороге нашлись два факта,
которые меняют картину сильнее, чем сами три точки.

## Сначала — два факта, без которых оценка неверна

### Обещанного `validate-manifests` workflow не существует

`CONTRIBUTING.md:144-145` обещает автору: «On every **PR** touching `templates/`: JSON Schema
validation runs (`validate-manifests` workflow)». В `.github/workflows/` его **нет**:

```
backend-ci.yml   install-e2e.yml   nightly-install-e2e.yml   profile-version-discipline.yml
```

И в `.gitignore:39-44` allowlist перечисляет ровно эти четыре — `validate-manifests` в него не
внесён, то есть файл не коммитился никогда. Диагноз ровно тот же, что был у backend-ci в #620.

### `manifest.v2.schema.json` не описывает ингредиенты вовсе

Ключ `ingredients` в схеме манифеста — **пустой объект `{}`**: ни `items`, ни `properties`, ни
`required`. Поэтому команда, которую CONTRIBUTING:127 даёт автору для локальной проверки —

```
check-jsonschema --schemafile templates/_schema/manifest.v2.schema.json templates/my-profile-id/manifest.yaml
```

— **не проверяет ни одного ингредиента и ни одной metadata**. А сама `ingredient.v1.schema.json`
требует на верхнем уровне только `kind` (свойства — `kind` и `supports`, остальное в `allOf`), то
есть она и есть проверка metadata по kind, и больше ничего.

**Вывод:** сегодня на пути автора нет ни одной работающей проверки метаданных — ни в CI, ни в
локальной команде из инструкции. Фраза приёмки не закрыта не только для `assets`, а вообще.

## Точка 1. Тест-глоб по всем 64 манифестам — ДЁШЕВО И БЕЗОПАСНО

**Опасение контролёра не подтверждается. Тест будет зелёным.** Перепроверил прицельно, обеими
схемами, валидируя ингредиент так, как он лежит в манифесте:

| схема | невалидных из 812 |
|---|---|
| `origin/main` | **0** |
| ветка `bl-750` (с `additionalProperties: false`) | **0** |

64 манифеста, 812 ингредиентов, ни одной находки. Сегодня `ingredient.v1` валидируется в 5
профильных тестах (`test_iva_ios_brownfield_profile`, `test_tacticum_dev_base_profile`,
`test_iva_brownfield_mail_profile`, `test_firebird_web_brownfield_profile`,
`test_tacticum_ui_base_profile`) — то есть 5 профилей из 64.

**Почему это работает как гейт:** `install-e2e.yml` триггерится по `paths: templates/**` и первым
шагом гонит `pytest tests/catalog`. Значит тест, положенный в `tests/catalog/`, запустится на любом
PR, трогающем манифесты. (`backend-ci.yml` для этого не годится — он слушает только
`apps/backend/**`.)

**Объём правки:** образец уже есть — `test_all_real_manifests_validate_against_v2_schema`
(`tests/catalog/test_manifest_schemas.py:143`) делает ровно такой глоб против v2. Копия под
`ingredient.v1` с внутренним циклом по `ingredients` — **12–15 строк в одном файле**.

## Точка 2. Сид — ДЁШЕВО РОВНО ПРИ ОДНОМ УСЛОВИИ

Точное место: `apps/backend/scripts/seed_community.py`, функция `_load_ingredient`.

- строка **74** — `metadata = dict(ing.get("metadata") or {})`, метаданные как в манифесте;
- строки **88 / 91** — впрыск `metadata[f"{cli}_body"]` и `metadata[f"{cli}_target_path"]`;
- строка **93** — сборка `IngredientPayload`, дальше в БД.

Впрыск идёт **после** чтения манифестных метаданных — подтверждаю строкой, как просили.

| куда вставить валидацию | невалидных из 812 | итог |
|---|---|---|
| **между 74 и 75** (до впрыска) | **0** | сид пройдёт на всех 64 профилях |
| перед 93 (после впрыска) | **8** | сид упадёт на 3 профилях |

Восемь падений после впрыска — это `skill_spec`, несущие `codex_body_path`:
`iva-qa-autotest-base` (4), `tacticum-autotest-core` (3), `iva-qa-delivery-base` (1). Ошибка:
`Additional properties are not allowed ('codex_body', 'codex_target_path' were unexpected)`.
Причина — `additionalProperties: false`, добавленное #750 у `skill_spec`: этих двух ключей в схеме
нет. На `origin/main` после впрыска падений 0, потому что схема там открыта.

Масштаб per-CLI тел: `codex_body_path` объявлен у **77** ингредиентов, `copilot_body_path` — у
**32**, суммарно затронуто **24 профиля из 64**.

**Объём правки:** 5–6 строк в `_load_ingredient` плюс загрузка валидатора модульного уровня.
**Условие, которое нельзя нарушить:** валидировать сырой манифестный `metadata`, до строки 88.
Если поставить после — сломается сид трёх профилей, а сид на `push main` уже боевой.

## Точка 3. Админский API — БЕЗОПАСНО, НО ДЛЯ ПРИЁМКИ БЕСПОЛЕЗНО

Радиус поражения мал, я проверил все четыре опасения:

- **кто ходит:** `apps/admin_web/src/lib/api.ts:564/576/587` (POST/PATCH/DELETE) и один тест —
  `tests/catalog/test_admin_catalog_authoring.py`. Больше вызовов нет;
- **что шлют тесты:** только канонические метаданные (`description_trigger`, `transport`+`command`,
  `model`+`description`). `codex_body`/`copilot_body` через API **не шлёт ни один тест** — все
  совпадения в `tests/` относятся к `codex_body_path` в манифестах;
- **что шлёт админка:** для `skill_spec` → `SkillEditor` (только `description_trigger`,
  `editors.tsx:126`), для `agent_spec` → `AgentEditor` (`description`+`tools`), остальные 7 kind →
  `GenericMetadataEditor`;
- **round-trip:** `GenericMetadataEditor` при редактировании существующего кладёт в textarea **весь
  JSON из БД** (`editors.tsx:861-863`) и отправляет его целиком. Это был бы способ вернуть
  `codex_body` на вход — **но именно те два kind, где `codex_body` лежит (`agent_spec`,
  `skill_spec`), идут через специализированные редакторы**, которые пересобирают metadata из полей
  формы. Значит включение схемной валидации админку не сломает.

**Почему бесполезно для приёмки — журнал прода:**

| действие | событий | акторов | период |
|---|---|---|---|
| `add_ingredient` | **33** | 1 | **всё 2026-05-14**, один день |
| `patch_ingredient` | **0** | — | за всю историю ни разу |
| `create_profile` | 2 | 1 | 2026-05-14 |
| `create_draft_version` / `publish_version` | 1 / 1 | 1 | 2026-05-14 |

Для сравнения, живые действия в те же три месяца: `create_membership_api_key` 136 (по 05.08),
`patch_installation` 45 (по 06.08). **Авторингом через API пользовались один раз, в день запуска
платформы, и с тех пор — ни разу.**

**Объём правки, если всё же брать:** POST — 5–6 строк рядом с существующей pydantic-проверкой
(`catalog.py:528-544`). PATCH — 10–12 строк: валидации метаданных там нет вовсе, `catalog.py:655`
просто пишет `blob.metadata_ = request.metadata`; `kind` доступен из пути.

**Побочное наблюдение, не по задаче:** `IngredientPatchRequest` (`catalog.py:111-117`) объявляет
`supports`, `install_scope`, `target_path_template`, но тело `patch_ingredient` применяет только
`body`, `tier` и `metadata`. Три поля принимаются и молча игнорируются.

## Главный вопрос: как автор реально заводит ингредиент

`templates/README.md:36` отправляет автора ровно в одно место — «To add a community profile, see
CONTRIBUTING.md». Там (`CONTRIBUTING.md:120-150`) описан единственный путь: положить
`manifest.yaml` + файлы ингредиентов в `templates/<profile-id>/`, проверить локально, **открыть PR
в `main`**; после мержа профиль автоматически сидится. Админка в инструкции автора не упоминается.

Журнал прода это подтверждает фактом, а не словами: 33 `add_ingredient` за один день 14 мая и ноль
`patch_ingredient` за всё время, при 500 активных версиях профилей в каталоге.

**Ответ: авторы профилей ходят через манифест и PR. Админский API — внутренний инструмент,
которым за три месяца не пользовались.** Значит запрета на пути «манифест → PR» достаточно, чтобы
фраза приёмки стала правдой, а API можно выносить в отдельную задачу.

## Минимальный честный набор

   строки 74). Закрывает путь «сид принял то, что тест бы отверг». 5–6 строк.
3. **Точка 3 — отдельной задачей.** Безопасно, но приёмку не закрывает и радиуса пользы не имеет,
   пока в ручки никто не ходит.

Отдельно стоит решить судьбу двух находок выше (несуществующий `validate-manifests` и пустой
`ingredients` в `manifest.v2`) — но это не #750, а причина, по которой запрет вообще потребовался.
