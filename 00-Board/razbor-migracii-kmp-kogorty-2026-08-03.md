# Почему у них ломается миграция: один `context.yaml` на всю команду

Разбор по прод-БД 03.08. Только чтение, ничего не менял.

## Корень: один `installation_id` на всех

`.tacticum/context.yaml` содержит привязку репозитория — `installation_id`, `workspace_slug`,
`profile_id`. У KMP-команды он **закоммичен в git**, и это видно в данных: по таблице
`installation_seen_users` через одну установку ходят разные люди.

**Установка `687db0e8` («iva-kmp brownfield — D:/iva/kmp», workspace `base`), 167 синхронизаций
— семь человек:**

| Кто | Последний заход |
|---|---|
| n.gribtsov@iva.ru | 02.08 15:12 |
| d.lebedev@tacticum.ru | 02.08 10:31 |
| a.chuvashov@iva.ru | 31.07 14:05 |
| i.manukhin@iva.ru | 31.07 10:01 |
| d.ostryakov@iva.ru | 31.07 09:40 |
| r.mirin@iva.ru | 31.07 09:37 |
| e.fadin@iva.ru | 30.07 15:40 |

Это не семь установок — это одна запись, которую делит вся команда, потому что файл с привязкой
приезжает к каждому из репозитория.

## Отсюда всё остальное

**1. «Мигрируй меня на роль» — не персональная операция, пока файл в git.** Миграция меняет в
`context.yaml` `installation_id` и `profile_id`. Файл общий, значит первый же мигрировавший
меняет привязку **для всех** — а следующий `git pull` возвращает чужую. Ровно это и увидел Мирин:
«поменял installation_id и profile_id… я это запушил, но потом откатил на то, что было раньше».

**Он поступил правильно, но причина не в миграции.** Сама смена обоих полей — штатное поведение,
у нас в runbook это записано как «интерим двух установок — норма»: установка роли живёт рядом с
legacy, привязка переезжает последним шагом. Агент отработал верно; сломан процесс вокруг файла.

**2. Порядок действий сейчас перевёрнут.** Пока `context.yaml` в git, миграция «по одному
пользователю» — а именно так предписывает runbook — невозможна физически: каждый следующий
пользователь конфликтует с предыдущим. Сначала файл из git, потом миграция.

**Целевая установка когорты `ec12b037` («IVA KMP — роль (раскатка когорты)», роль
`iva-role-kmp` 0.4.5, workspace `base`)** — на ней уже побывали:

- r.mirin@iva.ru — 02.08 15:50 (то есть Мирин всё-таки перешёл, после отката)
- n.gribtsov@iva.ru — 02.08 15:13
- r.berozov@iva.ru — 02.08 12:13
- d.lebedev@tacticum.ru — 02.08 06:14

**Фадина и Ивановой там нет.** Последний след Фадина вообще — 30.07, в brownfield и в пилотной
установке. То есть на роль он не переходил и, судя по данным, после 30.07 не заходил.

**Отдельная находка: 30.07 Фадин, Иванова и Мирин ходили через `cbb20b79`** — а это
`PILOT: role target (smoke), TZ #752` в workspace **`smoke-5d7bb70c`**, не в их рабочем `base`.
Это смоук-фикстура пилота, чужая. К этому workspace привязана только одна дизайн-система
(IVA Mobile), тогда как к `base` — четыре. Если кто-то из них проверял `design_*` оттуда,
картина была неполной не из-за прав, а из-за workspace.

## Что делать — по шагам

**Шаг 0, Беспалову, ДО всякой миграции.** Вынуть привязку из git:

```
git rm --cached .tacticum/context.yaml
echo ".tacticum/" >> .gitignore
git commit -m "chore: убрать привязку установки Tacticum из репозитория"
```

Файл остаётся на диске у каждого, но перестаёт ездить между людьми. У нас в `tacticum-dev`
сделано именно так — `/.tacticum` в `.gitignore`. **Пока этот шаг не сделан, миграцию когорты
запускать бессмысленно** — она будет ломаться у каждого следующего.

**Шаг 1.** Каждый у себя выполняет промпт Солонко «мигрируй меня на роль iva-role-kmp». Теперь
это локальная операция и никого не задевает. Смена `installation_id` и `profile_id` в своём файле
— так и должно быть, откатывать не нужно.

**Шаг 2, проверка.** Попросить агента вызвать `whoami` и убедиться, что видно:
профиль `iva-role-kmp`, workspace `base` (не `smoke-…`), аккаунт — свой собственный.
Именно так выглядят сообщения Мирина и Грибцова в чате — у них уже правильно.

**Шаг 3, для Фадина отдельно.** Он не мигрировал вовсе, так что начинать ему с шага 1 —
но только после шага 0, иначе он повторит путь Мирина.

## Чего я НЕ трогал

Ни одной правки: ни в их репозитории, ни в прод-БД, ни в профилях. Всё выше — SELECT'ы по
прод-каталогу и чтение наших доков (`role-migration-runbook.md`, `tacticum-mcp-install.md`).

## Что осталось непонятным

**Почему у Фадина не было активности после 30.07** — данных нет, возможно просто не заходил.

**Нужна ли каждому своя установка или общая на когорту — вопрос к владельцу.** Сейчас модель
org-shared: одна установка на репозиторий, и `ec12b037` заведена именно как «раскатка когорты».
При такой модели общий `installation_id` — это норма, ломает именно нахождение файла в git,
потому что миграция идёт по одному человеку, а файл меняется у всех сразу.
