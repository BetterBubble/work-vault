# US#2 — реализация: api-contracts-discovery, формат 3.1 + CT-n (вариант А)

Спека — [[spec-us2-api-contracts-format-31]]. Куплинг с US#1 (§1.6 + правила
честности) — учтён. autonomy off: локальный worktree, без push/merge/PR.

## Что сделано (человеческим языком)

Надстроил над существующим навыком разведки контрактов формат **проектирования**
контрактного раздела FR. Разведка (Карта источников + 5 шагов алгоритма) —
**не тронута**; всё аддитивно.

Новый раздел **«Контрактный раздел FR — формат 3.1»** (вставлен после Алгоритма,
перед «Правилами честности»), содержит:
- **Реестр изменений** — таблица `Контур | Контракт | Изменение | Назначение |
  Совместимость | Потребители`; колонка «Потребители» помечена обязательной
  (без неё «Совместимость» непроверяема).
- **По-операционная секция** на каждую строку реестра: заголовок с трассировкой
  (`CT-n` + `FT-n` + ссылка на пробу П.F), описание, права доступа (роль/scope +
  `403`), таблица параметров запроса (`Параметр|Где|Тип|Обязательность|Описание`),
  пример запроса JSON, таблица параметров ответа, коды ответа **с семантикой в
  терминах операции**, пример ответа с ошибкой.
- **Сквозные требования**: права/`403`, лимиты/`429` с окном, асинхронность/`202`
  + статус-ресурс/событие (для операций дольше ~1 c).
- **Серия `CT-n`** — контрактные требования, правила стабильности ID как у
  `FT-n`/`UC-n` (номер не переиспользуется; отменённый → «отменён (D-k)»).
- **JUMP-контур** — те же таблицы с поправкой на транспорт (Контур=`JUMP`, имя
  команды вместо метода+пути, payload вместо тела), конвенции distrohost с
  цитатой; **probe-first Шага 3 сохранён** (имена/payload только после успешного
  probe; probe упал → открытый вопрос владельцу servercore, не выдумка).
- **Чеклист полноты 3.2** — 11 пунктов; неприменимый → явно «не применимо».
- **Порядок проектирования 3.3** — контракт только после `CT-n` и проб;
  конвенции из ближайшего реестра **с цитатой**; альтернативы в П.F при вердикте
  «проектировать».

Плюс дополнил **Шаг 5** (negative evidence) требованием фиксировать
рассмотренные альтернативы при вердикте «проектировать» (аналоги + причина
отклонения) — разбор as-is в П.F, решение to-be в §1.6.

## Как согласовал правила честности с §2 US#1 (куплинг — критично)

Прочитал текущий §2 и §1.6 `fr-authoring` в этой же ветке (после US#1 — там
двухзонная модель). Переформулировал п.1–2 правил честности api-contracts так,
чтобы **не противоречить** §2, а точно к нему пристыковаться:

- **п.1 «Проба-разведка (П.F) — строго as-is».** Эндпоинт/команда в П.F — только
  с источником (метод/путь/команда, версия/`as_of`, дата probe). Проектных
  wire-имён в зоне фактуры нет, правило без ослаблений — **явная ссылка на §2
  fr-authoring, зона Приложения**. Реконструкция «как обычно делают» из П.F
  убрана в §1.6 под предохранители.
- **п.2 «Проектный контракт — в §1.6 под предохранителями, не в П.F».** Wire-имена
  без источника в зоне фактуры (П.F) запрещены даже с пометками. Проектные
  wire-имена живут **только в §1.6 (to-be)** и ровно под тремя предохранителями
  §2 `fr-authoring`, все одновременно: (а) основание в П.F/П.E со ссылкой;
  (б) плашка «**Предложение, требует утверждения: разработчик + CTO**» + открытый
  `Q-n`; (в) механический валидатор границы (шаг 7 / гейт шага 9 fr-authoring).
  Нет предохранителя — имя = выдумка, запрещено везде.

Формулировки взяты **дословно из §2/§1.6 fr-authoring** (те же три предохранителя,
та же плашка, тот же валидатор границы) — релаксация в двух скиллах не расходится.
`CT-n` уже объявлена в fr-authoring (таблица идентификаторов, стр.40, «навык
api-contracts-discovery (US#2)») — здесь она наполнена.

## Развилки / решения (durably)

1. **CHANGELOG про зеркало.** В fr-analyst-записи добавил под-пункт «Зеркало
   владельца iva-analysis-base (api-contracts-discovery — общий ингредиент,
   байт-в-байт)» — симметрично тому, как US#1 отметил зеркалирование fr-authoring.
   В owner-записи такого под-пункта нет (owner — источник). Если хочешь строгую
   симметрию текста CHANGELOG — скажу, выровняю.
2. **Альтернативы — два места.** Требование «рассмотренные альтернативы при
   вердикте проектировать» встроил и в Шаг 5 (где рождается negative evidence,
   as-is П.F), и упомянул в Порядке 3.3 п.3 (ссылкой на Шаг 5, без дублирования
   содержания). Сделал так, чтобы разбор физически лежал в П.F, а решение — в §1.6.
3. **`--with jsonschema`.** Для целевых тестов каталога нужен jsonschema (иначе
   collection-error на schema/preset тестах). Добавил в команду — на CI это уже
   часть окружения, локально в спеке не было указано.
4. **Байт-в-байт достигнут копированием.** Owner отредактирован Edit'ами, зеркало
   получено `cp owner → mirror` (гарантирует идентичность), check_mirror_sync
   подтверждает.
