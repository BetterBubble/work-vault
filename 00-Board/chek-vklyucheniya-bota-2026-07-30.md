# Чеклист включения бота выдачи доступа (iva-write) — готовность к «пришли ключи → включили»

Разведка, только чтение. Код: worktree `/Users/bubblemac/tacticum-worktrees/helm-iva-write-keystore`
(`baa7895`). Прод `helm` (159.194.233.33) читал через `ssh-manager exec helm` — ничего не менял,
значений секретов не выводил (только имена и длины). Прод на `b7341ab` (merge PR #95).

## Короткий ответ

**Шагов до работающего бота — три, все на нашей стороне, ~10 минут.** Две переменные в `.env` +
третья-флаг, `docker compose up -d helm`, проверка своим curl. Пересборка НЕ нужна: код бота
уже в задеплоенном образе (проверено импортом внутри контейнера — `router prefix: /api/bot/iva-write`).

**Но «включили и готово» ≠ «работает».** Единственное, что нельзя проверить с нашей стороны, —
дойдёт ли до нас вебхук платформы; и ровно это за 90 дней ни разу не случилось. Плюс четыре вещи
сломаются у первого же живого человека, и три из них чинятся ДО включения.

## 1. Что придёт от Васи и куда кладётся

**Придут ДВА разных секрета, а не один.** Подтверждено устройством бота «Поддержка», у которого
ключи уже есть: в `/opt/helm/.env` на проде лежат обе переменные раздельно —
`HELM_IVA_BOT_SUPPORT_TOKEN` (длина 114) и `HELM_IVA_BOT_SUPPORT_WEBHOOK_SECRET` (длина 64).
Разные длины = разные сущности, а не одно значение в двух местах.

Смысл каждого в коде:

- **bot-токен** — исходящий, уходит заголовком `X-Iva-Bot-Api-Token` в
  `POST {base_url}/api/bot/v1/chats/{chatRoomId}/send-message`
  (`infrastructure/bot_iva_write/client.py:54-57,95-98`);
- **секрет вебхука** — входящий, платформа кладёт его в заголовок `Iva-Bot-Api-Secret-Token`,
  мы сверяем `hmac.compare_digest` (`routers/bot_iva_write.py:377-379`).

Токены у нашего бота **свои**, делить с «Поддержкой» нельзя — прямо зафиксировано в конфиге
(`config.py:511-513`): «утечка одного секрета открывала бы оба канала».

### Переменные нашего бота — что обязательно, что с дефолтом

|---|---|---|

### Всё остальное на проде УЖЕ стоит — проверено

- четыре ключа Atlassian, оба `base_url`/`connect_url`, публичный адрес колбэка, мастер-ключ

- `HELM_DEV_TOKEN_EMAIL_DOMAINS` длиной 30 — ровно `iva.ru,tacticum.ru,iva-tech.ru`;
- `HELM_IVA_WRITE_MCP_URL` / `_JIRA_URL` / `_CONFLUENCE_URL` заданы **в compose**, а не в `.env`

- **схема БД накачена**: `bot_dialog_pending`, `oauth_state`, `external_credential`,

**Ни одной переменной `HELM_IVA_BOT_IVA_WRITE_*` в `/opt/helm/.env` сейчас нет** — то есть добавлять
предстоит с нуля, ничего не перетирая.

## 2. Порядок включения

Флаг читается **один раз при импорте процесса**: `_boot_settings = Settings()` (`main.py:101`),
и ветка `if _boot_settings.iva_bot_iva_write_enabled` (`main.py:205`) выполняется на импорте
модуля. Значит **на каждый запрос флаг НЕ перечитывается**, и включение требует перезапуска
процесса. Пересборка образа не нужна — код уже внутри.

Важная тонкость: переменные приходят через `env_file: .env` (`docker-compose.prod.yml:33-36`).
**`docker restart` env_file НЕ перечитывает** — контейнер стартует со старым окружением. Нужен
`up -d`, который пересоздаёт контейнер под изменившееся окружение.

```bash
# 1. дописать три строки в /opt/helm/.env (права 600 сохранить)
HELM_IVA_BOT_IVA_WRITE_TOKEN=<токен от Васи>
HELM_IVA_BOT_IVA_WRITE_WEBHOOK_SECRET=<секрет вебхука от Васи>
HELM_IVA_BOT_IVA_WRITE_ENABLED=true

# 2. пересоздать контейнер приложения (БЕЗ --build, БЕЗ deploy.sh)
cd /opt/helm && docker compose -f docker-compose.prod.yml up -d helm

# 3. убедиться, что роут появился: было 405, стало 401
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  -H 'content-type: application/json' -d '{}' \
  https://helm.tacticum.ru/api/bot/iva-write/webhook
```

**401 вместо 405 — и есть доказательство, что бот смонтирован.** 405 = роута нет (запрос ловит
статика SPA), 401 = роут есть и требует секрет. Сейчас на проде: iva-write → **405**,
support → **401** (проверено и изнутри контейнера, и снаружи через `helm.tacticum.ru`).

### 🔴 Чем нельзя включать

**`bash scripts/deploy.sh` сносит боевой граф.** `SEED` по умолчанию `1` (`scripts/deploy.sh:24,52`),
а `scripts/seed_db.py:150` зовёт `clear_graph` — тенант-скопнутый DELETE по Person, PersonEmail,
Initiative, Block и прочим. Условия по источнику нет. Для включения бота этот скрипт не нужен
вообще: миграции накачены, образ собран.

Открывать нам нечего — **если вебхук не дойдёт, причина на их стороне, и просить надо не «доступ»,

Егресс до платформы у нас есть: из контейнера `iva-uc.ru` резолвится (51.250.35.209) и TCP/443

## 4. Чем проверить без живого человека

**Да, событие имитируется полностью** — вебхук ничем не отличает наш curl от платформы, кроме
секрета. Форма тела взята из теста `tests/interface/test_bot_iva_write.py:52-76` (`_event`),
который гоняет ровно этот роутер.

```bash
# с самого сервера (или откуда угодно — путь публичный)
curl -s -X POST https://helm.tacticum.ru/api/bot/iva-write/webhook \
  -H 'content-type: application/json' \
  -H 'Iva-Bot-Api-Secret-Token: <ЗНАЧЕНИЕ_ИЗ_.ENV>' \
  -d '{
    "type": "CHAT_NEW_MESSAGE",
    "data": {
      "messageId": "probe-1",
      "chatRoom": {"chatRoomId": "<РЕАЛЬНЫЙ_CHAT_ROOM_ID>", "isGroupChat": false},
      "author": {"type": "REGISTERED_USER", "name": "Проверка",
                 "login": "<почта@iva.ru>", "profileId": "p-1"},
      "message": "дай доступ"
    }
  }'
```

Ожидаемое: `{"status":"accepted"}` мгновенно. Дальше смотреть **лог приложения** — там видно и
приём запроса, и исход отправки:

```bash
docker logs -f helm-helm-1 | grep -i "bot/iva-write\|send-message\|выдачи доступа"
```

Что означают исходы:
- строка `POST /api/bot/iva-write/webhook 200` — мы событие приняли;
- `send-message отклонён (chat=…): HTTP 401` — не тот bot-токен (повтора не будет, `client.py:117-123`);
- `HTTP 404` — такого чата нет (ожидаемо, если `chatRoomId` выдуман);
- тишина + `bot-токен выдачи доступа не задан` — забыли `HELM_IVA_BOT_IVA_WRITE_TOKEN`;
- ссылки реально дошли в чат — значит замкнулось всё, кроме входящего пути от платформы.

**Чего этот тест НЕ проверяет:** дойдёт ли до нас настоящее событие платформы. Это единственное
звено, которое проверяется только с их стороны.

⚠️ **Лог живёт ровно столько, сколько контейнер.** Драйвер `json-file` без ротации, при
пересоздании контейнера история теряется. Контейнер перезапущен сегодня в 09:29 UTC, поэтому
утверждение «за 90 дней платформа ни разу не достучалась» из логов **сейчас не проверяется ни
подтвердить, ни опровергнуть**: у traefik accesslog не включён (в `command` его нет), а у
приложения лог короче. Единственная строка `POST /api/bot/support/webhook 401` за всю жизнь
контейнера — моя же проверка. Если факт «не достучались» важен как аргумент в разговоре с Васей,
его нужно либо перепроверить у них, либо включить accesslog у traefik заранее.

## 5. Что сломается сразу после включения

### 🔴 Ч1. Бот скажет «подключено», канал ответит 403 — и оба будут «правы»

Разобрано в [[razbor-403-pochty-2026-07-30]]. Через бота почта — `SOURCE_DECLARED`, канал ищет
доступ по почте из ключа Tacticum. Разошлись — 403 при живом согласии, причём «статус» бота в ту
же минуту говорит «подключено». **Чинится ДО включения** дешёвой правкой (назвать адрес в отказе
канала и в «готово», ~25 строк).

### 🔴 Ч2. Почты в событии может не быть — и тогда включается самый слабый путь

`author.login` мы принимаем как почту, только если он похож на адрес в разрешённом домене
(`routers/bot_iva_write.py:262-264`). Если платформа шлёт там не почту (логин, id) — бот
**спрашивает почту в чате** (`:296-302`), и это ровно тот путь, который порождает Ч1.
Контракт события мы видели только по спецификации. **До включения не чинится** — нужен либо
ответ Васи, либо первое реальное событие.

### 🟡 Ч3. «Статус» может не работать вовсе

Статус отвечает ТОЛЬКО по `login_email` от платформы (`:305-310`). Нет почты в `login` — человек
получает `status_identity_unknown_text`, то есть «подтвердить, чей это чат, нечем». Это осознанное
решение, но для человека выглядит как половина бота. Зависит от того же неизвестного, что Ч2.

### 🟡 Ч4. У человека нет ключа Tacticum — и бот об этом узнает последним

Бот через `key_status=unknown` честно пишет «если ключа Tacticum у вас ещё нет — сообщите».
Дальше человек упирается в **401** на канале (не 403), и в боте нет ни команды выдать ключ, ни
внятного объяснения, куда идти. По находке 30.07 выпуск ключей `phk_` целиком в нашем коде
(`tacticum-dev`, три админские ручки) — то есть чинится, но это фича, а не правка.

### 🟢 Ч5. Отзыв доступа бот не умеет

Известное ограничение Б2: на «отзови доступ» сработает намерение `access` и человек получит
**новые ссылки-согласия**. Только `POST /api/iva/oauth/revoke`.

### ⚠️ Ч6 (новое, нашёл в проде). Аутентифицированный путь согласия на проде НИ РАЗУ не проходил

В `oauth_state` на проде обе строки живого прогона 30.07 имеют `subject_source = declared` и
**пустой `chat_room_id`**. То есть прогон шёл не через `POST /api/iva/oauth/start` (он всегда
кладёт `SOURCE_AUTH`, `routers/iva_write.py:259`) и не через бота, а вызовом `start_consent`
напрямую, где дефолт параметра — `declared` (`application/iva_write.py:164`).

Три следствия:
1. **путь `SOURCE_AUTH` на проде не проверен живьём вообще** — а именно его я рекомендовал как
   починку Ч1;
2. **доставка «готово» в чат на проде не проверена** — пустой `chat_room_id` означает, что
   `notify_access_ready` даже не вызывался (`routers/iva_write.py:400-407`);
3. журнал это подтверждает: `key_status|key_unknown|2`, ни одной строки `key_known_present`.

Живые доступы при этом настоящие: `jira` и `confluence`, `kind=oauth`, привязка логина есть,
не отозваны; access истекает через час после выдачи (19:42/19:43 UTC при текущем 19:29),
дальше вступает продление по refresh.

### Сводка «до / после»

| # | Чинится ДО включения | Только после реального события |
|---|---|---|
| Ч1 разрыв почт → 403 при «подключено» | ✅ ~25 строк | — |
| Ч2 нет почты в событии | — | ✅ нужен контракт/факт |
| Ч3 статус без личности | — | ✅ то же неизвестное |

Если этот путь работает, у нас есть рабочий обход Ч1 на случай, если бот подведёт.

## 6. Чего не хватает в самом боте под сценарий Президента

**Бот понимает ДВА намерения, и второе — узким списком слов.**

- `INTENT_STATUS` — если в тексте есть `«статус»`, `«status»` или `«что подключено»`
  (`application/bot_iva_write.py:44`);
- `INTENT_ACCESS` — **всё остальное** (`:81-86`). Это осознанный «односценарный» дизайн.

Что это значит для названных Президентом команд:

| Человек пишет | Что сделает бот сейчас | Правильно ли |
|---|---|---|
| «выдай доступ» / «дай доступ» | `access` → ссылки на Jira и Confluence | ✅ да |
| **«потерял ключ»** | `access` → **выдаст ссылки-согласия на Atlassian** | ❌ нет. Человек спрашивает про ключ Tacticum, получает OAuth-ссылки; пройдёт их — и всё равно упрётся в 401, потому что ключа у него нет |
| «отзови доступ» | `access` → новые ссылки | ❌ известное Б2 |
| «помощь» / «что умеешь» | `access` → ссылки | ❌ справки нет |

**Справки о командах в боте нет ни в каком виде.** Вокабуляр упоминается только внутри других
ответов: `status_text` заканчивается «Чтобы подключить или продлить — напишите «дай доступ»»
(`:187`), `ready_text` — «Проверить состояние: напишите «статус»» (`:209`). Человек, написавший
боту впервые, узнает про «статус» только если сначала успешно получит доступ.

### Оценка в строках

| Что добавить | Где | Строк (с тестами) |
|---|---|---|
| Намерение «помощь» + текст справки со всеми командами | `application/bot_iva_write.py` (константы, `parse_intent`, новый текст) + `routers/bot_iva_write.py:305-313` | **~45-60** |
| Намерение «потерял ключ» — честный ответ (ключ не показывается, только перевыпуск; куда идти) | те же два файла | **~40-55** |
| Намерение «отзови доступ» — с реальным отзывом | + вызов `creds.revoke_credential`, ветка на выбор системы | **~70-90** |
| Ссылка на справку в ответе на непонятое сообщение | `offers_text` / новый fallback | ~15 |

Итого «бот понимает названные команды и объясняет себя» без реального отзыва — **~100-130 строк**;
с отзывом — **~180-220**. Всё это правки одного слоя (`application` + одна ветка роутера), новых
таблиц и миграций не нужно.

**Отдельно, крупнее:** «потерял ключ» с настоящим перевыпуском — это три вызова к админским
