# C++ / Qt десктоп — официальные источники best practices

> **Коротко (IVA Mail desktop):** в профиле — «C++ / Qt desktop» **без версии Qt и без системы сборки**; актуальная на 2026-08-03 — Qt 6.11.1 от 13.05.2026 (разумная цель — Qt 6.8 LTS с поддержкой до октября 2029); сверять нечего — версия в профиле не зафиксирована, и до её фиксации половина рекомендаций каталога остаётся условной.
>
> **Коротко (IVA Connect Desktop / ivcs):** в профиле — C++20 и **Qt 5.15 ровно**; актуальная — Qt 6.11.1; **то, что в профиле, не поддерживается: Qt 5.15 вне стандартной поддержки с 26.05.2025**, последний релиз ветки — коммерческий 5.15.19 (19.05.2025), дальше только платная Extended Security Maintenance по библиотекам Qt.

## Стек по профилю

Один стек, две ветки с разной технической базой — смешивать рекомендации нельзя.

**IVA Mail desktop** (профили `iva-brownfield-mail`, `iva-role-one-mail-desktop`) — C++ / Qt desktop, Qt Widgets UI-тесты, дизайн-токены IVA, cpp-сборка, Qt runtime-деплой, integration-checklist. Версия Qt и система сборки в блёрбе профиля не зафиксированы — см. «Чего не нашёл».

**IVA Connect Desktop / ivcs** (профиль `iva-role-ivcs`) — C++20 / **Qt 5.15 ровно** + Qt Quick (QML), сборка **qmake** (`.pro`/`.pri`), ресурсы через `res.qrc`, googletest в `core_test`, бинарные SDK звонков `ivawebrtc` / `ivaclientsdk` / `ivavirtualbg`.

Ключевой факт для ivcs: **Qt 5.15 вышел из стандартной поддержки 26.05.2025**. Последний открытый патч — 5.15.2 (20.11.2020); коммерческая LTS-ветка закончилась на 5.15.19 (19.05.2025, «это самый последний релиз Qt 5.15»). Дальше — только платная Extended Security Maintenance, и та покрывает только библиотеки Qt, без сторонних зависимостей и без техподдержки. Значит: документацию берём из `doc.qt.io/qt-5/` (это и есть 5.15.19), новых фиксов не ждём, а вопрос «на чём мы сидим — 5.15.2 или коммерческий 5.15.x» надо закрыть отдельно.

## Что изменилось за последний год

Пять вещей, которые реально меняют то, как агент должен писать код.

**1. C++26 технически закрыт (март 2026) — но это не про ivcs.** На встрече комитета в Кройдоне 23–28.03.2026 разобран 411 комментарий национальных органов, работа над содержанием завершена, стандарт ушёл на финальный ISO-балл. Вошли reflection (P2996), контракты (голосование 114 за / 12 против / 3 воздержались), `std::execution`, устранение UB для неинициализированных локальных переменных и hardened standard library. GCC 16.1 (30.04.2026) уже содержит reflection, контракты и safety-hardening. Комитет начал работу над safety-профилями с прицелом на C++29. Для ivcs, зафиксированного на C++20, это горизонт, а не руководство.

**2. Qt 5.15 окончательно вышел из поддержки.** 5.15.19 (19.05.2025) — прямо объявлен последним релизом ветки; стандартная поддержка закончилась 26.05.2025. Единственное, что осталось, — платная ESM с патчами только по библиотекам Qt. Практический вывод: у ivcs больше нет апстрим-канала багфиксов, и любой найденный дефект Qt чинится обходом на своей стороне.

**3. clazy 1.17 (15.02.2026) удалил `qt6-*` проверки миграции.** Из changelog дословно: *«qt6-\* porting checks are removed»*, а `qstring-ref` переведён в `manuallevel`, потому что несовместим с Qt 6. Одновременно clazy 1.16.1 (22.03.2026) выпущен как патч для совместимости с Qt Creator и поддерживает LLVM 19–21. Итог: **если ivcs собирается мигрировать на Qt 6 с помощью официального рецепта Qt, ему нужна ветка clazy 1.16.x, а не свежая** — официальная страница `porting-to-qt6-using-clazy.html` описывает проверки, которых в текущем clazy уже нет. Это прямое расхождение документации и инструмента, и его надо знать заранее. В неизданной 1.18.0 добавлены `modernize-overloaded-connects` (убирает ставшие ненужными `qOverload`/`static_cast` в `connect`), `modernize-list-initialization` и `-line-filter` для линтинга только изменённых строк диффа.

**4. Qt выпустил официальные скиллы для агентов (28.04.2026).** `TheQtCompanyRnD/agent-skills`, двойная лицензия (`LicenseRef-Qt-Commercial OR BSD-3-Clause`): 13 скиллов, включая ревью C++ и QML по 60+ правилам (память, потокобезопасность, производительность), генерацию документации, работу с CMake-проектами и Qt Quick Test. Заявленная цель — 6.x. Это первый случай, когда вендор сам публикует машиночитаемые правила стиля — их стоит разобрать как источник правил для наших профилей, даже там, где сам скилл не применим.

**5. Изменилась политика LTS и вышли новые релизы.** LTS теперь каждый 4-й минор (было каждый 3-й), и начиная с 6.8 срок поддержки — 5 лет вместо 3: Qt 6.8 LTS живёт до октября 2029. Qt 6.5 вышел из поддержки 03.04.2026. Актуальная линейка: Qt 6.11 (23.03.2026), 6.11.1 (13.05.2026), 6.12 Beta 1 (12.06.2026). В 6.11 для десктопа заметны Qt Canvas Painter, Qt TaskTree (декларативная композиция асинхронных C++-цепочек), Qt Labs StyleKit, а в QML появились ключевые слова `override`/`virtual` для property — защита от случайного шэдоуинга. **Единственная разумная цель миграции для ivcs — 6.8 LTS**, а не последний минор.

## Что неприменимо к Qt 5.15 / qmake

Честный разрез: что из современных рекомендаций ivcs брать нельзя и почему.

**Сборка.** Всё, что построено вокруг CMake, для ivcs мимо: `qt_add_executable`, `qt_add_qml_module`, `find_package(Qt6 …)`, `qt_standard_project_setup`. Официальная граница Qt 6 сформулирована так: qmake остаётся рабочим инструментом сборки приложений, но им **нельзя** собирать кастомные плагины Qt и библиотеки, опирающиеся на внутренности сборочной системы Qt 5 — для этого нужен CMake. То есть ivcs на qmake живёт легально, но потолок у этого пути есть. Отдельно: у Qt 6 qmake включает C++17 по умолчанию, у Qt 5 — нет, поэтому C++20 в ivcs держится явным `CONFIG += c++20` (или прямыми флагами) в `.pro`, и это надо не потерять при правках сборки.

**Модули QML.** Система модулей Qt 6 (`qt_add_qml_module`, генерация `qmldir`, помодульный `qmlcachegen`, строгий `qmllint` с типовой информацией) — это Qt 6 + CMake. **Но декларативная регистрация типов ivcs доступна**: в 5.15 работает `QML_ELEMENT` / `QML_NAMED_ELEMENT` вместе с `CONFIG += qmltypes`, `QML_IMPORT_NAME` и `QML_IMPORT_MAJOR_VERSION`. Если в коде ещё ручные `qmlRegisterType`, это как раз тот современный шаг, который **применим** к 5.15 — не надо путать его с недоступным.

**API Qt 6.** Всё, что появилось после 5.15, — не рекомендация, а мираж: система биндингов `QProperty`/`QBindable`, `QStringView`-ориентированные новые сигнатуры, `QTextStream::setEncoding` вместо `setCodec`, слияние `QList`/`QVector`, RHI-графика, Qt Canvas Painter, TaskTree, StyleKit, `override`/`virtual` для QML-property из 6.11. Агент, обученный «на Qt 6», выдаст это как норму — и оно просто не соберётся.

**Стандарт языка.** ivcs — C++20 ровно. Значит вне игры всё из C++23 (`std::expected`, `std::print`, `std::mdspan`, `std::flat_map`) и тем более из C++26 (reflection, контракты, `std::execution`, hardened stdlib). Сюда же: `modernize-*` проверки clang-tidy умеют предлагать конструкции новее C++20 — набор проверок надо ограничивать явным `-std`/`Checks` в `.clang-tidy`, иначе линтер будет советовать несобираемое. Отдельная тонкость: официальная страница поддерживаемых платформ Qt 5.15 фиксирует довольно старые компиляторы (GCC 5+, MSVC 2015–2022, MinGW 8.1), а C++20 требует куда более свежих — то есть реальный набор доступных фич определяется не Qt, а конкретным компилятором сборки, и сверять его надо по таблицам cppreference.

**Инструменты.** Официальный рецепт миграции через `qt6-*` проверки clazy на текущей версии инструмента не воспроизводится — проверки удалены в 1.17 (см. выше), нужна 1.16.x. Скиллы Qt для агентов заявлены под 6.x и включают `qt-cmake-project` — для ivcs это источник правил, а не готовый инструмент.

**Безопасность.** Рекомендации вида «обновитесь до патча с исправлением CVE» для 5.15 не работают без подписки ESM. Практика для ivcs другая: следить за [списком известных уязвимостей](https://wiki.qt.io/List_of_known_vulnerabilities_in_Qt_products) и оценивать применимость к своему билду вручную.

**Что применимо полностью, без оговорок:** C++ Core Guidelines (они про C++11 и новее, а не про версию Qt), Qt Coding Style и Coding Conventions, API Design Principles, QML Coding Conventions в версии 5.15, best practices QML/Qt Quick в версии 5.15, clang-tidy и cppcheck (с `qt.cfg`), clazy 0–2 уровней в части не-Qt6-специфичных проверок, GoogleTest, Qt Test для симуляции GUI-событий.

## Что переписать в профиле прямо сейчас

Действия над текстом скиллов профилей `iva-brownfield-mail` / `iva-role-one-mail-desktop` (Mail) и `iva-role-ivcs`. Каждый пункт — замена конкретной формулировки.

1. **Mail: «Qt desktop» → точная версия Qt и система сборки.** Дописать в блёрб профиля «Qt 6.x, CMake» либо «Qt 5.15, qmake» — что окажется правдой. Пока строка безверсионная, скиллы cpp-сборки и Qt runtime-деплоя нельзя привязать ни к одной ветке документации, а рекомендации Qt 5+qmake и Qt 6+CMake расходятся принципиально.
2. **ivcs: «Qt 5.15 ровно» → «Qt 5.15.x, стандартная поддержка закончена 26.05.2025» с указанием конкретного патча.** В том же месте прописать, что апстрим-багфиксов нет и дефект Qt чинится обходом на своей стороне, а документация `doc.qt.io/qt-5/` описывает 5.15.19 — то есть при работе на 5.15.2 часть страниц описывает поведение, которого в сборке нет.
3. **ivcs: в инструкции миграции на Qt 6 зафиксировать clazy 1.16.x, а не «свежий clazy».** Официальный рецепт Qt построен на `qt6-*` проверках, а они удалены в clazy 1.17 — инструкция, отсылающая к последней версии инструмента, не воспроизводится.
4. **ivcs: в `.clang-tidy` прописать явный `-std=c++20` и урезать группу `modernize-*`.** Без этого линтер предлагает конструкции C++23/26, которые в проекте не соберутся; сейчас в скиллах ограничения стандарта для линтера нет.
5. **ivcs: ручные `qmlRegisterType` заменить на `QML_ELEMENT` / `QML_NAMED_ELEMENT` + `CONFIG += qmltypes`.** Это работает в 5.15 с qmake — единственный «современный» шаг, применимый без миграции, и его не надо путать с недоступными модулями QML из Qt 6.
6. **ivcs: в скилле cpp-сборки закрепить явный `CONFIG += c++20` в `.pro` как норму.** Qt 5 qmake не включает даже C++17 по умолчанию (в отличие от Qt 6), поэтому потеря этой строки при правке сборки молча роняет проект на старый стандарт.

## Чего не нашёл / где источник слабый

**Версия Qt и система сборки для IVA Mail desktop не зафиксированы.** Блёрб профиля говорит «C++ / Qt desktop, Qt Widgets UI-тесты, cpp-сборка, Qt runtime-деплой», но ни версии Qt, ни системы сборки (qmake или CMake) в нём нет — в отличие от ivcs, где всё указано явно. Пока это не выяснено, половина таблицы для Mail помечена «если Qt 6» условно. **Это надо закрыть до того, как каталог уйдёт командам**: рекомендации для Qt 5 + qmake и Qt 6 + CMake расходятся принципиально.

**Не выяснено, на какой конкретно 5.15.x сидит ivcs.** Открытая ветка кончилась на 5.15.2 (2020), коммерческая — на 5.15.19 (2025). Между ними ~5 лет багфиксов и закрытых CVE. Документация `doc.qt.io/qt-5/` описывает 5.15.19, то есть при работе на 5.15.2 часть страниц описывает поведение, которого у нас нет.

**Официальная страница статуса стандарта C++ устарела.** [isocpp.org/std/status](https://isocpp.org/std/status) на дату сверки утверждает, что идёт работа над C++26, хотя техническая работа завершена в марте 2026. Самый надёжный первоисточник здесь — рассылки WG21 на open-std.org; наиболее содержательный человекочитаемый отчёт — блог Херба Саттера, но это **не** формальный документ ISO. Формальную дату публикации ISO/IEC для C++26 я не нашёл — на 2026-08-03 стандарт на стадии финального балла, не опубликован.

**cppreference блокирует автоматические загрузки.** Сайт живой (curl отдаёт 200 по всем проверенным адресам), но на программный fetch отвечает 403. Для регулярной автосверки агентом это неудобно: страницы придётся читать глазами или через кэш поиска. Кроме того, cppreference — **источник сообщества, не ISO**; для спорных вопросов первоисточник — черновик стандарта в рассылках WG21.

**У clazy нет GitHub Releases.** Раздел releases в зеркале KDE/clazy пуст; версии живут тегами в KDE GitLab и в файле `Changelog`. Для автоматического отслеживания «вышла новая версия линтера» надо смотреть теги через API GitLab, а не GitHub Releases.

**Версия manual cppcheck на HTML-странице не указана.** Номер (2.21.0) есть только в PDF-варианте; HTML-страница версии не называет. При автосверке ориентироваться на PDF.

**Не нашёл официального заявления Qt о поддержке C++20 в Qt 5.15.** Страница поддерживаемых платформ 5.15 перечисляет компиляторы, но не называет стандарт языка. Утверждение «Qt 5 не включает C++17 по умолчанию в qmake, в отличие от Qt 6» подтверждается только форумными обсуждениями, не документацией. То есть сборка ivcs на C++20 официально Qt не описана — она работает, но опоры в документации у неё нет, и это ещё один довод в пользу планирования миграции на 6.8 LTS.

**Не нашёл официальных Qt-рекомендаций по интеграции бинарных SDK** (`ivawebrtc`, `ivaclientsdk`, `ivavirtualbg`) — общие страницы деплоя описывают библиотеки самого Qt и плагины, а не поставку сторонних бинарных зависимостей. Здесь официального источника нет вообще; практика придётся описывать своими нормами.
