# Куда делись 315 номеров проекта 12

**ПРЯМОЙ ОТВЕТ: авария, а не практика.** Это две разовые уборки в июне, разнесённые на два дня и
сделанные разными руками; в проекте 12 с 20.06 не удалено ни одной задачи — 48 дней тишины, а во
всей инсталляции последнее удаление было 14.07.

Регулярной практики удаления нет ни у кого. Наводить гигиену можно, не дожидаясь ответа на этот
вопрос.

## Как получены числа

Прод-БД Taiga напрямую, только `SELECT`: сервер `project_hub`, контейнер `infra-taiga-db-1`
(postgres 12.14), база `taiga`, доступ через `docker exec … psql` (наружу порт не проброшен).
Кредиты взяты из окружения контейнера, значения никуда не выводились. Ничего не восстанавливал,
не создавал и не менял.

Две таблицы, на которых всё держится:

- **`references_reference`** — распределение номеров: `(project_id, ref) → (content_type, object_id)`,
  с уникальным индексом по паре `(project_id, ref)`. Строка **переживает удаление объекта**, поэтому
  по ней видно, какие номера были выданы и кому.
- **`history_historyentry`** — журнал: `type=3` означает удаление, `key` вида
  `userstories.userstory:182`, `user` — автор (jsonb с `pk` и `name`), `snapshot` — полный слепок
  объекта на момент события.

## 1. Что произошло: 315 номеров — это ровно 315 удалённых объектов

Номера в проекте 12 выданы **сплошь: 834 строки, ref от 1 до 834, без единой дыры**. Значит
пропуски в моём прошлом замере — не сбой счётчика, а объекты, которых больше нет.

| Тип | Номеров выдано | Объектов живо | **Удалено** |
|---|---:|---:|---:|
| user story | 459 | 303 | **156** |
| task | 192 | 78 | **114** |
| epic | 72 | 28 | **44** |
| issue | 111 | 110 | **1** |
| **Итого** | **834** | **519** | **315** |

Число сошлось с прошлым замером точно: 834 − 519 = 315.

**Побочно закрылась дыра прошлого отчёта.** Живых объектов в БД — 110 issues, 303 US, 78 tasks,
28 epics; это в точности то, что отдал MCP. Значит выдача инструментов полная, пагинация ничего не
резала, и пункт «пагинация не доказана» из прошлого вердикта снимается — теперь доказана.

Два разных почерка, и это важно для чтения:

- **156 историй** удалены со скоростью, недостижимой руками (74 в минуту), под аккаунтом `admin` —
  тем самым, под которым в Taiga ходит MCP. Это API/скрипт. **Кто именно за ним стоял, установить
  нельзя:** аккаунт общий, в журнале только он.
- **44 эпика** удалены человеческим темпом за 2 часа 48 минут под личным аккаунтом «Дмитрий
  Лебедев» — это ручная работа в интерфейсе. Среди удалённых эпиков E0, E1, E6, E18, E26, E34,
  E42, E43 — то есть та самая рубрикация, обломки которой до сих пор видны в заголовках живых
  историй (`[E3] …`, `[E4] …`).

**114 подзадач ушли каскадом, и это доказано, а не предположено:** у всех 114 в журнале есть
история, **ни у одной нет записи об удалении**, и у **всех 114** родительская история входит в те
самые 156 удалённых. Taiga при каскаде записи не пишет — отсюда и молчание журнала.

## 6. Проверка отдельного вопроса: выразим ли фильтр «не менялось дольше N дней» в Taiga

Проверял по этой инсталляции — исходники `taiga-back` и собранный `taiga-front` в контейнерах,
плюс таблицы БД. Не по документации Taiga вообще.

**Короткий ответ: рекомендацию про фильтр надо снять в текущем виде.** В веб-интерфейсе такого
фильтра нет и сохранить его нельзя. В REST API — есть.

### 6.1. Что умеет API (есть)

В `taiga/base/filters.py` объявлены `CreatedDateFilter` и `ModifiedDateFilter` на базе
`BaseCompareFilter` с операторами `""`, `lt`, `gt`, `lte`, `gte`. Оба **подключены** в
`filter_backends` и у `/api/v1/userstories`, и у `/api/v1/issues`. То есть запрос вида
`?project=12&status__is_closed=false&modified_date__lt=2026-05-08` выразим точно.
`order_by` тоже принимает `created_date` и `modified_date`.

Оговорка: это прочитано в коде задеплоенной версии. Живым HTTP-запросом я не проверял — своего
пользовательского токена Taiga у меня нет, а MCP-обёртка таких параметров не пробрасывает
(`list_issues` принимает только `status`, `assigned_to`, `priority`).

### 6.2. Что умеет веб-интерфейс (не умеет)

Полный список категорий фильтра в собранном фронте:

`ASSIGNED_TO`, `CREATED_BY`, `EPIC`, `PRIORITIES`, `ROLE`, `SEVERITY`, `STATUS`, `TAGS`, `TYPE`.

**Даты в этот список не входят.** Строк `modified_date__lt` / `created_date__lt` в бандле фронта
нет вовсе. `modified_date` во фронте встречается только как **колонка отображения и сортировки**
в таблице Issues (`ISSUES.TABLE.COLUMNS.MODIFIED` с кликабельной стрелкой) и как дата в вики и
профиле.

Это даёт ровно одну доступную вещь: **на вкладке Issues можно отсортировать по колонке «Изменено»**
и увидеть самые давние сверху. Для user stories нет и этого — у них только бэклог и канбан,
табличного представления с колонками не существует (строк `US.TABLE.COLUMNS.*` в бандле нет).

**И это бьёт ровно по той проблеме, которую предлагалось закрыть фильтром.** Когорта «заведено и
забыто» из замера — 37 задач возрастом 85–91 день, из них **36 user stories и 1 issue**.
Сортировка по «Изменено» на вкладке Issues покрывает **1 из 37**.

### 6.3. Сохраняются ли фильтры (да, но личные)

Механизм есть: во фронте это `custom-filters`, `custom-filters-add-form`, `custom-filter-list`.
Хранятся в таблице `userstorage_storageentry` — **`key`, `value`, `owner_id`**, поля проекта нет.

Живые примеры из базы, все три принадлежат одному пользователю (owner_id 7):

```
{"in_progress": {"exclude_status": "81"}}
{"active": {"exclude_status": "18"}}
{"active": {"exclude_status": "165"}}
```

Отсюда два факта:

- **Фильтр личный, а не проектный.** Привязка к владельцу, не к проекту; механизма поделиться
  сохранённым фильтром в схеме нет. Очередь, которую видит один человек, очередью не является —
  это твой же критерий, и он тут не выполняется.
- **Сохраняется ровно то, что умеет UI-фильтр** (в примерах — исключение статуса). Даты в UI нет,
  значит и в сохранённый фильтр она не попадёт.

Не проверял: применит ли фронт параметр `modified_date__lt`, если подсунуть его прямо в URL.
Своих параметров он не знает, и скорее всего проигнорирует, но это догадка — проверка потребовала
бы входа в интерфейс под живым пользователем.

### 6.4. Свои доски и представления (нет)

Кастомных представлений в Taiga нет: вкладки фиксированы (бэклог, канбан, спринты, issues, эпики,
вики). Ближайшее к «своей доске» — **swimlanes** канбана, таблица `projects_swimlane` в схеме
есть, но **во всей инсталляции ноль строк**: фича не используется нигде. И это в любом случае не
запрос, а ручная раскладка карточек.

### 6.5. Что есть ближайшее, если фильтр снять

| Вариант | Выразимо | Цена |
|---|---|---|
| Сортировка по «Изменено» на вкладке Issues | да | покрывает 1 задачу из 37; для US недоступно; не сохраняется как именованная очередь |
| Тег-маркер (`stale`) + сохранённый фильтр по тегу | да | фильтр по тегам в UI есть и сохраняется. Но тег кто-то должен ставить: руками — это ручной труд, скриптом — это снова код, то есть обещанного «ноль кода» не остаётся |
| Отдельный статус («Забытые») | да | то же самое: перевод статуса руками, плюс искажает воронку статусов |
| Запрос к REST API с `modified_date__lt` | да, точно | это код и его поддержка — ровно то, чего вариант с фильтром должен был избежать |
