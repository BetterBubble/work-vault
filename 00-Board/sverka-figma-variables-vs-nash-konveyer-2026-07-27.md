# Грабли Figma Variables API против нашего сборщика токенов

Источник — `90-Materials/export-tips.md` (Пётр Крыкин), восемь правил, снятых с граблей плагина
`var-exporter`. Сверял с `apps/backend/scripts/merge_iva_tokens.py` (341 строка, ветка `main`).

**Важное первым.** Плагин `var-exporter`, на граблях которого написан гайд, — **тот самый, которым
в веб-библиотеке ИВА выгружаются цвета** (`libs/design-system/src/lib/figma-integration/colors/`).
То есть гайд описывает не абстрактную теорию, а опыт эксплуатации именно того канала, к которому
нас разворачивают требованием «вход со страницы Figma».

**Что важно понимать про применимость.** Сегодня наш вход — **экспорт плагина Tokens Studio**, а не
Variables API. Пока это так, шесть из восьми правил нас формально не касаются: мы получаем уже
готовый JSON, а не ходим в API сами. **Но** ровно два из них бьют по нам уже сейчас, независимо от
источника, и все восемь становятся нашими в ту минуту, когда мы переходим на чтение со страницы
Figma. Ниже разведено.

---

## Бьёт по нам УЖЕ СЕЙЧАС

### 1. «Дедуплицируй только по ID; не объединяй токены из-за одинакового имени»

**Наш конвейер работает целиком по именам, идентификаторов в нём нет вообще.** Конкретно:

- Ссылки одного токена на другой ищутся регуляркой `\{([^}]+)\}` (строка 98) и проверяются как
  строковые пути — `alias_resolves` это буквально `ref in all_paths` (строки 215-218).
- Светлое и тёмное деревья сливаются по **совпадению имени ключа** (`merge_modes`, строки 135-188).
- На верхнем уровне при совпадении имён из разных входных файлов — **«later wins» молча**: коллизия
  печатается в отчёт, но сборка продолжается и поздний ключ затирает ранний (строки 293-303).
- Словарь связей с кодом матчит компоненты **по имени с алиасами** (Radio↔Radiobutton,
  Tabs↔Tab Group, Scroll Area↔Scroll, Select↔Dropdown) — и у всей мобильной системы это
  единственный способ матча, поскольку ключей Figma там ноль.

**Чем это грозит:** два разных токена с одинаковым именем в разных коллекциях схлопнутся в один без
ошибки. Переименование токена в Figma выглядит для нас как «старый исчез, новый появился» —
связь с кодом рвётся молча.

### 2. «Резолви алиасы рекурсивно, с кешем, защитой от циклов и отдельными ошибками»

**У нас нет ни рекурсии, ни защиты от циклов.** `alias_resolves` проверяет только, что путь-цель
существует в множестве путей. Следствия:

- **Цепочка** `A → B → C` не проверяется на разрешимость до конца: достаточно, чтобы каждый шаг
  существовал.
- **Цикл** `A → B → A` пройдёт проверку успешно — оба пути существуют. Ошибку поймает уже сервер
  при резолве, а не сборка.
- Нет различения «цель отсутствует» и «цель недоступна» — есть только общий список неразрешённых.

Оговорка честности: сервер при заливке валидирует блоб токенов и требует, чтобы алиасы
резолвились, — то есть вторая линия защиты есть. Но ловится это на сиде, а не при сборке.

## Станет нашим при переходе на вход со страницы Figma

### 3. Режимы задаются отдельно для каждой коллекции

Наш сборщик исходит из того, что тем ровно две и они приходят **двумя файлами** — `light` и `dark`
(строки 277-282 обращаются к этим ключам жёстко). Одномодовая или трёхмодовая система падает по
ошибке ключа. Мультиколлекционная модель `collection → mode → variable`, о которой говорит гайд, в
нашу схему не ложится вообще — понадобится переписывать слияние режимов, а не настраивать.

### 4. Не превращать ошибку чтения в «пустой набор токенов»

Прямо сейчас это не про нас (читаем файлы, а не API), но у нас есть **родственный дефект в другую
сторону**: при расхождении формы деревьев светлого и тёмного сборщик пишет предупреждение и
**тихо оставляет светлое значение** (строки 176-181); при расхождении типов — «keeping Light type».
То есть тёмная тема может потерять значение, и сборка при этом успешна. Код возврата ненулевой
только для неразрешённых ссылок.

### 5. Политика для hidden / remote / library переменных

**У нас политики нет, и это признано в самом коде.** Скрытые от публикации переменные считаются и
попадают в вывод, а строка отчёта прямо говорит: `hiddenFromPublishing: N (kept in output,
MCP-side filter TBD)` (строка 322). То есть скрытое в Figma доезжает до разработчика наравне с
опубликованным, а обещанный фильтр на стороне сервера не сделан.

**Это единственный пункт сверки, который я бы закрывал независимо от Figma-темы** — он не про
будущий вход, а про то, что уже выдаётся людям.

### 6. Не склеивать структурные ключи

Прямой склейки вида `collection - mode` у нас нет. Но есть родственная зависимость от имён:
мобильный `context` заворачивается в неймспейс по имени ключа (строки 269-270), а неймспейс
`legacy` вырезается по имени (строки 277-278). На новом профиле с таким же именем ключа обе ветки
сработают молча.

### 7. Сохранять исходные типы и точность; фиксировать формат цвета и альфы

Значения мы переносим как есть, своей арифметики над цветом не делаем — здесь чисто. Единственное
место, где тип может поменяться, — расхождение `$type` между светлым и тёмным, где берётся светлый.

### 8. Типизированная модель `collection → mode → variable`, имена — только для отображения

Это архитектурное требование, и оно **противоположно** тому, как устроен наш конвейер сегодня
(см. пункт 1). Если вход со страницы Figma станет обязательным, это не настройка, а переработка
модели данных сборщика.

## Итог в трёх строках

- **Закрыть сейчас, вне зависимости от остального:** фильтр скрытых переменных (`TBD` в коде) и
  рекурсивная проверка ссылок с защитой от циклов.
- **Знать как риск:** весь матч у нас именной, а не по идентификаторам — переименование в Figma
  рвёт связь молча; при коллизии имён поздний побеждает без ошибки.
- **Понимать масштаб:** переход на Variables API как вход — это не «поменять источник», а
  переписать модель сборщика под коллекции и режимы. Оценку в днях не даю.

**Чего не делал:** ничего не правил, это сверка. Правки по первому пункту итога стоит завести
отдельной задачей — в текущей задаче A правится только затирание словаря, трогать соседнее в том же
изменении не буду.
