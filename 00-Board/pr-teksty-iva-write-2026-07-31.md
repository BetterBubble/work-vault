## PR: `feat/iva-write-mcp-profile` → main (tacticum-dev)

**Заголовок:**

```
Канал записи iva-write у профиля аналитика: объявление, паки, квикстарт
```

**Описание — первый абзац обязателен, не удалять:**

```markdown
> ## ⚠️ Мержить только вместе с `feat/iva-write-rollout-roles`, следом за этим PR
>
> Этот PR объявляет канал записи в лейне `iva-analysis-fr` **без `allowed_tools`**. Лейн
> композит не только аналитик, но и **архитектор** — значит в одиночку этот PR выдаёт
> архитектору полную поверхность записи в контуре заказчика, **включая удаление**, которой у
> роли никогда не было (у неё был interim-канал со скоупом).
>
> Сужение прав лежит в `feat/iva-write-rollout-roles`. Мержить строго подряд, между ними не
> сидить каталог и не выкатывать профили.

## Что это

Задеплоенный в helm канал записи `/mcp/iva-write` до людей не доезжал: MCP-сервер не был
объявлен в каталоге профилей. Человек мог дать согласие, но применить его было нечем.

## Состав

- **Ингредиент `helm-iva-write`** — http, `https://helm.tacticum.ru/mcp/iva-write`, bearer, тот
  же `TACTICUM_TOKEN`. Отдельный ключ не нужен.
- **Паки роли переключены** на новый канал как основной. Без этого объявление не дало бы
  эффекта: промпты называли каналом публикации старый `iva-atlassian-write`, и агент ходил бы
  мимо. В паках сказано прямо: отказ до согласия — **не поломка и не повод искать обход**.
- **Старый канал оставлен** временным запасным; в манифесте оба названы друг через друга.
- **Квикстарт** — шаги согласия с объяснением, **почему порядок Jira → Confluence обязателен**:
  Confluence не отдаёт почту, личность подтверждается на Jira и оттуда переносится привязка.
- **Памятка раскатки** — восемь шагов, чтобы выдача роли была механикой.

## Что проверено

**1081 тест, 0 падений.** Проверка не ограничена манифестом: e2e делает реальный сид в базу →
сборку профиля → выкладку на диск → сверку. До обновления эталонов тест падал **именно на
MCP-конфиге** — это и есть доказательство, что ингредиент доезжает.

## Чего здесь нет

- живого ответа сервера по адресу — проверялось отдельно на боевой учётной записи;
- раскатки на остальные роли — в следующем PR;
- снятия временного канала — отдельный шаг после живого прогона.
```

## PR: `feat/iva-write-rollout-roles` → main (tacticum-dev)

**Заголовок:**

```
Раскатка канала записи: QA получает канал, архитектор — сужение прав
```

**Описание:**

```markdown
> Мержить **сразу после** `feat/iva-write-mcp-profile`. Этот PR в том числе чинит
> непреднамеренное расширение прав, внесённое предыдущим.

## Что сделано

**QA** (`iva-role-qa`, `iva-role-qa-web`) — канал выдан, скоуп Jira: дефекты и статусы,
перенесён с временного канала.

**Архитектор — сужение, а не выдача.** Он композит общий лейн, где канал объявлен без
ограничений, то есть **полная поверхность записи у него уже есть** после предыдущего PR. Здесь
тот же ингредиент объявлен у роли повторно, суженным (Confluence: авторство страниц; Jira:
операции над задачами) — выигрывает как более поздний в цепочке зависимостей, механика та же,
что уже работала для временного канала.

**Техпису не выдан** — намеренно. У роли нет паков, и агент на первом отказе молча уйдёт на
временный канал, где **подпись автора чужая**. Тихая подмена авторства хуже отсутствия
инструмента. Цена отсрочки — один блок и строка в тестах.

**`iva-fr-analyst` не выдан** — профиль замещён преемником, у которого канал есть.

**dev-роли не тронуты** — канал записи в контур заказчика им не нужен.

## Четыре уровня проверки, которых не было в репозитории

За сутки один и тот же класс дефекта всплыл четырежды: **инструмент роли выдан, а текст, который
ведёт человека или агента, про него не знает.** Сначала промпты, потом пользовательские
инструкции, потом README. Чинить это внимательностью не выходит — добавлены проверки.

Каждая ловит своего читателя, и разъезжаются они независимо:

| Уровень | Кого ведёт |
|---|---|
| промпт роли | агента, который выполняет работу |
| квикстарт | человека, который ставит профиль |
| README роли | того, кто выбирает роль и сверяет, что она умеет |
| страница согласия | человека в роли **без** квикстарта — единственный текст, который до него доедет |

Плюс проверка на невырожденность: набор ролей считается по наличию файла, и переименование
инструкции молча опустошило бы параметризацию — тогда проверки стали бы всегда зелёными.

**Оракул README окупился сразу после написания — поймал два реальных расхождения:** README
архитектора называл единственным каналом публикации временный, под личным токеном Atlassian,
уже после выдачи нового; а README аналитика не показывал ни канал, ни лейн, в котором тот живёт —
то есть карточка роли умалчивала о единственном способе роли что-либо опубликовать.

Все проверки идут по одному набору ролей: новая роль в нём автоматически попадает под все четыре.
Отсутствие квикстарта — законный пропуск с причиной, а не провал.

## Числа

**1099 passed, 2 skipped, 0 failed** (эталон был 1081/0). Дельта сходится по составу:
невырожденность 1 + квикстарт 4 + страница согласия 4 + README 4. Оба пропуска — архитектор:
у него нет ни промптов, ни квикстарта.

Дисциплина версий — 59 профилей чисто. Синхронность зеркал — 73 ингредиента в 6 парах.
Ветка сведена с актуальным `main`.

## Что осталось непроверенным

- **имена инструментов живьём** — скоуп перенесён с временного канала по выводу из кода
  (поверхность в helm — прозрачный прокси перед тем же пакетом). Оговорка и лечение записаны в
  комментариях обоих манифестов;
- **архитектор до диска не прогонялся** — у роли нет паков, сквозной прогон для неё не
  существует;
- шаги согласия для QA и архитектора — отдельная общая страница, в работе.
```

## PR: `fix/catalog-docs-truth` → main (tacticum-dev)

**Заголовок:**

```
Доки: убрать несуществующую ручку выдачи phk-ключей и её модель
```

**Описание:**

```markdown
Страница установки профиля описывала эндпоинт `POST /admin/api-keys`, которого **не
существует** — идущий по ней получал 404.

За неверной ручкой стояла и неверная модель: страница считала, что ключ принадлежит установке.
В коде он принадлежит **членству в организации** и покрывает все её установки, а профиль
выбирается параметром запроса, а не токеном. Отсюда там же «нужны два ключа» вместо одного,
отзыв через несуществующий путь и описание ручки как будущей, хотя она приехала и токенов не
выдаёт вовсе.

Заодно исправлено устаревшее утверждение, что создать пользователя через админский API нельзя:
ручка есть и работает как найти-или-создать по почте.

**216 + 923 теста зелёные**, правки только в текстах.

Контракты читались по коду и тестам; живых запросов к админскому API не делалось.
```

## PR: `feat/iva-write-texts-rest` → main (helm)

Линии закрылись, ветка одна, кнопка одна. Три ночные ветки (`bot-revoke`,
`identity-from-platform`, `key-lookup`) и сводная `night` — её предки; **мержить их отдельно не
нужно и вредно.**

**Заголовок:**

```
Бот iva-write: отзыв доступа, личность из события платформы, проверка ключа
```

**Описание:**

```markdown
## Что это

Три возможности бота выдачи доступа плюс правка текстов, которые обещали больше, чем бот умеет.
Ветка сводит три ночные линии — они трогают соседние строки одних функций, и раздельный мерж дал
бы рабочий на вид код с потерянной логикой (три таких стыка найдены и закрыты, см. ниже).

## Что сделано

- **Отзыв доступа через бота.** Закрывает последний невыполненный пункт критерия приёмки —
  «отзыв гасит доступ». Раньше бот на просьбу отозвать выдавал новые ссылки, а отзыв жил только
  в ручке `POST /api/iva/oauth/revoke`. Планка личности та же, что у статуса: названный в чате
  адрес отзыва не даёт.
- **Личность из события платформы.** Почта выводится из логина и **проверяется в справочнике
  Jira**, а не принимается на слово. Чинит причину разрыва почт, а не симптом: раньше человек
  называл почту в чате, и если она расходилась с почтой из ключа — согласие ложилось на один
  субъект, а канал искал по другому. Опирается на соглашение «логин = локальная часть почты»,
  подтверждённое на 4 учётках из 4, — но **за выключателем**, потому что это соглашение чужой
  организации, а не гарантия.
- **Проверка наличия ключа.** Бот отвечает, есть ли у человека ключ и пользовались ли им
  (последнее и есть случай «потерял»). **Выключено по умолчанию** — нужен админ-токен каталога,
  а это широкие права у сервиса с публичным входом.
- **Тексты.** Починены все места, где бот обещал то, чего не будет, или советовал ход, который
  сам же отклонит.

## Три стыка, ради которых сведение делалось руками

Ни один не ловится тестами отдельных веток — в каждой логин всегда почта:

1. личность обогащалась **после** того, как отзыв и проверка ключа принимали по ней решение →
   человек с логином-не-почтой получал «личность неизвестна» на отзыв. То есть ровно те люди,
   ради которых писалась ветка про личность;
2. в таблице подсказок оставалась заглушка «отзывать я не умею» **рядом с работающим отзывом** —
   прямая ложь пользователю;
3. «отозвать ключ» при включённой проверке каталога теряло объяснение разницы между ключом и
   доступом.

Доказано экспериментом: наивный порядок вызовов → ровно 4 падения.

## Проверено

- **2538 тестов, 0 падений, 32 skipped** (база `main` — 2435). 25 файлов, +4709/−311.
- Независимый гейт — **GO** с 7 оговорками; три мутации в чистой копии. Сначала был NO-GO, обе
  претензии закрыты коммитом `b57c188`.
- Добавлен оракул «что бот говорит о себе против того, что он умеет» плюс защита от
  вырождения — снимок и оракул не могут ослепнуть молча.

## Чего здесь нет

- **Проверка ключа выключена** — до решения по админ-токену в окружении helm.
- **Личность из события платформы не проверена живьём**: платформа ботов за 90 дней не
  достучалась до helm ни разу, ключи от их команды не получены.
- **Открытый вопрос к команде ботов:** редактируется ли поле `author.login` в событии самим
  пользователем. Если да — человек получит чужой статус и **чужой отзыв доступа**. Запись при
  этом защищена сверкой на колбэке, а отзыв — нет. Изнутри проверить невозможно.

## Мерж не означает выкатку

Деплой отдельным шагом и **`bash scripts/deploy.sh` с дефолтами не запускать** — `SEED=1` сносит
боевой граф. Безопасный порядок: `pg_dump` → `alembic current` → `up -d --build` →
`alembic upgrade head` руками.
```
