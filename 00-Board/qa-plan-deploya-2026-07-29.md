## Порядок сида — соблюдается автоматически

**Ручное разделение «сначала лейн, потом роль» НЕ требуется.** `seed_community.py:144-161` делает
two-pass: сначала манифесты **без** `depends_on` (лейны и базы), затем зависимые (роли). Комментарий
в коде прямо ссылается на ADR-0056: алфавитный порядок засеял бы роли раньше баз и дал
`depends_on_missing_ref`.

**Почему это важно помнить всё равно:** порядок критичен по сути — ребро `depends_on` фиксируется в
момент сида роли на **последнюю активную** версию базы. Засей роль раньше лейна — она приколотится к
старому 0.3.0, и вся работа не доедет при зелёных проверках. Сидер это делает правильно сам, но
если кто-то будет сидить профили поштучно — порядок придётся держать руками.

## ⚠️ Сидер сидит ВЕСЬ каталог

`seed_community.py` читает `templates/*/manifest.yaml` целиком — **выбрать один профиль нельзя**.
Значит вместе с нашим поедут все изменения из `main`, включая чужой PR #172 (`tacticum-lite-base`).
Это не побочный эффект нашей работы, а свойство сидера, но знать надо: если у чужого профиля
окажется проблема с версионированием, сид сообщит об этом в общем выводе.

## Последовательность

**Шаг 0 — бэкап.** Перед любой записью:
```
pg_dump -Fc -U catalog tacticum_catalog > /tmp/catalog_backup_$(date +%F_%H%M).dump
```
(в контейнере `tacticum-postgres-1`; прежние бэкапы лежат в `/tmp/catalog_backup_*`, ~11 МБ).

**Шаг 1 — подтянуть `main`** на сервере в `/opt/tacticum` до `f72467a`.

**Шаг 2 — сид.** Ручной one-off контейнер, образ **НЕ пересобирать** (меняется только контент):
```
docker compose run --rm --no-deps -v ./scripts:/app/scripts -v ./templates:/app/templates \
  catalog-mcp python scripts/seed_community.py templates
```

**Шаг 3 — перепин установки** инженера с 0.5.1 на 0.5.4. Без этого он останется на старой версии:
пин установки сам не двигается.

**Шаг 4 — сказать инженеру сделать pull** (текст ниже).

## Чем доказать, что доехало

**После шага 2 — версии засеяны:**
```sql
SELECT profile_id, version, status, seeded_at FROM profile_versions
WHERE profile_id IN ('iva-role-qa','iva-qa-autotest-base')
ORDER BY profile_id, seeded_at;
```
Ожидаем новые строки: лейн **0.5.0**, роль **0.5.4**, обе `active`.

**Главная проверка — ребро село на новый лейн:**
```sql
SELECT dv.profile_id AS role, dv.version AS role_ver,
       bv.profile_id AS base, bv.version AS base_ver
FROM profile_version_dependencies d
JOIN profile_versions dv ON dv.id = d.dependent_version_id
JOIN profile_versions bv ON bv.id = d.base_version_id
WHERE dv.profile_id = 'iva-role-qa' AND dv.version = '0.5.4';
```
**Обязано быть `iva-qa-autotest-base 0.5.0`.** Если там 0.3.0 — сид прошёл в неверном порядке,
и роль надо переиздавать заново. Это единственная проверка, ради которой стоит останавливаться.

**После шага 3 — пин обновлён:**
```sql
SELECT profile_version_pinned, last_synced_version, sync_count
FROM installations WHERE id = 'b258bb6b-f241-47b9-8b8d-3ec8ed04cdaa';
```
`profile_version_pinned` = **0.5.4**.

**После шага 4 — доставка состоялась (главный признак):**
тот же запрос, **`last_synced_version` = 0.5.4** и `sync_count` вырос с 3.

Пока `last_synced_version` не равен 0.5.4 — **работа до человека не доехала**, чем бы ни были зелены
наши проверки. Это и есть критерий готовности, а не «мы задеплоили».

**Дополнительно — что реально приземлилось у него**, по телеметрии:
```sql
SELECT occurred_at, tool_name, profile_version
FROM telemetry_events
WHERE installation_id = 'b258bb6b-f241-47b9-8b8d-3ec8ed04cdaa'
ORDER BY occurred_at DESC LIMIT 10;
```

# Деплой №2 — правка утечки в MR (готовится)

**Почему срочно.** На версии, которая **уже стоит у инженера** (лейн 0.5.0, роль 0.5.4), навык
подготовки MR-ветки не исключает файлы профиля: непокрытыми оказались **78 файлов из 99**. При
первой же доставке через этот навык каталог профиля уедет в **продуктовый репозиторий заказчика**.

Ветка `fix/qa-mr-exclusions`: лейн 0.5.0 → **0.5.1**, роль 0.5.4 → **0.5.5** (переморожена на 0.5.1).
Плюс снято противоречие «кто заводит дефект» и закрыты хвосты к несуществующим файлам.

**Последовательность — та же, что в деплое №1**, и порядок так же критичен:

1. Бэкап `pg_dump -Fc` (прежний: `/tmp/catalog_backup_predeploy_2026-07-29_0903.dump`).
2. `git pull --ff-only` на сервере до коммита с правкой.
3. Сид: `docker compose -f docker-compose.prod.yml run --rm --no-deps -v /opt/tacticum/apps/backend/scripts:/app/scripts -v /opt/tacticum/templates:/app/templates catalog-mcp python scripts/seed_community.py templates` — образ не пересобирать, two-pass соблюдается сидером.
4. **Проверка ребра:** роль 0.5.5 обязана указывать на лейн **0.5.1**.
5. Перепин установки `b258bb6b` на 0.5.5 через `PATCH /admin/installations/{id}`.
6. Сказать инженеру обновиться.

**Признак доставки прежний:** `last_synced_version` = 0.5.5 у инженера.

**Что сказать инженеру дополнительно:** до обновления **не пушить MR не глядя** — посмотреть дифф
перед пушем. Это уже вписано в письмо ниже.
