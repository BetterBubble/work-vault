# Критик B по #621: правка слишком широка

Ветка `fix/621-seed-changelog`, голова `f0db0cd8`, worktree `~/tacticum-worktrees/bl-621`.
Дерево чистое, HEAD на старте и в конце разбора совпадают. Ничего не правил, не коммитил, на
сервер не ходил. Тезис к доказательству: второй коммит вносит риск, которого задача не требовала.

**Итог: частично.** Второй коммит нужен — без него ни одна прод-строка не заполнится никогда, это
я перепроверил и подтверждаю. Но написан он на одно условие шире необходимого, и именно это лишнее
условие тянет за собой весь названный риск.

---

## Главное, одним числом

Условие в `seed_profile.py:267`:

```python
if payload.changelog is not None and existing.changelog != payload.changelog:
```

Строго более узкий вариант — заполнять только пустое:

```python
if payload.changelog is not None and existing.changelog is None:
```

**Прогнал весь `tests/catalog` на этом варианте: 1293 теста, 0 падений, 0 ошибок, 57 skip, RC=0.**
Ни один тест ветки не удерживает разницу — включая все 17 новых. Прогон в изолированной копии
(`git archive HEAD` в скретчпад, рабочее дерево не тронуто, импорт проверен по `__file__`):

```
PYTHONPATH=<копия>/src .venv/bin/python -m pytest tests/catalog -q -p no:randomly
→ tests="1293" errors="0" failures="0" skipped="57"   RC=0
```

Покрытие каталога от сужения не меняется: прод-колонка пуста везде (симптом задачи), значит
`existing.changelog is None` истинно для всех 64 строк, и backfill даёт те же 64/64.

Разница между написанным и необходимым — ровно одно поведение: **молчаливая перезапись release
notes уже опубликованной версии**. Его никто не просил, его не проверяет ни один тест, и оно
единственное создаёт всё, что перечислено ниже.

## Что лишнее — с ценой каждого пункта

### 1. Обход неизменяемости собран из двух по отдельности верных шагов — блокирует

Это не «changelog вне хеша», как написано в обоих отчётах. Проверено вызовом
`canonical_payload_hash`:

```
поле SeedPayload.changelog меняет hash?          False
ключ manifest['changelog'] меняет hash?          True
правка manifest['changelog'] A → B меняет hash?  True
```

`manifest_for_hash` (`seed_profile.py:132-133`) исключает только `deprecated`, `visibility`,
`owner_org`, `superseded_by`. Ключ `changelog`, если он объявлен в манифесте, **в хеш входит** —
и до этой ветки release notes жили именно там. Значит **до ветки правка release notes
опубликованной версии была невозможна**: она меняла хеш и упиралась в
`version_already_exists_with_different_content`, то есть требовала бампа ровно по ADR-0009.

Коммит 1 переносит источник значения из хешируемого манифеста в **нехешируемый файл**
`CHANGELOG.md`. Сам по себе шаг верный. Коммит 2 делает этот нехешируемый источник авторитетным
над опубликованными строками. Тоже по отдельности объяснимый. Композиция даёт канал записи в
опубликованную версию, не проходящий через `payload_hash` вообще — то, чего в этой системе не
было.

Подтверждение из репозитория, что дыра именно тут: гейт дисциплины версий явно и намеренно
освобождает `CHANGELOG.md` от требования бампа — `scripts/check_profile_version_discipline.py:34`,
«ANY file change under `templates/<profile_id>/` **other than `CHANGELOG.md`** requires
`manifest.yaml` `version:` to differ from the base». Освобождение было безопасным ровно потому,
что файл до сих пор никуда не доезжал. Теперь единственный файл, который гейт пропускает без
бампа, пишет в прод.

**Цена.** Утверждение «ослаблен только сопроводительный текст» верно по смыслу поля, но граница
проходит не там, где сказано в отчёте: ослаблен не тип данных, а **механизм защиты** — снят
единственный сторож, который стоял на этом поле. При сужении до backfill-only канал закрывается:
записать можно только в пустое, переписать написанное нельзя.

### 2. Перезапись задним числом — не гипотеза, у неё измеренная частота

Прогнал историю каталога прод-функцией `extract_changelog_section` **из самой ветки**: для каждого
коммита сравнил секцию версии, объявленной в манифесте, до и после, при условии что версию в этом
же коммите не бампали (то есть строка в проде уже существует).

| срез истории | коммитов с правкой `CHANGELOG.md` | **перезапись секции опубликованной версии** | дозаполнение пустой |
|---|---|---|---|
| все коммиты | 401 | **75** (52 уникальных пары профиль+версия) | 6 |
| только мержи в main (= деплои) | 172 | **7** (5 уникальных пар) | 1 |

Честная цифра — вторая: `--first-parent`, потому что сид отрабатывает на мерже. **7 раз за всю
историю каталога** прод-строка опубликованной версии получила бы новый текст release notes без
бампа. Это ~1 случай на 25 мержей, трогающих `CHANGELOG.md`.

Это не косметика. Пример `7dedb5e3` (04.06, `iva-rn-brownfield` 0.3.1, 1423 → 2004 символа) —
в секцию уже выпущенной версии дописан целый новый скилл `rn-local-launch` с описанием на десять
строк. Та же пара `iva-rn-brownfield` 0.3.1 росла так трижды (`b4ae01d0` 948→1423, `7dedb5e3`
1423→2004, `3ef196ac` 2004→2187). При этом шапка той самой секции в тот момент гласила:
«Content change → new immutable version (ADR-0009); must be re-seeded».

`check_updates.py:99` отдаёт `latest.changelog` агенту дословно. Значит сценарий вреда конкретный:
пользователь читает release notes версии, на которой стоит; через неделю тот же вызов на той же
версии возвращает другой текст, и ничто в ответе не говорит, что текст менялся.

**Цена.** Блокирует: после мержа и деплоя перезаписанные значения уже не восстановить (истории
колонки нет), а сужение стоит одно условие и ноль правок в тестах.

### 3. Храповик в одну сторону — очистить нельзя вообще, и пути нет ни одного

Перебрал все writer-ы колонки. `grep -rn "changelog" src/ --include='*.py'` даёт ровно три записи:
`seed_profile.py:369` (создание версии), `catalog.py:357` (создание **черновика** через админку),
`seed_profile.py:269` (новая ветка noop). Список ручек админки —
`@router.post/patch/delete` в `catalog/interface/admin/catalog.py` — **не содержит ни одной,
меняющей `changelog` существующей версии**: `ProfilePatchRequest` и `IngredientPatchRequest` этого
поля не имеют, `/publish`, `/retract` его не трогают.

Значит на вопрос «как выкинуть ошибочно засеянный текст из прода» ответ такой: **никак, кроме
прямого SQL по проду**. Ни ретракт, ни бамп версии старую строку не чистят.

**Цена.** Долг, но обязан быть записан: сейчас его нет ни в отчёте реализатора, ни в задаче.
Замечу, что сужение до backfill-only храповик не снимает (после SQL-очистки сид зальёт снова) —
это отдельный пункт, и честный его закрыватель — админская ручка на `changelog`, вне скоупа #621.

### 4. Записи нет ни в одном следе, который переживёт ротацию логов — блокирует вместе с п.1

- `seeded_by` проставляется только при создании (`seed_profile.py:368`), на noop не меняется.
- `seeded_from_commit` на noop тоже не меняется. После перезаписи строка утверждает, что текст
  пришёл из коммита X, тогда как он пришёл из коммита Y.
- `AdminAudit` на пути CI **не пишется вообще** — `grep -n "AdminAudit" scripts/seed_community.py`
  пусто. На пути `/admin/seed` запись есть (`platform/admin/router.py:139-148`), но с
  `result="success"`, `status="noop"`, `reason="identical_payload"` — то есть аудит утверждает, что
  ничего не менялось.
- Человекочитаемый вывод деплоя (`seed_community.py:269`) печатает `[noop    ] <профиль> @ <версия>`
  и `reason: identical_payload`. Оператор видит «ничего не изменилось» ровно там, где изменилось.

Это прямо противоречит двум объявленным последствиям ADR-0009 (§Положительные): «**Audit trail**:
`seeded_at`, `seeded_from_commit`, `payload_hash` дают точное соответствие „что было в DB на момент
T“ и „откуда оно пришло“» и «**Replay-возможность**: `seeded_from_commit` позволяет re-checkout
commit и сверить содержимое». Для колонки `changelog` оба обещания после второго коммита неверны.

**Цена при разборе инцидента:** вопрос «когда и из-за какого коммита release notes стали такими»
из базы не решается; остаётся только структурный лог `seed_changelog_updated_on_noop` с
неизвестной глубиной хранения. При сужении до backfill-only цена падает почти до нуля: событие
однократное на строку и его результат совпадает с содержимым файла на момент любого последующего
деплоя.

### 5. У записи нет фильтра по статусу версии — долг

`existing` выбирается без условия на `status` (`seed_profile.py:218-224`), а ретракт лишь ставит
`status="retracted"` (`platform/admin/router.py:181-190`). Значит ветка noop перепишет release
notes и у **отозванной** версии — той, которую ADR-0009 хранит именно как замороженный след
(«Retraction … не через DELETE и не через overwrite»). На проде это редкий случай (у отозванной
версии обычно уже нет своего манифеста в каталоге), поэтому долг, а не блокер, но условие
`existing.status == "active"` стоит одну строку.

### 6. Решение принято, но нигде не зафиксировано — долг

Редактируемость release notes опубликованной версии автор называет намеренным решением. Тогда у
неё должны быть три вещи, и нет ни одной: **теста**, который её удерживает (доказано выше — сужение
проходит 1293/1293), **строки в ADR-0009** (файл `docs/adr/0009-pinned-immutable-versioning.md` не
менялся, в диффе его нет), **следа в данных** (п.4). Решение, которое живёт только в тексте отчёта
на доске, через месяц будет снято первым же, кто сузит условие — и все тесты останутся зелёными.

## Направления, где риска НЕ нашёл — проверял, называю честно

**Обнуление колонки пустым значением.** Атаковал, не подтвердилось. `extract_changelog_section`
заканчивается `return section or None` (`seed_community.py:146`), `_build_payload` берёт
`manifest.get("changelog") or _read_changelog(...)` — пустая строка до payload не доходит ни одним
путём, а `payload.changelog is not None` стоит первым условием. Тест
`test_reseed_without_changelog_does_not_wipe_existing` это удерживает.

**Клобберинг админского черновика.** Проверял: админка создаёт версию со `status="draft"` и
манифестом из двух ключей (`catalog.py:346-358`), её `payload_hash` считается по этому манифесту,
поэтому сид от CI на ту же пару даст **другой** хеш → `rejected`, а не noop. Ветка noop до
админского текста не дотягивается.

**Откат ветки.** Безопасен для заполнения: значения корректны и останутся в базе, `check_updates`
продолжит их отдавать, обратной миграции не нужно. Невосстановимы только те значения, которые
ветка успела **перезаписать** до отката — история колонки не ведётся. То есть цена отката целиком
сидит в том же лишнем условии.

**«Числа сняты на устаревшей базе».** Ветка отстала от `origin/main` (`0176410b`) на три коммита,
и main успел тронуть `CHANGELOG.md`/`manifest.yaml` трёх профилей. Перемерил покрытие парсером
ветки на **актуальном** `origin/main`: `профилей=64 заполнено=64 пусто=0` — то же самое, что на
базе `757c5dc2`. Претензии нет, ребейз ничего не ломает.

**Альтернатива «коммит 1 + разовая миграция».** Проверял, честнее не выходит. Alembic-миграция
должна была бы читать `templates/**` с диска (данные лежат в репозитории, а не в БД) — это
миграция, зависящая от рабочего дерева, что хуже постоянного кода. Разовый флаг
(`seed_community.py --backfill-changelog`) означал бы, что колонку нужно чинить руками при каждом
новом профиле, засеянном до правки. Backfill на noop — верная форма; спор только про то, что
считать backfill'ом.

## Что предлагаю (применяет лид, я не правлю)

1. **Сузить условие до `existing.changelog is None`** — одно слово, 0 правок в тестах, 1293/1293
   зелёные (измерено). Закрывает п.1, п.2, п.4 целиком.
2. Если решение «release notes редактируемы» сознательно оставляют — тогда **до мержа**: тест,
   пиннящий перезапись непустого; addendum к ADR-0009; и хотя бы `seeded_from_commit` или
   `AdminAudit` на этой ветке, иначе п.4 остаётся.
3. Добавить `existing.status == "active"` в условие — одна строка (п.5).
4. Записать в долг отсутствие любого пути очистки колонки (п.3) — сейчас его не знает никто.
