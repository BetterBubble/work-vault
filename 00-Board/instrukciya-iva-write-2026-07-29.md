# iva-write: как включить и как выдавать доступ

Требование к этому тексту сформулировано дословно: он должен работать для человека **не очень
умного, но исполнительного**. Поэтому: каждый шаг — законченное действие, после каждого сказано,
как понять, что получилось, и что делать, если нет. Ничего не «подразумевается».

Документ из двух частей. **Часть А — для того, кто настраивает** (делается один раз).
**Часть Б — для сотрудника**, который получает доступ (тридцать секунд, ничего не настраивает).

---

# ЧАСТЬ А. Настройка — один раз

## Шаг 1. Получить четыре значения от администратора Atlassian

Отправить запрос по готовому тексту: [[zapros-adminu-atlassian-2026-07-29]].

Вернуться должны **четыре значения**:

| Что | Откуда |
|---|---|
| Client ID для Jira | регистрация в `jira.iva.ru` |
| Client secret для Jira | там же |
| Client ID для Confluence | регистрация в `wiki.iva.ru` |
| Client secret для Confluence | там же |

**Адрес возврата, который администратор обязан вписать посимвольно:**

```
https://helm.tacticum.ru/api/iva/oauth/callback
```

Один и тот же для обеих систем. Если он отличается хоть одним символом — согласие будет
отклоняться, и сообщение об ошибке человеку ничего не объяснит.

**Как понять, что шаг выполнен:** на руках четыре значения и подтверждение, что адрес возврата
вписан именно такой.

## Шаг 2. Сгенерировать мастер-ключ шифрования

Этим ключом шифруются доступы людей. **Он не хранится в базе и не лежит в репозитории.**

```
openssl rand -base64 32
```

Полученную строку сохранить в надёжном месте (менеджер паролей). **Если ключ потерять —
все сохранённые доступы станут нечитаемыми, и всем людям придётся давать согласие заново.**

## Шаг 3. Прописать настройки helm

Все значения — в окружение сервиса helm (файл `/opt/helm/.env` на сервере), **не в код и не в git**.

```
# ключ шифрования из шага 2
HELM_KEYSTORE_MASTER_KEY=<строка из openssl>

# от администратора, шаг 1
HELM_IVA_OAUTH_JIRA_CLIENT_ID=<...>
HELM_IVA_OAUTH_JIRA_CLIENT_SECRET=<...>
HELM_IVA_OAUTH_CONFLUENCE_CLIENT_ID=<...>
HELM_IVA_OAUTH_CONFLUENCE_CLIENT_SECRET=<...>

# адреса систем заказчика
HELM_IVA_OAUTH_JIRA_BASE_URL=https://jira.iva.ru
HELM_IVA_OAUTH_CONFLUENCE_BASE_URL=https://wiki.iva.ru

# наш публичный адрес — из него собирается адрес возврата
HELM_IVA_OAUTH_PUBLIC_BASE_URL=https://helm.tacticum.ru

# КАК helm физически дотягивается до Jira и вики: через SSH-туннель.
# Имя системы берётся из base_url выше, а подключение идёт по этому адресу.
HELM_IVA_OAUTH_JIRA_CONNECT_URL=https://172.18.0.1:8443
HELM_IVA_OAUTH_CONFLUENCE_CONNECT_URL=https://172.18.0.1:8443

# PKCE. Оставить как есть; выключать ТОЛЬКО если администратор ответил,
# что их сервер PKCE не поддерживает (вопрос 1 из письма).
HELM_IVA_OAUTH_PKCE_ENABLED=true
```

⚠️ **Переменных `HELM_IVA_WRITE_MCP_URL`, `HELM_IVA_WRITE_JIRA_URL`, `HELM_IVA_WRITE_CONFLUENCE_URL`
в этот файл добавлять НЕ НУЖНО.** Они уже заданы в `docker-compose.prod.yml` (строки 73–75), а
значения из `environment:` в compose **перекрывают** `.env` — то, что вы пропишете здесь, просто
не подействует. Там они с портом туннеля (`https://jira.iva.ru:8443`), и это правильно: имя нужно
для сертификата, порт — для туннеля.

**Имя Confluence должно совпадать в двух местах:** в `HELM_IVA_OAUTH_CONFLUENCE_BASE_URL` выше и в
регистрации у администратора. Боевое имя — **`wiki.iva.ru`**, проверено на сервере.

## Шаг 4. Поднять контейнер записи

Он уже описан в `docker-compose.prod.yml`. Проверить перед запуском **самое важное**:

```
ATLASSIAN_EXTERNAL_AUTH_ENABLE=true
MCP_ALLOWED_URL_DOMAINS=iva.ru
extra_hosts: jira.iva.ru → 172.18.0.1, wiki.iva.ru → 172.18.0.1
expose: 9000        # наружу НЕ публикуется
```

⚠️ **В окружении этого контейнера не должно быть ни одного ключа доступа** — ни `JIRA_*`, ни
`CONFLUENCE_*`, ни OAuth-значений, и **файл `.env` от helm туда монтировать нельзя**. Причина не
косметическая: если контейнер найдёт у себя учётные данные, то при любом сбое подстановки он
запишет в Jira **под служебной учёткой, молча и с успешным ответом**. Пустое окружение превращает
такой сбой в честный отказ.

**Как понять, что шаг выполнен:** контейнер поднялся, наружу не виден, в его окружении пусто по
учётным данным.

## Шаг 5. Накатить миграции и перезапустить

**Без этого шага таблицы не появятся, и канал не заработает** — в этой поставке четыре новые
ревизии базы.

```
bash scripts/deploy.sh
```

Скрипт сам пересоберёт, применит миграции (`alembic upgrade head`) и поднимет сервисы.
Если запускаете руками — миграции обязательны:

```
docker compose exec -T helm uv run --no-sync alembic upgrade head
```

**Как понять, что получилось:** команда отработала без ошибок, в логе видно применение ревизий.

## Шаг 6. Проверить, что канал жив

```
curl -s -o /dev/null -w "%{http_code}\n" https://helm.tacticum.ru/mcp/iva-write/
```

| Ответ | Что это значит |
|---|---|
| **401 или 403** | **Правильно.** Без ключа человека канал не пускает |
| **503** | Канал не сконфигурирован: не заданы адреса или не поднят контейнер записи. Вернуться к шагам 3–4 |
| **404** | Поверхность не смонтирована — смотреть логи helm |
| **200 без ключа** | **Остановиться и разбираться.** Такого быть не должно |

## Шаг 7. Бот (когда придут ключи от команды Медведева)

```
HELM_IVA_BOT_IVA_WRITE_ENABLED=true
HELM_IVA_BOT_IVA_WRITE_TOKEN=<токен бота>
HELM_IVA_BOT_IVA_WRITE_WEBHOOK_SECRET=<секрет вебхука>
```

Их стороне нужно прописать у себя адрес: `POST https://helm.tacticum.ru/api/bot/iva-write/webhook`.

**Пока ключей нет — бот не нужен.** Ссылку человеку можно отдать вручную, всё остальное работает
так же.

# ЧАСТЬ Б. Для сотрудника — как получить доступ

1. Напиши боту: **«дай доступ к iva-write»**.
2. Бот пришлёт **ссылку**. Если он спросит рабочую почту — напиши её.
3. Открой ссылку, нажми **«Разрешить»**. Так дважды: сначала для задач, потом для вики.
4. Бот ответит **«готово»**. Всё.

**Что происходит дальше.** Записи в Jira и Confluence идут **от твоего имени и с твоими правами** —
ровно то, что ты и так можешь. Ничего сверх твоих прав не появляется.

**Токен тебе не нужен и не выдаётся** — он хранится у нас в зашифрованном виде и на твой компьютер
не попадает.

**Если передумал:** напиши боту «отозвать доступ». Доступ перестанет работать сразу.

**Проверить состояние:** напиши боту «статус» — покажет, какие системы подключены и до какого срока.

# Если что-то пошло не так

| Что видно | Что это значит | Что делать |
|---|---|---|
| При переходе по ссылке — ошибка Atlassian про `client_id` | приложение не зарегистрировано или идентификатор не тот | вернуться к шагу 1 |
| Ошибка про `redirect_uri` | адрес возврата у администратора отличается от нашего | сверить посимвольно, шаг 1 |
| «Не удалось подтвердить, чья это учётная запись» | сотрудник вошёл не под своей учёткой, **либо** Atlassian не отдаёт почту | если вошёл верно — вопрос к администратору про видимость почты |
| Ссылка не открывается | одноразовая ссылка уже использована или просрочена | запросить новую у бота |
| Агент пишет, что нет инструментов записи | согласие не дано или отозвано | «статус» у бота |
| Запись прошла, но автор — не человек | **контейнер поднят с учётными данными в окружении** | немедленно остановить, очистить окружение, шаг 4 |

## Чего эта инструкция ещё не проверяла

Написана до живого прогона. По норме **проходить её должен не автор** — и каждое место, где
проходящий споткнулся, считается дефектом текста, а не человека.

Не подтверждено до получения ключей: поддерживает ли сервер заказчика PKCE (если нет — выключается
настройкой, править код не нужно); какой набор прав реально выдаётся; видна ли почта в ответе
Atlassian; заводится ли учётка Confluence сама у того, кто туда ни разу не заходил.
