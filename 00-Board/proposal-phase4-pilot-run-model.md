# Пропозал — как прогнать пилот Фазы 4 при read-only серверах

**От:** lead-ds. **Кому:** президент (через ГД, вместе с Figma-развилкой). **Тип:** чистая аналитика, серверов/кода НЕ трогает.

## Что должен сделать пилот (Фаза 4)
Прогнать capability на **ContactDetailScreen**: (1) прочитать образец iva-one (Angular, adp) READ-ONLY; (2) **написать** целевой экран в su.ivcs.messenger (Compose) из `Iva*` (кейс «починить до паритета»); (3) **собрать и прогнать тесты** — `runComposeUiTest` + Roborazzi (скриншот) + сверка паритета (веб-образец + токены + Compose-скриншот/VLM). Итог — приёмка.

## Жёсткое ограничение (президент)
ВСЕ серверы (adp/teststand/prod) — **только чтение**. Запрещено: запись/установка/рестарт/git fetch/pull/push/checkout, клонирование НА сервер. Чтение (cat/grep/git log/ls, скачивание-вниз) — можно.

## Ядро проблемы
Пилот по сути требует **write-цель + build/test-окружение** (KMP: Gradle/JDK/Android SDK + codex/node/serena). Оба конфликтуют с read-only серверами. Ниже — варианты, где это разместить.

## Варианты

### Вариант A — Локальный прогон (скачать вниз → писать и собирать локально)
Скачать target `su.ivcs.messenger` + source `iva-one` + shared `kmp` ВНИЗ с adp (ssh-чтение = не мутирует сервер) в локальную рабочую копию; агент читает источник, пишет целевой экран локально, локальный Gradle собирает + гоняет тесты.
- **Плюсы:** полностью read-only-чисто (сервер не меняется); реальный write+build+test; изолировано; ничего не пушим.
- **Минусы:** (1) нужен KMP-тулчейн локально (JDK/Android SDK/Gradle + codex/node/serena) — на этой машине может не быть, поднять нетривиально; (2) Gradle тянет внутренние зависимости с `git.hi-tech.org` — **у нас нет GitLab-учёток** → сборка может не резолвить деписы; (3) большой перенос дерева вниз; (4) расхождение с эталонным окружением teststand (уровень-3 гайда Глеба).
- **Вывод:** чисто по read-only, но **риск нерабочей сборки** из-за внутренних деп и отсутствия тулчейна/учёток.

### Вариант B — Teststand scratch-копия (там тулчейн уровня-3)
teststand уже несёт тулчейн (codex/node/serena, уровень-3) + kmp-full/kmp-pilot. Сделать ОТДЕЛЬНУЮ scratch-копию на teststand, агент пишет/собирает/тестит там.
- **Плюсы:** тулчейн и внутренние деп уже настроены (уровень-3 — штатное место пилота по исходному сигналу); реалистичное окружение; сборка резолвит деписы.
- **Минусы:** создание scratch-копии + запись = **смена состояния сервера → гейт президента** (нарушает «read-only» без явного исключения); нужно оговорить границы (отдельный путь, не трогать kmp-full/kmp-pilot, снести после).
- **Вывод:** технически лучший прогон, но **требует явного точечного исключения президента** на write в scratch-песочницу teststand.

### Вариант C — «Сухой» пилот: локально ПРОИЗВЕСТИ + статически проверить (без live-сборки)
Агент читает источник (adp read-only), **пишет** ported-экран в ЛОКАЛЬНУЮ рабочую копию (не на сервер), проверка — **статическая**: экран собран из `Iva*` (ноль сырых Color/dp), состояние поднято, списки keyed, паритет с образцом по составу/состоянию/действиям, незамапленный компонент → стоп. Live-компиляция/`runComposeUiTest`/Roborazzi/VLM — **отложены** до появления write+build-окружения.
- **Плюсы:** полностью read-only-чисто, БЕЗ разблокировок; выдаёт реальный ported-код + прогоняемую статическую приёмку; можно закрыть бOльшУю часть Сц.4-приёмки сразу; гейтится controller'ом.
- **Минусы:** не покрывает рантайм-критерии приёмки (компиляция, скриншот-тесты, VLM-паритет) — они честно помечаются «отложено до окружения».
- **Вывод:** максимум пользы без единой разблокировки; неполная приёмка (рантайм — потом).

### Вариант D (гибрид, рекомендуемый) — C сейчас → (A или B) на рантайм-шаг
1. **Сейчас, без разблокировок:** Вариант C — произвести ported-экран локально + статическая приёмка + controller-гейт. Двигает пилот максимально.
2. **Рантайм-верификация** (компиляция + runComposeUiTest + Roborazzi + VLM) — отдельным шагом, выбрать окружение:
   - **B** (рекомендую для рантайма): президент даёт **точечное исключение** — write в изолированную scratch-песочницу на teststand (там тулчейн+деписы), с границами (свой путь, не трогать kmp-full/kmp-pilot, снести после, отчёт). Это единственный способ реально СОБРАТЬ (внутренние деп + KMP-тулчейн уже там).
   - **A** — только если удастся поднять локальный KMP-тулчейн И решить доступ к внутренним деп (GitLab-учётки) — иначе сборка не пройдёт.

## Рекомендация
**Вариант D:** C немедленно (read-only-чисто, без разблокировок — двигаем пилот и статическую приёмку сейчас), а рантайм-верификацию — через **B с точечным исключением президента на teststand-scratch** (тулчейн/деписы уже там; A локально рискует нерабочей сборкой из-за внутренних деп и отсутствия учёток).

## Решение президенту (одной строкой)
Рантайм-сборка пилота: (B) дать точечный write-scratch на teststand ПОД гейтом (бэкап/границы/снос), ИЛИ (A) подтвердить, что локальный KMP-тулчейн + доступ к внутренним деп реалистичны? Статическую часть (C) начинаю по «go», разблокировок она не требует.
