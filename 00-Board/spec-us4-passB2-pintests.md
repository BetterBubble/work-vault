## Вход (из аналитика, v2 FR)
Проектные серии: `CT-n` (§1.6 контракты), `DM-n` (§1.7 модель данных/состояния), `EV-n` (§1.8 события). brd их регистрирует и наследует вниз (Проход A/B1 — уже в main).

## К-2 — pin-authoring реализует серии (v2 only)
На v2-FR PIN реализует проектные разделы по стабильному ID:
- каждый `CT-n` (контракт §1.6): реализовать контракт ИЛИ зафиксировать расхождение;
- каждый `DM-n` (модель данных §1.7): реализовать модель/состояния ИЛИ расхождение;
- каждый `EV-n` (событие §1.8): реализовать событие/консистентность ИЛИ расхождение.
- **report статус каждого CT/DM/EV**: реализован / расхождение / blocked.
- Ссылка по стабильному ID (трассировка), не переномеровывать, не выдумывать.
- v1-FR — серий нет → шаг пропускается.
- **К-3 уважать:** проектный раздел реализуется только если утверждён D-n (гейт на входе start-task, Проход C-канон); pin честно репортит pending/blocked, не имитирует.

## К-4 — pin-authoring таблица расхождений FR↔KB на проектные разделы (v2)
Расширить существующую таблицу расхождений FR↔код на проектные разделы: проект контракта/модели данных сверяется с кодом (`kb_verify_api_exists` и аналоги стека); конфликт проекта с реальностью = **критичное расхождение** в выводе pin. Per-stack (у каждого профиля свои kb-инструменты/проверки).

## К-2 — tests-authoring (v2 only)
TESTS порождает контрактные тесты с `Covers: CT-n`; статус каждого CT/DM/EV в отчёте тестов. v1 — без серий, как раньше.
