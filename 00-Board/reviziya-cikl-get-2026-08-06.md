# ВЕРДИКТ

**Дефект. Чинить — правка минимальная (3 строки в одном файле), риск низкий.**
Версия лида верна по механике и подтверждена кодом клиента; версия ГД верна по
симптому («200 вместо честного отказа»), но неверна по причине — резолв у этих
людей успешен, а `401` был бы худшим из двух правильных ответов. Правильный ответ —
**405**.

---

## 1. Дефект ли это (нет, не штатное поведение)

Дефект. Механика доказана построчно по исходнику клиента, а не выведена по догадке.

Клиент MCP на streamable-HTTP открывает поток «сервер→клиент» запросом `GET` c
`Accept: text/event-stream`. Референсный клиент —
`@modelcontextprotocol/sdk` (локальная копия v1.29.0,
`/Users/bubblemac/.npm/_npx/eea2bd7412d4593b/node_modules/@modelcontextprotocol/sdk/dist/esm/client/streamableHttp.js`):

- строка 78 `_startOrAuthSse` — `GET`, **content-type ответа не проверяется**;
  `response.ok` (наш 200) → `_handleSseStream(response.body, options, true)`,
  третий аргумент `isReconnectable = true`;
- строка 102 — **`if (response.status === 405) return;`** «сервер не предлагает
  SSE на GET» — штатный исход, ошибки нет, реконнекта нет;
- строка 158 `_handleSseStream` — наше тело (`{"jsonrpc":"2.0","id":null,"result":{…}}`,
  `content-length` выставлен) прогоняется через `EventSourceParserStream`: ни одной
  строки `data:` → цикл чтения сразу `done`, `receivedResponse` остаётся `false`;
- строки 218–226 — `canResume = isReconnectable(true) || …` → `needsReconnect = true`
  → **`this._scheduleReconnection({…}, 0)`** — счётчик попыток **захардкожен нулём**
  на ветке штатного закрытия потока;
- строка 138 `_scheduleReconnection` — `attemptCount(0) >= maxRetries(2)` никогда не
  истинно; задержка = `_getNextReconnectionDelay(0)` = `initialReconnectionDelay`
  = **1000 мс** (строка 7), экспоненциального роста нет, потому что attempt всегда 0.

Итого цикл замкнут: GET → наш 200 с конечным телом → «поток закрылся штатно» →
ровно 1000 мс → GET. Бесконечно, счётчик обнуляется каждый круг.

**Арифметическая проверка на живых данных.** У `y.belcheva@iva.ru` (единственный
клиент, см. §2) минимальный интервал между запросами за час = **1,150 с**, средний
2,547 с. Пол ровно на 1000 мс + наша задержка ответа (~150 мс). Ни один backoff
такой формы не даёт: у backoff интервалы растут, здесь — плоские с полом 1 с.

Наш код в этом месте: `/Users/bubblemac/tacticum-worktrees/helm-integration/src/helm/interface/mcp/iva_write_surface.py:1013`
— `handshake = call is None or …`. `call is None` — это результат `_jsonrpc(b"")`
(строка 339) на пустом теле, то есть **любой GET**. Дальше строка 1027
`await _handshake_reply(send, call)` (тело функции — строка 840) отдаёт JSON-RPC
результат `initialize` с `content-type: application/json` и `content-length`.
Метод запроса в этой ветке не смотрят вообще.

Тестов на GET у поверхности нет ни одного: в
`tests/interface/test_iva_write_surface.py` все обращения — POST телом
(единственное упоминание метода — `assert upstream.last.method == "POST"`,
строка 297). Дыра структурная, не случайная.

**Много процессов, не один.** Частоты за час (`credential_use_log`, `system='jira'`,

Поминутные частоты — 250 : 105 : 47 : 25 ≈ 10 : 4 : 2 : 1, чистые кратные ~25/мин.
`min gap = 0` у первых трёх — признак нескольких независимых клиентов, чьи циклы
накладываются; у Бельчевой пол 1,150 с не пробивается ни разу — один клиент.
Вывод: у Беспалова ~10 одновременно открытых клиентских сессий (окон редактора),
у Савицкого ~4, у Фадина ~2, у Бельчевой 1. Это вывод из кратности, не замер.

**Человека за клавиатурой нет.** У Беспалова поток идёт с 2026-08-05 22:29 UTC
(01:29 МСК) непрерывно, максимальная пауза за 14 часов — **257 секунд**, 151 557
запросов. Машина оставлена включённой с открытыми окнами.

**Связь с отсутствием согласия — доказана естественным экспериментом, не
рассуждением.** `a.itskovich@iva.ru` пересёк границу на глазах журнала:

```
a.itskovich@iva.ru|missing|missing|850|10:12:27 → 10:17:52   (5,5 мин, ~155 зап/мин)
a.itskovich@iva.ru|ok|      |120|10:17:44 → 11:00:42         (43 мин, 60 запросов)
```

В 10:17:44 появилось согласие — поток оборвался в ту же секунду и упал в ~110 раз.
То же у `d.lavrov@iva.ru`: `missing` 09:35:53–09:36:13, дальше `ok` и тишина.
**При согласии цикл не воспроизводится**, потому что GET уходит в `_proxy`
(строка 892) наверх в `mcp-atlassian`, а тот держит настоящий SSE-поток открытым.
Среди четверых из наблюдения людей с согласием нет — все четверо `missing`.

Замер прежнего разведчика проверен и подтверждён независимо: за 20 минут
8303 `GET`, 0 `POST`, 2 `DELETE`, все `GET` — 200. За всё время жизни контейнера

## 4. Права ли версия ГД про 401

**Симптом назван верно, причина — нет, лекарство — не лучшее.**

- «Неудачный резолв» — в логе действительно `POST …/api/internal/resolve → 401` на
  каждом запросе, и это, видимо, и породило версию. Но это **штатный** путь:
  `require_write_identity` (`routers/iva_write.py:134`) ловит `ResolveError` и
  добирает личность через dev-MCP (`phk_`-токен), после чего 200 — законный ответ.
  Личность у всех четверых установлена успешно; отсутствует согласие, а не резолв.
- «Ответь сервер 401 — клиент бы остановился» — **остановился бы**: строка 96
  `if (!response.ok)` → 401 без `authProvider` → `throw` → путь ошибки в
  `_scheduleReconnection(options, attemptCount + 1)` (строка 154), счётчик растёт,
  после 2 попыток стоп. Но 401 плох по трём причинам: (а) это ложь — человек
  аутентифицирован, у него действующий ключ Tacticum, нет только согласия;
  (б) строка 98: `if (response.status === 401 && this._authProvider) return await
  this._authThenStart();` — у клиента с настроенным OAuth-провайдером 401 запустит
  повторную авторизацию, то есть другой цикл вместо этого; (в) клиент покажет
  человеку ошибку `Failed to open SSE stream`.

**История, которую надо учесть, проверена.** Убирали не наш 401, а хождение
хендшейка наверх:

- до `c6c5b8c` (04.08, «по двум ревизиям: хендшейк, строгий replace…») исключения
  для хендшейка не было вовсе — всё без согласия получало **403 `no_credentials`**;
- `c6c5b8c` ввёл `handshake = call is None or …` и на этой ветке **проксировал**
  наверх;
- `f74889f` (04.08, «хендшейк без согласия: отвечаем сами, а не проксируем наверх»)
  заменил проксирование на `_handshake_reply`, потому что контейнер Atlassian
  отвечал `401 no Atlassian credentials were provided`, клиент не поднимал сессию и
  не видел `iva_write_connect`.

Чинили **POST `initialize`**. GET-поток — отдельный необязательный канал протокола,
он к подъёму сессии отношения не имеет. Поэтому **правка, трогающая только GET,
прежний тупик не возвращает** — это проверяемо, а не на веру: ветка `initialize`
(строка 1013, `call` не `None`, метод `initialize`) остаётся нетронутой.

## 5. Минимальная правка

**Отвечать на `GET` кодом 405, когда мы отвечаем сами** (то есть в ветке
«согласия нет»). Спека streamable HTTP и референсный клиент трактуют 405 как
«сервер не предлагает SSE-поток на GET»: строка 102 — молчаливый `return`, без
ошибки, без реконнекта, без сообщения человеку.

Место одно: `src/helm/interface/mcp/iva_write_surface.py:1016` (`if handshake and
not credentials:`) — перед `await _handshake_reply(send, call)` (строка 1027) добавить ветку по
`scope.get("method")`: не `POST` → отдать 405 с пустым телом. Три строки, один
файл, обратимо. Вес — лёгкая задача.

Что правка НЕ ломает:

- POST `initialize` без согласия — путь прежний, `_handshake_reply` остаётся;
- GET при наличии согласия — как был, `_proxy` наверх (строка 892), не задет;
- появление согласия позже: GET-поток необязателен, инструменты работают по POST;
  на следующем старте клиента поток поднимется настоящий.

Что правка НЕ чинит и о чём стоит знать: две строки в `credential_use_log` пишутся
в `_issue` (строка 261) **до** любого разбора запроса, то есть и на GET тоже. После
405 объём упадёт примерно в 800 раз сам собой, поэтому отдельная правка не нужна —
но если захочется чистоты, «журнал подстановки доступа» на запросе, который ничего
не подставляет, писать не обязан. Это второй, необязательный шаг.

Ретеншен/чистка накопленных 350 тыс. строк — отдельное решение, к правке не
относится.
