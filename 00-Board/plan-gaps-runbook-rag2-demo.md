# Пробелы плана + ранбук демо-дня — RAG#2 /analyst (Роскосмос 16:00)

_Роль: планёр. Составлено 2026-07-22 (день, МСК). Только анализ, ничего не менял._
_Источники: [[План-оф-рекорд- RAG-2 -analyst «мозг-план» — демо Роскосмос 16-00]] · [[Техплан RAG-2 -analyst — синтез triva на -api-rag2-answer]] · [[recon-demo-roskosmos-rag2]] · [[impl-rag2-analyst-ui]] · [[verifier-brief-rag2-analyst-demo]] · [[demo-hero-features-iva]]_

## TL;DR
UI-ветка готова и типизируется, но **бэкенд-синтез (A, `/api/rag2/answer`) в памяти не подтверждён**, **ветки фрагментированы** (UI на `-ui`, план ждёт `feat/rag2-analyst-sintez`), **vite build не гонялся**, **прогон верификатора ещё не сделан**. Три вещи реально ломают показ: живой бэкенд `/answer`, SSH-туннель к triva (истинный SPOF), рабочий вход tenant=iva. Ранбук ниже завязан на «деплой+прогон закончить к T-60, не позже».

---

## A. ПРОБЕЛЫ ПЛАНА

1. **Бэкенд-статус — главный слепой пятно.** Есть impl-заметка по UI, но **нет impl-заметки по A (синтез triva на `/api/rag2/answer`)**. UI уже зовёт `POST /api/rag2/answer`. Если эндпоинта нет — фронт получит 404/500, а `rag2Answer` бросит исключение (это НЕ тот путь, где UI мягко падает на `context` — мягкий фолбэк срабатывает только при `synthesis=null/failed` в **успешном 200**, не при отсутствии роутера). **Проверить, что бэкенд-ветка вообще существует и отдаёт 200.**

2. **Фрагментация веток / кто собирает.** План: `feat/rag2-analyst-sintez`. UI лёг в `feat/rag2-analyst-sintez-ui` (отдельная, от main 9571b1f). Бэкенд — ещё где-то. В плане НЕТ шага «собрать A+UI(+B) в одну ветку и кто это делает». autonomy off → PR+деплой делает пользователь, но **сборка веток — это dev-шаг до PR**, и он бесхозный. Верификатор-бриф прямо пишет «гонять ПОСЛЕ мержа UI в sintez» — этот мерж не назначен.

3. **vite build не проверен.** UI прошёл только `tsc --noEmit`; `vite build` НЕ гонялся (в worktree нет node_modules). Прод-деплой собирает бандл — если build упадёт (напр. неиспользуемый импорт при strict, CSS), это всплывёт **в момент деплоя = в последнюю минуту**. В критериях приёмки build отсутствует.

4. **Нет плана отката (rollback).** Деплой в прод `/opt/helm` (159.194.233.33, helm-helm-1 Up 15h) в день демо, без зафиксированного «как быстро вернуть предыдущий образ, если после деплоя `/analyst` не поднялся». Деплой пересобирает контейнер → короткий даунтайм. В плане нет ни отката, ни «дедлайна деплоя» (после которого не трогаем прод).

5. **Контракт-дрейф A↔UI.** UI писался «под зафиксированный контракт», но два независимых worktree. Расхождение имён (`synthesis_failed` vs camelCase, `topology`/`tests` строка vs объект — координатор уже ловил объектную версию) тихо убьёт панель. **Нет шага «сверить JSON-контракт двух веток на реальном ответе».**

6. **B (топология) зависит от прод-конфига.** Требует `assistant_enabled` (session_factory+retriever). Если на проде не сконфигурено — `topology=None` (fail-soft ок), но тогда акт «как технически сделать» теряет глубину. **Не проверено, что B живёт на прод-конфиге.**

7. **D (docs-корпус) — регрессионный риск для ВСЕХ ответов.** D трогает `federate`/RRF/`SOURCE_LABELS` — общий путь ретрива каждого вопроса. Поспешный мерж D может ухудшить выдачу везде (дубли docs↔confluence, вес в RRF). **Рекомендация: D в демо-ветку НЕ мержить без отдельной верификации** — риск>выгода, это stretch.

8. **Свежесть данных как нарратив.** as_of Jira/Confluence 2026-07-10 (~12 дней), дисклеймер показывается. В плане это «ок», но **презентующий должен проговорить это первым**, иначе заказчик поймает.

9. **Не указан презентующий, его машина, сеть и доступ.** Демо 16:00–18:00. Кто показывает, с какой машины, есть ли VPN/сетевой доступ до `helm.tacticum.ru` из места показа, рабочий ли логин tenant=iva. Ни в плане, ни в критериях этого нет, кроме строчки «вход проверить».

10. **triva-нагрузка не откалибрована по числам.** Критерий «стабильна в мини-прогоне под нагрузку» без конкретики: сколько параллельных, какая целевая латентность приемлема для живого показа (25с таймаут-guard = в худшем случае зритель ждёт 25с и видит фолбэк — это долго для сцены). Нужен порог «сколько секунд ждём вживую, прежде чем ведущий переключается».

## B. ДЕМО-РИСКИ (что реально ломает показ 16:00–18:00)

- **SSH-туннель к triva — истинный SPOF** (важнее самой triva). Recon: туннель `127.0.0.1:8790` держится на `ssh pid 75397`. Упадёт ssh — синтез умрёт на весь показ, и каждый вопрос будет 25с ждать→фолбэк. **Проверить туннель прямо перед демо и знать команду перезапуска.**
- **Latency / холодный старт.** Первый вызов triva после простоя может быть медленным (загрузка модели). Без прогрева первый «живой» вопрос рискует уехать в таймаут.
- **Пустые/слабые ответы на «минных» вопросах:** запись/скачивание ВКС (Rejected+403), настройка SIP-trunk, ссылка переводчика Terra (absent), `who_to_involve(system_id)` (пусто). Задавать их вживую нельзя.
- **Auth tenant=iva.** Страница за логином дэша; API 401 без bearer — это норма, но **презентующему нужен реальный рабочий вход**, проверенный не по API, а через саму форму логина.
- **Деплой в последнюю минуту** на прод + отсутствие отката = если `/analyst` не встал в 15:50, спасать нечем.
- **Экспектейшн-мисматч (из recon):** до этой фичи веб `/analyst` отдавал цитируемый поиск, а не прозу-план. Вся ценность демо держится на том, что A+UI реально доехали до прода. Если доехал только retrieval — позиционировать как «цитируемый поиск», не как «бот-план».
- **Регрессия фолбэков:** `/context` и `/iva-docs` (RAG#1) должны остаться живы — это спасательный круг. `/iva-docs` — всегда-живой фолбэк для показа, если `/answer` синтез сломается.
