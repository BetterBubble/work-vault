## Задача 1 — #750, ветка `fix/750-skill-assets-schema`

### Развилка и моё решение

Постановка предлагает выбор: **реализовать доставку** `assets` либо **убрать поле и запретить
валидацией**. Решаю в пользу **убрать**, и вот факты, на которых это стоит:

1. **Поле не используется никем.** `assets` в `templates/*/manifest.yaml` — **0 объявлений** на 64
   манифеста. Два вхождения слова, которые находит grep, это комментарии-сторожа
   (`tacticum-lite-base/manifest.yaml:76-78` — «у скилла НЕТ и быть не должно»;
   `iva-qa-autotest-base/manifest.yaml:364`). Удаление ничего не ломает.
2. **Оба реальных случая уже решены другим механизмом** — `tacticum-lite-base` переносом в тело
   навыка (PR 172), `iva-qa-autotest-base` через ингредиенты `repo_config`. То есть доставка через
   `assets` на практике не понадобилась ни разу.
3. **Реализация доставки была бы крупной работой в `templates/` и голденах** — а там сейчас
   активно работает Глеб. Это прямой риск конфликта, которого постановка не требует.

**Это моё допущение, а не решение владельца.** Если ГД или Президент скажет «реализовать доставку» —
план переписывается, работа другая по размеру. Пока ответа нет, иду по «убрать»: он обратим
(вернуть строку в схему тривиально), а «реализовать» — нет.

### Отдельный вопрос на решение ГД: поле `scripts`

Рядом с `assets` в схеме и модели живёт **`scripts` — ровно тот же дефект**: объявительное поле без
доставки, оба описаны одним абзацем в докстринге `SkillMetadata`. Постановка называет только `assets`.

**Прошу решение:** чистить оба (правка та же по размеру, дефект исчезает целиком) или строго по
букве постановки только `assets` (тогда `scripts` остаётся миной на будущее и нужна отдельная issue).
**Дефолт, если ответа не будет:** чищу **только `assets`**, а на `scripts` завожу отдельную issue —
расширять скоуп молча нельзя.

### Что делаю

1. `templates/_schema/ingredient.v1.schema.json:81` — убрать `assets` из `skill_spec.metadata`,
   добавить `"additionalProperties": false` в этот объект, если его там нет (иначе запрета не выйдет —
   схема продолжит молча принимать поле).
2. `apps/backend/src/backend/catalog/domain/ingredients/skill_spec.py` — убрать
   `assets: list[str]` из `SkillMetadata`; переписать докстринг: он сейчас описывает поле как
   существующее, после правки это станет ложью.
3. Тест-запрет в `apps/backend/tests/catalog/test_manifest_schemas.py` — манифест с
   `metadata.assets` обязан **падать** валидацией (сейчас проходит).
4. Прогнать `pytest tests/catalog` целиком: `extra="forbid"` в модели означает, что снятие поля
   может уронить рендер на любом манифесте, который его объявит.

### Приёмка (моя, в постановке её нет)

- манифест с `metadata.assets` не проходит валидацию — есть падающий тест, который до правки зелёный, после правки красный на старом поведении;
- `pytest tests/catalog` зелёный целиком, число прошедших названо цифрой;
- `git grep assets -- templates/*/manifest.yaml` не даёт ни одного **объявления** (комментарии-сторожа остаются, они теперь верны);
- голдены не перегенерируются — правка не трогает контент профилей.

## Задача 2 — #816, ветка `ci/816-taiga-commit-link`

Постановка предлагает три варианта по возрастанию цены и сама говорит: **«Вариант 2 достаточен»**.
Беру вариант 2 дословно: *«CI-шаг, который на merge в main парсит `#NNN` из сообщений коммитов и
постит в Taiga комментарий со ссылкой на коммит (без автозакрытия — закрытие остаётся решением
человека)»*.

### Главная опасность — парсинг. Голый `#NNN` брать НЕЛЬЗЯ

В этом репозитории `#NNN` в заголовке коммита — это **чаще номер PR на GitHub, а не задача Taiga**:

- `fix(ops): reap catalog-mcp healthcheck zombies — init:true + urlopen timeout (Taiga #442) (#235)`
  → `#442` это Taiga, `#235` это PR;
- `fix(dev-base): гейт готовности среды … (Taiga US #774) (#243)` → `#774` Taiga, `#243` PR;
- `fix(go-role): гардрейлы по dogfood-серии iva-role-go (US #810, #811, #770, #769)` → список.

Наивный `#\d+` начнёт постить комментарии в чужие задачи Taiga по номерам PR — то есть **мусорить
в трекере ровно той задачей, которая заведена против мусора в трекере**. Поэтому распознаю только
явные формы после префикса `Taiga`/`US`. Голый `#N` игнорирую всегда.

**Живые формы, вычитанные из 600 коммитов `main`** (тест-корпус берётся отсюда, не выдумывается):

| Форма | Пример из истории |
|---|---|
| `Taiga #N` | `fix(docker): … (Taiga #632) (#241)` |
| `Taiga US #N` | `fix(dev-base): … (Taiga US #774) (#243)` |
| `US #N` | `chore(profiles): … (US #775)` |
| `US #N, #N, #N` — перечисление | `fix(go-role): … (US #810, #811, #770, #769)` |
| `Taiga #N/#N/#N` — **через слэш** | `fix(tests+templates): Taiga #735/#736/#737 — CI-гейт …` |

Пятую форму (слэш) я при написании плана не предусмотрел — нашёл при сборе корпуса. Отмечаю
честно: это ровно тот случай, когда «очевидный» регексп пропустил бы треть ссылок.
Плюс `US #N` встречается внутри прозы (`version collision with US #756 relink`) — тоже валидная
ссылка, отбрасывать по позиции в строке нельзя.

### Что делаю

1. **`scripts/taiga_commit_link.py`** — чистая функция разбора (`extract_refs(message) -> set[int]`)
   плюс отправка комментария. Разбор без сети, чтобы тестировался офлайн.
2. **`.github/workflows/taiga-commit-link.yml`** — на `push` в `main`: берёт диапазон
   `${{ github.event.before }}..${{ github.sha }}`, гоняет скрипт.
3. **Секрет `TAIGA_TOKEN`.** Скрипт **обязан мягко пропускать работу, если секрета нет**: печатает
   предупреждение и выходит с кодом 0. Иначе первый же мерж после вливания даст красный main.
4. **Идемпотентность.** Перед постингом читаю историю задачи и не дублирую комментарий с тем же
   sha — перезапуск workflow не должен плодить копии.
5. **Комментарий** — короткий: sha, заголовок коммита, ссылка на GitHub. Статус **не меняю**,
   `assigned_to` **не трогаю**.
6. **Тесты** `apps/backend/tests/` или `tests/` (место выберу по факту, где лежат тесты скриптов):
   разбор всех живых форм из истории репозитория + негативные (`(#235)` не даёт ref, `#123`
   отдельно не даёт ref), идемпотентность на моке.

### Приёмка — процитирована из постановки

> - Задача, закрытая коммитом, не может остаться в `New` незамеченной дольше одного релизного цикла.
> - Решение принято до запуска US #789, иначе триаж-петля будет писать в замусоренный бэклог.

Плюс моё, проверяемое:
- на **реальных** коммитах из истории `main` (не на выдуманных строках) разбор даёт ровно ожидаемые номера, цифра названа;
- ни один номер PR не распознан как задача Taiga — отдельный тест;
- без секрета скрипт завершается кодом 0 и ничего не отправляет;
- **сухой прогон против живой Taiga** (`--dry-run`) на диапазоне последних коммитов: печатает, куда бы написал, ничего не пишет.

### Что здесь НЕ моё решение

- **Секрет `TAIGA_TOKEN` в настройках репозитория ставит Президент** — у меня нет и не должно быть
  доступа к настройкам GitHub-репозитория. До этого шага фича лежит выключенной и безвредной.
- **Какой именно ключ класть.** Рабочий на проект 12 сейчас один — `phk_535c…b093`, и это личный
  admin-ключ `mr.diaret@ya.ru` (Дмитрий Лебедев). Класть личный ключ руководителя в CI — решение
  не моё; возможно, нужен отдельный сервисный ключ. **Вопрос Президенту.**

## Порядок и доставка

Ветки независимы, общих файлов нет — делаю параллельно, мержить можно в любом порядке.

1. `fix/750-skill-assets-schema` — от `origin/main`, в отдельном worktree.
2. `ci/816-taiga-commit-link` — от `origin/main`, в отдельном worktree.
3. По каждой: тесты на реальных данных → `controller` (гейт) → **два `critic` с оппонированием**
   (вес крупный).
4. Пуш обеих веток явным refspec, текст PR — **в чат Президенту текстом**, не файлом.
5. PR создаёт и мержит человек. Секрет `TAIGA_TOKEN` ставит человек — до этого #816 выключен.
