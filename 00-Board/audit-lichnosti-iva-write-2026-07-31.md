## 2. Инвариант «строка, названная в чате, не становится подтверждённой личностью»

**Держится везде. Но держится по-разному, и в двух местах — не тестом.**

| Место | Чем держится | Тест |
|---|---|---|
| `/api/iva/oauth/start` | у `StartIn` **нет поля почты** (`routers/iva_write.py:182`), subject берётся из принципала | ⚠️ **теста нет.** Лишнее поле в теле сегодня молча игнорируется дефолтом pydantic (`extra=ignore`) — то есть безопасно, но по умолчанию библиотеки, а не по нашему решению |
| Канал записи | почта только из принципала, `X-Atlassian-*` вырезаются | есть (`test_client_atlassian_headers_are_dropped`, `test_unauthenticated_is_refused_regardless_of_auth_required`) |
| Колбэк | `subject` из одноразового состояния, сверка `whoami` | есть (`test_callback_email_mismatch_saves_nothing`, `test_login_mismatch_saves_nothing`) |
| Бот, доступ | источник считается по происхождению строки; в ветке ответа из переписки `platform_email` пуст по построению | есть, моя ветка: `test_declared_email_never_becomes_platform_identity` |
| Бот, статус | адрес только из `login` | есть (`test_status_of_foreign_email_is_not_shown`) |
| Бот, отзыв | адрес только из `login`; чужой названный адрес прерывает отзыв | есть в ветке revoke («чужой и вслепую — не гасит») |
| Бот, ключ | адрес только из `login` | тесты в незакоммиченной ветке — не смотрел прогон |
| Внутренняя ручка A8 | `subject` из тела — **инвариант тут сознательно не действует** | по проекту: доверие делегировано шлюзу и держится служебным ключом |

**Находка 1 (низкая, дешёвая).** Инвариант на `/api/iva/oauth/start` держится формой модели и
дефолтом pydantic, а не тестом. Пять строк теста («POST с `subject: victim@iva.ru` в теле →
ссылка выдана на почту токена») закрывают класс регрессий: достаточно однажды добавить в `StartIn`
поле с таким именем.

## 3. Обратное: где подтверждённая личность теряется

**Находка 2 (трение, не дыра).** `complete_consent` считает `key_status` по
`tacticum_key_status(identity_source)` (`application/iva_write.py:355`), то есть по источнику
subject, а НЕ по каталогу. В ветке key-lookup появился реальный ответ «ключ есть/нет», но он
доступен только боту в ответе на вопрос про ключ; страница колбэка и «готово» после согласия
по-прежнему говорят осторожное «если ключа ещё нет» даже там, где мы можем знать точно. После мержа
обеих веток это стоит свести — иначе два ответа про один ключ будут разной точности.

**Находка 3 (трение).** `phk_*`-ветка `require_write_identity` не кэширует отказ, но кэширует
успех на 5 минут (`dev_token.py:29-31`) — отзыв ключа вступает в силу с задержкой. Задокументировано,
осознанно; называю ради полноты карты.

## 4. Стыки трёх веток — ГЛАВНОЕ

Все три правят один и тот же участок `_reply_for`/`_aside_reply` и **конфликтуют по смыслу, а не
только по тексту**.

### С1. Порядок вставки решает, работают ли отзыв и ответ про ключ у половины людей — ⚠️ ГЛАВНОЕ

- `revoke` меняет сигнатуру на `_aside_reply(intent, *, login_email)` и по `login_email` решает,
  делать отзыв или отказать (`:299,392`);
- `key-lookup` меняет её же на `async _aside_reply(settings, intent, *, login_email)` и по
  `login_email` решает, отвечать ли про ключ по существу (`:330`);
- **моя ветка обогащает `login_email` ПОСЛЕ вызова `_aside_reply`** (`:400-410`) — намеренно, чтобы
  «привет» и «потерял ключ» не стоили запроса в Jira.

Сведённые «как есть», три ветки дадут молчаливую потерю: человек с логином `n.breykin` (без почты
в `login`) — тот самый, ради которого делалась моя ветка, — на «отзови доступ» получит
«личность неизвестна», а на вопрос про ключ — общую фразу. Тесты каждой ветки при этом
зелёные: в тестах revoke и key-lookup `login` всегда почта.

**Как мержить правильно** (это правка на 3 строки, но её надо сделать осознанно): в объединённом
`_reply_for` вызвать `_identity_from_platform` СРАЗУ после `parse_intent` и ДО `_aside_reply`,
пропуская только `INTENT_HELP`:

```python
intent = texts.parse_intent(text)
if intent != texts.INTENT_HELP:                     # справке личность не нужна
    platform_email = await _identity_from_platform(settings, login=login)
    if platform_email:
        login_email = platform_email
aside = await _aside_reply(settings, intent, login_email=login_email)
```

Цена — один запрос в Jira на сообщение «потерял ключ». Выигрыш — отзыв и ответ про ключ работают
по подтверждённой личности, а не по тому, повезло ли платформе прислать почту.

### С2. Проверок источника по СПИСКУ нигде нет — новый `platform` безопасен

Искал специально: и `_verify_identity:266`, и `tacticum_key_status:77` сравнивают с `SOURCE_AUTH`
через `==`, а не «входит ли в набор доверенных». Значит новый источник по умолчанию попадает в
строгую сторону (fail-closed), а не расширяет права молча. Ветка key-lookup `tacticum_key_status`
не трогает — после мержа `platform` → `unknown`, то есть верно. **Конфликта тут нет.**

### С3. `KEY_ABSENT` и `key_note` — текстовый конфликт, смысл сходится

Обе ветки (моя и key-lookup) правят `tacticum_key.py`: я добавляю источник, key-lookup — третий код
состояния и третью ветку в `key_note`. Пересечение только в докстрингах. При разрешении важно
сохранить обе правки абзаца «Мешает не код, а подтверждённость личности»: я снизил стену
(`platform`), key-lookup опроверг утверждение «обратного индекса нам никто не отдаёт».

### С4. Отзыв через бота стал сильнее ровно настолько, насколько верен `login`

`revoke` гасит доступ по `login_email` без второго шага (обосновано: обратимо, ручка API тоже
одношаговая). Это верно ровно до тех пор, пока `author.login` не может назначить себе сам человек —
см. сценарий Z2.

## 5. Что бы сломал злоумышленник

**Z1. Ссылка-согласие на чужой адрес (классика).** Пишет боту «дай доступ», называет
`victim@iva.ru`, получает ссылку, пересылает жертве. Жертва соглашается в своей Jira.
*Останавливает:* сверка `whoami` — доступ сохранится под адресом жертвы, а ключ Tacticum на этот
адрес у атакующего отсутствует; писать он не сможет (`_verify_identity`, `issue_credentials`).
*Но остаётся хвост,* см. Z3.

**Z2. Подделка `author.login` — единственный настоящий корень доверия платформенного пути.**
Мы верим полю `login` входящего события. **Справочник Jira эту веру НЕ проверяет:** он отвечает на
вопрос «существует ли учётка с такой почтой», а не «принадлежит ли она автору сообщения». Значит
если в платформе ИВА человек может задать/сменить свой `login` сам, он получает: чужой **статус**
(A11), чужой **отзыв доступа** (A12, ветка revoke — необратимое на вид действие) и чужой ответ
**про ключ** (A13). Записи в Jira он не получит — там сверка на колбэке.
*Проверить изнутри невозможно.* Вопрос команде платформы, дословно: «редактируется ли `author.login`
самим пользователем и совпадает ли он с корпоративным SSO-логином?». **До ответа не стоит
расширять список действий, которые делаются по одному `login`,** а отзыв — самое опасное из уже
сделанного.

**Z3. Утечка факта «человек дал согласие» через уведомление «готово».** `chat_room_id` берётся из
состояния, а состояние заводит тот, кто попросил ссылку (`bot_iva_write.py:213-226` main). В
сценарии Z1 «готово» приходит **атакующему** — то есть он узнаёт, что жертва прошла согласие. Ровно
эти сведения бот принципиально отказывается отдавать в «статусе» («у кого есть доступ» — сведения о
человеке). Это несогласованность нормы с реализацией, а не только теория.
*Стоимость:* низкая (факт, не доступ), но чинится дёшево: слать «готово» только когда
`subject_source != declared`, либо когда адрес состояния совпадает с подтверждённой личностью чата.
Первое станет почти бесплатным после мержа моей ветки — большинство ссылок будут `platform`.

**Z4. Служебный ключ шлюза = чужой токен Jira по одному имени.** A8 отдаёт расшифрованный секрет
любому, кто предъявил `HELM_IVA_WRITE_SERVICE_KEY` и назвал `subject`. Это спроектированная
делегация, и защищена она двумя вещами: ручка не смонтирована по умолчанию и ключ отдельный от
всего остального. *Замечание:* ротации/срока у этого ключа нет, а компрометация даёт доступ ко
ВСЕМ сохранённым доступам сразу. При включении шлюза стоит завести ротацию.

**Z5. Разговор с ботом из чужого чата.** Личный чат, `isGroupChat` отсекается, ответ уходит в тот
же `chatRoomId`, откуда пришёл. Отдельной дыры не нашёл.

1. **С1 — порядок вызова при сведении веток.** Не находка о дефекте, а находка о МЕРЖЕ: пройдёт
   молча, сломается у живых людей. Три строки, но их надо написать руками.
2. **Z2 — задать вопрос платформе про `author.login`.** Ответ определяет, можно ли оставлять отзыв
   одношаговым. Стоит письма, не кода.
3. **Z3 — «готово» не должно уходить тому, кто не подтверждён.** Дешевле всего после мержа моей
   ветки.
4. **Находка 1 — тест на то, что `/start` не принимает почту из тела.** Пять строк.
5. **Находка 2 — свести два ответа про ключ** (страница колбэка/«готово» vs ответ бота) после мержа
   key-lookup.

## 7. Как сводить ветки — готовый фрагмент, а не описание

Раздел для того, кто будет мержить: логику ниже не надо восстанавливать заново, её надо перенести.
Сводить можно после того, как `feat/iva-write-key-lookup` закоммичена (на 31.07 работа лежит
незакоммиченной, поэтому само сведение преждевременно).

### 7.1. Что с чем спорит в одном участке

| Ветка | Что делает с `_aside_reply` | Чем решает |
|---|---|---|
| `bot-revoke` | `_aside_reply(intent, *, login_email)` — синхронная | по `login_email`: пусто → «личность неизвестна, отзыва нет»; иначе `_revoke_reply` |
| `key-lookup` | `async _aside_reply(settings, intent, *, login_email)` | по `login_email`: пусто → общая фраза про ключ; иначе поход в каталог |
| `identity-from-platform` | не трогает сигнатуру, **заполняет `login_email` ПОСЛЕ вызова** | вывод из `login` + подтверждение справочником Jira |

Итоговая сигнатура — от `key-lookup` (она шире): `async _aside_reply(settings, intent, *, login_email)`.

### 7.3. Что при этом НЕ должно сломаться (и почему не сломается)

- **`subject_source` считается по-прежнему по происхождению строки.** Условие
  `SOURCE_PLATFORM if platform_email and email == platform_email else SOURCE_DECLARED` не трогать:
  в ветке `pending` `platform_email` остаётся пустым по построению, и адрес из переписки не может
  стать подтверждённым. Тест `test_declared_email_never_becomes_platform_identity` обязан
  оставаться зелёным ДОСЛОВНО — если после сведения он покраснел, сведение неверное.
- **Порядок ссылок (Jira раньше Confluence) сохраняется:** `platform` не снимает сверку на
  колбэке, её снимает только `auth`.
- **Асимметрия остаётся сознательной:** в ветке `pending` личность не выводится. Это не пропуск —
  в состоянии «ждём ответа с почтой» мы оказались именно потому, что вывод для этого `login` уже
  не сработал. Исключение одно: диалог, заведённый до появления справочника или во время сбоя
  Jira; человек в этом случае просто отвечает адресом, как раньше.
- **Цена:** одно обращение в Jira на сообщение с намерением, отличным от справки (было — только на
  доступ/статус). Для единиц пользователей это ничто; при росте — резать здесь же, по намерению.

### 7.4. Ещё два стыка, найденных при написании патча (оба молчаливые)

**С5. `_ASIDE_TEXTS` — таблица, из которой ОБЕ ветки убирают по строке.** `revoke` убирает
`INTENT_REVOKE`, `key-lookup` убирает `INTENT_KEY`; после сведения в таблице обязан остаться ТОЛЬКО
`INTENT_HELP`. Опасен именно наивный исход, где побеждает версия `key-lookup`: в ней
`INTENT_REVOKE: revoke_help_text` ещё на месте, и бот начнёт отвечать «отзывать я не умею» — при
том что код отзыва рядом и работает. Это не деградация, а прямая ложь пользователю, и ни один тест
её не ловит: тесты `revoke` проверяют новый текст, а тесты `key-lookup` про отзыв не знают.
**Проверка при сведении:** в `_ASIDE_TEXTS` ровно одна строка; `revoke_help_text` в коде больше не
вызывается (если функция осталась — удалить, иначе она вернётся при следующей правке).

**С6. «Отозвать ключ» теряет объяснение разницы.** `revoke` специально научил `parse_intent`
уводить «отозвать ключ» в `INTENT_KEY` (иначе просьба погасила бы человеку рабочие доступы) и
дописал в `key_help_text` строку: «Ключ и доступ — разные вещи: доступ я погашу по команде
„отозвать доступ“, а ключ отзывает администратор». В `key-lookup` при включённом каталоге ответ про
ключ идёт другой функцией — `key_status_text`, — и этой строки в ней **нет ни в одной из трёх
веток**. Итог после сведения: человек пишет «отозвать ключ», получает «ключ у вас есть, им
пользовались… » и НЕ узнаёт, как отозвать то, что он хотел отозвать. Обе ветки по отдельности
правы, теряется только их стык.
*Чинится одной строкой:* тот же хвост про разницу ключа и доступа добавить в `key_status_text`
(рядом с `_KEY_TAIL`), а не только в `key_help_text`.
