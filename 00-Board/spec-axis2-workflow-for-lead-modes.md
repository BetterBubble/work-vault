# Спека для lead-modes — ось-2 (мульти-репо) в `brownfield-task-workflow`

**От:** lead-ds (поставщик требований). **Кому:** lead-modes (single-owner пакета `brownfield-task-workflow`). **Через:** ГД (координирует очередь, вклинить после текущего bundle-фикса lead-modes). **Основание:** ТЗ Сц.4 + `figma-ds-multirepo-and-selection.md` §«Ось 2». **Файлового пересечения нет:** мой п.3 (reference-скилл) в `iva-kmp-development-base`; п.1/2/4 — в вашем `brownfield-task-workflow`.

## Зачем (контекст Сц.4)
Перенос экрана iva-one (Angular) → su.ivcs.messenger (KMP Compose) требует ДВУХ деревьев в одной задаче: **исходное** (iva-one, читаем образец READ-ONLY) + **целевое** (su.ivcs.messenger, пишем). Сейчас профиль/workflow работает с ОДНИМ деревом (`start task` принимает задачу + папку доков; второго репо нет). Нужна поддержка source+target. Сервер нейтрален — ему ничего не нужно (правки только клиент/workflow).

## Требования (строго по ТЗ, без сверх-ограничений)

### Требование A (п.1 ТЗ) — `start task`: аргумент source/reference-репо
- Добавить **опциональный** аргумент **исходного/референс-репо** в `start task` (сейчас 2-й аргумент — только папка доков).
- Опциональность обязательна: одно-древесные задачи (обычный brownfield) работают как раньше без регресса.
- **Приёмка:** `start task` принимает source-репо; при его отсутствии поведение не меняется; при наличии — доступен путь/привязка исходного дерева для read-only чтения.

### Требование B (п.2 ТЗ) — workflow: read-only source + write target
- Ослабить модель «рабочая директория — ОДНО дерево» до **read-only исходное дерево + write целевое**.
- Исходное дерево привязано к СВОЕМУ `.tacticum/context.yaml` / installation и (если нужно) своему прогону `kb_discover`.
- **ДС письма определяет ЦЕЛЕВОЙ репозиторий** (не источник).
- **Приёмка:** в задаче с source-репо агент может читать исходное дерево и писать целевое; запись в исходное дерево не предполагается на уровне workflow (жёсткое правило read-only-источника живёт в моём reference-скилле `web-to-kmp-source-reference` — workflow даёт механику доступа, скилл — контракт поведения).

### Требование C (п.4 ТЗ) — гейт готовности Phase 3.0 (два дерева)
- Расширить проверку кросс-репо-готовности: сейчас «клон другого репо доступен (иначе отдельная сессия)» → до **реальной проверки двух деревьев**, когда привязан исходный репозиторий.
- **Приёмка:** при привязанном source-репо гейт проверяет доступность/валидность обоих деревьев (исходного read-only + целевого write) прежде чем пускать задачу в работу.

## Стык с моим п.3 (reference-скилл)
Мой навык `web-to-kmp-source-reference` (в `iva-kmp-development-base`, repo-native) — это **контракт поведения** агента: доступ к источнику через sibling-клон / `kb_discover`, жёсткое «в источник не писать», «ДС письма=целевой репо». Ваши A/B/C — это **механика workflow** под этот контракт (аргумент, послабление дерева, гейт). Они дополняют друг друга, не конфликтуют.

## Не-цели (по ТЗ — не расширять)
- НЕ трогать сервер (N:M ДС, platform/framework_hint, design_system_id — готов).
- НЕ делать ось-1 (несколько ДС: iva-core/VCSWEB) — отдельный заход после iva-one.
- НЕ вводить ограничений/инвариантов сверх перечисленного в ТЗ (принцип президента 17:00).
