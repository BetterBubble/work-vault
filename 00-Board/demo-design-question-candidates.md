# Кандидаты для demo-design-акта RAG#2 /analyst (Роскосмос)

> Дата: 2026-07-22. Автор: design-scout. Источник: ИВА-MCP helm-analyst (tenant=iva), только чтение.
> Задача: новый тип демо-вопроса — «как добавить в фичу X возможность Z» (генеративно-проектный). Ниже 3 реальных кандидата, ранжированы по демо-силе. Все проверены живьём — материал непустой.

- [ ] to:director from:design-scout топ-кандидат №1 — ЕСИА в IVA ID (максимально релевантно Роскосмосу: ЕСИА/SSO/ИБ, partial-покрытие, есть прецедент в ВКС). №2 — DLP-проверка файлов, №3 — SIEM-аудит. Готов собрать акт+эталон по №1.

## №1 (топ) — IVA ID (SSO) + вход через ЕСИА (Госуслуги)

**Фича X:** IVA ID — SSO платформы (форк Keycloak 26.6, OIDC/OAuth2, SAML, LDAP-федерация).
**Возможность Z:** добавить аутентификацию через ЕСИА (Госуслуги) как внешний провайдер входа.
**Почему сильный:** прямое попадание в Роскосмос (ЕСИА/Госуслуги/ИБ/on-prem). Покрытие **partial** — идеальное «добавляемое Z»: клиент знает внешних провайдеров и умеет OAuth2-редирект (RedirectAuthStrategy), но ЕСИА-кнопка **явно исключена**; в «Требования к IVA One 3.0» статус «Не реализовано (Q2 2027)». При этом есть **прецедент**: в ВКС (MCU) ЕСИА уже сделали — можно опереться на факты, а не фантазировать.

**Опорные факты:**
- Топология (контейнер `id` = IVA ID): рёбра `web → id` (Вход OIDC), `apigw → id` (Проверка токенов, OIDC/JWT), `id → nats` (события iva.id.*). Затрагивает клиентов (web/mobile) и API Gateway.
- Требования реестра: `1.0-455` (SSO Kerberos + AD FS + SAML 2.0 + **ЕСИА**, статус candidate/partial), `1.0-497` (интеграция с инфраструктурой заказчика: ADFS/LDAP/OAuth), `1.0-500` (2FA — реализовано полностью). Смежное `1.5-cc71b0f325f` (данные ID для IP-телефонии) — клиенты: Гознак, МВД, Мосбиржа, Транснефть, Еврохим, Мосметро.
- Прецедент-задачи (Jira): `VCSWEB-6884` «Поддержка ЕСИА как стандартного провайдера аутентификации» (Закрыт, Сухов С.), `VCSWEB2-8182` «Вход через Госуслуги при гостевом участии» (Закрыт), `VCSWEB-5500` «Интеграция с IVA ID, 1 этап» (Закрыт), баг `VCSMASH-479` «Ошибка внешней аутентификации через Госуслуги» (Открыт).
- Прецедент-доки: «Вход в мероприятие через ЕСИА» (IVCS), «Вход через OpenID в TatSud» (модель провайдера ЕСИА + Цифровой профиль РТ), «IVA MCU Release Notes» (ЕСИА как стандартный провайдер), «IVA ID Структуры» (payload OAUTH2/SAML).
- Владелец/кто вёл: система IVA ID (владелец платформы Медведев В.И.); недавние контрибьюторы похожего — Родионов Алексей, Сухов Сергей, Андрияшин Анатолий.
- API-реестр: `api_registry_check` → **found=false** (проверены реестры clients 2.30, integration 1.30, bot 1.30). Честный факт: отдельной API-ручки «добавить IdP» нет — это конфигурация провайдера в Keycloak, а не операция клиентского API. Хороший материал для рубрики «что уточнить».

**Paste-ready демо-вопрос:**
> «Как нам добавить в IVA ID вход через ЕСИА (Госуслуги)? Куда встраивать, что затронет и кого подключить?»

**Ожидаемая форма ответа (рубрики):**
- **Куда встроить:** внешний IdP в IVA ID (Keycloak-провайдер, OAuth2/OIDC к Госуслугам) + клиентская RedirectAuthStrategy (снять исключение ЕСИА-кнопки) + отображение провайдера на странице логина/гостевого входа.
- **Что затронет:** контейнер `id` (конфиг провайдера, маппинг атрибутов ЕСИА→профиль), `apigw` (проверка выданных токенов), `web`/`mobile` клиенты (кнопка + редирект), события `iva.id.*` в NATS; смежно — гостевой вход в мероприятия (прецедент ВКС).
- **Кому задача:** владелец IVA ID + Родионов А./Сухов С. (вели ЕСИА в ВКС) как носители прецедента.
- **Что уточнить:** уровень учётной записи ЕСИА (упрощённая/подтверждённая), потребность в СМЭВ, ГОСТ-TLS на канале, on-prem vs SaaS (IVA 360), сопоставление ЕСИА-профиля с корп-учёткой, взаимодействие с 2FA. Ручки в клиентском API нет — конфигурируется на уровне провайдера.

**Проверка живьём:** `analyst_context` по ЕСИА/IVA ID вернул 6 насыщенных фрагментов (requirements + Jira + Confluence), `constraints` — 6 пунктов (реестр требований, TatSud, MCU Release Notes, «Вход через ЕСИА»), `affected_systems` → контейнер `id`, `nearest_spec` → 4 постановки-аналога, `related_tasks` → 5 задач. Материал богатый.

## №2 — Загрузка файлов (Мессенджер/Disk) + DLP-проверка содержимого

**Фича X:** загрузка/хранение файлов (Disk Storage, Java/Quarkus + S3/NFS; пайплайн обработки: превью FFmpeg, конвертация, статус done) + Мессенджер.
**Возможность Z:** добавить DLP-проверку содержимого файлов (антивирус по ICAP уже есть — прецедент; DLP — новое/в REVIEW).
**Почему сильный:** богатая топология одной фичи + чёткая точка интеграции (пайплайн обработки файла, статусы, WS-событие message updated). Релевантно Роскосмосу (ИБ, DLP on-prem: Search Inform, ICAP). Покрытие **partial**: антивирус ICAP — реализован (IVAONE-7081, Закрыт), DLP — в REVIEW/DRAFT.

**Опорные факты:**
- Топология: `apigw → disk` (Файловый прокси, HTTPS+mTLS), владелец Disk — **Сухов Сергей**. Клиентская часть (статус файла, заглушка «Обрабатывается», WS message updated): `chats`, `web`, `mobile-ios/android`, `kmpc`.
- Требования: `1.0-235` (аудит в SIEM + **антивирус ICAP**, candidate/partial), `1.0-234` («Интеграция с DLP-системами и песочницей для файлов»).
- Прецедент-доки: «[REVIEW] DLP: применение политик безопасности для файлов в мессенджере» (двухшаговый пайплайн: антивирус + DLP; sync/async; статус done без ожидания DLP), «[Research] Администрирование DLP/SIEM/антивирус», «[DRAFT] Политики доступа к данным: изменение статуса DLP» (sequence: uploadFile → processing → done; клиент игнорирует политики до DONE), «ТЗ IVA Disk 1.5» и «FR» (заблокированный/недоступный файл, скачивание запрещено).
- Прецедент-задачи: `IVAONE-7081` (антивирус ICAP, Закрыт), `IVAONE-9650` (DLP+Антивирус на MULTISTAGE: Search Inform + ICAP-конфиги), «[ADM] статус FAIL в обработке ответов Антивируса».
- Владельцы/кто вёл: Сухов С. (Disk), Медведев В.И. (chats); контрибьюторы — Фёдоров С., Кильдибеков А., Серов Д.

**Paste-ready демо-вопрос:**
> «Как нам добавить в загрузку файлов мессенджера DLP-проверку содержимого — по аналогии с антивирусом по ICAP?»

**Ожидаемая форма ответа:**
- **Куда встроить:** новый шаг DLP в пайплайн обработки Disk Storage (после превью/конвертации, рядом с антивирусом ICAP); политика запуска — в настройках коннектора у администратора (для всех / для федеративных / список объектов).
- **Что затронет:** `disk` (шаг DLP, статусы, блокировка файла), логика статуса `done` (проставлять без ожидания медленного DLP, чтобы не блокировать UX), `apigw` (файловый прокси/HEAD), клиенты (`chats`/`web`/`mobile`) — заглушка обработки + WS message updated, админ-панель (коннектор DLP, поведение при ошибке DLP).
- **Кому задача:** Сухов С. (Disk) + команда chats/админки.
- **Что уточнить:** синхронный/асинхронный режим, поведение при недоступности DLP (блокировать или пропускать), проверять ли текст сообщений (не только файлы), федеративные объекты, конкретный DLP-вендор (Search Inform), пороги размера.

**Проверка живьём:** `analyst_context` — 6 фрагментов, `constraints` — 5 (REVIEW DLP, ТЗ Disk 1.5, Research, FR, DRAFT статус DLP), `affected_systems` → chats/web/mobile/kmp. Материал богатый.

## №3 — Аудит безопасности + отправка событий в SIEM

**Фича X:** подсистема аудита (события ИБ во всех продуктах: IVA ID, One, MCU, CS, MAIL, SBC).
**Возможность Z:** добавить отправку событий аудита во внешний SIEM заказчика в едином формате (JSON) по syslog TCP/UDP/TLS.
**Почему средний:** сильная релевантность ИБ Роскосмосу, но это скорее сквозная кросс-продуктовая договорённость о формате, чем глубокая топология одной фичи. Покрытие **partial/na** — формат согласован (JSON), но не у всех продуктов реализован единообразно.

**Опорные факты:**
- Требование `1.0-235` (аудит в SIEM UDP/TCP, candidate).
- Прецедент-доки: «Соглашения по аудиту» (IVACORE; таблица «как сейчас vs к чему идём» по продуктам: ID=RFC5424/RFC3164/JSON→json, One=—→json, MCU=JSON→json, CS=CEF→json, MAIL=—→json; транспорт syslog tcp/udp; решение от 06.05.2026 — единый JSON), «Административная панель» (настройки аудита: события ИБ→SIEM vs бизнес; параметры подключения syslog), «Отправка событий аудита в syslog» (SBC).
- Прецедент-задачи: `IVAONE-10009` «[Back] Отправка логов аудита в SIEM (syslog)» (Закрыт; RFC5424, go-syslog, TLS 1.2, конфиг address/network/tls/ca), `IVAONE-10998` «[DevOps] Настроить отправку SIEM событий IVA ID» (Закрыт, syslog TCP).

**Paste-ready демо-вопрос:**
> «Как нам добавить в IVA One отправку событий аудита в SIEM заказчика в едином формате? Что затронет и с кем согласовать формат?»

**Ожидаемая форма ответа:**
- **Куда встроить:** форматтер событий (единый JSON) + syslog-транспорт (tcp/udp/tls) в продуктовых сервисах; настройки серверов SIEM и списков событий — в админ-панели.
- **Что затронет:** каждый продукт-источник событий (ID/One/MCU/CS/MAIL/SBC приводят формат к JSON), EventBus→форматтер→syslog, админ-панель (типы событий ИБ vs бизнес, параметры подключения).
- **Кому задача:** платформенная команда (соглашение по аудиту IVACORE) + владельцы каждого продукта-источника.
- **Что уточнить:** финальная JSON-схема события, набор ИБ-событий, TLS/mTLS к SIEM, поведение при недоступности SIEM, ретеншн/буферизация.

**Проверка живьём:** `analyst_context` — 6 фрагментов (Соглашения по аудиту + Jira + SBC + админка). Материал богатый.

## Отброшено
- **E2EE / сквозное шифрование мессенджера** — `analyst_context` вернул «ничего не найдено». Фактуры нет, для демо-акта не годится.

## Итоговое ранжирование по демо-силе
1. **ЕСИА в IVA ID** — максимальная релевантность Роскосмосу + partial-покрытие + прецедент в ВКС + чистая история «почему нельзя/что уточнить» (нет API-ручки).
2. **DLP-проверка файлов** — богатейшая топология одной фичи + чёткий пайплайн-инжект по аналогии с антивирусом.
3. **SIEM-аудит** — сильная ИБ-тема, но кросс-продуктовая, менее «топологичная».
