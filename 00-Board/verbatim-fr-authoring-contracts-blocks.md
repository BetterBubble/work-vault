### Пункт 1. Правила честности §1–§12 (строки 593–622, дословно)

```markdown
## Правила честности (соблюдать строго)

1. **Не выдумывать.** Каждый факт — с цитатой `[n]`. Чего тулы не дали — пиши
   «[уточнить у …]», не заполняй по догадке.
2. **Не отмывать выдумку через маркировку.** Конкретные имена параметров,
   enum-значения, команды и пути (`recipientIds`, `action: "recall"`,
   `messageRecall`, `POST /messages/{id}/recall`), которых нет в источнике,
   ЗАПРЕЩЕНЫ даже с пометками «выведено из требования» / «предполагаемая
   структура» / «по паттерну» — разработчик скопирует их как спеку. Пиши
   требованиями без wire-имён: «операция должна принимать идентификатор письма
   и признак замены».
3. **Не приписывать источнику** содержимого, которого в нём нет.
4. **Риски/противоречия из тулов** — «кандидат на проверку», не вердикт.
5. **`effort_hint` — справка, не оценка.** Никогда не выдавай за срок.
6. **Gap перед сборкой:** критичные пробелы — аналитику до черновика (шаг 2).
7. **Скилл не пишет финал за аналитика.** Результат — черновик + вопросы;
   решение и утверждение — за аналитиком.
8. **Дисклеймеры тулов не терять** (Confluence/live-деградация/`not_found`,
   недоступная KB) — переноси в FR, не маскируй.
9. **Пороговая гигиена RAG:** хиты со score < ~0.02 — лексический шум, не
   подтверждение.
10. **Код-факты — только из kb_*.** Не «вспоминай» код по памяти модели и не
    проси никого «посмотреть в репозитории» — у профиля нет клона намеренно.
11. **Диаграммы = визуализация текста FR, не новый источник фактов.** Участник
    или сообщение, которого нет в UC/FT/П.H/evidence, на диаграмму не
    попадает; спорное — сначала в Q-реестр, потом (после D-n) на диаграмму.
12. **Часть 1 = выводы, Приложение = факты.** Часть 1 не вводит ни одного
    факта, отсутствующего в Приложении; каждый вывод прослеживается ссылкой
    (→ П.x). Расхождение Части 1 с Приложением — дефект документа: чинить
    Часть 1, не Приложение.
```

```markdown
## Скелет FR — ДВЕ ЧАСТИ (заполняй по шагам)

FR состоит из читаемой «Постановки» и «Приложения» с фактами. **Порядок сборки:

**Правила Части 1 (для человека):**
- пиши простыми словами, пространно, без внутреннего жаргона и wire-имён;
  идентификаторы FT/UC/Q/D в тексте Части 1 не расшифровываются читателю —
  они живут в ссылках вида `(→ П.B UC-1)`;
- **все перекрёстные ссылки — КЛИКАБЕЛЬНЫЕ**: разделы Приложения несут
  anchor-макросы (`p-a` … `p-j`, см. скелет), источники в П.J — якорь `src-n`

  `[x](#имя)` НЕ навигируют: Confluence префиксует id якоря именем страницы):
  `<ac:link ac:anchor="p-b"><ac:plain-text-link-body><![CDATA[П.B]]></ac:plain-text-link-body></ac:link>`
  — тот же шаблон для источников (`ac:anchor="src-2"`, текст `[2]`).
  Элемент переживает markdown-конвертацию — вставляй в текст как есть;
- НЕ приводи полные таблицы, цитаты и реестры — только готовые выводы;
  каждый вывод прослеживается ссылкой на факт в Приложении;
- Часть 1 не вводит НИ ОДНОГО факта, которого нет в Приложении (правило §12);
- объём — 1–2 экрана; если больше, ты пересказываешь Приложение, а не делаешь
  выводы.

Конвейер (`/start-task`, BRD/TESTS) наследует `FT-n`/`UC-n`/`D-n` из
**Приложения** — его форматы и нумерация неизменны.
```

```markdown
4. Probe реально упал (DNS/таймаут/4xx-5xx) → только тогда зафиксируй в FR:

Правила оформления negative evidence:
- **Недоступный источник — тоже строка таблицы** (источник, фактическая ошибка

- **Аналога нет** (соседние команды не покрывают нужный паттерн, напр. async-отчёт
  по массиву получателей) — так и пиши в конвенциях: «паттерн X в реестре
```

```markdown
## Правила честности

1. Эндпоинт без источника в FR не попадает. Реконструкция «как обычно делают» —
   только в блоке «требования к контракту» (что контракт обязан покрывать), не как готовый API.
2. **Не отмывай выдумку через маркировку.** Конкретные имена параметров, enum-значения,
   имена команд и пути (`recipientIds`, `action: "recall"`, `messageRecall`,
   `POST /messages/{id}/recall`), которых нет в источнике, ЗАПРЕЩЕНЫ даже с пометками
   «выведено из требования» / «предполагаемая структура» / «по паттерну» — разработчик
   скопирует их как спеку. Пиши требованиями к контракту без wire-имён: «операция
   должна принимать идентификатор письма, признак замены и признак запроса отчёта».
3. Не приписывай источнику того, чего в нём нет («страница содержит параметры» —
   только если параметры реально на странице).
4. Negative evidence — полноценный результат: перечисли, ЧТО проверено, версии и дату.
5. Смежный аналог всегда с пометкой неполноты (нет флага, нет отчёта и т.п.).
6. Версии реестров меняются — не цитируй по памяти, перекачай спеку. Для wiki/KB
   вместо версии указывай `as_of` индекса.
7. Недоступный источник (после фактически упавшего probe, не по предположению) —
   открытый вопрос с адресатом, а не молчаливый пропуск.
8. URL источников копируй из выдачи тулов, не реконструируй по памяти
   (wiki.iva.ru ≠ confluence.iva.ru).
```
