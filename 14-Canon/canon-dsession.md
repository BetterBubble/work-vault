# Ассистент проектной сессии — канон

## Дословно

**2026-08-05 · ADR-0065 (автор Д. Солонко) · `90-Materials/0065-design-session-assistant-discussion-journal.md`, раздел «Контекст»**
> Одновременно бо́льшая часть нужного уже построена и находится в проде:
> - **Факт-база** — `helm-analyst` (`affected_systems`, `arch_map`/`arch_container`, `arch_drift`, `constraints`, `related_tasks`, `nearest_spec`, `requirement_tests`, `requirement_coverage`) и `iva-read`, приходящие из `tacticum-analysis-core`.
> - **Постановка** — скиллы `fr-authoring`, `brd/adr/pin/tests-authoring`, агент `tacticum-workflow`, команды `/start-task` → `/approve-docs`.
> - **Запись** — `iva-atlassian-write` под личным Atlassian PAT (ADR-0058), авторство родное.
> - **Леджер решений с обоснованием** — контур диспозиций, доступный через architecture BC, но физически хранимый в **arch-mcp** (`record_triage`/`list_triage` — MCP-вызовы через `arch_mcp_adapter.py`; SoR = arch-mcp per ADR-0048): `signal_type` / `signal_key` / `disposition` / `rationale` / `tracker_ref` / `expires_at`, upsert по identity, workspace-scoped fail-closed, побочная запись в Memory. `signal_type` и `disposition` — свободные строки без enum-валидации на API.

**2026-08-05 · ADR-0065 · там же**
> Не хватает ровно трёх вещей: **журнала обсуждений** (чат — v1, транскрипт — Фаза T — как читаемый агентами контекст), **типа сигнала для решений встречи** в существующем леджере и **двух новых поверхностей** — session-bot в чатах и агента, отвечающего на комментарии к документу.

**2026-08-05 · ADR-0065 · Решение 1**
> Три таблицы — `chat_message`, `decision_candidate`, `transcript_segment` (задел Фазы T) — в **Postgres helm** (alembic helm), рядом с уже существующими `meetings` / `media_transcript` / `dialogue`. Точка чтения для агентов — MCP-tools `discussion_*` как расширение уже работающего `helm-analyst` (`/mcp/analyst`); отдельный MCP-сервер не заводится.

**2026-08-05 · ADR-0065 · Решение 1, «Чем обеспечивается неразрывность с леджером»**
> Общим `signal_key = hash(session, semantic_anchor)`, хранимым по обе стороны: в леджере — identity диспозиции, в журнале — ссылка кандидата и цитат. […] Обратное направление — «пункт документа → решение» — держится **сохранённым линком, а не повторным вычислением якоря**: в момент фиксации пункта FR ещё не существует, хеши не совпадут.

**2026-08-05 · ADR-0065 · Решение 4**
> `signal_type = "design_decision"`, `signal_key = hash(session, semantic_anchor)` — тот же якорь, что для пункта документа (Р.8б ADR-0064 переиспользуется как есть, без изменения формата).
>
> Что достаётся без разработки: `expires_at` как «вернуться к вопросу»; `status=pending` + approve вышестоящим как эскалация «заказчик предложил → архитектор подтвердил»; **одна очередь разбора с одним SLA**.

**2026-08-05 · ADR-0065 · Решение 5, «Атрибуция»**
> Для `signal_type=design_decision` поле `created_by` обязательно (422 без него). В домене и порту поле есть, но **не пробрасывается через HTTP-контракт** — `RecordTriageRequest` его не содержит (`router.py:1210-1217`); правка контракта входит в scope Фазы 1.

**2026-08-05 · ADR-0065 · Решение 5, «READ» (решение owner 2026-08-06)**
> **READ:** через техканалы `iva-read` + `helm-analyst` под собственным токеном бота (решение owner 2026-08-06). Эти каналы уже выданы всем разработчикам через `tacticum-analysis-core` — их скоуп и есть граница видимости; расчёт прав по составу комнаты в v1 не делается.

**2026-08-05 · ADR-0065 · Решение 10**
> Бот-механизм платформы используется целиком, **клиентская разработка iva-one не требуется**: […]
> - **Карточки** — `ReplyKeyboard = [[{Label, Message}]]`: нажатие отправляет `Message` **от имени нажавшего** → боту прилетает webhook с автором. Это штатная механика и HITL-апрува, и атрибуции `created_by`.
>
> **Identity IVA ↔ Tacticum** — переиспользуется резолв `bot_iva_write` (`application/bot_iva_write.identity_candidates` + подтверждение справочником Jira; боевая гоча: платформа не шлёт `login`, рабочий путь — по `name`).

**2026-08-06 · решение owner · README эпика, п. «Блокеры до старта Фазы 1»**
> Policy кнопки фиксации — **утверждена owner**: архитектор/аналитик/тимлид жмут `enforce` сразу, заказчик — `pending` с approve любым из трёх; классификации решений по типам в v1 нет.

## Уточнения и карта (это МОЁ, не канон)

- **`signal_key` в проде считается иначе, чем говорит ADR.** Прод: `compute_signal_key(standard_id, repo, path, semantic_anchor)` — sha256 четырёх частей (`review_rules.py:403-411`). ADR: `hash(session, semantic_anchor)`. Передать готовый ключ можно (`signal_key: str = ""` в контракте), но «тот же якорь, что для пункта документа» тогда не следует автоматически.
- **`status=pending` в SoR отсутствует.** Прод-arch-mcp (`record_triage`, интроспекция рантайма): 8 параметров, без `status`/`requested_by`/`justification`/`resolution_comment`. Таблица `arch_triage` — те же колонки. Прод-фасад при этом уже шлёт все пять. Значит policy кнопки фиксации на существующем механизме не поедет.
- **Кто пишет решение — определяется правами в Tacticum, а не ролью в чате.** `record_triage_for_scope`: «`requested_by` is not the caller's to choose. Without `ARCH_REVIEW` the row is stamped `developer` — hence `pending`». Участники дизайн-сессии — люди ИВА; учётка hub у них не обязана существовать.
- **Таблиц `media_transcript`/`dialogue` в проде нет.** Есть одна таблица `media_request` с текстовыми колонками `transcript` и `dialogue`. Таймкодов нет вовсе — миграция `trn420` прямо пишет, что LiteLLM нормализует ответ whisper до `{"text": …}`.
- **Кнопок в `blocks` нет, но `replyKeyboard` — отдельное поле и оно работает.** `bot_iva_write/blocks.py`: «Кнопок нет вовсе: `actions`/`button`/`section` отвергнуты с HTTP 422». При этом `agents/…/ivaone/connector.py:150` шлёт `replyKeyboard` рядом с `message` — это другой механизм, ADR имеет в виду именно его.
